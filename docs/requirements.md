# LiveRecorder — 要件定義書

## TikTok LIVE・ツイキャス自動録画／コメント記録Webアプリケーション

### WSL2・SQLiteローカル実行版｜趣味・個人利用・実用性優先

---

> 製品要求の正本。設計詳細は `docs/system-design.md`、UI固有条件は `docs/ui-spec.md`。節番号・AC/TC IDは安定した識別子として管理する。実行プロンプトは本書の要求を変更しない。

## 1. プロジェクト概要

### 1.1 開発目的

TikTok LIVEおよびツイキャス（TwitCasting）のライブ配信を24時間自動監視し、配信開始を検知したら動画を自動録画するとともに、配信中に投稿された視聴者コメントを自動収集・保存するWebアプリケーションを開発してください。

アプリケーションはWindows 11上のWSL2（Ubuntu 24.04 LTS）のローカルLinuxプロセスとして稼働させます。趣味の個人利用を想定し、商用品質の形式的厳密さよりも、動くこと、分かりやすさ、問題を追えることを優先します。

Webブラウザから以下の操作を行えるようにしてください。

1. 監視対象配信者の登録・編集・削除
2. 監視の有効化・無効化
3. ライブ配信状態の確認
4. 自動録画状況の確認
5. コメント収集状況の確認
6. 録画履歴の検索・管理
7. 視聴者コメントの検索・閲覧、音声文字起こし・統合ASS字幕の生成状況確認・再生成・発話検索
8. 保存容量や各種設定の管理
9. エラー・障害情報の確認
10. アプリケーションログの時系列検索・閲覧と関連する配信・障害の調査

**動画のWebブラウザ内再生機能は不要です。**

通常運用では録画動画、コメントSRT、音声SRT、統合ASS字幕をWindows側の指定ドライブへ直接保存します（隔離開発時のみ§15.2.1の専用Linux領域）。エクスプローラーで保存先を開き、外部の動画プレイヤーで利用します。Web管理画面とAPIは録画動画・字幕のダウンロードを提供しません。

動画の録画とコメントの収集は独立した処理とし、一方で障害が発生しても、もう一方が可能な限り継続できるようにしてください。

### 1.2 最重要要件

次の要件を優先してください。

**個人利用の開発原則**：まず最小の一連の録画・コメント取得を動かし、使いながら改善する。企業向けの過剰な抽象化、完全なテスト網羅率、大量の設計書を要求しない。ただし取得済みデータの保全、秘密情報の保護、障害の詳細な追跡は省略しない。

Web管理画面の主要ナビゲーションは、「運用・データ」5項目（ダッシュボード／配信者一覧／録画履歴／コメント／音声字幕）と「管理」3項目（システム状態／ログ／設定）の**計8画面**とします。主要画面のURLは `/`、`/streamers`、`/recordings`、`/comments`、`/speech`、`/system`、`/logs`、`/settings` とし、下位の詳細ビューは主要画面数に含めません。画面の情報設計・視覚表現・操作動線の詳細は `docs/ui-spec.md` に従ってください。

初期確定方針：ツイキャスAPIはClient ID / Client SecretによるHTTP Basic認証、TikTokLiveはEuler Streamの無料枠、コメントSRTは録画完了時に、字幕対象コメントがある録画セグメントごとに自動生成し、対象コメントがない区間はスキップとして記録する。配信状態監視頻度はサービス別に設定可能（TikTok最大10回／分・ツイキャス最大60回／分、ツイキャスの初期設定は10回／分）。ツイキャス公式APIの利用枠はコメント収集を優先する。ツイキャス匿名番号は視聴用WebSocketで取得・照合できる場合のみ保存する。Web UIはPC向けのみとする。

- TikTok LIVEの取得手段を公式APIに限定しないこと
- TikTokLive、Streamlink、yt-dlpなどの非公式オープンソース実装を積極的に検証すること
- TikTok LIVEの配信開始検知、自動録画、コメント受信を実装対象とすること
- ツイキャスは原則として公式APIを利用すること
- 録画ファイルをWSL2からWindows側の指定ドライブへ直接保存すること
- コメントを投稿者情報・時刻付きで永続保存すること
- コメントを録画セッションと対応付けること
- Windows再起動やWSL2停止からの復帰時に監視を自動復旧できること
- 長時間の無人運用を前提とすること
- Python 3.12 + uvでWSL2上へ簡単に導入できること
- 動画のWeb再生機能を実装しないこと

技術調査や設計だけではなく、実際に動作するアプリケーションのソースコードと設定ファイルを作成してください。

非公式ライブラリの利用は実装上の要件ですが、対象は公開配信または必要な録画権限を有する配信に限定し、適用されるサービス利用条件を確認してください。

DRM、CAPTCHA、認証、アクセス制御、地域制限などの回避は実装しないでください。

取得方法が動作しない場合は、その原因を検証・記録し、利用可能な別の正当な取得方法を評価してください。動作未確認の機能を完成済みとして扱わないでください。

### 1.3 要求・設計の拘束力（全正本共通）

**拘束力（全正本共通）**：MUST＝確定製品機能・利用者指定・安全上の不変条件、SHOULD＝実用品質・標準設計、MAY＝候補・高度化・追加品質検証。MUSTは利用者の承認なく変更しない。SHOULDは原則実装するが、同じ利用目的を満たす単純な方式への変更、段階的実装、低リスクの詳細の延期をAIに委任する。MAYは必要性で選択する。既存本文の「必須」「〜する」等の表現だけで内部実現方式や追加試験をMUSTへ格上げしない。分類は要求§1.3を正とし、個別の安全条件は常に優先する。判断理由・残課題はtasks.md等に短く記録し、個別承認不要。

| 分類 | 適用範囲 |
| --- | --- |
| MUST | 初期製品の確定機能（両サービス、録画・コメント独立、SQLite、3種字幕、8画面、設定・検索・診断・運用）、確定UI条件（主要URL、意味色、単一ライト、フォント2択、3案から利用者が明示選択）、§10.2〜3の保存・命名、データ保全・正確な状態、削除・版／世代照合・期限削除、秘密保護・HTTP防御・外部制限・隔離・Git境界、明示した設定値・監視上限・公開契約の意味。 |

## 2. ホスト環境・実行環境

### 2.1 ハードウェア・ホストOS

実行ホスト：

- ホストOS：Windows 11
- 実行基盤：WSL2
- Linuxディストリビューション：Ubuntu 24.04 LTSを基本とする
- CPUアーキテクチャ：x86-64を基本とし、実環境を確認
- アプリケーション：WSL2内のPythonプロセスとして稼働
- データベース・設定・ログ：WSL2のLinuxファイルシステム／録画動画・全対応字幕：Windows側のローカルドライブ
- 常時監視：Windows起動・サインイン・WSL2のライフサイクルを考慮

利用可能なメモリ、空き容量、WindowsとWSL2のバージョンを起動時に確認可能としてください。Windows画面ロック中とディスプレイOFF中は録画を継続する一方、Windowsのスリープ・休止では処理が中断することを前提に設計してください。

### 2.2 ネットワーク環境

- 自宅インターネット回線を利用
- 外部VPSは原則使用しない
- クラウドストレージも原則使用しない
- Web管理画面には**ログインなし**でアクセスできる
- 初期状態のWebサーバーは `127.0.0.1` にのみバインドする
- Windowsのブラウザから原則 `localhost` 経由でアクセスする
- LANやTailscaleへの公開は初期対象外で、公開時は認証等を再設計する

特定の固定IPアドレス、Windowsユーザー名、WSL2内部IPを前提としないでください。

Web管理画面は**設定された固定ポート（通常運用のデフォルト8082、隔離は§15.2.1）**で待ち受け、`http://127.0.0.1:8082` を初期URLとします。ポートは設定画面で1024〜65535の整数として変更でき、SQLiteに永続化し、次回の正常起動から反映します（0は不可）。設定ポートに直接バインドし、確保済みソケットを閉じずにUvicornへ渡してください。使用中・バインド失敗時は理由と設定値を通知して起動を失敗させ、他のポートへ自動変更せず、他プロセスを停止しないでください。Web待ち受けが成立するまで監視・録画ジョブを開始しないでください。起動URLをコンソールと実行時状態ディレクトリの `runtime/endpoint.json`（通常 `~/.local/state/live-rec-lab/runtime/endpoint.json`）に原子的に記録し、CLIでも確認可能としてください。稼働中のポートと保存済みの次回起動ポートを区別し、再起動要否を表示してください。起動不能時に備え、停止状態で利用できるCLIによるポート設定の確認・変更手段を用意してください。ファイルにはPID・起動時刻・インスタンスIDも残し、参照時に生存確認して古いURLを案内しないでください。

実際に使用するWSL2ネットワークモード（NATまたはmirrored）でWindows側localhost接続を実測し、接続できない場合は診断情報を示す。未使用モードは追加検証。

不必要に重いフロントエンドフレームワークを導入しないでください。

React、Next.jsなどが明確に必要でない限り、Jinja2 + HTMXで実装してください。

Redis、Celery、Kubernetesなども、明確な必要性がなければ採用しないでください。

### 2.4 アプリケーションの実行構成

初期版は**単一管理Pythonプロセス・Uvicorn 1 worker**とし、Web/API・配信監視・ジョブ管理を同じプロセスで起動します。`--reload` を常用せず、多重起動を排他ロックで防止してください。録画エンジンは管理対象の子プロセスです。音声認識は同じ管理プロセスから起動する専用子プロセスに隔離し、Uvicornや監視タスクのイベントループで推論を行わない。別常駐サービス、別Webプロセス、Dockerを必須にしない。

#### app（Web / API）

- FastAPI
- Web UI（日本語・PCブラウザ向け）
- REST API（`/api/v1`）
- 設定管理
- 録画履歴管理
- コメント検索・閲覧
- 録画完了時のセグメント別SRT自動生成・必要時の再生成
- 音声字幕・統合ASSの状態管理、再生成、発話本文検索（§11.9）
- システム状態・障害情報の要約表示
- 構造化ログの時系列検索・閲覧（`/logs`。既存のログ・イベント情報を安全に参照）
- 管理者ログインなし（localhost専用）

#### worker（同一プロセス内の非同期タスク）

- 配信開始・終了の監視
- サービス別の監視頻度・APIレート制限制御
- TikTokイベント受信とEuler Stream無料枠の管理
- ツイキャスコメント収集・匿名番号WebSocket取得
- 録画プロセスの起動・監視・停止
- Streamlink / yt-dlp / FFmpeg実行
- 録画セグメントの確定・検証
- 障害復旧・未確定ファイル回収
- 確定動画の音声文字起こし・統合ASS待ち行列、管理対象の推論子プロセス、字幕公開・再生成・復旧（§7.9–7.10）
- 保存容量・保存先アクセス状態の監視

#### db（別サーバーを必要としないSQLite）

- 配信者情報
- 配信セッション情報
- 録画ジョブ・セグメント情報
- コメントとコメント収集ジョブ情報
- 欠損区間・設定・エラーイベント情報
- WSL2ローカルの単一DBファイル（WAL）

録画とコメントのタスクは独立させ、アプリケーション内部の責務を分離してください。将来必要になればWeb/APIとworkerを別プロセスに分けられる設計とし、最初から複数コンテナや分散キューを作らないでください。SQLiteの同期書き込みでasyncioイベントループを長く塞がないよう、短いトランザクションと必要時の専用スレッド／小規模キューで対応してください。

## 4. 対応プラットフォーム

### 4.1 TikTok LIVE

TikTokについては、非公式オープンソースライブラリを使用して配信状態確認、録画、コメント収集を実装してください。

主な調査対象：

TikTokLive：
<https://github.com/isaackogan/TikTokLive>

Streamlink：
<https://github.com/streamlink/streamlink>

yt-dlp：
<https://github.com/yt-dlp/yt-dlp>

TikTokLiveドキュメント：
<https://isaackogan.github.io/TikTokLive/>

実装前に最新のAPI仕様と使用方法を確認してください。

#### 4.1.1 配信者の登録

次の入力形式を受け付けてください。

- TikTokユーザーID
- `@username`
- TikTokプロフィールURL（`/live` 形式を含む。受理条件は§5.1.1）

入力を正規化し、内部では正規化されたユーザーIDを使用してください。

入力検証を実装し、不正なURLやパストラバーサルを拒否してください。

同一アカウントの重複登録を防止してください。

#### 4.1.2 配信状態確認

署名サービスを消費しない公開room API等の正当な配信状態確認経路を第一の検証候補とし、安定性・利用条件・状態判定・実際の署名枠消費を実証して採用してください。TikTokLiveの `is_live()` 等は比較／代替候補とする。アクセス拒否・制限時の迂回は行わない。監視の総回数上限とコメント接続の署名枠を維持する。

実装対象：

- 配信中・オフラインの判定
- 配信開始の検知
- 配信終了の検知
- Room IDの取得（可能な場合）
- 配信タイトルの取得（可能な場合）
- 配信開始日時の取得（可能な場合）
- 配信状態の最終確認日時
- API・通信エラーの判定

TikTokLiveが提供する `is_live()` などの機能を検証してください。

存在しないAPIやメソッドを仮定して実装しないでください。

配信状態を取得できない場合は、オフライン状態と区別してUNKNOWNまたはERRORとして扱ってください。

`https://www.tiktok.com/api-live/user/room/` の `liveRoom.status` は、次のように扱ってください。

- `2` は配信中です。部屋 ID があるとき録画を開始します。
- `4` は終了です。短い途切れでは、猶予のあとで録画を止めます。
- `1` と `3` は、この API での意味を確認できるまで配信中にも終了にもしません。開いている録画は止めません。一時停止と終了を同じにはしません。
- 取得失敗、空の応答、上記以外の値は終了と区別し、UNKNOWN または ERROR にします。解釈できない応答で、その後の確認を止めないでください。終了（`4`）を見逃すためです。

HTTPステータスはJSON等の本文を解析する前に判定し、403・429・5xxを空本文・HTML本文の場合も識別してください。DNS・接続失敗・接続／読取タイムアウト・不正な応答・API拒否・レート制限を、確実に得られた情報の範囲で診断コードに分けます。サービス側の制限による待機・バックオフは、無関係な配信者や独立タスクを止めず、待機理由と次回確認可能時刻を追跡してください。サービス全体に適用される429／Retry-After等の明示的な制限は当該サービスの共有枠に反映する。空応答や5xx等の個別障害は対象別バックオフを基本とし、一律300秒停止を固定しない。待機秒数は外部契約と実証で決める。

#### 4.1.2.1 監視方式の採用判定

署名不要経路を第一候補とし、利用条件・契約を確認して有望な方式を実装する。採用版のLIVE／終了／UNKNOWN／ERROR、Room ID、HTTP異常、連続巡回・公平性、署名消費は実測まで未検証。候補の版・実測・判定理由をresearch.mdに簡潔に記録し、主経路が不適合なら許可された代替を評価する。全候補が署名を必要とする場合は無料枠の必要量と余裕を確認し、利用者が許可する範囲でのみ実運用監視を有効化する。未実証・枠不足・許可なしは当該機能を保留しUNKNOWN／理由を返す。有料枠の自動利用は禁止。実配信を待って独立機能の実装を止めない。

#### 4.1.3 コメントイベント

TikTokLiveのCommentEventを利用し、**Euler Streamの無料枠（無料APIキーを使用可能なら優先）**で配信中のコメントをリアルタイム収集してください。`is_live()`、WebSocket初回接続、署名、再接続、長時間維持、複数同時接続の各操作について、Euler Streamの利用枠を実際に消費するか、署名・接続の制限は何かを個別に検証してください。全操作が同じ枠を消費するとは仮定せず、確認できた消費・429応答・残枠・再試行待機を追跡します。無料枠の数値は固定せず実装時に確認します。

取得対象：

- コメント本文
- コメント投稿者ID
- 投稿者の表示名
- コメントID（取得可能な場合）
- 投稿時刻（取得可能な場合）
- 受信時刻
- 配信Room ID
- 対象配信者ID

TikTokLiveのイベント構造を確認し、存在するフィールドのみ利用してください。

特定のフィールドが存在しない場合はNULLなどで扱い、架空の値を生成しないでください。

TikTokLiveの `start()` / `connect()` が返す値・バックグラウンド受信タスクの寿命は、**採用するSDKバージョンで実際に確認**してください。接続開始コルーチンの終了をコメント受信の終了と同一視せず、受信タスクが生存する間はイベントを処理し、停止時にはキュー残件の保存、受信例外の伝播、WebSocket・HTTPクライアント・子タスクの解放を行います。遅延して届くコメントと接続準備中のオフライン判定を、別のケースとして検証してください。

各WebSocket接続・再接続について、監視が対象とするRoom IDと実際の接続先Room IDの一致を確認する。確認前のイベントは接続世代ごとに上限付きで一時保留し、一致確認後だけ対象セッションに保存する。ID不一致・確認不能・旧接続の遅延イベントは別配信へ混入させず、有限の再確認／再接続を行う。保留超過・検証不能による破棄は件数と理由、判明した欠損範囲を記録する。確認のための通信も既存の監視枠・署名枠に従い、録画は独立して継続する。

単なる抽出失敗やライブラリ不整合であれば別の録画エンジンを試行できますが、アクセス制御や認証制限を回避する目的でフォールバックしないでください。

録画エンジンの切り替え履歴を記録してください。

#### 4.1.4.1 SDK取得媒体URLの信頼境界

### 4.2 ツイキャス（TwitCasting）

ツイキャスは**Client ID / Client SecretによるHTTP Basic認証**で公式API v2を利用してください。ブラウザ管理画面のログインや利用者ごとのOAuth登録は不要です。匿名コメントの表示番号に限り、公式APIにない情報を取得できる視聴用WebSocketの利用を検証してください。

#### 4.2.1 配信状態確認

実装対象：

- 配信終了検知

- 配信タイトルの取得

#### 4.2.2 コメント取得

ツイキャスAPIの `GET /movies/:movie_id/comments` を基本とし、`slice_id` による増分取得、`limit` 最大50件、必要時のページ取得を検証してください。視聴用WebSocketは匿名番号取得の補助経路とし、まず同一Movie ID内の共通コメントIDで照合します。共通IDがない場合は本文・投稿時刻等から一意に対応すると確認できたものだけ補完し、複数候補がある場合は照合せず番号をNULLのまま保持してください。APIとWebSocketの受信内容を重複コメントとして保存しないでください。

取得対象：

- コメントID
- コメント本文
- 投稿者ID
- 投稿者表示名
- 投稿日時
- Movie ID
- 匿名コメント番号（取得できる場合のみ、配信セッション内の表示用番号）

以下に対応してください。

- 増分取得
- ページネーション
- コメントIDによる重複排除
- APIレート制限
- 認証エラー
- 一時的なAPI障害
- 取得できなかった期間の記録

公式APIのコメントを基本として収集してください。**匿名番号については視聴用WebSocketからの取得を優先して実配信で検証**し、接続方法・受信フィールド・Movie ID・コメントIDとの対応・アクセス権限・切断時動作が確認できた場合に採用してください。WebSocket障害や曖昧な照合は公式APIからのコメント収集を止めず、匿名番号の欠損と理由だけを記録してください。ツイキャス公式のRealtime API `/lives` はライブ発見用であり、コメント番号を返すと仮定しないでください。

取得件数や履歴に制約がある場合は、その制約を実装に反映してください。番号が取得できない場合はNULLのまま保存し、`c:tw1` 等の共有匿名アカウントから番号を捏造しないでください。匿名番号は配信ごとにリセットされ、同一人物を別配信間で紐付けません。

増分取得ではコメントIDの連続性を仮定しない。初回0件後の大量投稿、50件上限への到達、短いページでも追加の新着を示す応答情報がある場合、コメント削除による総数の減少、疎なIDに対応する。採用する公式API契約に従って必要なページを追加取得し、同一Movie IDの取得済み境界・応答の件数情報・ページの進捗を照合する。ページ重複／順序逆転／空応答／進捗なしで無限ループしない。ページ追跡中の失敗や枠不足では、既に受信した確実なコメントを保存し、未到達範囲と理由を記録する。未確認の範囲を取得済みとするカーソル更新を禁止し、再取得可能な境界を維持する。回復不能な範囲を明示して次の収集へ進める場合は欠損として追跡する。外部APIの総件数や保存件数だけで全件取得を保証しない。

#### 4.2.3 録画

公式APIの `current_live.hls_url` を優先して実配信で検証し、取得できない場合は利用条件に適合する取得手段を評価してください。配信用の `GET /rtmp_url` は録画元URLと混同しないでください。

映像と音声を保存し、原則として再エンコードを行わないでください。

配信の終了を検知し、録画ファイルを確定してください。

ツイキャスの公式HLSでは、公開配信の本編より前に短いプリロールや不連続が現れます。**録画成功の条件は本編を収録できたこと**です。プリロールの判定には、プレイリストの更新、セグメントと初期化情報、明示キュー、既知の映像・音声との照合を用います。セグメント名、再生時間、不連続タグのいずれか一つで冒頭を切る処理は避け、プリロールと判別できない本編候補は保全してください。実際の初期化情報の切り替わりに合わせ、必要なら別のFFmpeg入力で本編の取得を継続します。

プリロールと確認できた区間は配信本編から除外し、録画ファイルの正式保存、セグメントの採番、録画履歴のセグメント、SRTの対象外としてください。採番には既存のセッション内連番を使い、本編の収録が途切れた区間は欠損として扱います。複数の公開配信パターンで確認し、環境依存の待機時間は実証に基づいて決定します。公式URLのアクセス制限を回避せず、外部ホストへの任意リクエストと秘密URLのログ記録を防ぎます。

#### 4.2.4 ツイキャスの録画入力の健全性

§4.2.3の公式API HLS優先を維持する。許可された公開HLSが得られない／利用できない場合は、視聴側の公開 `tc-hls`、次いでStreamlink HLSを順に評価する（公式API HLS→公開tc-hls→Streamlink HLS）。正当な取得が可能であることと本編取得・継続・再接続・確定を実証して候補を有効化する。明示アクセス拒否・制限では切り替えない。品質選択は§6.2。TikTok用のエンジン順序を流用しない。低遅延WebSocket映像（llfmp4）は初期録画対象外とする（匿名コメント番号取得の補助WebSocketとは別）。

外部配信元のHLSは許可した配信元のHTTPS URLに限定し、リダイレクト・相対URI・バリアント・初期化ファイル・セグメント・鍵参照も同じ検証境界に含める。確認済みプリロールを取り除く場合だけ必要なプレイリスト変換を行い、メディアシーケンス、初期化情報、バイト範囲、通常の本編不連続の意味を壊さない。本編待ちは有限とし、確認済みプリロールだけで終了した試行を成功にしない。判別不能な本編候補の保全を優先する。無出力・読取停滞時は§6.5.1に従い、公式監視による同一Movie IDの再確認と起点URL再解決を行う。

#### 4.2.5 共通のアクセス制限判定（両サービス）

合言葉・会員限定・年齢制限・非公開等のアクセス制限が、公式応答、採用SDKの確実な情報、またはアクセス拒否の明示根拠から判明した場合、初期版は録画・コメント収集の双方を開始しない。稼働中に制限が確認された場合も新規取得・再接続・候補切替を禁止して両方を安全停止し、既に正当に取得した媒体・コメントを保全する。停止原因を `restricted` 等で識別し、OFFLINE・利用者の手動停止・通常の通信障害とは区別する。制限が解除されたことを正当な状態確認で確認するまで再開しない。単なる403・429・タイムアウト・状態不明だけで制限種別を断定せず、アクセス可否が確認できない新規試行／フォールバックを保留し、既存の正当な独立取得は§5.2・§6.5.1に従う。既存の利用条件・必要な権限の確認と回避禁止は維持する。新規の取得権限を確認できない対象にはアクセスしない。

### 4.3 将来の対応プラットフォーム

初期実装はTikTok LIVEとツイキャスのみ。将来はYouTube Live、ニコニコ生放送、Twitch、SHOWROOMへ順次拡張する。プラットフォーム別の認証・API制限・コメント属性・録画方式はアダプターで吸収し、共通処理を変更しすぎず追加できるようにする。未検証サービスを対応済みとして扱わない。

#### 5.1.1 登録・編集の入力契約

入力はサービス選択とIDまたはプロフィールURL、任意の表示名、3つの明示的な真偽値を受け取る。サービス別アダプターで検証し、TikTokはID／@ID／プロフィールURL／同プロフィールの `/live` URL、ツイキャスはID／プロフィールURLを対象とする。次表は初期の検証候補であり、外部サービスの普遍的な仕様と断定しない。事前調査と入力プロファイルの採用実証で利用条件・公式情報・許可済み実アカウントの境界例を確認し、採用した入力プロファイルをresearch.mdに記録する。未確認の形式を黙って受理・同一視しない。候補の変更は正本とテストを照合する。

| 対象 | 初期検証候補 |
| --- | --- |
| TikTok ID | ASCII英数字・`_`・`.`、2〜24文字、`.`／`..`、連続ドットを拒否する候補 |
| TikTok URL | HTTPS、`tiktok.com`／`www.tiktok.com`／`m.tiktok.com`、`/@ID` または `/@ID/live` のみ |
| ツイキャスID | ASCII英数字・`_`、1〜50文字（`c:`等の識別形式は実際の公式契約で確認してから追加） |
| ツイキャスURL | HTTPS、`twitcasting.tv`、`/ID` のみ（末尾スラッシュ許容、その他のパスは実証まで拒否） |

登録文字列は最大2048文字、前後空白を除去し、制御文字・バックスラッシュ・資格情報・非既定ポート・不正なpercent encoding・区切りを変える符号化・パス逸脱を拒否する。許可URLは構文解析し、クエリ／fragment付き入力を拒否する。登録したURL自体を外部コマンドに渡さず、検証済みIDから正規プロフィールURLを構成する。表示名は前後空白を除去し最大100 Unicodeコードポイント、制御文字を拒否、未指定または空なら正規IDを表示する。超過は黙って切り詰めずフィールドエラー。表示名はHTMLとして解釈しない。

アカウント同一性（platform＋正規ID）、検索用NFKC/casefold、Windows保存安全名は別の変換とする。外部IDの大小文字同一性は採用サービスの契約で確認し、不明なら勝手に統合しない。登録後のplatformと正規IDは変更不可。表示名・3設定・順位は編集可能。別アカウントは新規登録とし、既存履歴を移さない。同一キーの有効行は重複拒否、論理削除済み行は既存仕様どおり再有効化する。

### 5.2 監視間隔とサービス別の監視枠（TikTok 10回／分・ツイキャス60回／分）

**監視上限はシステム全体ではなく、配信サービスごとに独立しています。実際に使う監視頻度はWeb管理画面の設定でサービス別に変更できます。**

- TikTok LIVE：最大10回／分（最短約6秒／回）
- ツイキャス：**設定可能な上限**60回／分（最短約1秒／回）。**デフォルトは10回／分**とし、公式API側の残枠を優先
- 初期2サービスの合計：最大70回／分（配信状態確認のみの理論上限）
- 将来の各追加サービス：それぞれ独立した最大10回／分の枠を初期上限とする
- 各サービス固有のAPIレート制限がさらに厳しい場合は、その制限を優先する

確認回数の上限は、配信者ごとではなく、サービス内の監視対象者全員で共有する。例えばTikTokを10回／分に設定して5人なら約30秒／人、ツイキャスをデフォルト10回／分で2人なら約12秒／人となる（APIの他用途による消費がない場合）。ツイキャスの60回／分は最高頻度であり、通常運用で常に使い切る必要はない。対象者の増加によって監視間隔が延びるのは同一サービス内のみとする。確認の実行は配信者ごとのタスクに分ける。個別の失敗・一時停止・応答待ちは他の人の確認や独立した録画を止めない。ただしサービス全体の明示的な制限は共有枠に適用する。

初期設定の巡回は可能な範囲で均等・公平に配分する。管理画面ではサービスごとに「監視頻度（回／分）」を指定し、設定値はTikTokでは0より大きく10以下、ツイキャスでは0より大きく60以下（小数も可）とする。停止は監視ON/OFFで行い、0回／分は指定しない。設定値はSQLiteに永続化し、変更はアプリ再起動なしで次回巡回から反映する。監視間隔は設定値から算出し、サービス内の総確認回数が設定値とサービス上限を超えないよう制御する。対象者ごとの実際の確認間隔は、同サービス内の人数およびAPI残枠によって長くなる。

- 非同期監視
- サービスごとの独立したリクエスト間隔制御
- 指数バックオフ
- ジッター
- タイムアウト
- 監視タスクの独立性
- 監視対象の公平な巡回と最終確認日時の保存
- 同一サービスの対象者増加に応じた確認間隔の延伸
- `UNKNOWN` を `OFFLINE` と誤認しない障害時の状態管理

監視回数には定期確認、手動確認、再試行、配信開始／終了の再確認を含める。コメント取得API・WebSocket・録画通信は**アプリ独自の配信状態監視枠とは別**に扱う。ただしツイキャス公式APIの `X-RateLimit-*` 応答等から実際の制限単位（エンドポイント別・認証単位等）を判定し、共有する利用枠があれば統合制御する。**優先順位は①配信中のコメント増分取得 ②録画復旧に必要な状態確認・HLS情報取得 ③定期監視 ④手動更新**とし、残枠不足時は監視頻度を設定値より下げ、必要ならバックオフする。60回／分は許容最大値であり、実効回数の保証ではない。

複数アカウントの監視によって、単一アカウントのエラーが全体に波及しないようにしてください。配信IDが取得できない場合や一時的な `UNKNOWN`・短時間の `OFFLINE` 判定では即座に新しい配信セッションを作らず、短い終了判定猶予と既存録画の稼働状態で重複を防いでください。明示終了からの猶予は既定15秒、両ジョブ停止かつ正常確認不能時の孤立再確認は既定120秒（§11.8.2）。猶予経過だけで終了確定とせず監視枠内の再確認を必要とする。

同一配信者で同じ監視失敗が続くときは、警告イベントの重複を抑えつつ、失敗の継続・最終発生時刻・回復の事実を失わないようにします。**警告が減ったことを通信の回復と取り違えない**でください。

### 5.3 状態管理

配信者の監視状態は以下を基本としてください。

- OFFLINE
- LIVE
- UNKNOWN
- ERROR
- DISABLED

最後に正常確認できた時刻も保存してください。

進行中のセッションがある場合、単発または継続的な `UNKNOWN` / `ERROR` だけを根拠に `ENDING` / `ENDED` へ遷移させないでください。明示的な `OFFLINE` 等の終了根拠と終了猶予を区別し、猶予中（`ENDING`）も録画の継続を原則とします。監視が復帰せず録画プロセスだけ終了した矛盾状態は、無期限の正常な `LIVE` と断定せず、再確認対象の異常として追跡してください。

終了判定は、**有効な明示OFFLINE／配信終了イベント**で `ENDING` に入り、猶予中に `LIVE` が確認できれば元のセッションに復帰する方式とします。猶予満了時も終了根拠を再確認し、`UNKNOWN`／`ERROR` だけでは確認済み `ENDED` にしません。監視不能と録画・コメント双方の終了が継続する孤立セッションは、有限の再照合期限を設け、期限後も終了根拠がなければ**終了未確認の収束**として区別します（`platform_ended_at` を捏造せず、理由・最終LIVE確認・欠損を保存）。再照合期限と猶予時間は§11.8.2の内部ポリシーに従い、試験で注入可能にし、同じ配信IDの再検知で二重セッションを作らないでください。

### 5.4 配信開始時の動作

配信開始を検知した場合、以下の順序で処理してください。

1. 配信IDを特定する
2. 既存の配信セッションとの重複を確認する
3. 配信セッションを登録する
4. 録画設定を確認する
5. コメント収集設定を確認する
6. 録画ジョブを起動する
7. コメント収集ジョブを起動する
8. 各ジョブの開始状態を記録する
9. Web管理画面へ状態を反映する

録画ジョブとコメント収集ジョブは独立して管理してください。

## 6. 自動録画システム

### 6.1 基本動作

以下を実装してください。

- 配信開始時の自動録画
- 配信終了時の録画停止
- 複数配信の並列録画
- 録画中の状態管理
- 録画失敗時の再試行
- 一時的な通信断からの復旧
- 録画プロセスの異常終了検知
- 手動停止
- 手動再開（同一配信では新規セグメント）
- 重複録画の防止
- WSL2再起動後の復旧

手動停止した配信セッションには停止指示を保持し、同じ配信の監視で自動再開しないでください。手動再開時は新セグメントで開始し、次の別配信では通常の自動録画に戻してください。

**稼働中の設定変更契約：** 配信者の監視OFFは、その配信者の新規監視・自動起動を止め、稼働中の録画・コメント収集を**安全に停止**します（確認済みOFFLINEとは扱わず、セッションの終了未確認と停止理由を保存）。録画OFFは録画ジョブだけを、コメント収集OFFはコメントジョブだけを停止し、他方は継続します。システム全体のコメント収集ON/OFFと配信者別コメント収集ON/OFFは**AND条件**とし、全体OFF時も配信者別設定値は変更しません。各ON復帰時、監視ONかつ確認済みLIVEで対象設定が有効なら、同一セッションに**重複しない新しいジョブ**を起動可能とします。ただし、新ジョブに既存の試行予算・抑止を引き継ぎ（§6.5.2）、録画の手動停止指示がある同一配信は明示的な手動再開まで自動再開させません。設定変更による停止、手動停止、配信終了、内部取消を別の終了理由として記録します。

### 6.2 録画品質

映像と音声は、原則として元のストリーム品質を維持してください。

- 再エンコードを原則禁止
- FFmpegのstream copyを優先
- 利用可能な最高品質を優先
- 録画品質を設定から変更可能
- 音声と映像の同期を維持
- 不必要なCPU負荷を避ける

GPUエンコードを必須としないでください。

品質の選択肢・初期値は§11.8.1。`best` は利用可能な最高の元品質、`high`／`medium` はエンジンごとの検証済み品質対応表で上限を選ぶ。公開tc-hlsではbest/highはhigh→medium→low、mediumはmedium→lowを基本とする。公式HLSやTikTokの実際のラベル・解像度／ビットレートを検証し、指定を満たせない場合は利用可能な下位品質と理由を記録する。無根拠な品質名・解像度の仮定や再エンコードは行わない。要求品質と実際の品質を区別する。

### 6.3 録画形式

原則としてMP4形式で保存してください。

ただし、録画中の障害によるファイル破損を防ぐため、以下を検討してください。

1. MPEG-TSまたは適切な一時形式で録画
2. 録画終了後にファイルを確定
3. 必要に応じてMP4へ無劣化リマックス
4. ffprobeでファイルを検証
5. 正常なファイルを正式な保存先に登録

MP4に変換できない場合は、元の再生可能な形式を保持してください。

録画中断で保存された部分ファイルを可能な限り保全してください。

**セグメントの `valid` 判定**は、ファイルの存在・非0バイト・容器の長さだけで行わないでください。映像を録画する前提なら、ffprobe等で映像ストリームと識別可能な映像コーデック、必要な音声、最終的に**保持したファイル**の再生時間・形式・サイズを検証します。音声や持続時間だけ取得でき、映像の `codec_name` が不明なFLV、0バイトのMP4、失敗したリマックスを成功扱いにしません。MP4化できない場合も、元形式が再生可能と確認できたときだけ代替成功とし、未検証の元ファイルは回復可能な一時ファイルとして保持します。リマックス前と確定後の時間が異なることがあるため、DBの `duration_ms` とSRTの基準は**確定後の保持ファイル**から求めます。ffprobeで形式が読めることと全区間の収録・再生確認は別の受け入れ条件です。

### 6.4 録画ジョブ状態

以下の状態を管理してください。

- PENDING
- STARTING
- RECORDING
- RECONNECTING
- FINALIZING
- COMPLETED
- PARTIAL
- FAILED
- CANCELLED

状態遷移を明確に定義してください。

`COMPLETED` / `PARTIAL` / `FAILED` は、**録画ジョブ単体の終了状態**と、配信セッション全体の取得品質を混同しないでください。同一セッションに複数ジョブが存在する場合、最新ジョブが `COMPLETED` でも、前のジョブの失敗、無効・未確定セグメント、`collection_gaps` を消さず、セッション集計で把握できるようにします。空試行の破棄だけで有効ファイルを不必要に `PARTIAL` としない一方、**取得できなかった期間を「完全成功」にしない**こと。終了判定・手動停止・強制取消・再接続上限はそれぞれ真の理由に対応する状態・イベントとして記録します。

### 6.5 再接続

ネットワーク障害時には、録画処理の再接続を試行してください。

- 再接続回数の管理
- 指数バックオフ
- 配信状態の再確認
- 配信終了時の再試行停止
- 有効期限付きURLの再取得
- 録画セグメントの分割保存
- 再接続による欠損期間の記録

再接続回数は§11.8.1に従い、初回接続後の追加試行（同一エンジン再接続・候補切替）を共通予算から消費する。0は初回だけ。同一試行予算世代で自動的に予算をリセットせず、再試行上限で同じ原因の無限ジョブ再生成をしない。別の明示再開または新しい配信は新規ジョブとして判定する。コメント収集の再接続も同じ設定値を独立した種別の試行予算として適用し、ページング・通常ポーリングは再接続回数に含めない。

再接続後は原則として新しいセグメントに保存し、同じ配信IDなら同一セッションへ紐付けてください。**初期実装ではセグメントの自動結合を行いません**。

将来、複数セグメントを結合する場合は、動画形式・コーデック・タイムベース・PTS/DTS等の互換性を確認し、再エンコードを避けて安全に結合できる場合だけ実行してください。

結合できない場合は個別のファイルとして保存してください。各セグメントの開始・終了時刻、再接続回数、欠損区間をSQLiteに残してください。

空ファイルなど保持しない試行は、保存セグメントの連番を消費せず、同一配信セッションでジョブが分かれても**保持するファイルのセグメント番号を重複・逆戻りさせない**でください。空の試行をセグメント行から除く場合でも、そのために失われた収録区間、再試行、終了理由は欠損・イベント記録に保持します。再接続上限に達していないのに上限エラーを出さず、プロセスの正常終了と再試行対象の途中切断を区別します。

#### 6.5.1 録画の進捗監視と再試行判断

録画子プロセスが生存していてもメディア取得が進行しているとは限らない。接続開始・最初の有効メディアの待機、入力読取の停止、出力の停滞、正常な低ビットレート／バッファリング、確定処理を区別し、有限の監視期限と進捗検知を設ける。進捗停止を検出した場合は利用者による停止とは別の理由を記録し、子プロセスを回収して保持可能なデータを検証・確定したうえで、同じ配信の継続確認と再試行判断に進む。正常に増加する出力や本編の初期化情報切替を停滞扱いしない。

- アクセス拒否・保護配信・明示停止では代替エンジンによる回避を行わない。配信終了確定時は再試行しない。子プロセスの終了コード0だけで配信終了や完全収録を確定しない。
- 初回の抽出／接続失敗で有効メディアが取得できない場合は、許可された次の候補へ切り替えられる。有効なデータを取得後の中断では、成功したエンジンを優先して新規セグメントで復旧する。再試行・切替を合わせた有限の試行予算を管理し、無限ループを防ぐ。空・プリロールだけ・破損データを成功として扱わない。
- 判定には実際の進捗・取得量・メディア検証・失敗分類を用いる。具体的な無進捗タイムアウトや取得量のしきい値は採用エンジンで調査・検証する。これらの値は製品の設定項目として新設せず、テストで注入できる内部ポリシーとして管理する。
- セグメントごとに実際の取得エンジンと試行の結果を追跡する。録画プロセスの壁時計上の開始／終了範囲と確定メディアの再生時間・収録可能範囲を別々に記録し、書き込み停止や中断区間を再生時間だけで隠さない。

#### 6.5.2 再試行予算の永続化

録画・コメントの各ジョブが参照する試行予算をセッション・ジョブ種別・明示再開世代ごとにSQLiteへ永続化し、開始時設定の追加試行上限、初回予約有無、消費済み追加試行数、最後の試行ID、抑止理由、次回試行可能UTC時刻を保持する。設定による新ジョブ起動も同じ予算世代を参照し、初回を再使用しない。試行IDの一意予約と予算消費はネットワーク接続・子起動の前に同一短期トランザクションで確定する。初回は追加予算を消費しない。追加試行の予約後にクラッシュして実行有無を確認できない場合も返却せず、結果不明を記録する。同じ予約の照合は二重消費せず、未回収子と重複接続しない。再起動・設定変更・監視ON/OFF・同一配信IDの再発見では自動的に予算を復活させない。設定は新しい試行予算世代の開始時に固定し、通常ポーリング／ページング／待機だけでは消費しない。停止・制限・上限到達の抑止を再起動後も維持し、手動再開（録画は既存の手動再開、コメントは再試行上限到達等で停止した収集の確認付き明示再開）または別の確認済み配信IDのみ新予算を取得できる。いずれも監視・機能設定・同一LIVE・制限解除等の起動条件を満たす場合のみ許可する。停止からの通常復旧で新規接続する場合も残予算を使用する。予算0では初回のみ。バックオフ時刻を復旧し、時計不整合の場合は保守的な待機で再計算する。

#### 6.5.3 抑止理由と解除条件

抑止は原因ごとに独立して評価する。複数原因が成立するときは全条件が解消するまで起動不可。設定停止と明示停止を同じフラグで表現しない。新予算は有効な同一LIVE・権限・設定を確認した手動再開（録画の手動停止、録画／コメントの上限到達など明示再開可能な状態）または別の確認済み配信IDだけで開始し、制限・期限削除・削除中・未回収処理を迂回しない。

| 理由 | 解除条件 | 予算 |
| --- | --- | --- |
| 監視OFF／機能OFF／全体コメントOFF | 必要な設定がすべてON、同一LIVE確認 | 同一世代・残予算 |
| 手動録画停止 | 確認付き明示再開 | 新世代 |
| 再試行枯渇 | 確認付き明示再開 | 新世代 |
| アクセス制限 | 正当な制限解除確認 | 同一世代・残予算 |
| 利用枠・バックオフ | 利用可能枠・待機期限の回復 | 同一世代・残予算 |
| 容量・録画枠不足 | 条件回復（録画のみ） | 同一世代・残予算 |
| 状態不明・復旧保留 | 同一LIVE・復旧照合成立 | 同一世代・残予算 |
| 確認済み終了・コメント期限削除 | 当該終了セッション／期限削除済みコメントは再開禁止 | 再使用不可 |

設定変更・抑止解除だけでは枯渇を解除しない。新しい試行を予約する時点で全条件と予算を原子的に再照合する。手動再開の再送は既存の再開済み業務状態を返し世代を増やさない。試行中の停止、枠待機、未実行予約も§6.5.2に従う。

### 6.6 録画プロセス管理

録画プロセスはPythonのsubprocessまたはasyncio subprocessで管理してください。

- shell実行を原則使用しない
- 引数を安全に渡す
- PID管理
- 終了コード確認
- stdout/stderrの適切な処理
- プロセス停止時の安全な終了処理
- タイムアウト後の強制終了
- 孤立プロセスの検出

ワーカー再起動後に既存プロセスの状態を確認し、二重録画を防止してください。

停止タイムアウトやタスク取消が起きても、子プロセス回収と開いている有意な一時ファイルの確定・状態保存を可能な限り先行させます。手動停止でない取消を自動的に `CANCELLED`（利用者操作）へ丸めず、終了コード・停止指示・強制終了理由を記録します。再起動時は異常な `pending` や、過去に取消状態で終わった未確定セグメントも整合性照合の対象に含めてください。

## 7. 視聴者コメント収集システム

### 7.1 基本要件

ライブ配信中のコメントを自動取得し、データベースに保存してください。

コメント収集は動画録画と独立したジョブとして実行してください。

動画録画が失敗してもコメント収集を継続できるようにしてください。

反対に、コメント収集が失敗しても動画録画は継続してください。

### 7.2 保存するコメント情報

最低限、以下を保存してください。

- 内部コメントID
- プラットフォーム
- 配信者ID
- 配信セッションID
- プラットフォーム側の配信ID
- プラットフォーム側のコメントID（取得可能な場合）
- コメント投稿者ID（匿名等で得られなければNULL）
- コメント投稿者表示名
- 匿名フラグ・匿名番号（取得できる場合のみ）
- コメント本文
- 投稿日時（取得可能な場合）
- 受信日時
- 配信開始からの経過時間
- 録画開始からの経過時間（計算可能な場合）
- データベース保存日時

コメントの原文を保持してください。

UTF-8で保存してください。

絵文字、日本語、改行、特殊文字を適切に処理してください。

### 7.3 コメント時刻

コメントには複数の時刻を記録してください。

#### posted_at

プラットフォームから投稿時刻を取得できる場合は、その時刻を保存してください。

#### received_at

アプリケーションがコメントを受信した時刻です。

#### stream_offset_ms

配信開始時刻が取得できる場合、配信開始からの経過時間をミリ秒で保存してください。

#### recording_offset_ms

録画開始時刻からの経過時間をミリ秒で保存してください。

録画開始時刻より前のコメントは、負の値を許容するかNULLとして扱うかを設計で明確化してください。

録画が分割された場合は、セグメントの開始時刻も保存してください。録画プロセス開始時刻と実際のメディア取得・動画PTSは一致しない場合があるため、取得できる場合は `first_media_at`、`media_start_pts`、`sync_offset_ms`、`sync_method` を記録し、未確認の時刻精度を保証しないでください。

これらの時刻は外部動画プレイヤーや文字起こしとの照合に利用します。

ただし、Web画面での動画同期再生機能は実装しません。

### 7.4 コメント受信の信頼性

以下を実装してください。

- WebSocket切断検知
- 自動再接続
- コメント取得失敗の記録
- コメント欠損期間の記録
- 重複コメントの排除
- コメント保存失敗時の再試行
- バッチ書き込み
- 必要に応じたメモリ内キュー
- キュー容量上限
- 大量コメント受信時の負荷制御

コメントIDが存在する場合は、それを重複排除に利用してください。

コメントIDが存在しない場合は、投稿者ID、本文、時刻などを組み合わせた重複判定を検討してください。

ただし、同一投稿者が同じ本文を繰り返し送信した場合に、正当なコメントまで誤って削除しないようにしてください。

コメント受信ループの正常終了、受信例外、アプリ停止、セッション終了、キュー書き込み完了を別々に扱い、受信したが未保存のコメントを可能な限り書き切ってください。配信終了前に収集が `PARTIAL` となった場合は、保存失敗件数が0であっても、**終了した経路とその理由**を残してください。受信件数が0でも、収集タスク未起動・接続エラー・収集完了後の0件を混同しません。

コメントの識別子が得られる場合は同一セッション内の同一IDを重複として扱い、異なるIDの同一本文は別投稿として保持する。IDなしの場合も、投稿時刻または受信時刻が異なる正当な連投を消さない。時刻精度不足や同一秒だけを根拠に統合しない。保存済み・重複確認済みの情報と取得境界の更新はクラッシュ後にも照合可能にし、DB書込失敗や再接続後の重複取得を試験する。

### 7.5 コメント収集状況

コメント収集ジョブは以下の状態を管理してください。

- PENDING
- CONNECTING
- COLLECTING
- RECONNECTING
- COMPLETED
- PARTIAL
- FAILED
- DISABLED

以下の統計を管理してください。

- 受信コメント総数
- 保存成功件数
- 保存失敗件数
- 最終受信日時
- 再接続回数
- 取得できなかった時間帯

配信中の全コメントを取得できることは保証しないでください。

コメント収集が途中で終了した場合は、最後に受信できた時刻・終了理由・可能なら未収集区間を残し、エラー件数0を「途中終了なし」や「全件取得」と見なさないでください。

削除されたコメント、フィルタリングされたコメント、接続前のコメントなどは取得できない場合があります。

#### 7.5.1 収集統計の集計契約

収集ジョブごとに `received_count`（対象として受け付けたコメントイベントの延べ件数）、`stored_count`（新規DB確定件数）、`duplicate_count`（DB確定済みと一意照合できた重複）、`discarded_unverified_count`（接続先不一致・未確認・旧接続で破棄）、`discarded_overflow_count`（保留／受信キュー超過で破棄）、`discarded_other_count`（不正形式等、理由付き）、`save_failed_count`（有限再試行後に保存不能と確定したイベント）、`pending_count`（未判定・保存／再試行待ち）、`error_count`（処理／通信のエラー事象数、イベント件数とは別）、`reconnect_count`、最終受信日時・最終確定日時を管理する。カウンターの単位と範囲はジョブを基本とし、セッション要約は全ジョブを集計する。REST再取得イベントも受信延べ数に含める。保存に成功した再試行を最終保存失敗に二重計上しない。

イベントの最終分類は排他的とし、確定済み受信件数＝新規保存＋重複＋各破棄＋最終保存失敗＋未処理（カウンターの同一スナップショット）。保存／重複判定、確定カウンター、取得境界は同じSQLite取引で更新する。接続世代・バッチID等で処理結果の再適用を冪等化。永続化前の強制終了で失われた観測件数は推測せず、最後の確定値と計数の不完全性・欠損理由を表示する。通常終了時のキュー排出後はpending=0、未収束は保留／欠損として扱う。期限削除後の現存コメント数は累積stored_countとは別。未受信コメント総数・匿名番号欠損・API上の総数はこの等式の対象外で、0件のエラーや計数一致を全件取得の根拠にしない。

### 7.6 コメント検索

Web管理画面から以下の検索を行えるようにしてください。

- コメント本文検索
- 投稿者ID検索
- 投稿者表示名検索
- 配信者別検索
- プラットフォーム別検索
- 配信セッション別検索
- 日付範囲検索

検索結果は§11.5の配信別閲覧・横断検索に対応し、安定した時刻昇順／降順で表示してください。

大量のコメントが存在する場合にも対応できるよう、ページネーションと適切なインデックスを実装してください。

初期版は日本語を含む `LIKE` 検索＋ページネーションとし、遅くなった場合のみFTS5 `trigram` を検証してください（1〜2文字検索はLIKEを維持）。

必要以上に重い全文検索基盤は導入しないでください。

### 7.7 コメント字幕（SRT）

コメントの正本はSQLiteに保持し、ローカルに生成するコメント字幕は**SRT形式**とします。JSONL・CSV・TXT形式のエクスポートは実装しません。発話字幕とコメントの統合ASSは別機能です（§7.10）。

#### SRT

1コメントを基本的に1つの字幕キューへ変換します。

```text
1
00:00:12,000 --> 00:00:16,000
こんばんは (ユーザーA | @user_a)

2
00:01:34,000 --> 00:01:38,000
今日も見に来たよ (ユーザーB | @user_b)
```

- タイムコードは `HH:MM:SS,mmm` とし、開始＜終了を保証する
- **録画ジョブの終了時に、確定できた録画動画のセグメントごとに、字幕対象コメントがある場合はSRTを1つ自動生成し、対応する動画再生開始位置を0秒とする**（再接続等で複数セグメントがある場合は各ファイルに対応）
- コメントが録画開始より前の場合や時刻を確定できない場合の扱いを明記する
- 投稿者表記は本文末尾に半角括弧 ` (表示名 | @ID)` を付す。表示名のみ／IDのみは取得できた片方だけ、IDの先頭`@`は重複させない。両方不明は ` (投稿者不明)`。匿名として確認できたコメントは通常ID・表示名による同定を避け、照合済み番号があれば ` (匿名23)`、番号不明なら ` (匿名)` とする。番号を推定せず、原文と取得属性はSQLiteに維持する。本文なしは括弧だけとする。
- 表示用文字列はCRLF/CR→LF、本文内の空行を除去、名前・IDの改行と連続空白を単一空白へ正規化する。通常の非空改行、絵文字、日本語は保持。NUL等の構造を壊す制御文字は出力用に除去し、SRTタイムコードに見える本文行も構造を壊さないよう安全化する。DB原文は変更しない。同じ時刻はDB ID昇順、重なりを許容し後続cueをずらさない。既定表示4秒、§11.8.1で変更可能、媒体終端を超えず正の区間だけ生成する。ASSのCommentもこの投稿者表記を共有し、安全なASSエスケープと絵文字除去のみ追加適用する。
- SRT番号は1からの連番とし、同時刻のコメントも安定した順序で出力する
- 表示秒数は設定可能とし、動画末尾を超えるキューは必要に応じて打ち切る
- コメント投稿者ID・表示名・匿名番号は取得できた情報だけを表示し、個人同定を推測しない
- **時刻同期は動画タイムラインとの対応を検証できた実測値を優先**し、なければ録画開始時刻と投稿／受信時刻による近似値を用いる。手動補正値も記録し、実測・近似・手動補正・同期不能の区別と時刻根拠を追跡する。投稿時刻が無い場合は受信時刻を使用した旨を記録する
- 録画開始前・録画終了後・欠損区間のコメントは、誤った動画時刻へ押し込まない
- SRTはUTF-8で正しく保存し、絵文字・日本語・改行を破壊しない
- セグメント分割時は `recording_001.mp4` と `recording_001_comment.srt` のように動画stemと接尾辞で対応させ、各動画の再生時間軸と照合する。セッション全体のコメント正本はSQLiteに保持する
- 文字コードはUTF-8とする。日本語・絵文字・特殊文字を保持する
- 表示名や本文に改行があってもSRT構造が破損しないようにする

同期基準がなく字幕時刻を求められない場合は推測で補わず、該当セグメントのSRT生成を失敗／保留とし理由をログとWeb UIに示してください。SRT生成失敗時にも録画ファイルとSQLiteに保存済みのコメント原文を失わないでください。

### 7.8 字幕の生成・保存

コメントデータの正本はSQLiteに保持してください。

SRTは**録画ジョブの完了・停止時に自動生成**してください。録画が分割された場合は、確定済みの各動画セグメントについて字幕対象コメントが存在するとき§10.3の命名規則に従うコメントSRTを1つずつ生成し、0件の区間はスキップとして記録します。コメント収集処理の保存完了を可能な範囲で待ち、未保存・遅延が残る場合は**SRT（0件スキップを含む）をコメント確定待ちとして区別**してください。後から対象区間のコメントが保存された場合は再生成対象として追跡し、収集終了・キュー書込完了後に該当セグメントの自動再同期を試み、失敗や未反映を明示してください。録画ジョブがPARTIAL／CANCELLED等で終了した場合も、有効な動画セグメントにはSRT生成を試みます。

SRTは対応する動画と同じフォルダに保存してください。コメントや補正値が更新されたときは必要に応じて手動で再生成できるようにしてください。同期方式・近似精度・生成失敗理由は詳細ログと画面から確認できるようにします。

SRTの生成・再生成が失敗しても、収集済みコメントを保持してください。対象セグメントの**字幕入力版数**（対象コメントの追加・修正、時刻補正の変更で更新）と**生成時に使った版数**を区別して永続化し、相違時は「再同期待ち」にしてください。録画確定後、コメント収集ジョブが継続中／受信キュー未排出なら生成・0件スキップを**暫定**とし、収集の終了とキュー書込完了後に版数を再確認して対象セグメントを自動再生成／スキップ確定します。再生成中の追加入力は確定扱いせず再試行し、失敗時は既存の動画・元コメント・最後に正常生成したSRTを保全して「再同期失敗」を表示します。収集失敗・欠損が残る場合は、字幕が現在保存されているコメントに同期していても**コメント全件性を保証しません**。

**再生成の競合・確定契約：** セグメント単位で二重生成を抑止し、開始時に `srt_input_version` を読んでSRTを同一保存ボリューム内（通常はWindows、隔離はLinux）の一意な一時パスへ生成します。公開直前に現在の入力版数・コメント期限削除状態・進行中の期限削除操作・動画／保存先の同一性を再確認し、変更済みなら一時成果物を破棄して「再同期待ち」に戻します。旧SRTを公開済みの場合は**最後の正常版として保持**し、競合版で置換しません。版数一致時のみアプリ管理下の同一セグメントのSRTを安全に置換し、公開後のDB確定時にも版数を再照合します。公開とDB更新の間にコメントが追加された場合は生成版数を現行と偽らず「再同期待ち」として再試行し、再起動時は公開ファイル・生成版数・DBを照合します。生成失敗時は旧SRT・動画・元コメントを保全します。**0件への正常な更新**は旧SRTを安全に除去できて初めて「字幕対象なし（スキップ）」と確定し、除去失敗は成功にしません。コメント期限削除処理中・削除済みは再生成対象外です。

確定セグメントの時間範囲に字幕キューが**0件**の場合は、空のSRTを「生成済み」とせず、**対象区間に字幕対象コメントなし（スキップ）**として扱い、対応する空のコメントSRTを作成しないでください。一方、**コメントの収集そのものが未実施・失敗した場合**は、単なるスキップと混同せず、元の収集状態を併記します。字幕時刻の根拠と録画ファイルの実際の長さが矛盾する場合も生成成功と断定しません。

### 7.9 音声文字起こし（音声SRT）

- 初期版の正式機能として、収束済み配信の保持・検証済み動画セグメントを単位に、音声を抽出しローカルで設定言語（初期日本語）の文字起こしを行う。録画中・配信進行中・未確定・削除中・復旧保留の対象を処理しない。PARTIAL／CANCELLEDでも有効な確定動画は対象。音声なしは理由付き対象外、無発話は処理成功（発話なし）とし、空SRTを作らない。複数セグメントは結合しない。映像・音声から対象人物を識別したり、全発話が配信者本人だと断定したりしない。
- 設定は音声字幕自動生成 `speech_subtitles_enabled`（初期ON）、モデル `speech_model`（`large-v3` 初期値／`large-v3-turbo`）、認識言語 `speech_language`（初期`ja`、対応するWhisper言語コードのみ）、実行デバイス `speech_device`（初期`cuda`、明示選択`cpu`）をSQLiteに保存。次の試行から反映し、実行中の試行は設定スナップショットで完遂する。OFFは新規自動投入と自動起動種別の待機ジョブの開始を抑止し、実行中は安全に完遂または停止時に回収する。OFF中も既存字幕の閲覧、明示的な個別再生成・失敗一括再試行を可能とする（他の安全条件に従う）。ON復帰で適格な未処理対象を重複なく投入する。
- faster-whisperを初期実装に含める。録画・コメント・Webの基本環境はspeech extraなしで起動可能にし、推論ライブラリは遅延importまたは子プロセス内で読み込む。未導入は音声機能の理由付きblockedとし、音声extraの依存解決・モデル取得・実機試験をコア実装の前提にしない。CUDA利用可能性・モデル入手・依存バージョン・VRAM・CPU負荷を実測する。GPU利用不能を録画起動失敗にせず、理由付きblockedとして診断し、CPUへ黙って切り替えない。モデル未取得・ネットワーク障害・容量不足・推論異常は録画とコメント収集を止めない。音声・発話本文を外部推論サービスへ送信しない。モデルの初回取得のみ許可された配布元から行う。モデルキャッシュは§11.8.3の実効データディレクトリ配下に分離する。通常運用の取得は許可済み配布元のみとし、隔離開発環境では利用者が許可した明示的な準備工程でのみモデルを取得する（配信・署名通信の許可と混同しない）。ローカル自動試験は自動取得を禁止し、模擬推論または準備済みのテスト専用ローカルモデルを用いる。実GPU試験は§17の許可も必要。通常・隔離・テスト間でライブラリ既定キャッシュや通常資格情報を継承しない。取得不能・未取得はblocked／未検証として扱う。
- 同時推論は1件。録画・コメント・Web応答を優先し、推論・音声抽出は管理された子プロセスで実行し、CPU／GPU／I/O負荷を計測して必要時に新規開始を保留する。実行中の例外は当該試行のみ失敗とし、次の対象に進める。短いSQLite取引で投入・取得・状態変更を行い、推論中にDB書込ロックを保持しない。
- FFmpegで音声抽出時に確定動画の0秒と音声タイムラインを維持し、遅延・先頭無音・PTS・不連続を検証する。初期は温度0、VADあり、直前区間本文を条件にしない設定を候補とする。全cueを媒体長内に収め、空・逆転・範囲外cueを発行しない。語時刻による補正は品質改善項目とし、根拠が十分な場合のみ適用する（区間外・対応不足では元時刻を保持）。
- 品質フィルタは明らかな無音幻覚・空文字等を対象とする。圧縮率2.4、平均対数確率-1.0、反復・記号等による高度なフィルタは初期候補であり、実音声で偽陽性を評価して調整する。短い相づちや真の反復を一律削除しない。除外理由を診断し、認識精度・話者同定・全発話取得を保証しない。
- 追加品質改善（MAY）の候補：圧縮率2.4超、平均対数確率-1.0未満、記号のみ、無音の定型幻覚、同じ節3回以上の反復、12文字以上で直前と同一の本文を除外候補とする。真の反復発話を失う可能性を検証し、短い相づちを一律削除しない。除外数・理由を診断に記録（本文は通常ログに出さない）。認識精度・話者同定・全発話取得を保証せず、自動認識結果であることを表示する。
- 成果物はUTF-8の音声SRTとし、ファイル名は§10.3に従う。発話本文は管理済み音声SRTを安全に解析し、ページング・セッション／セグメント／本文検索・時刻昇降順のテキスト閲覧を提供する。ファイル本体のHTTP取得は不可。本文の複製をDBに恒久保存する必要はない。
- 個別再生成・失敗のみの一括再試行を提供する。待機・処理中の重複投入、削除済み・未確定対象を拒否。入力ファイルの世代と結果版を公開前後で照合し、管理下の同一保存ボリューム（通常はWindows、隔離はLinux）の一時ファイルを使い、最初は非上書き、再生成は管理物のみ原子的に置換する。失敗時は最後の正常版を保持し、最新失敗と旧結果を区別する。無発話への正常更新は旧音声SRTを安全に除去してから完了。強制終了・保存障害・再起動時は未完了台帳とファイルを照合し、公開済み結果を推測で成功にしない。

### 7.10 音声発話・コメント統合ASS字幕

- 確定動画ごとに同じstemの `.ass` を生成し、音声SRTとコメントSRTの時間軸に基づく一つのASSトラックにまとめる。発話は下中央・白・`Speech`スタイル、コメントはその上の複数レーン・黄・`Comment`スタイル。話者が確定していない発話に配信者名を付けない。縦横比、回転後の表示寸法、画面内余白を考慮し、重なりをレーン割当で処理する。レーン飽和時は決定的な縮退（上限と省略数を診断）とし、表示時刻を偽らない。ASSの制御文字、改行、タグ、バックスラッシュを安全にエスケープし、ASS本文の絵文字除去は音声SRT・コメント原文へ波及させない。
- 音声cueは次cueが終了後0.4秒以内に続く場合は自身の終了まで表示し、間が空く場合は1文字0.4秒を基準に最短2.5秒・最長10秒を目安とする。次cue開始・動画終端を越えない。コメントは既存SRT表示秒数と同期法に従う。全cueは確定媒体時間内。時刻補正・コメント欠損・音声未処理を隠さず、統合字幕は単一トラックで独立オンオフを保証しない。
- コメントSRT自動生成／再同期・音声SRT成功／無発話・手動ASS再生成を契機に更新する。初回はどちらかの有効cueがあれば暫定または片側のみのASSを生成可能。両方が確定または明示対象外／無発話なら確定とし、取得欠損・同期不能・生成失敗は理由付き部分結果として区別。両方0cueなら旧ASSの安全な除去後にスキップ。音声再生成失敗時の旧版使用は古い結果と表示する。入力の媒体世代・音声結果版・コメント入力版と生成版・表示設定を記録して、公開前後の一致と後着再同期を保証する。競合は保留・再試行、旧正常版を保存する。ただしコメント期限削除中／削除済みには旧コメントを含むASSを保持・再生成してはならない（§13.6）。
- ASS生成は録画・コメント・音声推論と別の軽量ジョブとし、セグメント単位の共通操作ガード・削除台帳・同一ボリューム上の排他的初回公開／安全な置換を適用する。生成状態（未生成／待機／生成中／暫定／生成済み／片側・欠損あり／失敗／スキップ／再同期待ち／期限削除済み／削除済み）、入力版、実ファイル有無・理由を独立表示する。利用はWindows側保存先の外部プレイヤーで行い、Web再生・ダウンロードは実装しない。


## 8. 録画ファイルとコメントの関連付け

### 8.1 セッション単位の管理

動画とコメントは共通の配信セッションIDで関連付けてください。

例：

```text
Stream Session
    |
    +-- Metadata
    |
    +-- Recording Job
    |      |
    |      +-- Segment 1
    |      +-- Segment 2
    |
    +-- Comment Collection Job
           |
           +-- Comment 1
           +-- Comment 2
           +-- Comment 3
```

動画が複数ファイルになった場合でも、同一配信のコメントを共通のセッションに紐付けてください。

### 8.2 時刻管理

内部保存時刻はUTCを基本としてください。

Web UI、通知、SRT出力に関わる日時表示は設定したIANAタイムゾーン（デフォルト `Asia/Tokyo`）に従ってください。内部記録と絶対時刻はUTCとし、SRTの相対タイムコードはタイムゾーンによって変えないでください。

元の日時データが存在しない場合、推測で日時を補完しないでください。字幕表示時刻は動画セグメント内の相対時間であり、タイムゾーンによる表示変換の対象ではありません。

時刻精度については、取得時刻と受信時刻の違いを考慮してください。

### 8.3 欠損管理

以下の状況を明確に記録してください。

- 配信開始検知の遅延
- 動画録画開始の遅延
- コメント受信開始の遅延
- 録画中の接続切断
- コメント収集中の接続切断
- 再接続後の欠損区間
- 録画ファイルの分割

欠損が発生した場合でも、取得済みデータは保持してください。

録画・コメントの欠損履歴は、**後続ジョブの成功では解消済みとみなさない**でください。複数ジョブにわたる同一配信の欠損区間、未確定・無効ファイル、再接続による分断をセッション全体で集計・照合できるようにし、既知のギャップを一覧・詳細から調べられる情報として提供します。

## 10. WSL2とWindowsの保存構成

### 10.1 アプリケーション保存先

基本構成（**リポジトリと実行時データを分離**）：

```text
~/projects/live-rec-lab/                   # Gitリポジトリ：ソース・テスト・設計書
    pyproject.toml
    uv.lock
    .env                                    # 任意。Git対象外
    src/
    config/                                # 必要な場合のみ
~/.local/share/live-rec-lab/
    data/app.sqlite3                       # SQLite / WAL
~/.local/state/live-rec-lab/
    runtime/endpoint.json                  # 起動URL・PID等
    logs/                                  # ローテーション対象ログ
```

上記を通常運用の既定値とし、開発時・複数worktreeで並行検証する場合はDB・実行状態・ログに加え、**録画動画・対応字幕の保存ルートも試作インスタンスごとに別パスへ設定**（隔離時は§15.2.1の専用Linux領域）し、意図しない共有・上書きを防いでください。起動前に、環境変数だけでなく**DBに保存済みの設定を優先順位どおりに解決した実効録画ルート**を確定し、他のアプリケーション・別インスタンスの実効録画ルート（運用者が事前に確認して指定したものを含む）と比較してください。Windows側の実体パスに正規化して、同一パスまたは親子関係の重なりが判明したら**録画ジョブ起動を拒否し、対象パスと対処方法を通知**します。既存アプリの保存先を自動検出できない場合は運用者の実設定確認を求め、未確認を「安全に分離済み」と表示しないでください。Git リポジトリ名は `live-rec-lab`、Python パッケージ名は `live_rec_lab`、アプリケーション名は LiveRecorder です。実行時ディレクトリ名はリポジトリ名 `live-rec-lab` に合わせます。Windows 側の既定録画ルート `D:\LiveRecorder` は、他のアプリケーションの保存先と混在させてはならない**変更可能な既定値**であり、WSL2 上の実行時ディレクトリとは別パスです。SQLiteはWSL2内のext4に置き、`/mnt/c`、NAS、SMB共有や同期ストレージ上へ直接置かないでください。通常運用の録画動画は別設定のWindowsドライブに保存し、各パスは設定可能にしてください。隔離のパス・設定解決・失敗時の拒否には§15.2.1を適用します。通常運用の媒体保存先だけの異常と、起動拒否を要する管理領域・隔離境界の異常を同節に従って区別します。

#### 10.1.1 リポジトリの標準フォルダ・ファイル構成

配置・責務・拡張先の詳細は `docs/system-design.md` §10.1.1に従う。

### 10.2 録画保存先

基本構成（既定 `D:\LiveRecorder`。設定画面で保存先の絶対パスを変更可能）：

```text
D:\LiveRecorder\
    streamer01\
        2026-11-09\
            tiktok_streamer01_20261109_210000_夜の雑談_s001.mp4
            tiktok_streamer01_20261109_210000_夜の雑談_s001_comment.srt
            tiktok_streamer01_20261109_210000_夜の雑談_s001_speech.srt
            tiktok_streamer01_20261109_210000_夜の雑談_s001.ass
            tiktok_streamer01_20261109_210000_夜の雑談_s002.mp4
            tiktok_streamer01_20261109_210000_夜の雑談_s002_comment.srt
            tiktok_streamer01_20261109_210000_夜の雑談_s002_speech.srt
            tiktok_streamer01_20261109_210000_夜の雑談_s002.ass
            twitcasting_streamer01_20261109_220000_作業配信_s001.mp4
            twitcasting_streamer01_20261109_220000_作業配信_s001_comment.srt
            twitcasting_streamer01_20261109_220000_作業配信_s001_speech.srt
            twitcasting_streamer01_20261109_220000_作業配信_s001.ass
```

通常運用では、WSL2の既定の録画ルートを `/mnt/d/LiveRecorder` とし、録画先はWindowsローカルドライブ配下の設定可能な絶対パスとしてください。実効値はSQLiteの保存済み設定、環境変数 `LIVE_REC_LAB_RECORDING_ROOT`、既定値の順で解決します。設定変更後は新規セッションの録画に適用し、既存セッションの固定保存先・再接続・既存ファイルは移動しません。起動時にマウント・書き込み権限・空き容量を検査し、さらに**DB永続設定を反映した実効保存先**と他の録画アプリケーション／別インスタンスの既知の保存先が同一・親子関係にならないことをWindows側のパス同一性を考慮して照合してください。衝突が判明した場合は録画を起動せず警告し、WSL2内や別ルートへ黙って切り替えないでください。比較対象の既存アプリの実設定が自動取得できなければ、起動前の手動確認を必須の導入チェックとします。 隔離データに限り§15.2.1の専用Linux領域を許容する。通常運用のWindows保存要件・命名・媒体確定契約は変更しない。
配信者フォルダ名は原則 `{normalized_streamer_id}` とし、**サービスをまたいで同じ正規化済み配信者IDなら同一フォルダ**に保存してください。Windowsで使用できない名前・衝突がある場合だけ、下記の安定した安全名に変換します。詳細な規則は次のとおりです。

- 第1階層は原則として正規化した配信者IDのみとし、サービス名をフォルダに付けない。Windowsでの利用不可名・別IDとの安全名衝突時だけ下記の固定識別子を付加する
- TikTokとツイキャスで同じ配信者IDなら、別サービスでも同じ配信者フォルダを使う
- 第2階層は `YYYY-MM-DD` とし、設定したIANAタイムゾーンでの配信開始日を使用する。配信開始日時が無いときは検知日を使う。同一配信のセグメントは同じ日付フォルダに置き、日をまたいでも分けない
- 第3階層には動画ファイルと対応するコメントSRT・音声SRT・統合ASSを置く
- 録画ファイル名にはサービス名を含め、別サービスの録画を識別する（例：`tiktok_...mp4`、`twitcasting_...mp4`）
- 表示名の変更では配信者フォルダを移動・改名しない
- Windows禁止文字・予約名・大文字小文字・Unicodeの正規化差、末尾の空白／ピリオド、パストラバーサルを安全に処理する。**異なる正規化済みID**が同じWindows上のディレクトリ名へ写像される場合は、正規化済みID由来の安定した短い識別子を末尾に付け、なお衝突する場合は延長して一意化する（サービス名・DB行IDによる分岐はしない）。元ID→実ディレクトリ名の対応はサービス横断で共通の永続マッピングに保持し、再起動・再登録・追加の衝突発生後も既存名を改名せず再利用する。管理外の既存ディレクトリを所有物として黙って取り込まず、実体の同一性を確認できなければ安全に拒否・復旧対象とする
- §10.3の5要素と衝突時の固定識別子・排他的確定で同名上書きを防止する。同じ配信では日時・タイトルを共有し、セグメント番号だけを進める
- **同じフォルダに保存してもDB上のサービス別アカウント・配信セッション・コメントは統合しない**（ID一致だけで同一人物と判断しない）

SRTは**録画ジョブの終了時に字幕対象コメントがあれば自動生成**し、確定した各セグメントの動画と同じフォルダに§10.3の命名規則で置きます。対象区間に字幕が無い場合はスキップとして扱います。動画の一時ファイルもWindows側の同一ボリューム上に保存し、検証・リネーム・DB確定の順序と再起動時の照合を守ってください。WSL2 ext4からのクロスデバイスrenameを前提にしないでください。

### 10.3 ファイル名

録画ファイル名は以下の5要素をこの順序でアンダースコア区切りにしてください。

- プラットフォーム
- 配信者ID
- 配信開始日時（設定したIANAタイムゾーン。`YYYYMMDD_HHMMSS`）
- 配信タイトル
- セグメント番号（`s001` から開始、最低3桁。1000以上も桁を切り捨てない）

通常の動画stemは `{platform}_{streamer_id}_{YYYYMMDD_HHMMSS}_{title}_sNNN` とします。`platform` は `tiktok` または `twitcasting`、`streamer_id` は正規化済み配信者IDをWindows安全名にした値、`title` は下記の安全化済み配信タイトルです。衝突時だけ後述の固定識別子を番号の直前に追加します。

同一配信では、最初の正式名の予約時に配信開始日時（未取得なら検知日時）を設定済みIANAタイムゾーンで変換した文字列と、安全化済み配信タイトルを固定し、セッションに永続化してください。日付フォルダも同じ日時に基づき固定します。以後はタイトルの変更・後着情報・タイムゾーン設定変更・再起動・別ジョブがあっても命名用の固定値を再計算せず、セグメント番号だけを進めます。各セグメントの録画開始日時はデータベースに残し、ファイル名には使いません。配信タイトルの原文はDBのメタデータとして別に保持します。

タイトルは日本語や通常の空白を保持し、UnicodeをNFCに正規化し、Windows禁止文字（`< > : " / \ | ? *`）・制御文字を `_` に置換し、前後の空白および末尾ピリオドを除去します。空欄・取得不能・安全化後に空になるタイトルは `untitled` とします。予約名・パストラバーサルを許容しません。動画および全字幕の接尾辞・拡張子、衝突識別子、セグメント番号の桁増加を考慮した安全な長さに、必要ならタイトル部分をUnicode文字の途中で破損させず短縮します。後続セグメントで固定タイトルの再短縮が必要になる場合や、タイトル短縮だけで安全なパス長を満たせない場合は上書き・改名せず確定保留として診断します。動画の拡張子を除いた正式名を `stem` とし、対応する字幕は次の固定命名規則で同じフォルダに保存します。接尾辞と拡張子はすべて小文字とし、配信者ID等を含む動画stem自体は変更しません。

| 種類 | ファイル名 |
| --- | --- |
| 録画動画（MP4の場合） | `{stem}.mp4` |
| コメントSRT | `{stem}_comment.srt` |
| 音声SRT | `{stem}_speech.srt` |
| 統合ASS | `{stem}.ass` |

他の許可された動画形式でも実際の確定動画stemを使用します。全字幕は同一セグメントの固定stem・衝突識別子を共有し、接尾辞を重ねません。統合ASSには追加の接尾辞を付けません。すでに保存したファイルは、この規則へ合わせるために改名しません。旧形式で予約済みのセッションは既存の固定命名を維持し、新規セッションから5要素形式を適用します。

同一配信が複数の録画ジョブに分かれた場合も、連番は**ジョブ単位で1へ戻さずセッション単位**としてください。取得物のない空試行は採番対象外です。過去に飛んだ番号は表示順を整えても機械的に再採番・改名しないでください。

同名ファイルによる上書きを防止してください。**別セッションまたは管理外ファイルと同名になる場合**、そのセッションで最初の正式名を予約する際に、永続化した `stream_sessions.id` 由来のWindows安全な短い識別子（例：`_q<session-token>`）を、セグメント番号の前に追加し、**同一セッションの以後の動画・全字幕でも同じ識別子を使用**してください。短縮値がさらに衝突する場合は識別子を延長して再予約します。決めた値を `filename_disambiguator` として保存し、すでに確定したファイルや番号を改名しません。途中から別の識別子へ切り替える必要がある不測の衝突は上書き・黙認せず、確定を保留して復旧対象として記録します。

動画と全字幕の正式名の予約（接尾辞・拡張子を含む長さとWindows同名性を考慮）、同一ボリューム上の一時ファイルからの確定、および字幕の初回作成は**存在確認だけに頼らず上書き禁止の排他的操作**で行い、Windowsの大文字小文字を区別しない同名性も考慮します。アプリが管理する既存字幕の**再生成**だけは、対象セグメントと記録済みパスの同一性・入力版数を検証したうえで一時ファイルから安全に置換できます（§7.8–7.10）。衝突や中断は監査・照合し、別セッション／管理外の実ファイルを消さないでください。

ファイル名の生成時には、特殊文字、不正なパス、パストラバーサルなどを適切に処理してください。配信者フォルダの安全名と、**セッション単位のファイル名衝突識別子 `filename_disambiguator` は用途の異なる独立した識別子**とし、前者の衝突解消が後者の規則を変更しないようにしてください。

排他的な確定の具体的手段は実装時に選ぶ。隔離Linux領域で先行実装し、実使用Windowsマウントの専用試験フォルダで同一ボリューム、大小文字同名、既存ファイル、競合時の非上書き・中断時の保全を代表実証する（通常媒体の利用開始前）。Linuxでの成功や存在確認だけをWindowsでの保証としない。方式が未実証・不適合なら当該媒体書込／公開を保留し、取得済み一時ファイルを保全する。命名・確定契約を弱めず、安全な別方式を選ぶ。

### 10.4 保存容量管理

以下を実装してください。

- Windows側の録画保存先ドライブの空き容量取得
- 録画総容量の集計
- 配信者別の容量集計
- 録画ファイル数の集計
- 保存容量上限の設定
- 最低空き容量の設定
- ディスク容量不足の検知
- 自動削除機能（任意で有効化）

デフォルトでは録画ファイルの自動削除を無効にしてください。Windows側録画保存先の実空き容量・書き込み権限・マウント状態を監視し、WSL2内のSQLite等については `ext4.vhdx` の増大とWindowsホストの空き容量不足も警告してください。

**初期版の削除契約：** セッション詳細で提供する削除は「**ファイルのみ**」（該当動画と対応するコメントSRT・音声SRT・ASSを削除、セッション・ジョブ・コメント・欠損および削除事実をDBに保持）と「**ファイル＋履歴**」（動画／全字幕の削除成功を確認してから、当該セッションと配下のジョブ・コメント・欠損を参照整合性を保って削除）の2方式に限定します。終了未確認のセッションは確認済み終了となるまで「ファイル＋履歴」を拒否（409）し、試行予算・手動停止・採番・期限削除情報を保持する。「ファイルのみ」は他の安全条件が成立するときに限り可能とし、再検知で削除済みファイルを復元しない。**履歴のみ削除は提供しません**（管理外の孤立ファイルを生むため）。進行中／未確定／復旧照合中のセッションや実行中の音声・ASS処理の対象を削除対象にせず、停止・確定後に再判定します。削除対象はDB上の管理パスと許可済み保存ルートを照合し、シンボリックリンク・ルート外・同名衝突ファイルには触れません。ファイル操作とSQLite更新の間で失敗・強制終了した場合は削除処理を未完了として保持し、再起動時に再照合・再試行します。**一部だけ削除した状態を成功と表示しません**。配信者削除は履歴・ファイルの暗黙削除にせず、履歴のある配信者は監視対象から除外する論理削除とします。

**動画の自動削除**は有効化時も「ファイルのみ」を用い、保持済み・確定済みの動画と全対応字幕に限定し、古いセッションから実行します。コメント・セッション・欠損・監査情報は残し、容量不足時に未確定ファイルや稼働中データを緊急削除せず、新規録画を安全に抑止して警告します。期限・容量しきい値の判定と実施結果を記録してください。

#### 10.4.1 削除対象の世代照合と競合防止

削除台帳には対象パスだけでなく、削除開始時点の管理対象・セグメントID・保存ルートと、対象ファイルの世代を識別できる情報を永続化する。再試行・再起動時に同名の新しいファイルが存在しても削除しない。世代・所有・ルートを証明できない場合は保留として診断し、無条件の再試行や新しいファイルへの自動付け替えを禁止する。ファイル不在とルート未接続／アクセス不能を区別し、後者を削除完了にしない。

録画の予約・確定、手動削除、自動削除、コメント期限削除、SRT・音声SRT・ASS公開／再生成と同一対象の操作を整合させる。削除中は対象への新規書込・公開を拒否し、競合中の操作は保留または拒否する。確認から実際の削除までの間のファイル置換も考慮し、使用環境で安全性を確認できない削除方式は採用しない。未完了・一部失敗・世代不一致を成功としない。

**簡易実装方針（SHOULD）**：セグメント単位の共通操作ガード、SQLiteの共通処理台帳（操作種別・対象・世代・版・進捗・結果）、同一ボリュームの一時ファイルを再利用する。セッション削除は対象セグメント全体を安全に保護する。独立した復旧エンジンや自動修復は不要。再起動時は未完了操作と未確定媒体を優先照合し、確定不能なら保留・診断・手動確認とする。単なるプロセス内ロックで外部置換防止を保証したことにせず、世代・ルート・安全な確定／削除を確認できない操作は無効にする。既存の台帳・版・期限の不変条件は維持する。

### 10.5 データ整合性

データベースに登録されているファイルが実在するか確認できる機能を実装してください。

以下を検知してください。

- ファイルが存在しない
- ファイルサイズが一致しない
- ファイルが破損している可能性
- データベースに未登録の録画ファイル
- 未確定の一時ファイル

ファイル修復や削除を自動実行する場合は、安全な条件を設定してください。意図した削除は `deleted`（削除方法・実施日時・対象・結果）として履歴に残し、ファイル不在・破損と混同しないでください。セッション削除は参照中のジョブ・コメント・欠損・字幕を整理し、途中失敗時の未完了情報を保持してください。

照合結果は登録済み対象の確認総数・正常総数・意図的削除済み・異常種別（不在、サイズ不一致、検証不良、未登録、一時ファイル）を区別し、集計時点・読取不能範囲・表示上限による省略を明示する。表示件数の制限で総数を変えない。照合は読取専用を基本とし、稼働中のサイズ増加を確定ファイルの破損と誤認せず、走査中の変更／アクセス不能を未確認として扱う。管理外ファイルの自動取込み・削除は行わない。

### 10.5.1 手動ストレージ照合

システム状態画面で読み取り専用の非同期照合を明示開始し、実行ID・状態（queued／running／completed／partial／failed／cancelled／interrupted）・開始／終了・確認済み件数・対象範囲・最新結果を取得できるようにする。初回未実行と正常0件を区別する。同一インスタンスで同時に1件だけとし、重複要求は既存実行IDを返す。取消は協調的に行い部分結果を保全する。再起動で未完了をinterruptedとし自動で全面再走査しない。起動復旧に必要な管理対象照合は別の限定処理として維持する。

照合は保存ルート・管理ID・ファイル世代のスナップショットを基準にし、稼働中／途中変更／マウント断は未確認。管理外ファイル・一時ファイルは別集計し、全対象数不明のときは処理済み数のみ表示する。DBの短い読取・小バッチと負荷制御、有限期限、取消点を設け、録画・コメント・字幕確定を優先する。全走査・長いファイルI/OをイベントループやDB書込取引内で行わない。照合結果は実行単位の集計・表示上限・未確認範囲・取得時点を保存し、前回の完了結果と実行中結果を区別する。5秒Web更新は保存結果を読むだけで走査を起動しない。照合による自動修復・削除・取込は行わない。

## 11. Web管理画面

### 11.1 基本方針・主要8画面

Web管理画面は**日本語・Windows PCブラウザ専用の運用コンソール**とし、`docs/ui-spec.md` に定める情報設計・表示・操作原則を適用してください。Jinja2＋HTMX＋軽量JavaScriptを用い、ログイン・ユーザープロフィール・モバイル専用画面・動画プレイヤー・ライブプレビューは設けません。

主要ナビゲーションとURLを次のとおり固定してください。**運用・データ5画面＋管理3画面＝合計8画面**です。セッション詳細、編集ドロワー、ログ詳細、設定内セクションは下位ビューであり、独立した主要ナビではありません。

- サイドバーの表示名と順序を統一し、主要URLを不用意に変更しないでください。「配信者一覧」は内部機能としての「配信者管理」に対応します。
- **ダッシュボードは現在の状況、システム状態は健康状態と影響、ログは時系列の詳細記録**にそれぞれ集中させ、同じログ全文を複数画面に重複掲載しないでください。
- 概要から対象セッション・コメント・障害診断・関連ログへ直接進め、一覧と詳細を行き来する際は可能な限り検索条件・ページ位置・スクロール位置を維持してください。
- データ取得失敗、古い情報、正常な0件、検索結果0件、取得不能を区別し、取得できない値を正常値・0・オフラインと断定しないでください。配信・録画・コメント収集・SRTの状態も独立して表示してください。
- 共通ヘッダーに**表示時点（最終取得時刻）**を置き、アプリ独自の画面再読込ボタンは設けません。ブラウザ再読込で外部配信サービスへの追加の監視リクエストを発生させないでください。必要な動的領域を**デフォルト5秒間隔**で自動部分更新してください。設定画面から1以上の整数秒で変更でき、SQLiteに永続化し、再起動なしで反映します。初回表示・手動再読込とは別に定期更新し、重複リクエストを抑止し、入力・編集・テキスト選択・ログ詳細の閲覧中や非表示タブでは対象の更新を延期します。自動更新はアプリ内部の保存済みデータを読み取るだけとし、外部配信サービスへの追加監視を発生させないでください。
- 配色は**ライト系の単一テーマ**とし、配信中＝緑、録画中＝赤、コメント収集中＝青を基本とします。エラーは録画中と形状・ラベルでも区別し、動きは控えめにし `prefers-reduced-motion` に従ってください。録画状態に連動するロゴ・ファビコンは状態が確認できた場合に限り変化させます。
- 表示フォントは**Windows標準（初期値）／Noto Sans JP**の2種類とします。Noto Sans JPは`palt`を有効とし、選択を再読込後も保持してください。テーマ切り替えやOSテーマ連動は不要です。
- 過剰な説明文・カード・装飾で情報構造の不明瞭さを覆わず、画面の役割と操作はレイアウト・分類・視覚的階層で理解できるようにしてください。キーボード操作、フォーカス、ラベル・コントラスト等はWCAG 2.2 AAを目標とします。

#### 11.1.1 自動更新の競合と操作状態の保全

定期更新の送信時と画面反映直前に操作状態を確認する。既に送信された更新応答が編集・確認ダイアログ・テキスト選択・ログ詳細閲覧の開始後に届いても、操作を壊す更新を適用しない。検索条件、対象ID、ページ、設定保存版が変化した場合は古い条件に対する応答を破棄し、古い応答が新しい操作結果・表示時点・録画マークを巻き戻さないようにする。更新失敗時には最後の取得成功時点と値を保持し、状態不明を示す。操作や非表示タブによる延期の解除後には現在条件の再取得を重複なく行う。設定の未保存変更を自動更新で破棄せず、不正入力時には入力値・選択カテゴリを保持する。

### 11.2 ダッシュボード（`/`）

**現在の運用状況をすばやく把握できる画面**としてください。情報の優先順位は以下です。

1. 優先KPI：監視対象配信者数、配信中、録画中、コメント収集中。
2. 稼働中セッション：配信者、サービス、配信状態、録画状態、コメント収集状態、開始時刻・経過時間（取得できる場合）。**該当配信セッション詳細への直接リンク**を付けます。
3. 影響のある異常・容量警告：必要な場合だけ要約し、システム状態／関連ログ／録画履歴へ進めるようにします。
4. 補足KPI：本日の録画件数、本日のコメント取得件数、録画ファイル総容量、Windows側保存先ドライブの空き容量。
5. 最近の録画：該当セッション詳細へ移動できるコンパクトな一覧。

一部の情報取得に失敗しても、正常に取得できた項目まで消さないでください。監視できていない状態を「現在配信中の対象はありません」と表示しないでください。

#### 11.2.1 補足診断情報

配信者別の管理対象動画・字幕保持容量をサービス＋配信者ID単位で集計し、共有フォルダであってもファイルを二重計上しない。論理削除済み配信者の保持ファイルも含む。容量上位とその他・総計、対象ルート、確認日時、未確認件数を区別し、個別録画履歴／システム状態へリンクする。実空き容量と管理対象容量は別の指標。

障害集計は直近24時間（既定）／7日／30日を選択し、UTCの半開区間 [基準時刻−期間, 基準時刻) でsystem_eventsの警告・エラー事象を集計する。重複抑制された障害は事象数と確認できる発生回数・継続中件数を区別し、同じイベントをログと二重計上しない。集計対象期間・データ保持範囲・取得状態・関連ログの絞り込みを示す。欠測・範囲不足を0件としない。現在の影響のある警告は期間外でも別表示する。

環境情報はアプリ版、WSL2/Linux・Python、SQLite、メディアツール、推論デバイスの利用可否と保存先の状態の短い要約／システム状態への導線とする。バージョン取得・容量走査等はバックグラウンドの保存済み診断を参照し、5秒更新ごとに実行しない。詳細や秘密値は表示しない。優先KPIと稼働中セッションを押しのけない。

### 11.3 配信者一覧（`/streamers`）

**監視対象配信者の一覧・登録・編集・削除**を扱う画面です。配信者表示名を主情報、配信者IDを補助情報とするテーブルを使用してください。

表示項目：プラットフォーム、配信者名、配信者ID、監視ON/OFF、配信状態、録画ON/OFF、録画状態、コメント収集ON/OFF、コメント収集状態、最終確認日時。最終配信日時・最終録画日時も詳細等で確認できるようにしてください。

- **監視・録画・コメント収集の3つの設定トグルは独立**させ、稼働ジョブの状態や手動停止・再開とは区別します。
- 追加・編集は共通フォームのドロワー／ダイアログを基本とし、入力形式・必須項目・重複登録・保存結果を適切に示します。論理削除済みの同一（サービス、正規化ID）を追加するときは新規配信者を作らず、**既存行の再有効化**として扱い、過去履歴を保持します。3つのON/OFFはフォームの明示値（いずれか未指定なら入力エラー）で確定し、以前の有効設定を黙って復元しないでください。
- 一覧の配信者から**その配信者に絞り込んだ録画履歴**へ直接移動できるようにします。
- 設定変更が失敗・未確定の場合にUIだけ成功扱いせず、削除では対象と影響範囲を確認させてください。

- 配信者名・正規化ユーザーIDの部分一致検索（日本語・英数字、大文字小文字を区別しない範囲は明示）と既存サービス・状態フィルターを併用する。検索は表示対象のみを変え、監視・録画には影響しない。
- デフォルト順はプラットフォーム（TikTok LIVE→ツイキャス）、表示名（Unicode NFKC＋casefoldの比較キー）、正規化ID、DB IDの安定順。カスタム順は全有効配信者の独立した `sort_order` をSQLiteに永続化する。切替でカスタム順を失わず、新規登録／再有効化は末尾へ。論理削除は順位対象から外し履歴を保持する。表示順は監視優先順位・API枠に影響しない。
- カスタム順のみドラッグハンドルとキーボード（上下移動、確定、Escape取消）を提供する。絞り込み中は並べ替えを無効化し理由と解除導線を示す（隠れた行の誤移動防止）。全対象のID順と並べ替え版を送信し、欠落・重複・未知／論理削除ID・版競合を拒否、トランザクションで全件保存する。登録／削除／再有効化も版を更新。保存中は更新・重複操作を抑制し、失敗時は直前の確定順を復元または最新順を再取得、成功時のみ確定。ページ分割が必要な場合は専用の全順序編集ビュー（下位操作）を用いる。

### 11.4 録画履歴（`/recordings`）・配信セッション詳細

**一覧は動画ファイル単位ではなく配信セッション単位（1セッション＝基本1行）**としてください。「録画履歴」という画面名でも、録画しなかった／録画できなかった配信セッションのうちコメントだけ残っているものを除外してはいけません。

一覧表示項目：配信者、プラットフォーム、配信タイトル、配信開始・終了日時、録画時間、録画ファイル数、合計サイズ、コメント件数、録画状態、コメント収集状態、詳細への導線。未取得値を0に置き換えないでください。

検索条件：配信者、プラットフォーム、日付範囲、録画状態。検索条件と並び順・ページ位置を保持し、コメントのみ取得できたセッションも探せるようにしてください。

配信セッション詳細は上から次の構成とします。

1. 配信概要：配信者・プラットフォーム・タイトル・開始／終了時刻・配信状態。
2. 取得結果：録画状態とコメント収集状態を分けた表示、録画ファイル数とコメント件数。
3. 録画セグメント：連番、開始／終了、長さ、形式、サイズ、検証状態、および**同じセグメントのSRT生成状態・生成日時・再生成操作**（実際に可能な場合）。
4. このセッションのコメントに絞り込んだ**コメント画面へのリンク**。
5. 欠損・失敗情報と、その影響・理由、システム状態の診断要約／関連ログへのリンク（関連付けできる場合）。
6. 削除操作：**ファイルのみ／ファイル＋履歴**の対象・影響範囲・復元可否・処理中／失敗を示す独立領域。履歴のみ削除は提供しない。

- 録画なしのコメント取得セッションではコメント閲覧へ誘導し、**録画セグメントのないセッションにSRT生成・再生成を表示しません**。
- コメントSRTは§10.3の命名規則で対応する動画と同じWindows側フォルダに保存し、時刻同期の根拠（実測・近似・手動補正・同期不能）や失敗理由は取得できる範囲で確認できるようにしてください。コメント期限削除済みの場合は、残る動画と混同せずSRTも期限削除済みと表示し、再生成操作を無効にしてください。
- **Web／APIで録画動画・SRTのダウンロードは提供しません**。動画再生・ライブプレビュー・同期コメント再生も設けません。Windows側の保存先でファイルを取り扱います。
- 録画取得とコメント取得の一方が失敗しても、もう一方の結果を隠してはいけません。
- 録画状態のセッション要約は**最新ジョブだけで決定せず**、過去の全録画ジョブ・セグメント検証結果・欠損区間を照合してください。最新ジョブの状態は必要なら「最新ジョブ：完了」等の補足として示し、同じ配信に `FAILED` / `invalid` / `pending` / 欠損が残っているのに**「セッション全体が完全に録れた」かのように表示しない**でください。
- DB上の動画名が存在しない、0バイト、確定後の長さと不一致、検証不能などの情報を、ファイルの存在・完全性を保証する値として扱わず、必要な診断結果を表示してください。
- 過去の `last_error` が残っていても現在の録画失敗とは限らないため、発生時刻・対象ジョブ・その後の回復を区別し、エラーの有無だけで現在状態を決定しないでください。
- セグメントのSRTが0cueでスキップされた場合は「字幕対象なし」と示し、コメント収集失敗やSRT生成失敗と混同しないでください。

### 11.5 コメント（`/comments`）

コメント本文を中心に、**配信別閲覧と配信横断検索の2モード**を同じ `/comments` で提供する。初期表示は配信別閲覧。配信別はコメントを取得した／収集中／取得失敗・期限削除済みのセッションを検索・ページングし、配信者・サービス・日時・コメント件数・収集状態を表示する。動画なしのコメントのみセッションも対象。配信選択で本文一覧へ移動し、録画詳細からは対象セッションを直接開く。横断検索は従来の全条件を維持する。両モードで本文・投稿者・日付等の該当フィルター、投稿時刻（不明なら受信時刻）とDB IDによる安定した昇順／降順を選択可。既定は配信別昇順・横断降順。投稿時刻不明の旨を示し、日付範囲は表示タイムゾーンに基づく同じ実効時刻に適用する。モード、条件、順序、ページをURL・戻る操作で保持する。期限削除済みは本文を再取得せず状態を表示し、真の0件と混同しない。

- 主検索条件：コメント本文。詳細条件：投稿者ID、投稿者表示名、配信者、プラットフォーム、配信セッション、日付範囲。
- 一覧項目：投稿日時または受信日時、配信者、プラットフォーム、投稿者表示名・ID、コメント本文、録画開始からの経過時間（取得できる場合）、関連セッション。
- 検索・絞り込み・ページネーションを実装し、長文・改行・絵文字を欠落させないでください。関連セッションへ移動後に検索条件・ページ位置を可能な限り復元してください。
- ツイキャス匿名コメント番号は実際に取得・一意照合できた場合だけ表示します。未取得番号や人物の同一性を推定しないでください。
- コメント画面にCSV／JSONL／TXT等の出力メニューを設けず、SRT生成状態の確認や再生成は**録画履歴の該当セグメント**へ案内してください。保存期限による消去済みセッションでは「0件」と混同せず消去済みと表示し、削除されたコメントは検索結果に出しません。

### 11.6 システム状態（`/system`）

**現在の健康状態・影響範囲・診断要約**を扱います。ログ全文の時系列検索や詳細ビューをこの画面に重複実装しないでください。

表示項目：

- Webアプリケーション／同一プロセス内ワーカーの状態、最終監視実行日時
- SQLiteファイル・WAL・書き込み状態、保存先ドライブのアクセス状態・空き容量
- 録画エンジンの状態とStreamlink／yt-dlp／TikTokLive／FFmpeg等のバージョン・利用可否
- 外部サービスの接続状態、監視制限・再試行待ち（実際に取得できる範囲）
- 影響のある直近の警告・エラーについての**時刻・重要度・対象・影響・状態の要約**、保存先の照合結果

障害が分かった場合は、関連する録画履歴のセッション詳細、またはログ画面の該当条件・エントリに直接進めるようにしてください。詳細ログが閲覧不能でも、健康状態を架空の正常に変えないでください。

メディア診断では、実際に起動された `ffmpeg` / `ffprobe` のバージョン・解決元、最終ファイル検証の結果、不一致や未回収ファイルの**存在と影響**を、取得可能な範囲で見分けられるようにしてください。特定環境の絶対パスを固定の正常条件にしないこと。

#### 11.6.1 照合と診断操作

§10.5.1の照合開始／取消／状態・結果取得をこの画面内で提供する。進捗が不定なら件数と経過時間を示し、完了率を推測しない。前回の完了結果・今回の部分結果・未実施を分け、走査対象範囲と中断理由を表示する。照合は画面再読込・削除とは別操作。

### 11.7 ログ（`/logs`）

**ログ画面を8つの主要ナビの1画面として必ず実装**してください。システム状態が障害の要約を示すのに対し、ログ画面は「いつ、どの処理で、何が記録されたか」を時系列で調査します。これは14.3節に定義する構造化ログおよび`system_events`の範囲で実装し、初期版で新しい外部ログ基盤・全文検索エンジン・ログ専用DBの導入を要求しません。**ただし必要なログ読取・絞り込み・ページング・詳細取得のバックエンド処理は初期実装の必須範囲**です。既存コードに読取器がなくてもUIだけで完了としないでください。

- **初期表示は発生時刻の降順**とし、発生時刻、実際のログレベル、出力元（サービス・コンポーネント等）、要約メッセージを一覧に表示します。配信者・セッション・イベント・ジョブIDは実際に記録された場合のみ使います。
- 時刻範囲、重要度、出力元、本文キーワードについて、**実際に取得・検索できる条件**を提供してください。相関ID、配信者・セッション別絞り込みは信頼できる識別子が存在する場合のみ有効にします。
- 検索条件・結果件数・対象期間・並び順・現在位置を示し、**サーバー側で件数を制限したページング／段階的読取**を行います。ブラウザへ全ログを転送して検索させないでください。
- 行の詳細を開くと、**秘密情報を除去した完全な本文**、絶対日時、ログレベル、出力元、実際に記録されているメタデータ・スタックトレースを閲覧・コピーできるようにします。ログの内容を書き換えたり、記録されていない値を生成しません。
- システム状態の警告／エラーからログへのリンクでは、確認できる**時刻・レベル・出力元・関連対象**を可能な限り引き継ぎます。識別子がなければ曖昧な関連付けを断定しないでください。ログから配信者一覧・録画履歴の該当対象にも移動できるようにします。
- ログの0件、フィルター結果0件、取得失敗、情報が古い状態、取得可能期間の制約を区別します。**0件を無障害の保証としません**。
- UIからのログの一括削除・クリア・ダウンロード・ライブ追尾・保持期限変更は初期必須ではありません。ログレベルの変更は設定画面に集約し、未提供操作を空のボタンで見せないでください。
- アプリケーション内部のログのみ参照し、OS全体や他アプリのログ、任意パスのファイル閲覧を勝手に提供しないでください。ログの読取は許可したディレクトリ・ファイルに限定し、外部リクエストのパス指定を信用しないでください。

### 11.8 設定（`/settings`）

設定項目を**監視／録画・保存／コメント・SRT／音声字幕／表示／詳細設定**の6領域に整理し、主要画面は増やさないでください。

- **監視**：サービスごとの監視頻度（回／分）、変更不可の上限と設定値／実効値の違い。TikTokは `0 < r ≤ 10`、ツイキャスは `0 < r ≤ 60`（初期値10回／分）。小数可、設定値の永続化と次回巡回からの即時反映。外部APIの残枠・コメント収集優先で実効頻度が低下する場合は、確認できる範囲で表示。
- **録画・保存**：同時録画上限、録画品質、Windows側保存先（§10.2の既定値・変更契約）、最低空き容量、保存容量上限、保存期限、自動削除、TikTok録画エンジン優先順位、再接続回数。
- **コメント・SRT**：コメント収集ON/OFF、ツイキャスコメント取得間隔、字幕表示秒数、コメント保存期限（日数。初期値`0`＝無期限）。コメント期限削除は動画・履歴・音声SRTを消さずコメントSRT・統合ASSも対象となる旨、取り消し不能である旨を明示。
- **音声字幕**：自動生成ON/OFF、モデル、認識言語、実行デバイス（§7.9）。GPU／モデルの可用性は読み取り専用診断とし、生成中の設定と次回設定を区別。ASSは自動同期し個別再生成可。
- **表示**：表示タイムゾーン（IANA形式、初期値`Asia/Tokyo`）、フォント（Windows標準／Noto Sans JP）のプルダウンと保存前プレビュー、自動更新間隔（秒、§11.1）。
- **詳細設定**：ログレベル、固定Webポート（§2.2の既定値・範囲・次回起動反映、現在値と保存値の区別）。

フォームで編集可／読み取り専用／未保存／保存中／反映済み／失敗／再起動後反映を区別してください。APIキーや秘密情報を平文表示しないこと。設定範囲外・不正値・保存競合・再起動要否を適切に示し、未保存変更を画面移動で不用意に破棄しないでください。

| 詳細 `log_level` | 列挙 | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR` | 保存直後、管理イベント・状態監査はレベル変更で失わない |
| 詳細 `web_port` | 整数 | 8082（隔離は§15.2.1） | 1024〜65535、0不可 | 次回正常起動。現待受を変更しない（§2.2） |

`recording_root` は登録する実効値と既存セッションに固定した保存先を区別する。容量上限は複数の管理済み保存ルートを通じた実体の保持動画・全対応字幕の合計とし、未確定作業ファイル・DB・モデル・管理外ファイルを含めない。空き容量は新規録画の実効ドライブごとに判定する。上限・空き容量の判定不能は0や無制限としない。自動削除OFFでは容量・期限到達のみでファイルを削除しない。録画・コメント期限は独立する。SRT表示秒数変更による再同期は期限削除済み・ファイル削除済みの対象に適用しない。表示時刻変更で既存のSRT相対時刻は変更しない。

数値はNaN・Infinity・真偽値の数値への暗黙変換・整数欄の小数・実装の表現範囲を超える値を拒否する。上限を設けていない正整数はSQLiteの符号付き64bit整数の範囲、正の実数は表現と換算が安全な値に限定し、長いタイマーは分割待機して桁あふれを避ける。UI/API/CLIは共通の型・単位・検証器を用いる。文字列のフォーム入力は明示的に型変換し、JSONは型を検査する。未知キー・列挙不正・重複・秘密キーのPUTを拒否。設定保存は現行版との比較と全対象値の検証を一つの短いトランザクションで行い、一部だけ保存しない。不正値はフィールド別理由、競合は現行版を返し、入力を保持する。設定の保存成功と実行時の利用可能性・反映失敗を別表示する。起動時に不正な保存済み設定を診断し、影響する機能を安全に保留する。Webポート・DB等の必須起動条件の不正は起動拒否とする。

## 13. セキュリティ

### 13.1 Webログインを設けない場合の運用境界

Web管理画面とローカルAPIにユーザーアカウント、パスワード、セッションログインを実装しないでください。趣味の個人利用であり、起動後すぐ操作できることを優先します。

- `127.0.0.1` へのバインドを初期状態で必須とする
- 管理画面から録画・設定変更・削除が可能なことを明示する
- 認証なしの状態でLANやインターネットへ公開しない
- 外部公開が必要になった場合は別途認証付きリバースプロキシ等を検討する
- POST等の状態変更操作にCSRFトークンとOrigin/Host検証を行う。CORSを無条件許可せず、localhostからの意図した操作だけ受け付ける。限定例外は§13.7の隔離データの非ブラウザ専用経路のみ
- HTTP GETで状態変更・削除を実行しない

初期段階でパスワードハッシュ、管理者ユーザーDB、ログイン・ログアウト機能は不要です。

### 13.2 API・入力値の検証

- SQLインジェクション対策
- XSS対策
- CSRF対策
- SSRF対策
- パストラバーサル対策
- コマンドインジェクション対策
- URL正規化
- ホスト名検証
- アップロード先など、ユーザーが指定するパスの検証

ユーザーから入力された任意のURLを無検証でFFmpeg、Streamlink、yt-dlpへ渡さないでください。

#### 13.2.1 HTTP応答と外部入力の防御

HTML・JSON・部分更新・静的資産・エラー応答に `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: same-origin` を付与する。CSPは `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'; form-action 'self'` を基本とし、必要な資産は同一オリジンから提供する。実ブラウザでHTMX・アイコン・フォント・動的状態・エラー画面を検証し、必要な例外がある場合は最小範囲と根拠を設計で確定する。`unsafe-inline`／`unsafe-eval` の一律許可、外部CDN依存は行わない。テンプレート自動エスケープ、外部入力のテキスト挿入、HTMXのeval無効化、インラインイベントハンドラ禁止を基本とする。コメント・表示名・エラー・ログ・URLを未検証HTML／JSとして挿入しない。既存のHost／Origin／CSRF検証とループバック限定を維持し、CSPをその代替としない。動的な秘密・個人情報を含む応答は `Cache-Control: no-store`。

#### 13.2.2 HTTP共通入力・操作契約

全管理APIは統合設計§17に従い、本文・検索・ページサイズ・ソート許可リスト・型・日付境界を検証し、日本語エラー・機械判定コード・相関IDを返す。GETは副作用なし。登録・編集・設定・順序等は同期トランザクションと一意制約／設定版／順序版を使用する。長時間の録画・字幕・照合・削除等は既存の業務ジョブ／削除台帳で重複防止し、受付と完了を区別する。汎用の永続操作受付台帳・全変更への操作キー・詳細失効管理は不要。結果不明時は現在値・業務状態を確認し、危険な自動再実行を行わない。秘密・媒体本体を応答しない。

通常運用・通常起動ではSwagger UI `/docs`、ReDoc `/redoc`、OpenAPI `/openapi.json` およびSwagger OAuth補助ルートを無効化し404を返す。通常運用相当の試験でも同じ制約を維持する。開発者モードに限る公開例外は§13.7に従う。通常設定への公開切替項目は追加しない。

### 13.3 秘密情報

以下の情報を安全に管理してください。

- ツイキャスAPIのClient ID / Client Secret（HTTP Basic）
- Euler Stream無料APIキー（使用する場合）
- 必要に応じた将来の通知用認証情報

秘密情報をGitリポジトリへコミットしないでください。

`.env.example` にはダミー値のみ記載してください。

#### 13.3.1 外部署名通信の最小化

Euler Stream等、利用条件に合う採用SDKの許可済み署名先だけにHTTPSで接続する。署名を要する操作だけに必要な配信識別子・SDKの必要なUser-Agent・設定済みAPIキー等の最小情報を送信する。TikTokログインCookie・sessionid・アカウント資格情報・コメント本文・録画／音声・任意の秘密情報を送らない。CAPTCHA解決・署名自前生成・アクセス制限回避は行わない。SDKが送信する項目・宛先・リダイレクトを採用版で確認し、余分な送信を止められない経路は採用しない。外部通信は無料枠と既存レート制御に従い、署名を消費する全経路（監視代替・コメント初回／再接続・SDK録画）で同じ資格情報／枠単位の共通予約を行う。要求枠・同時接続枠を区別し、並行予約・実消費・429／Retry-After・期限／残枠不明を照合する。不明な消費を0とせず、上限不明時は安全な確認または保留、再起動後も枠が回復した根拠なしに初期化しない。外部サービスの具体的な枠・リセット規則は実証して確定し、有料移行しない。ログには秘匿済み宛先種別・結果・使用枠だけを記録する。

### 13.4 ネットワーク

- 不要なポートを公開しない
- SQLite DBファイルをネットワーク共有しない
- worker専用管理ポートを初期実装で増やさない
- Web UIはWindowsからのlocalhostアクセスを基本とする
- LAN公開時は認証・アクセス制限・HTTPSを別途設計する
- 設定された固定ポート番号と実際に待ち受けているURLを起動時に表示する

### 13.5 WSL2プロセス・ファイル権限

- 通常のLinuxユーザー権限で実行する
- DB、ログ、録画、秘密情報ファイルに必要最小限の権限を設定する
- 管理用コマンドをrootで常用しない
- 子プロセスとWebサーバーを不必要に権限昇格させない
- 録画動画・字幕のファイル本体はHTTPで提供しない

### 13.6 コメントデータの保護

視聴者IDやコメント本文を含むため、コメントデータを含む管理画面はローカル専用にし、LAN等へ無認証公開しないでください。

コメントデータの保存期限（日数、`0`＝無期限／期限削除なし、初期値`0`）を設定画面の「コメント・SRT」で変更可能としてください。**録画ファイルの保存期限・容量上限とは独立**した設定です。`0` 以外は1〜36,500の整数（§11.8.1）とし、UTCのセッション収束日時 `ended_at` を起算点に、保存期限を過ぎた**収束済み・コメント取得と書込キューが終了済み・復旧照合中でないセッション**だけを削除対象とします。進行中・終了未確定のまま未収束・未確定処理中のコメントは消さず、取得不能を期限経過と誤認しないでください。

期限削除では**該当セッションのSQLiteコメント本文・投稿者識別情報と、それに由来する全コメントSRTおよび統合ASS**を一体の削除対象とし、動画・配信セッション・ジョブ・`collection_gaps` は残してください。`deletion_operations` に内部操作「コメント期限削除」を先行記録し、**開始したセッションではSRT再生成・新たなコメント保存を排他停止**してください。許可済み保存ルート上のコメントSRT・統合ASS削除完了を照合した後でSQLiteコメントを削除し、`stream_sessions.comments_purged_at` と `purged_comment_count`（元の取得件数との区別用）を確定します。途中失敗時は未完了として再起動後に冪等再照合し、**SQLiteコメントを消したのに派生SRT・ASSが残る状態を成功扱いしません**。既存の手動削除2方式は増やさず、動画の自動削除とも区別します。

期限削除済みセッションはコメント一覧・詳細・件数表示で「保存期限により削除済み」と示し、未収集・0件・取得失敗と区別します。SRTも「保存期限により削除済み」とし、古い字幕を再生成・自動復元しません。保存済みの集計値を残す場合は**削除済み件数**と現在閲覧可能な件数を分けます。通常ログにコメント本文や秘密情報を記録しないでください。

**手動バックアップの運用境界：** `backup` CLIが作るSQLiteバックアップは、その時点のコメント本文・投稿者情報を含む可能性がある**独立したスナップショット**であり、コメント期限削除によって自動消去されません。初期版のバックアップ保存先は利用者管理とし、作成・終了時に保存場所と個人情報の残存、期限削除との関係を警告します。利用者は**保存期限を過ぎたコメントが含まれる古いバックアップを継続保持せず、不要になったら安全に破棄するか期限削除後の新しいバックアップに差し替える**運用としてください。アプリは管理外のバックアップを探索・無断削除せず、バックアップも削除されたと誤表示しません。期限削除が保証する範囲は**稼働DBと本アプリが管理するコメントSRT・統合ASS**に限り、バックアップ側の破棄は別途手動確認が必要です。初期版にバックアップからの復元CLI・自動復元は設けません。通常の再起動の冪等性・試行予算保証はDBが巻き戻らない範囲に限る。手動復元は§15.2.1の復元安全契約に従う。復元DBのファイル世代・削除／字幕／業務ジョブ・試行予算・停止指示・配信ID・外部消費枠・現在適用すべき保持期限を現実の状態と照合し、未確認の操作再実行・予算復活・削除済みコメントの復活を禁止する。必要な情報が失われた場合は安全を確認できるまで再開しない。

適用される個人情報保護法令、配信者の権利、サービス利用条件を考慮してください。

コメント期限削除の台帳登録以降は、音声再生成を契機とするものを含め、ASS公開を禁止する。音声再生成自体は期限削除完了後に許可する。統合ASS（音声のみの暫定版を含む）とコメントSRTの削除・一時成果物の回収を確認してからDBコメントを消去する。音声SRT・音声ジョブ情報・動画は残し、音声本文の閲覧・音声再生成は可能とするが、期限削除済みセッションの統合ASSは再生成しない。復元DB・残存一時ASSによるコメント復活を防ぐ。管理外の手動コピーは削除保証外。

### 13.7 通常運用モードと開発者モード

AIコーディングエージェント（Cursor、Codex、Claude Code等）がソース・API・DB・実行状態・ブラウザを横断して分析、再現、修正、検証できるようにする。実行モードは **通常運用（既定）と開発者（明示起動）だけ** とし、共通アプリケーションコア・共通診断基盤を利用する。診断はモードではなく両モードの読み取り専用CLI機能とする。独立診断サーバー、MCP、専用常駐プロセス、開発専用主要画面、任意SQL／シェル／ファイル操作HTTP APIは不要。

- 通常運用は§13.1〜13.6の防御・公開範囲を維持する。開発者モードは `start --dev` の明示指定だけで起動し、通常設定DB・環境変数・Web設定画面・自動起動へ有効状態を永続化しない。停止・再起動で通常に戻る。開発用ルートは通常運用で登録しない（404）。
- 開発者モードの既定は隔離データ。DB・設定・ログ・runtime・録画／字幕保存先・ポート・資格情報を実運用と分離し、外部配信／署名通信は既定で停止する。実接続試験は許可済み対象と必要な資格情報を明示的に選び、既存の制限・採用条件と§15.2.1の共有外部通信排他を適用する。模擬操作・障害注入・初期化は隔離データだけに許可する。
- 実運用データを開発者モードで直接開くことは禁止する。通常運用の読み取り専用診断とSQLite Online Backupを使い、必要なら利用者が明示した一貫性スナップショットを隔離環境へ取り込む。取り込み時に保存先・資格情報・自動処理・削除／公開予約を実運用から切り離し、隔離の設定と管理対象へ再対応付けする。実媒体は許可したコピーだけを使い、通常のファイルへの参照・変更・削除は禁止する。コピーで再現できない場合は読み取り専用調査を行う。
- 両モードでループバック限定、Host検証、入力検証、XSS／SSRF／SQL・コマンドインジェクション／パストラバーサル防御、GET無副作用、秘匿、媒体本体のHTTP非公開、業務の整合性・外部サービスの制限を維持する。CORS全許可、CSP全解除、任意のOrigin許可は不可。
- 開発者モードだけでSwagger UI・ReDoc・OpenAPI JSON、秘匿済み詳細例外・診断情報を提供する。ソースマップは必要な場合に限り有効化する。静的資産はローカルとし、CSP例外は必要な開発専用ルートに限定する。ブラウザの管理操作は従来のCSRF・Origin／Host検証を維持する。非ブラウザの隔離データ操作に限り、起動単位の短命なローカル専用トークンを検証する専用経路でCSRF／Originの代替を許す（Origin付き不正要求は拒否、Host検証は必須）。既存の保護付きAPIをCLIやHTTPクライアントから扱う方法でもよい。採用した方法でAIがAPIを直接操作できるよう、curl／Python等による安全な読取・変更要求の再現手順をマニュアルに記載し、隔離環境で検証する。実運用データではこの例外を適用しない。トークン・診断情報はURL・ログ・Git・外部送信に混入させない。

初期開発支援は既存APIをcurl／Pythonから利用できる手順、Swagger UI／OpenAPI、秘匿済み詳細ログ、読取専用diagnose、隔離fixture・スナップショットで十分。既存CSRF保護付きAPIを優先し、専用トークンや多数の障害注入HTTPルートは必要な場合だけ追加する。専用デバッグ画面は不要。境界の実装は省略しない。

§15.2.1の起動・データ境界と§14.6の開発支援を併せて実装し、TC-108およびTC-110〜111で通常運用の回帰と開発者モードを検証する。

通常運用の登録・有効化による通信許可と、開発者モード／実接続試験の明示許可は§15.2.1で区別する。開発時の既定拒否を通常運用の配信ごとの確認に適用しない。

### 14.1 対応すべき障害

以下を想定してください。

1. Windows再起動・シャットダウン
2. WSL2停止・Ubuntuセッション終了
3. Pythonアプリケーション異常終了
4. SQLiteのロック競合・書き込み失敗
5. インターネット回線切断
6. TikTok接続エラー
7. ツイキャスAPIエラー
8. Streamlink異常終了
9. yt-dlp異常終了
10. FFmpeg異常終了
11. 配信の突然の終了
12. コメントWebSocket切断
13. コメント保存失敗
14. ディスク容量不足
15. 保存先への書き込み権限エラー
16. ディスプレイOFF・Windows画面ロック・スリープ／休止の違い

### 14.2 自動復旧

- Windowsサインイン後のWSL2起動・アプリ起動手順を用意する（サインイン前の常時起動は初期保証しない）
- WSL2内でsystemd等によるプロセス再起動を検討する（systemdだけでWSL2自体の常時稼働は保証されない）
- Windows画面ロック中／ディスプレイOFF中も録画を継続する
- Windowsスリープ／休止では録画が中断するため、運用設定と復帰時の再照合を提供する
- SQLite接続再試行・ロック時の待機
- 監視ジョブ再起動
- 録画ジョブ状態の再照合
- コメント収集ジョブ状態の再照合
- 孤立プロセスの検出
- 二重録画の防止

WindowsやWSL2停止中に配信が終了した場合、録画できなかった区間を取得できたかのように扱わないでください。

#### 14.2.1 中断区間と起動時の復旧判定

正常停止・内部障害・強制終了・Windows／WSL2停止を区別する。アプリ停止は配信終了・利用者による録画手動停止を意味しない。停止時の手動停止指示と個別設定は永続化し、再起動後も優先する。未完了セッションを起動時に再照合し、既存の録画・コメントジョブ、未確定媒体、削除台帳、SRT版数を確認する。

- 同一配信の継続が確認でき、対象機能の設定・停止指示・永続試行予算（§6.5.2）を満たす場合だけ、重複のないジョブまたは既存ジョブの再接続で再開する。録画では容量・録画枠を確認して新規セグメントを使用する。録画の容量・枠不足はコメントの再開を妨げない。確認済み終了済みセッションを再接続へ戻さない。別配信IDは新しいセッションとする。終了未確認の再利用は§5.3の規則に従う。
- 監視がUNKNOWN／ERRORの場合は直ちに完了・失敗・配信終了を確定せず、既存の有限収束規則に従って診断し、確認できない配信期間を取得済みとしない。
- 再起動に伴う欠損を `worker_restart` 等の理由で記録する。録画では最後に保全できたメディアの実測終端（近似の場合は根拠を明記）、コメントでは最後の確実な収集／保存境界を使う。最後の取得時刻が不明なら欠損開始を時刻不明として扱い、再起動時刻を最後の取得時刻と捏造しない。次の確実な取得または終了確認まで欠損を開いた状態で管理し、復旧の再実行で重複欠損を作らない。
- 配信中の継続収録の確定、台帳とファイルの照合、期限削除・SRT再同期をそれぞれ独立に再開できるようにする。対象の復旧が保留中であれば関連する書込・削除を抑止し、無関係な対象の処理は継続できる。

復旧は安全な保留を優先する。初期は有限再接続・再起動時の未完了対象の検知／照合・確実に検証できた対象だけの再開／確定を実装する。不明な世代・孤立ファイル・複雑な競合は保持し、対象を保留して診断または手動確認へ回す。全面自動修復・全異常組合せの検証は不要。取得済み媒体やコメント、停止指示、採番、期限、予算の不変条件は維持する。

### 14.3 ログ

ログには以下を記録してください。

- 監視開始
- 監視終了
- 配信開始検知
- 配信終了検知
- 録画開始
- 録画終了
- 録画失敗
- 録画エンジン切り替え
- コメント収集開始
- コメント収集終了
- コメント収集失敗
- 再接続
- ディスク容量不足
- システム再起動

障害の再現・追跡ができるよう、構造化ログ（JSON Lines等）へ以下の情報を可能な範囲で記録してください。

- UTC日時、ログレベル、component（モジュール）、event_code（事象種別）
- exception type、例外メッセージ、traceback（スタックトレース）
- correlation_id、job_id、stream_session_id、service、streamer_id
- リクエスト対象API・HTTP status・レート制限ヘッダー（秘密情報は除外）
- WebSocketの接続・切断理由・再接続回数・再接続待機時間
- 録画エンジン名・バージョン・子プロセス終了コード・stderr（秘密情報を除外）
- 再試行結果、保存先エラー、残容量、データ欠損の開始・終了時刻
- 開始／成功／失敗／復旧など各処理段階と、再現・切り分けに必要な状態

SQLiteの `system_events` には検索用の要約を保存し、詳細ログと処理IDで対応付けてください。ログに存在しない配信者ID・セッションID・発生時刻等を本文から推測して埋めず、確認できる相関識別子に限って関連付けてください。例外を握りつぶして正常終了として扱わず、外部APIの失敗・録画失敗・コメント収集失敗を別々に記録してください。

ログローテーションを実装してください。初期ポリシーは1ファイル10 MiB、現行を含め5ファイル（旧世代4）とし、Linux側のアプリ専用ログだけを対象にする。単一の書込責務と安全なローテーションでレコードを分断しない。巨大行は秘密除去後の上限付き記録と切詰め理由を残す。旧世代から順に削除し、読取中の回転・欠落は再照合と範囲不足として扱う。UIで保持変更・クリアは追加しない。system_eventsの要約はログファイルの世代削除とは別管理とし、期間集計に必要な事象数と取得可能範囲を保持する。

同一監視失敗や同一のエンジン切替イベントは、単なる巡回回数に比例して無制限に増やさないでください。ただし継続中の障害・件数・回復を追跡できる情報は残します。録画・SRT・コメントのジョブ状態、診断イベント、ログの間で**発生時刻と対象を区別**し、過去の `last_error` を最新失敗として誤読させないこと。

外部サービスのエラー時はHTTP status・レート制限ヘッダー・WebSocket切断理由・エンジン切替結果を記録し、秘密情報をマスキングしてください。

APIキー、署名付きストリームURL、認証トークンなどの秘密情報をログに残さないでください。

**ログ画面への提供**：第11.7節の `/logs` は、上記の構造化ログ・ローテーション済みログと、利用可能な`system_events`要約を読み取り専用で参照します。**既存実装の有無にかかわらず、ログ読取サービスとWebからの取得処理を初期版で実装**してください。閲覧用に新たなログ収集インフラを増設する必要はありません。記録済みのタイムスタンプ・レベル・コンポーネント・事象種別・本文・相関IDを対象に、取得可能な範囲で時刻降順の検索・絞り込み・詳細閲覧を実現してください。ファイル読取は許可されたログ保存ディレクトリに限定し、パス操作やファイルサイズによるメモリ枯渇を防ぎ、件数を制限して段階的に取得します。ローテーション中やファイル消失時の取得失敗と情報鮮度を正確に表示し、ログ本文・トレースバック等の**秘密情報は記録段階で除去し、閲覧段階でも保護**してください。古いファイルや外部ライブラリの例外文に残った秘密情報も、一覧・検索結果・詳細・コピー対象を含む**応答生成前**に再マスキングし、非秘匿部分は省略せず表示してください。マスキング済みテキストだけをクライアントへ渡し、生ログの直接配信はしないでください。ログ閲覧を理由に録画・監視処理を長時間ブロックしないでください。

### 14.4 安全な停止

アプリケーション停止時には以下を実施してください。

1. 新規ジョブ受付停止
2. 実行中ジョブへの停止通知
3. 録画プロセスの安全な終了
4. コメントキューの可能な範囲での書き込み
5. ジョブ状態の保存
6. 終了処理のタイムアウト管理

停止は単調時計の共通30秒予算（CLI・管理プロセス・子の全体）で進める。開始時に新規受付と巡回を止め、録画には最大20秒の安全終了・確定猶予、コメント受信停止・キュー書込には最大5秒、音声推論には停止通知と最大20秒の安全回収を並行で割り当てる。未完了のFFmpeg・推論子は25秒までに所有確認の上で段階的に終了／必要時強制停止し、残る5秒を台帳・欠損・状態・ログflushとDB解放に確保する。長いリマックス・推論完了を待って全体予算を超えない。安全に収束できない処理は永続台帳・一時ファイルを保全し次回復旧へ回す。停止要求受付、完了、期限超過／未回収を区別し、停止不能を成功表示しない。CLIはプロセス生存／所有・endpointを確認し、他プロセスを停止しない。停止中はヘルスをstoppingとする。

強制終了で未確定ファイルが残った場合は、次回起動時に回収・検証できるようにしてください。

### 14.5 機能別ヘルスチェックとエンジン診断

Web応答、SQLite読取・書込、監視（サービス別）、録画管理／稼働中子プロセス、コメント（サービス別・接続世代）、音声推論管理／子、ASS、保存先（ルート別）、ログ・保守の状態を個別に管理する。`ok`／`idle`／`disabled`／`blocked`／`starting`／`stopping`／`degraded`／`error`／`unknown` を区別し、各項目に最終確認時刻・最終成功時刻・期待次回時刻・鮮度・理由・影響・関連対象を持つ。利用対象がない、設定OFF、正当なAPIバックオフ、GPU保留を障害・正常稼働と混同しない。

管理ループのハートビートを10秒周期で更新する。単調時計で30秒超を古い情報、60秒超を応答異常候補とし、起動猶予・停止処理を区別する。外部配信監視は設定頻度・対象数・枠待ち・タイムアウト込みの次回予定を基準にする（全対象共通の30秒判定はしない）。無コメント・長時間推論・低ビットレートをハートビート停止と同一視しない。子プロセスは生存・進捗・制御応答を別々に診断する。DB／保存先が確認できない場合は最終値の時刻とunknownを示し、新規の破壊的操作を拒否する。健康状態はキャッシュされた実測を集約し、Webポーリングによる外部API・GPU推論・全ディスク走査を行わない。

`GET /api/v1/health` は instance_id、取得時点、Web生存、必須基盤ready、録画稼働の三値（true/false/null）、機能別状態を返す。DB接続不能・停止中・必須基盤未準備は503、任意の字幕・外部サービス等の劣化だけではWebを503にしない。`/api/v1/system` は詳細・鮮度・影響・診断リンクを返し、取得不能項目を個別表示する。健康状態は外部の配信有無や全件取得を保証しない。

録画エンジンはサービス＋エンジンの組で、実行ファイル／SDKの版と解決元、利用可否（未検証／可／不可）、最終確認・最終取得成功・最終試行失敗日時、直近失敗理由、累積試行失敗数・連続失敗数・再試行数を永続化する。利用可否の検査と実配信成功を区別し、正常取得後も過去の失敗日時を消さず連続失敗数だけリセットする。試行IDで重複計数を防ぎ、アクセス拒否・利用者停止・正常終了をエンジン障害に混ぜない。最後の成功は有意な本編取得・媒体検証を根拠とし、実績がない候補は未検証と表示する。

#### 14.5.1 診断更新契機・鮮度・負荷

診断は取得時点と期待次回時点、取得不能理由を伴う保存済みスナップショットとし、Webの表示周期と独立する。管理ハートビート10秒／鮮度30・60秒は既定どおり。録画・コメント・字幕・エンジンは状態遷移／試行確定時、GPU・モデルは起動時／設定変更時／推論異常時、実行ツール版は起動時／解決元変更時、空き容量は起動時／新規録画判断前／定期保守（内部既定60秒）、管理ファイル容量は確定・削除時および照合完了時に更新する。定期保守で既知ルートの存在・空き容量のみを確認し全面走査しない。GPU／版診断は有限タイムアウトと重複抑止を持ち、モデルロード・推論を診断目的で実行しない。障害集計はDBイベント確定時の更新または有限の集計キャッシュを使用する。診断の遅延・失敗で最終正常値を現在正常と表示しない。録画等の負荷を優先し、診断は延期可能、延期理由と次回予定を示す。負荷試験で走査バッチ、診断タイムアウト等の内部値を決め、未検証値を設定に追加しない。

### 14.6 共通診断と開発支援

- 両モードで `diagnose --json` を提供する。既存のヘルス・構造化ログ・DB診断・実行状態を再利用し、インスタンスID、モード、データ環境、コード版／起動時刻、設定の非秘密実効値と由来、監視・再試行・録画PID／進捗、コメント・音声・ASSのキュー／接続／ジョブ状態、SQLite・保存先の状態を取得可能な範囲で機械可読化する。通常運用の診断は読み取り専用で、取得時点・未確認・範囲不足を明示し、外部API呼出・全面走査・ジョブ開始を発生させない。有限の時間・件数・サイズ、安定したエラーコードと終了コードを設ける。 JSONの最低契約は下記とする。
- `diagnose --json` はUTF-8の単一JSONオブジェクトのみをstdoutへ出力し、人向けログはstderrへ分離する。`schema_version`（整数、初期1）、`instance_id`、`mode`（`normal`／`developer`）、`data_environment`（`live`／`isolated`）、`code_revision`（稼働コードの識別子、未確認はnull）、`started_at`、`observed_at`（UTC ISO 8601、未確認の起動時刻はnull）、`status`、`components`（オブジェクト）、`warnings`／`errors`（安定コードと秘匿済み説明の配列）を必須キーとする。取得できない識別情報はnullとし、要求対象を観測済み事実として偽装しない。`status` と終了コードは `ok`=0、`partial`=1、`unavailable`=2、`target_mismatch`=3。引数構文エラーは通常CLIの扱いで診断結果と区別する。各componentは取得時点・状態・未取得理由を示す。追加項目は後方互換、非互換変更はschema_versionを更新する。コード識別子は起動時の実行ソース内容（未コミット変更を含む）から確定し、診断時の作業ツリーで置き換えない。検証前に期待する修正版の識別子と照合し、不明／不一致なら再起動または未検証扱いとする。
- `diagnose` は停止中もDB作成、Alembic移行、DDL、設定・保護パス・外部予算の初期化／更新を誘発しない。互換性不明・DB未作成・確認不能は取得不能または部分取得とする。
- 開発者モードではDEBUGログ、秘匿済みスタック／処理相関・非同期タスク待機状態、API入出力の安全な要約を必要に応じ取得する。診断バンドル（例：`diagnose --bundle DEST`）は秘匿済みの有界なローカル出力とし、コメント／発話原文、Cookie、署名URL、認証ヘッダー等を含めない。DB詳細調査はローカルの読み取り専用接続または明示した一貫性スナップショットを使う。任意SQLのHTTP提供は行わない。ログ保持と秘匿は§14.3を維持する。
- 隔離データの開発者モードでは、固定時刻・モック配信／コメント・ローカルHLS・テスト用アダプターを再利用し、開始／終了／再接続、403／429／500・タイムアウト、録画／FFmpeg異常、DBロック／失敗、保存容量／権限異常、キュー滞留・GPU不可、Web遅延／逆順応答を決定的に再現する。シナリオの実行・隔離初期化はCLIまたはテストハーネスで提供し、製品に任意障害注入APIを増設しない。実環境を傷つけるために実ディスクを埋めたり、実サービスへ故意に負荷をかけたりしない。
- ブラウザ操作、DOM／スクリーンショット、Console／Network、アクセシビリティはUI正本§14.4〜14.5に従い既存検証ツールを使用する。ホットリロード・プロファイリングは隔離環境での任意の開発手段とし、別の製品機能・常駐プロセスを要求しない。診断・fixture・実証の証跡を分離し、修正後は通常運用相当のセキュリティでも回帰試験を実施する。

### 15.2.1 起動モードとデータ境界

`live-rec-lab start` は通常運用、`live-rec-lab start --dev` は隔離専用の開発者モードとする。第三のモードおよび実運用データ指定の開発者起動は実装しない。

隔離データは実運用と異なる専用ルート、別の設定と固定ポートを使用する。具体的な既定値と設定解決は以下に従う。起動前に実効パスを正規化し、DB／保存先／状態／設定／ログの同一・親子・別名・シンボリックリンク等による重複、既知の別インスタンスとの衝突、ポート競合を拒否する。隔離境界・DB／設定／runtime／ログの所有・排他またはポート確保を確認できない場合は起動拒否する。通常運用の媒体保存先だけの異常は次項の区別に従う。自動的なポート変更や実運用へのフォールバックは禁止。通常と隔離の併用は完全分離と独立した排他確認を満たす場合に限る。

**起動拒否と機能保留の区別**：実運用と隔離の境界侵害・確認不能、管理領域（DB・設定・runtime・ログ）の衝突／所有不明、固定ポート競合は起動拒否。通常運用で境界自体は確認済みだがWindows録画ドライブ未接続・権限／容量不足・媒体ルート衝突または比較未確認の場合は録画・媒体書込／削除／復旧だけを保留し、安全な監視・コメント・Webを継続する。代替保存しない。未接続の保護パスは解除しない。

**モード別設定解決と隔離境界（§10.2、§11.8.1〜3の明示例外）**

- 全CLI・app factory・テスト入口は設定／`.env`／DBの読込前にモードを決定する。通常運用は既存解決規則、隔離は専用設定コンテキストだけを使う。スナップショット取込は§13.7の明示的保守操作に限る。
- 隔離の既定はデータ `~/.local/share/live-rec-lab-dev/data`（SQLite・モデル）、状態 `~/.local/state/live-rec-lab-dev`（ログ・runtime）、録画 `~/.local/share/live-rec-lab-dev/recordings`、固定ポート8083。ホーム展開後の絶対パスで扱う。隔離データ／状態の専用基底は明示的な隔離設定でのみ変更可。`DEV_LIVE_REC_LAB_DATA_DIR` を変更する場合も専用基底直下の `data` とし、その親ディレクトリを隔離用データ基底、兄弟の `recordings` を録画専用領域兼録画既定値とする。録画ルートはこの録画専用領域以下に限定し、DB・モデル等の管理領域と分離する。隔離DBの保存値 > 専用環境の初期値 > 隔離既定値（ポートは隔離DB保存値 > 隔離既定値）。設定値の型、版、反映時期、媒体の命名・確定は共通契約を維持する。
- 複数worktreeでは専用基底・状態・固定ポートを割り当てる。空の隔離DBからも `config set web_port PORT --dev` で隔離設定を初期化できる。通常DBやジョブには接続しない。外部通信排他は共通とする。
- 隔離のアプリ設定・秘密は `DEV_` を先頭に付けた§11.8.3のキー（例：`DEV_LIVE_REC_LAB_DATA_DIR`、`DEV_SIGN_API_KEY`）を専用プロセス環境 > リポジトリルートの `.env.dev` > 隔離既定値の順で読む。通常の同名キー、通常 `.env`、通常DBにフォールバックしない。PATH等の非秘密OS環境は必要最小限のみ利用し、子プロセスにも通常のアプリ設定・秘密を継承させない。隔離の実接続は利用者が対象・資格情報を承認したうえで起動時に `--allow-live` を明示した場合だけ許可する。指定がない限り隔離資格情報が存在しても外部配信・署名通信を行わない。このフラグは隔離開発者起動専用とし、永続化しない。実運用の保護対象を照合するための非秘密パス情報だけは、運用者が確認した実効／過去の管理ルート一覧等の境界確認情報として取得する（通常設定の継承ではない）。確認不能なら拒否する。
- 隔離境界は全操作の不変条件。共通検証器で設定・DB／ログ／媒体操作・バックアップ・fixture・子起動の対象を照合する。隔離の書込先は専用Linux領域に限り、通常／他インスタンスの保護パス・別名・親子・リンクによる逸脱を拒否する。ファイル操作直前に実体・所有・世代を確認し、保証できなければ保留する。

- **保護パスと排他**：専用領域を構造的に分離し、利用者が既存アプリの管理領域・現在の実効録画先・保護が必要な旧ルートを非秘密の保護パス設定に記載する。設定は `~/.local/state/live-rec-lab-shared/` の所有者限定領域に置く。初回は既存環境の有無を確認し、未確認の領域を安全扱いしない。共通の短い設定変更ロック下で現行・変更先・稼働インスタンスと衝突検査し、不明・設定破損は該当操作を拒否する。変更途中は旧・新を保護し、必要な旧パスを明示保持する。独立した境界台帳・予約履歴・専用登録／復旧システムは不要。固定共通領域を削除・初期化・バックアップ先から除外する。インスタンス排他・固定ポート・実体照合は維持する。

**手動DB復元の安全契約（§13.6）**

- 利用者の明示指示で通常運用を停止し、同じインスタンス排他を取得する。現行DBをSQLite Online Backupで退避し、候補の `PRAGMA integrity_check`・スキーマ・管理ルートを確認する。DB外の簡単な復元未完了マーカーを作成してから利用者がDBを手動交換する。WAL/SHMを混在させず、外部予算状態を交換しない。
- 排他を保持して、現行の保持期限・削除済み記録・媒体世代・停止指示・ジョブ試行予算と復元DBを照合する。古いDBだけで削除・再送・外部枠初期化・字幕再生成を行わない。コメント／派生字幕の復活防止に必要な処理は対象を確認したうえで既存業務処理を使用する。照合できない対象は保留し、退避DBへ差し戻すこともできる。
- マーカーがある間は通常起動・自動処理・一般変更を拒否し、停止中の読み取り診断は可能とする。安全確認完了後にのみマーカーを解除する。中断時も残し、再入場では排他・対象を確認する。自動復元機能・復元世代台帳は不要。監視停止環境変数だけで代替しない。採用した保守手順をマニュアルに記載する。

初期は上記を満たす短い停止中保守手順と既存業務処理の再利用でよい。専用復元UIや全面自動照合機構は不要。複雑な競合はマーカーを維持したまま手動確認または安全な退避DBへの差戻しを選び、照合不能な状態で通常起動しない。復元の代表試験は復元機能利用前に行い、他の機能の実装を止めない。

**外部通信排他と永続予算**

**通信許可の適用範囲**：通常運用は、利用者が設定・有効化した登録済み対象（必要な資格情報・利用条件・採用経路の確認を含む）について、共通排他・永続予算の範囲で自動監視・録画・コメント取得・通常再試行を行う。配信ごと／リクエストごとの追加承認は不要。開発者モード・実接続試験は別の許可であり、通常設定から継承しない。対象・目的・期間または終了条件・資格情報・予算範囲をまとめて明示許可でき、その範囲内の通常再試行に個別承認は不要。範囲拡大・期限切れ・利用条件違反・枠不足は停止／再確認する。ローカル自動試験は外部通信禁止。開発依存取得・公開資料閲覧・正当な静的資産取得は開発開始指示で委任済み（モデル取得は§7.9の別条件）。

- 初期版は同一WSL利用環境で実配信／署名通信を許すインスタンスまたは試験を1つに限定する。固定共通位置のロックを接続前から子回収まで保持。隔離の実接続は `--allow-live` と許可済み対象・専用資格情報が必要。既存の別アプリによる共有枠利用が不明なら接続を保留する。オフライン隔離は通常運用と併用できる。
- サービス別の監視頻度・コメント優先・無料枠・同時接続上限・429待機を共通レートリミッターで守る。外部予算はアプリDBと独立した小規模なSQLiteまたは原子的状態ファイルに、共有単位・制限窓・消費済み／不明・待機期限を保存する。通信前に安全側に計上し、不明な消費は確実な残枠または制限窓の終了まで戻さない。再起動・インスタンス切替・DB復元で予算をリセットしない。提供者の信頼できる残枠情報を利用可。高度な多段階予約・回復台帳は不要。DM-21のジョブ再試行予算は別に維持する。

`status`、`url`、`stop`、`backup`、`config`、`diagnose` は通常対象または `--dev` の隔離対象を選択する。対象・実効ルート・モードを確認し、他方を操作しない。Windows自動起動は常に通常運用。

### 15.3 WSL2固有の注意点

以下を考慮してください。

- WSL2のNAT / mirroredネットワークモード
- WSL2とWindows間のlocalhostアクセス
- Windows画面ロック・画面OFF中の継続動作
- スリープ・休止・シャットダウンによる監視の中断
- systemdサービスとWSL2インスタンスのライフサイクルの違い
- タスクスケジューラ等を利用したサインイン後の起動
- Linuxファイル権限とWindows側録画ドライブのNTFSアクセス権限・ファイル名制約
- WSL2側DB・ログとWindows側録画ファイルの容量増加、双方の実ディスク空き容量の確認
- 起動・停止・再起動時のログ

Windowsホスト側に操作が必要な場合は、理由と実行コマンドを明示してください。Docker Composeは初期必須ではありません。

## 16. パフォーマンス要件

音声推論とASS処理は録画・コメント・Web応答を阻害しないことを実測する。モデル取得・一時音声・GPU/CPU・ディスクI/Oの負荷を診断し、適格対象の開始を抑制できるようにする。

### 16.1 基本方針

Windows 11＋WSL2での継続運用を前提とし、CPU・メモリ使用量を抑えてください。

- 動画の再エンコードを避ける
- 監視は非同期処理
- DB書き込みは短いトランザクションと少量バッチを基本とし、同期I/Oでイベントループを塞がない
- コメントは必要に応じてバッチ保存
- 不必要なポーリングを避ける
- 大量コメントによるメモリ増大を防止

### 16.2 並列録画

複数配信の録画に対応してください。

同時録画数の上限を設定できるようにしてください。

デフォルト上限・範囲・反映時期は§11.8.1に従う。実測によって設定値を調整可能にする。

録画対象が増えた場合は、同時接続数、ネットワーク帯域、Windows側保存先（DrvFS）の書き込み性能を実測してください。コード・SQLiteは性能のためWSL2内を維持します。

### 16.3 データベース

コメントが大量に蓄積されることを想定してください。

- 適切なインデックス
- ページネーション
- バッチINSERT
- 長時間トランザクションの抑制
- WALモードとbusy_timeoutの調整
- 定期メンテナンス方法とOnline Backup APIを使う手動バックアップの文書化

## 17. テスト要件

pytestを使用してください。以下の **`TC-001` 形式の固定ID**は要求テスト項目の識別子です。`TC` は単体・統合・障害テストを横断して一意とし、追加するときは既存IDを振り直さず末尾に新しいIDを割り当てます。最終受け入れ基準（§23）の **`AC-001` 形式の固定ID**を少なくとも1つの `TC`／実機検証へ対応付け、未検証・未実装を空欄にせず明示してください。

**検証優先度（固定IDは維持）**：以下の分類は検証時期を表し、機能削除や安全要件の免除ではない。

- A：初期必須。該当機能の利用開始前に代表正常系・重要な否定系を確認する。実機が必要な条件は実測まで未検証として該当機能を保留する。
- B：実用安定化。通常障害・復旧・詳細操作／統計などを段階的に検証する。Bのうちデータ保全・秘密・外部制限・危険操作に関わる条件はA相当として利用開始前に確認する。
- C：追加品質。詳細UI復元・詳細集計・診断最適化・稀な競合・未使用環境・長時間負荷等。必要に応じて追加する。Cの固定IDでも基本機能の正確さ・安全性に関わる代表条件はAとして先に確認し、追加の詳細条件だけを延期する。

1 TC＝1専用pytestは不要。代表的な統合テスト、実機試験、手動ブラウザ操作、簡易開発チェックで複数IDを確認してよい。全組合せの直積は不要。部分実施は確認範囲と未検証部分を記録する。ACの意味を変更せず、Cのみ未検証であることは安全な機能の利用開始を阻害しない。

**初回の代表検証範囲**：Aはコア経路と重大事故防止に絞る（40 ID）。複合TCのAは基本正常系・重要な否定系に限り、詳細条件・多重故障・反復競合・網羅的組合せはB/Cとして分割記録してよい。B/Cの安全上の条件は、以下の代表確認を含め、該当機能の利用開始前に必ず確認する。分類は個別の安全条件を上書きしない。未検証の危険操作は無効のままにし、L2実装や独立機能を止めない。

| 利用対象 | 利用開始前に確認する代表条件（複数IDの統合検証可） |
| --- | --- |
| 起動・停止・隔離 | 排他・固定ポート・正常停止・他プロセス非干渉、実運用と隔離の非継承・保護パス、通常ルート非公開（TC-052、070、108、110、111） |
| 検知・録画・コメント | 両サービスの基本経路、UNKNOWN区別、独立動作、手動停止優先、Room/配信ID一致、重複排除、有限再試行・再起動時の停止／予算保持、制限時停止、許可先のみ・秘密保護（TC-004〜007、018、023〜028、033、041、052、065、071〜074、079〜080、092、097、101〜102、104、106）。プリロールでは本編を誤破棄しない代表例（TC-020、067） |

上表は新たなテストIDや全体ゲートではない。基本動作の実装時に関連する代表試験だけを追加し、詳細な条件は必要性・使用頻度に応じて追試する。TC-068／069／109は優先度Bの簡易開発チェックとして扱うが、Feature誤上書き防止と利用者のUI選択は該当操作の前提のまま維持する。

**テスト実行方針（開発基盤）**：pytest-xdistを開発依存に採用し、独立した単体・統合・障害・ブラウザ自動試験は原則として並列実行する。固定ポート、実GPU、実配信・共有API予算、実機等の分離できない資源を占有する試験に限り `serial` マーカーを付与し、理由をテストコードに記録する。`serial` は排他要否のみを表し、実接続・実機の許可とは独立する。標準のローカル自動試験は次の2段階を順次実行し、同時実行しない。

```bash
uv run --locked pytest -n auto -m "not serial and not live and not hardware"
uv run --locked pytest -n 0 -m "serial and not live and not hardware"
```

音声実装段階では `uv sync --locked --extra speech` 後、上記 `uv run --locked` に `--extra speech` を加えて関連試験を実行する。音声未導入段階で必要な音声試験は明示的に未検証とする。

実行環境のCPU・メモリ・I/O・子プロセス負荷に応じて `-n N` または `PYTEST_XDIST_AUTO_NUM_WORKERS` で調整する。少数の対象テストの反復・デバッグは直列でよい。並列失敗を隠す全体直列化はしない。コマンド、選択件数、結果、重要な未検証を記録する。0件は収集結果で確認し、想定外なら失敗とする。

**最小の隔離と段階的な検証基盤**：初期に一時DB・専用保存先・worker別runtime／ポート・模擬外部API・資格情報非継承を整備する。通常データ・外部通信は既定拒否とし、ローカルHLS等の許可済みloopbackのみを通す。製品の保護パス／外部予算状態をローカルテストから読み書きしない。一時設定・依存注入・ネットワーク遮断等を利用する。各機能の実装に合わせて必要なfixtureと否定試験を追加し、テスト基盤の全体完成を後続実装の条件にしない。

`live`／`hardware` は実配信／外部APIと専用実機（実GPU・Windows等）を区別する。`--run-live`／`--run-hardware` がない場合はskip。対象・必要資源・利用者許可を実行前に確認し、両方必要なら両方指定する。マーカーやフラグだけで実接続を許さず、fixture／アダプター・HTTP・子起動の実効境界で既定拒否する。実接続は§15.2.1の共通ロックと実予算を使用し、実運用DB・録画先には触れない。モデル自動取得も禁止する。

子プロセスはテスト専用のプロセスグループ・所有識別と有限タイムアウトで回収し、異常終了時も所有が確認できる子だけを停止する。回収不能は失敗／保留とする。TC-111は各機能の境界と代表的否定試験を確認する。ローカル模擬、実配信、実機を区別し、skipを合格にしない。

## 19. 開発手順

最小隔離・一時SQLite・ログ・保存先の直後にTikTok CLIによる検知→録画→コメント→SQLite→コメントSRTの垂直スライスを実装する。共通設定全項目・詳細診断・削除台帳・完全な復旧基盤の完成は着手条件にしない（未整備の危険操作は無効）。初期計画直後に架空データのUI比較3案を提示する。ツイキャス・Web/API・共通基盤の拡充・音声extraは独立して進める。空の隔離DBからの登録・起動・停止・保存確認経路を用意する。実配信・音声字幕の実証は機能単位で行い、未実証でもUI・他サービス・後処理の独立実装を進める。UIは `prompts/redesign-ui.md` §15に従い、初期実装・単独再設計ともに3案を提示し、利用者が採用案を明示選択する。選択前は採用案に依存する製品UI実装だけを保留し、実証待ちと相互に依存させず、独立作業を継続する。

実行手順は `prompts/implement.md`。安全性に関するHard Gate、品質上のSoft Gate、機能別Release Criteriaを区別する。安全に影響しない未検証・品質不足は記録して独立作業を続ける。

採用Skill固有の承認・成果物の契約は守るが、プロジェクト独自の重複承認を追加しない。Checklistは簡潔、Analyzeは原則1回、Convergeは重要な残課題がある場合だけ。承認が必要な操作のみ保留し、実行環境が質問でターンを終了する場合は同一Featureに現在地を残して再開する。正本は必要な節を段階参照し、派生文書に全文転記しない（implement.md §1〜2）。

外部連携は利用条件に適合する有望な第一候補から実装する。採用経路の必須確認は残すが、全候補の同時実装・実証は求めない。進展のない調査・修正の反復は打ち切り、試行内容・原因・残課題を記録して独立作業へ移る。安全な利用条件が満たされない機能は無効のままとし、統合時に重要な残課題を再評価する。

## 25. 利用シナリオ・機能要求索引・成功基準

本節は固定要件への導線と利用シナリオを定義する。FRは固定製品要件索引であり、生成Featureでは原本FRへの対応を明示する。上位の具体的な確定条件と矛盾する場合は本文の該当節を正とし、統合時の簡易照合で不整合を解消する。R=本書、D=統合設計、U=UI仕様、C=AGENTS.mdの開発原則。

### 25.1 利用シナリオと独立検証

#### US1 配信を検知し、録画とコメントを個別に記録する（P1）

利用者は公開または許諾済みのTikTok LIVE／ツイキャス配信者を複数登録する。各サービス内の共有監視枠で配信を検知し、録画とコメント収集を個別に設定・運用する。ローカルHLSと模擬配信／コメントを用いて、配信開始からセッション・ジョブ・保持動画・コメント・SRTの相互参照までCLIで独立検証できる。

1. 配信IDを伴うLIVEを検知すると、同一セッションで許可されたジョブを最大1件ずつ起動する。
2. 一方の障害、設定OFF、通信断はもう一方の動作から分けて記録する。手動停止は同じ配信の自動録画に優先する。
3. 状態不明中は稼働ジョブを維持する。明示終了の猶予中にLIVEへ戻れば同じ配信を続ける。両ジョブが止まったままなら再確認期限の後に終了未確認を記録する。

#### US2 取得した記録を探し、保存・削除の結果を確認する（P1）

利用者は配信セッション単位で動画・コメント・欠損を探す。有効な動画とDBの原文から暫定／確定のSRTを生成し、必要に応じ再生成する。時刻と故障を制御できるローカルデータで独立検証できる。

1. 複数ジョブでも保持セグメントの連番を継続し、過去の欠損や無効ファイルを新しい成功で隠さない。
2. 部分取得でも動画とコメントを保全する。0件の字幕対象、収集未実施、同期待ち、同期不能を区別する。
3. 安全に停止・確定した配信だけ削除できる。ファイルだけを削除するか、続けて履歴も消すかを確認する。コメントの期限削除と再登録時の履歴保全を独立して確認できる。

#### US3 運用画面で設定、記録、障害を調べる（P2）

利用者はローカルのブラウザから指定順の8画面を使う。記録の有無と取得状態をそれぞれ確認し、関連記録と診断・ログの間を移動する。記録済みのデータとブラウザを使い、URL、画面操作、幅、状態表示、ログ再マスキングを独立検証できる。

1. 監視や表示・保持条件の変更は保存結果を確認でき、必要な設定の反映時期を示す。
2. システム状態から記録のある相関条件でログを開き、検索位置を保って関連セッションを往復できる。
3. 未取得、エラー、古い情報、正常な空、検索結果0件、期限削除を区別し、表示時刻と操作結果を確認できる。

#### US4 WSL2 上で起動し、停止や障害から復旧する（P2）

利用者は一般ユーザーで起動し、固定ポート（要求仕様§2.2）・生存確認付きURL、手動バックアップ、状態確認と安全停止を使う。分離した検証用環境で再起動と競合を再現し、Windows固有の動作は実機で確認する。

1. 起動前に他の録画アプリケーションとは異なる実効録画ルートを確認する。マウント・権限・容量・重複に問題があれば録画を抑止する。
2. 確定・削除・SRT公開の途中停止から復旧する。管理対象の取得済みデータと他の録画アプリケーションのデータを守る。
3. バックアップ作成時に保持期限の範囲を説明し、手動復元後は再評価してから通常運用へ復帰する。

#### US5 録画後に音声字幕と統合ASSを利用する（P1）

確定動画のローカル認識を自動投入し、別の録画・コメントを継続しながら、音声字幕・統合ASSの状態と発話を管理できる。既知音声付き動画と模擬コメントを使い、推論・同期・再生成・削除・復旧を独立検証する。

1. 音声字幕画面で待機・処理・完了・無発話・対象外・失敗を確認し、個別再生成／失敗一括再試行を行う。
2. 対応するコメントSRT・音声SRT・ASSをWindows保存先で使い、Webでは発話本文検索と状態確認のみ行う。
3. GPU不可・推論異常・停止・入力版競合でも取得済み動画／コメント／旧正常字幕を保全する。コメント期限削除では統合ASSのコメントも消える。

#### 境界事例

- HTTP拒否、制限、空本文、不明な配信状態、終了猶予中の復帰、配信IDなし。
- 外部アダプターの一方だけ利用不可、コメント元IDなし、匿名番号が曖昧。
- Windowsの同名、親子ルート、予約名、ケース／Unicode差、管理外ファイル、マウント消失。
- 空試行、無映像、リマックス失敗、確定直前／直後の強制終了、後着コメント、古いバックアップ。
- 未確定のセッションへの削除要求、部分削除の再試行、期限削除中のコメント保存／SRT生成、旧ログの秘密情報。
