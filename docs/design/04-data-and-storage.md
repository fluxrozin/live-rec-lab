# 04. データベース・ファイル保存設計

> 出典：[`requirements.md`](../../requirements.md) §9–10、§15。**設計ドラフト。以下はDDL確定版ではない。**

## 1. 永続化アーキテクチャ

SQLite 3（SQLAlchemy 2.x / Alembic）を**WSL2内のLinux ext4**に置き、WAL、`busy_timeout`、`foreign_keys=ON`、短いトランザクション、適切なインデックスを用いる。動画・対応SRTはWindowsローカルドライブに保存。NAS／DrvFS上にSQLiteの正本を置かない。

| 情報 | 既定の保存先例 | 主な用途 |
| --- | --- | --- |
| SQLite | `~/.local/share/live-rec-lab/data` | 設定・配信者・セッション・ジョブ・コメント |
| ログ | `~/.local/state/live-rec-lab/logs` | 障害調査と詳細ログ |
| 起動状態 | `~/.local/state/live-rec-lab/runtime/endpoint.json` | 自動ポート、PID、インスタンス識別 |
| 動画・SRT | `/mnt/d/live-rec-lab/recordings/` | Windows側の録画保管（ドライブ可変） |

別worktreeからの同時試験実行時は**DB、ログ、endpoint.jsonに加え、Windows側の録画動画・SRT保存ルートもインスタンス別に分離**して競合・上書きを避ける。DB永続設定を反映した実効録画ルートと、運用者が確認した既存LiveRecorder／別インスタンスの実効ルートをWindows実体パスで照合し、同一・親子衝突なら録画開始を拒否する。自動取得できない既存アプリの設定は導入時に手動照合する。SQLiteバックアップにはOnline Backup API等を使い、稼働中DBファイルだけを直接コピーしない。

## 2. 初期エンティティ候補

| テーブル | 責務 | 主要関連 |
| --- | --- | --- |
| `streamers` | サービス別監視アカウント、3種ON/OFF、最終監視 | `(platform, platform_user_id)`一意 |
| `stream_sessions` | 1回の配信、配信ID、期間、状態、`next_segment_number`、期限削除状態、衝突識別子 | `streamer_id` |
| `recording_jobs` | 録画実行単位、エンジン、停止指示、再試行 | `stream_session_id` |
| `recording_segments` | 分割動画、物理ファイル、検証状態、同期、SRT | `recording_job_id`＋`stream_session_id`（親整合検証） |
| `comment_collection_jobs` | コメント収集実行、再接続、件数、失敗 | `stream_session_id` |
| `comments` | 元コメント、識別・時刻・ソース | `stream_session_id` |
| `collection_gaps` | 録画／コメント取得の欠損期間と理由 | `stream_session_id` |
| `system_settings` | 監視頻度などの通常設定 | `key` |
| `runtime_instances` | 起動インスタンスの生存管理（必要なら） | `instance_id` |
| `system_events` | 検索可能な警告・障害イベントの要約 | 関連セッション等 |
| `deletion_operations` | 削除開始前の台帳、対象・方式・進捗・失敗・再開 | 削除後にも残る対象ID |

重要制約：`streamers`のサービス＋正規化IDは一意。`archived_at` 設定済み配信者の同じキーによる再登録は既存行を復活させ、過去履歴を保持し、3種のON/OFFは新しい登録操作の明示値で再設定する。配信ID取得時は同一配信の二重セッション生成を防止。コメントID取得時は同セッション内 `(stream_session_id, platform_comment_id)` を一意化する。セッション削除時のDB関連レコードとWindowsファイルの扱いは詳細設計で確定する。秘匿情報を `system_settings` に通常文字列として不用意に入れない。

**録画セグメントの整合性**：`recording_segments` に `stream_session_id` を保持し、`recording_jobs` の `(id, stream_session_id)` への複合外部キー（親側複合一意キー付き）で親ジョブとセッションの一致を保証する。**`UNIQUE(stream_session_id, segment_number)`** により全録画ジョブ横断の保持番号を一意にする（未採番行はNULL）。未確定レコードは仮ID／一時パスで追跡し、空試行は番号を消費しない。実データの保持判断後、同一SQLite書込トランザクションで `stream_sessions.next_segment_number` を排他的に進めて番号・正式パスを予約する。予約後のクラッシュ・削除・確定失敗でも番号を再利用しない。renameは同一Windowsボリューム内で上書き禁止とし、再起動時は予約・一時ファイル・正式ファイル・DBを照合する。保持した `invalid`／`pending` や過去の番号を隠さず、詳細DDLと復旧状態はfeatureの `data-model.md`／migrationに落とす。

**実体との照合**：DBの `valid`、`duration_ms`、ファイル名は単独では実ファイルの存在・再生可能性を保証しない。動画の最終実体の映像・音声ストリーム、コーデック、長さ、サイズ、検証日時と状態、古いエラー／欠損の記録を対応づける。既存DB上の誤判定を無検証で一括書換えしない。

## 3. 動画とSRTのフォルダ設計

```text
D:\live-rec-lab\recordings\
└── streamer01\
    └── 2026-11-23\
        ├── tiktok_streamer01_20261123_210000_s001.mp4
        ├── tiktok_streamer01_20261123_210000_s001.srt
        ├── tiktok_streamer01_20261123_210000_s002.mp4
        ├── tiktok_streamer01_20261123_210000_s002.srt
        ├── twitcasting_streamer01_20261123_220000_s001.mp4
        └── twitcasting_streamer01_20261123_220000_s001.srt
```

- 第一階層は原則**正規化済み配信者IDのみ**（異なるサービスでも正規化済みIDが同じなら同一フォルダ）。Windows上で危険／表現不能な文字列や異なるID同士の安全名衝突があるときのみ、元の正規化済みID由来の短い識別子を付加する。**ID→実ディレクトリ名の対応はプラットフォーム非依存の永続マッピングで固定**し、後から衝突が見つかっても既存ディレクトリは改名しない。管理外ディレクトリを自動的に所有物と見なさない。**DB上でアカウントは統合しない**。
- 第二階層は配信開始日の `YYYY-MM-DD`（設定タイムゾーン）。配信開始時刻が無いときは検知日。同一配信のセグメントは同じ日付フォルダに置き、日をまたいでも分けない。第三階層に動画と対応SRTを保存。
- ファイル名はプラットフォーム、配信者ID、配信開始日時、セグメント番号を含む。同一配信では日時を共有し、**全ジョブを通じた保持セグメントの番号**だけを進める。空の破棄試行を `sNNN` の採番対象としない。各ファイルの録画開始時刻はファイル名に使わない。別サービス・別配信の同名上書きを防ぐ。最初の正式名の衝突時のみセッションID由来の安全な短い識別子を番号の直前へ追加し、同一セッション内で永続固定する（追加衝突なら延長して初回予約、途中衝突は保留・照合）。排他的なファイル確定とWindows大文字小文字の同名判定を使う。表示名の変更でディレクトリを改名しない。すでに保存したファイルは改名しない。
- Windows禁止文字／予約名／大文字小文字・Unicode正規化／末尾空白・ピリオド／パストラバーサルと管理外ディレクトリへの衝突を `storage.py` で集中処理する。正規化済みIDの一意なマッピングとWindowsディレクトリ名の一意制約・既存ファイルとの照合は `storage.py` と `specs/001-initial-live-recorder/data-model.md` に具体化されている。ファイル名の `filename_disambiguator`（セッション単位）とは別の機構とする。各コンポーネントで独自にパスを結合しない。

## 4. セグメントの安全な確定処理

```text
recording_segmentsに未確定レコードを先行作成（空試行の採番は保留）
    ↓
Windows録画先と同一ボリューム上の一意な一時ファイルに記録
    ↓
有意な保持対象と空の破棄試行を分け、後者は採番しない
    ↓
必要ならリマックスし、保持する最終形式をffprobe等で検証
    ↓
映像・音声・コーデック・長さ・サイズ・実在を確認
    ↓
同一セッションの保持番号と衝突時の固定識別子をDBで予約し、上書き禁止で同一ボリューム内の正式名へ確定
    ↓
SQLite上で最終ファイル・検証結果・実メディア長を確定
    ↓
対象コメントがあれば対応SRT生成、0件ならスキップ（収集未確定なら暫定）；入力版数と生成時版数を照合して再同期
```

ファイルシステムのrenameとSQLiteコミットは完全には原子的にならない。強制終了後は一時ファイル・正式ファイル・DB状態を**双方向で照合**し、異常 `pending`、手動停止でない取消で残った一時ファイル、DBが `valid` でも0バイト／不在の正式ファイルを検出する。未登録ファイルを即削除しない。WSL2 ext4からNTFSへのクロスデバイスrenameに依存しない。**未確定レコードを先に作ること**と**空試行に番号を消費させないこと**の両立は、仮ID／仮パス等を使う詳細設計で実現する。

## 5. 容量・整合性・削除

- 起動時／監視時に録画先のマウント状態、書き込み権限、空き容量を確認。利用できない場合に勝手にWSL2内へ保存しない。
- 保存容量上限、最低空き容量、録画件数・配信者別容量を管理。**自動削除は初期OFF**。有効化時は確定済みの古い動画＋対応SRTの「ファイルのみ削除」に限定し、DBのコメント・履歴・欠損は保持。容量不足時は未確定データを消さず新規録画を抑止して警告。
- コメント保存期限は初期`0`（無期限）、正整数なら収束済み・収集／キュー書込完了・復旧照合済みセッションを`ended_at`起算で判定する。期限削除は動画を残し、削除操作開始後のコメント書込・SRT生成を排他停止してから、派生SRTの削除を照合してSQLiteコメントを削除、`comments_purged_at`・`purged_comment_count`と`deletion_operations`の内部モードに記録する。途中失敗は冪等に再開し、未収集／0件と区別して表示する。期限削除済みSRTは再生成不可。**手動SQLiteバックアップは削除対象外**であり、利用者が旧バックアップを安全に破棄・更新する。初期版に自動復元は設けず、手動復元後は保持期限・派生SRTの再照合なしに再開しない。
- 手動削除は「ファイルのみ」または「ファイル＋履歴」の2種。履歴のみ削除は提供しない。ファイルのみは意図的削除の時刻とメタデータを維持（`validation_status` と別に記録）。両方の場合は動画／SRT削除完了後にセッション配下のジョブ・コメント・欠損を参照整合性を保って削除する。`deletion_operations` に削除前から対象・方式・進捗を記録し、履歴削除後も操作台帳を保持する。配信者削除は履歴ありなら `archived_at` による論理削除とする。
- 進行中・未確定・照合中のセッションは削除不可。削除処理の未完了・一部失敗を永続化し、再起動時に再照合。許可済みルート外／シンボリックリンクをたどらず、一部成功を完了として扱わない。
- DB登録済みファイルの不在、0バイト、最終ファイルのサイズ・長さ・メディア検証の不一致、無効／未確定、一時ファイル、孤立ファイルを判別する。異常の回復・再検証は変更履歴付きで行い、過去の取得欠損を後続ジョブの成功によって削除しない。
- WSL2 `ext4.vhdx` のホスト側容量増加にも注意する。安全条件が明確でない自動修復・削除を行わない。

## 6. 詳細設計で確定する事項

型・NOT NULL・補助インデックス・ON DELETE方針の詳細、保存期間ポリシー、削除処理の再開状態、トランザクション境界、ファイル復旧状態の詳細は `specs/001-initial-live-recorder/data-model.md` と `alembic/versions/` に具体化されている。本書の列挙を完成したDDLとみなさない。サービス非依存の配信者IDからディレクトリ名への永続対応、セッション単位連番、空試行の回収、全ジョブと欠損の集計、SRTの版数照合、期限削除と削除台帳の意味は、そのデータモデルと現行コードを参照する。
