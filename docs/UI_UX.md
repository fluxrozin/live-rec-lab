# LiveRecorder — UI/UX再設計・実装プロンプト

> **上位仕様**：`requirements.md`（確定済み。機能・制約・実装対象の判定は常にこちらを優先）  
> **対象**：LiveRecorderの日本語Web管理画面（Windows PCブラウザ）  
> **本書の範囲**：情報アーキテクチャ、画面と下位ビュー、情報の視覚的階層、操作動線、状態表現、デザインシステム、UIコンポーネント、ユーザビリティ、アクセシビリティ、UI実装・検証

## 1. 目的と適用範囲

LiveRecorderの管理画面を、**稼働状況を正しく把握でき、目的の記録や問題の原因へ迷わず到達できる運用コンソール**として再設計・実装してください。単なるCSSの装飾変更ではなく、情報構造、画面の責務、画面間の導線、共通コンポーネント、操作時の状態、視覚表現を一貫して設計してください。

- 実際に操作できるUIを完成させ、モックアップだけで終わらせないこと。
- **本書はUI/UXだけの指示書**とする。録画・コメント収集の内部動作、データベース設計、APIの内部仕様、OS構成、起動方式、保存処理、ジョブ制御などは記述・再設計しないこと。
- 既存の画面やデータ取得手段は利用可能な範囲で活用し、UI改善を理由とする不要なバックエンド変更や新機能の先行実装を行わないこと。
- `requirements.md` の機能名とUIの表示名が異なる場合でも、機能の意味、権限、対象、制約は変えないこと。未提供のデータ・操作を架空の値や動かないボタンで補わないこと。
- UIに必要な情報を取得できない場合は、表示できない事実を明記し、未対応項目を報告すること。新しいAPIや機能が実装済みだと仮定しないこと。

### UIに直接関係する確定前提

- 初期対象：TikTok LIVE、ツイキャス。日本語・Windows PCブラウザ専用。モバイル専用UIは不要。
- ログイン・ログアウト画面、ユーザープロフィールのUIは不要。
- Web上での動画再生・ライブプレビューは不要。録画動画はダウンロードして扱う。
- コメントエクスポートは**SRTのみ**。対応する録画セグメント単位で自動生成・ダウンロード・必要時の再生成を扱う。
- フロントエンドは`requirements.md`にあるJinja2＋HTMX＋軽量JavaScriptを前提とし、UIのためだけに大規模SPAを導入しない。
- **単一のライト系テーマ**を採用し、表示フォントのみ設定画面で2種類から選択可能とする。

## 2. デザイン原則とデザインシステム

### 2.1 コンセプト

#### LiveRecorder — Modern Operations Console

Linear、Vercel Dashboard、Raycast、GitHubの管理画面に見られる整理された情報階層や、控えめで精密なビジュアル表現を参考にしつつ、特定製品を模倣せず独自のUIを設計してください。

目指す品質：**Modern / Minimal / Refined / Professional / Data-centric / Calm / Precise / Functional / Consistent**。

- レイアウト、整列、余白、文字の大小・濃淡、コントラストによって操作の意味と情報の優先順位を伝える。
- 画面に説明を重ねすぎない。意味の重複する見出し・サブラベル・案内文を減らし、詳細な説明や診断情報は必要な場面で展開する。
- **省略してはいけない情報**：操作対象、数量と単位、現在の状態、情報の鮮度、影響範囲、失敗理由、回復可能な操作、破壊的操作の結果。
- ダッシュボードは状況把握を優先し、一覧は情報密度と検索性を優先する。あらゆる情報をカード化しない。
- 強い原色、巨大なカード、目立つ装飾、過剰なグラデーション、グラスモーフィズム、派手な動き、多数の色付きバッジ、ボタンの密集を避ける。

### 2.2 色：ライト系の単一テーマ

**ライトテーマに近い、明るく落ち着いたテーマを1種類だけ**設計してください。ダークテーマ、ライト／ダーク切り替え、OS・ブラウザの配色設定への追従は実装しないでください。

| 用途           | 参考色          |
| -------------- | --------------- |
| Background     | `#F7F9FC`       |
| Surface        | `#FFFFFF`       |
| Surface Alt    | `#F0F3F8`       |
| Border         | `#DAE1EA`       |
| Text           | `#1D2735`       |
| Muted          | `#58677A`       |
| Accent         | `#4769C8`       |
| 配信中（LIVE） | `#168466`（緑） |
| 録画中（REC）  | `#C93446`（赤） |
| コメント収集中 | `#2876B9`（青） |
| Success        | `#168466`       |
| Warning        | `#9B640C`       |
| Danger         | `#B9434A`       |

数値は出発点であり、実際のコントラストと画面全体の調和に合わせて調整してください。色・面・境界線・文字・状態・余白・角丸・影・動きはCSSカスタムプロパティ等で共通化し、画面ごとに散在させないでください。状態は必ず文字と必要最小限の記号を併用し、色だけで判断させないでください。

### 2.3 フォント・文字組み

設定画面の**「フォント」プルダウン**から、次の2種類のみを選択可能とします。

| 表示名                    | 指定                                                          | 補足                               |
| ------------------------- | ------------------------------------------------------------- | ---------------------------------- |
| **Windows標準**（初期値） | `"Segoe UI Variable", "Segoe UI", "Yu Gothic UI", sans-serif` | `palt`指定なし                     |
| **Noto Sans JP**          | `"Noto Sans JP", sans-serif`                                  | `font-feature-settings: "palt" 1;` |

- 選択は画面全体に適用し、ページ移動・再読込後も保持する。フォントを切り替えてもレイアウトの破綻や文字の欠けを生じさせない。
- 設定画面に日本語・英数字・数字が混在する短いプレビューを設ける。保存前のプレビューと保存済みの設定を明確に区別する。
- Noto Sans JPの読み込み失敗時は代替フォントでも操作可能にし、適用できていないことを誤認させない。
- Page Title / Section Title / Body / Secondary / Caption / Table Header / Metric Numberの階層を揃える。
- 件数、時刻、容量、経過時間など比較する数値には`font-variant-numeric: tabular-nums`を用い、表の数値列は原則右揃えとする。
- 識別子・ファイル名・パス・技術ログは読み分けやすい書体とし、省略時も全文を確認・コピーできるようにする。

### 2.4 余白・密度・配置

- 4pxを基本単位とするスペーシング体系を採用する。表の列、行高、フォームのラベル、入力欄・ボタンの高さ、カードの端を一貫して整列させる。
- 状態を見分けるための余白は確保するが、業務向けテーブルの一覧性を損なうほど行高を広げない。
- 情報の強調には、文字の階層と背景面を優先し、意味のない強調バッジを増やさない。
- アニメーションは待機・状態変化の理解に必要な範囲に限り、`prefers-reduced-motion`を尊重する。

### 2.5 説明文に依存しないUI（構造的自己説明性）

**「文字を追加して説明する前に、レイアウトそのものを改善する」ことを全画面の設計原則としてください。** 目標は文字数の最小化ではなく、利用者が必要な情報と操作を、最小限の解読負荷で正しく把握できることです。

- 画面の目的、情報同士の関係、状態、操作の優先順位は、まず**情報の分類・近接配置・整列・余白・サイズ・文字の強弱・コントラスト・適切なコンポーネントの選択**で表す。見た目だけ整えた後に説明文を貼り付けて補わない。
- UIが分かりにくい場合、次の順序で修正する：**①情報の分類と粒度 → ②グルーピングと配置 → ③視覚階層・整列・余白 → ④操作部品と状態表現 → ⑤必要な短いラベル → ⑥それでも不可欠な補助説明**。説明文の追加を最初の解決策にしない。
- 関連する情報は近くに置き、異なる責務の情報は適切な距離または控えめな区切りで分ける。区別のためにカード・枠線・色面を無条件に増やさない。
- 画面見出しの直下に「この画面では〜できます」のような自己説明的な副題を機械的に追加しない。見出し・ラベル・バッジ・ツールチップ・説明文で同じ内容を繰り返さない。
- 画面ごとに適した表示形式を選択する。比較・検索が中心ならテーブル、状態の即時把握ならコンパクトなインジケーター、属性の確認ならキー／値、補足診断なら詳細展開を優先し、すべてを均一なカードへ変換しない。
- 低頻度の技術情報は、必要時に詳細を開ける**段階的開示**を基本とする。ただし、異常の存在、影響、重要な状態、回復に必要な操作を隠してはならない。
- アイコンや色だけで意味を説明しようとしない。操作名・数値の単位・状態名・エラー理由・破壊的操作の影響など、判断に必要な文字情報は残す。短文化によってアクセシビリティや安全性を損なわない。
- グラフやアニメーションは、実データの比較・変化・状態遷移の理解に明確に寄与する場合に限る。文章を減らすためだけの意味のない図表・ピクトグラム・動きを追加しない。

**補助説明文の追加判断**：その文章を一時的に隠したとき、主要な情報の関係と操作が分からなくなるなら、まず配置とラベルを見直してください。なお、安全上の警告や専門的な制約まで削除するためのテストではありません。

### 2.6 AI生成UIの定型化・過剰装飾を防ぐ

Claude Opus 5.5等のUI生成モデルが採用しがちな**汎用SaaSテンプレート、説明過多、カードの多層化、装飾の定型化**を無批判に持ち込まないでください。

- 見栄えのためのヒーロー領域、大きなスローガン、毎回のアイキャッチ文、不要な集計カード、架空のKPI、装飾的なグラフ、意味のないピル型バッジを追加しない。
- カード内カード、深い枠の入れ子、過大なパディング、無意味な角丸・シャドウ、過密なアイコン・アクション列を避ける。余白は「大きいほど上質」ではなく、**関係性と一覧性を伝える適切な密度**で評価する。
- 一部の画面だけ別の色・角丸・フォント・影・アイコン体系に変えない。個別画面の改善では既存のデザイントークン・共通部品を優先し、局所的なCSS上書きで見かけだけ整えない。
- 参考画面・デザインSkillは**情報の整理、視線誘導、密度、操作配置、状態表現**を分析する材料とし、色や装飾だけを模倣しない。外部Skillの一般的な美意識より、本書と`requirements.md`を優先する。
- 表示内容は実際の利用者タスクから決める。仕様書で長く説明されている機能を、それだけで大きなUI要素へ昇格させない。仕様外の「便利そうな」機能や指標は実装しない。
- 視覚的な一貫性とユーザビリティに関する判断を、実装モデル自身の「洗練された」「分かりやすい」という自己評価だけで確定しない。実表示と操作で検証する。

### 2.7 UI文言：必要なラベルは残し、冗長な説明だけを削る

- 見出しは情報の対象、ボタンは実行する操作、状態ラベルは現在の事実を**短く具体的な日本語**で示す。技術的な内部処理名・英語表現の直訳・宣伝調のコピーをそのままUIへ持ち込まない。
- 「録画中」などの状態を、見出し・バッジ・本文で三重に説明しない。単一の視覚的まとまりで識別できるようにする。ただし、別々の文脈で必要な状態表示の反復は許容する。
- ラベルのないアイコンだけの操作へ置き換えて、説明文を減らしたことにしない。誤認しやすい操作は可視ラベルを優先し、ツールチップは代替の唯一の説明手段にしない。
- エラー、未保存変更、制約、権限・対象、不可逆な操作、反映時期など、事前判断に必要な内容には短い補足を残す。補足が長くなる場合は詳細展開へ分離する。
- 文字数・語数に一律の上限を設けない。文章を削った結果、意味・状態・操作対象が曖昧になったなら設計上の失敗として扱う。

## 3. 情報アーキテクチャ：6つの主要ナビ＋下位ビュー

### 3.1 「主要ナビゲーション数」と「画面数」を分ける

**サイドバーに置くのは6つの主要ナビゲーション項目です。** その下に、配信セッション詳細、障害詳細、追加・編集ドロワー、設定内セクションなどの下位ビューを設けます。**「画面は全部で6枚」と解釈しないでください。**

| グループ     | サイドバー表示名   | 主要URL（変更しない） | 役割・利用者の問い                       |
| ------------ | ------------------ | --------------------- | ---------------------------------------- |
| 運用・データ | **ダッシュボード** | `/`                   | 今、何が起きているか？                   |
| 運用・データ | **監視対象**       | `/streamers`          | 誰を監視し、何を収集するか？             |
| 運用・データ | **配信記録**       | `/recordings`         | どの配信で、何が記録・取得されたか？     |
| 運用・データ | **コメント**       | `/comments`           | 誰が、いつ、何を投稿したか？             |
| 管理         | **システム状態**   | `/system`             | 何が正常で、どこに問題があるか？         |
| 管理         | **設定**           | `/settings`           | 監視・保存・表示の条件をどう変更するか？ |

- **「監視対象」**は`requirements.md`の「配信者管理」のUI表示名、**「配信記録」**は同「録画履歴」を含むセッション中心のUI表示名です。名称変更を理由に主要URL、既存機能、保存対象を変更しないでください。
- `/recordings`の一覧は**配信セッションを基本単位**として扱い、録画の有無とコメント収集の有無を独立して見せる。録画のないセッションも、取得可能な既存データとして存在する場合は見失わせない。
- 新しい独立した「ライブ状況」「ストレージ」「イベント履歴」「音声字幕」等の主要ナビ項目は設けない。必要な情報はダッシュボード、配信記録、設定、システム状態の下位領域に置く。
- ログイン、ログアウト、ユーザー管理、モバイル専用画面、動画プレイヤー、未対応サービスのナビは追加しない。

### 3.2 主要ナビと下位ビューの階層

```text
LiveRecorder
├─ 運用・データ
│  ├─ ダッシュボード
│  │   ├─ 稼働中の配信 → 該当する配信セッション詳細
│  │   └─ 最近の録画・警告 → 該当する記録／障害箇所
│  ├─ 監視対象
│  │   ├─ 一覧・絞り込み
│  │   ├─ 追加／編集（ドロワーまたはダイアログ）
│  │   └─ 配信者の履歴 → 絞り込み済みの配信記録
│  ├─ 配信記録
│  │   ├─ セッション一覧・絞り込み
│  │   └─ 配信セッション詳細
│  │       ├─ 配信概要・録画／コメントの状態
│  │       ├─ 録画セグメント・対応SRT
│  │       └─ 欠損・失敗・削除対象
│  └─ コメント
│      ├─ 横断検索・閲覧
│      └─ 関連セッションへ移動
└─ 管理
   ├─ システム状態
   │   ├─ 構成要素・録画方式・保存先の状態
   │   └─ 警告／エラー詳細（展開・関連記録へのリンク）
   └─ 設定
       └─ 監視／録画・保存／コメント・SRT／表示／詳細設定
```

- 配信セッション詳細は**配信記録の下位ビュー**とし、ダッシュボードや検索結果から直接開けるようにする。サイドバーに独立項目を増やさない。
- システムのイベント・障害詳細は原則としてシステム状態内の詳細展開を基本とし、必要な場合のみ既存の画面体系内に下位ビューを設ける。
- 追加・編集は一覧からのドロワー／ダイアログで扱い、メインナビを増やさない。
- 新しい公開URLを実装の前提にしない。既存のページ、クエリ、部分更新、詳細表示でこれらの動線を成立させ、未提供の操作は見せかけで実装しない。

### 3.3 画面を分ける判断基準

1. **目的が異なるか**：全体監視／対象設定／配信単位の確認／コメント横断検索／障害診断／全体設定は分ける。
2. **情報の粒度が異なるか**：集約KPI、配信セッション、セグメント、コメント、イベントを混在させず、概要から詳細へ進ませる。
3. **利用頻度が異なるか**：毎回見る情報は前面へ、低頻度の詳細設定・技術ログは下位へ置く。
4. **操作の危険度が異なるか**：通常の閲覧・ダウンロードと削除・停止操作を明確に分離する。
5. **画面間移動を減らせるか**：関連情報へ直接遷移できるなら独立メニューを追加しない。

### 3.4 共通アプリケーションシェル

```text
┌──────────────────┬────────────────────────────────────────────────────┐
│ LiveRecorder    │ 現在地 / ページ名             表示時点    主操作 │
│                  ├────────────────────────────────────────────────────┤
│ 運用・データ     │                                                    │
│  ダッシュボード  │ 必要な概要 → 一覧 → 詳細                             │
│  監視対象        │                                                    │
│  配信記録        │                                                    │
│  コメント        │                                                    │
│                  │                                                    │
│ 管理             │                                                    │
│  システム状態    │                                                    │
│  設定            │                                                    │
└──────────────────┴────────────────────────────────────────────────────┘
```

- サイドバーは220〜250pxを目安として固定し、選択中の主要画面を明確に示す。Lucide等の統一アイコンと日本語ラベルを併記する。
- 上部の共通位置に、**現在地・ページ名、表示時点（最終取得時刻）、ページの主操作**を配置する。アプリ独自の画面再読込ボタンは設けず、ページ全体の再読み込みはブラウザ標準機能（F5／Ctrl+R等）に委ねる。取得時刻が不明なら「未取得」と表示し、現在時刻を取得時刻の代わりにしない。
- 下位ビューでは親ページが分かるパンくず／戻る導線を設ける。主要画面だけの状態では不必要なパンくずを増やさない。
- 破壊的操作は通常の主操作と距離を置いた「危険な操作」領域に配置する。
- 大画面では読みやすい最大幅を考慮するが、テーブルには必要な幅を与える。PCでウィンドウ幅や拡大率が変わっても主要操作を維持する。

## 4. 情報の階層と画面間の動線

### 4.1 共通のデータ粒度

- **配信者**：監視の対象とその設定。録画ジョブそのものと同一視しない。
- **配信セッション**：一回のライブ配信を表す、記録の最上位の単位。
- **録画セグメント**：一つの配信セッションに属する個々の動画ファイル。セグメントごとにSRTの対応と生成状態を示す。
- **コメント**：配信セッションに紐づく投稿。動画がなくても検索・閲覧対象となり得る。
- **障害イベント**：問題の発生箇所、影響対象、時刻、理由、確認できる範囲の回復情報を扱う。

**録画の成功とコメント収集の成功を「配信成功」の1状態にまとめないこと。** 配信セッションの概要の下に、録画・コメント・SRTの状態をそれぞれ表示してください。

### 4.2 代表的なタスクフロー

| 利用者がしたいこと                     | 開始地点 → 到達先                                             | 維持する文脈                    |
| -------------------------------------- | ------------------------------------------------------------- | ------------------------------- |
| 現在の録画を確認                       | ダッシュボードの稼働中セッション → 該当セッション詳細         | 対象配信、表示時点              |
| 配信者を追加・編集                     | 監視対象 → 追加／編集ドロワー                                 | 一覧の並び・絞り込み            |
| 配信者の過去の配信を確認               | 監視対象の行 → その配信者で絞り込んだ配信記録                 | 配信者フィルター                |
| 昨日のコメントだけ取得できた配信を探す | 配信記録 → 対象セッション → コメント                          | 日付・配信者・セッション        |
| 録画ファイル／SRTを取得                | 配信記録 → セッション詳細 → 対象セグメント                    | セグメント連番、動画とSRTの対応 |
| コメント本文を検索                     | コメント → 検索結果 → 関連セッション                          | 検索条件・ページ位置            |
| 録画失敗の理由を調べる                 | ダッシュボードの警告 → 該当イベント／セッション → 詳細情報    | エラー対象と時刻                |
| 容量不足を確認する                     | ダッシュボードの容量表示 → システム状態／設定の該当セクション | 保存先・利用可能容量            |

- **主要な導線はコンテキストリンクを優先する。** 画面の一覧へ戻って再検索しなければ対象に辿り着けない設計を避ける。
- 一覧 → 詳細 → 一覧に戻る際、できる限り検索語、選択フィルター、並び順、ページ番号、スクロール位置を保持する。
- 「配信記録へ」「コメントを見る」「エラー詳細」などのリンクは、移動後の画面の文脈を具体的に示す。
- ブラウザによるページ再読み込みは画面データの再取得に限り、外部サービスへの監視要求を追加発生させない。外部サービスへの手動再確認機能を別途提供する場合に限り、その目的と影響が分かる名称で表示する。

### 4.3 配信セッションの扱い

| 録画         | コメント収集 | ユーザーへ見せるべき内容                             |
| ------------ | ------------ | ---------------------------------------------------- |
| 成功         | 成功         | 動画セグメント、コメント件数、対応するSRT            |
| 成功         | 失敗・不完全 | 動画と、コメント欠損・失敗理由                       |
| 失敗・未取得 | 成功         | コメントが残っていること、動画がない理由             |
| 無効         | 成功         | コメントだけを収集した配信であること                 |
| 失敗・無効   | 失敗・無効   | セッションが存在する場合は、記録された状態・障害内容 |

- 上表は**画面上の分類例**であり、内部のジョブ状態を新設する指示ではない。表示は`requirements.md`に定義された状態と実際の取得データに従う。
- 動画のないセッションでも、コメントが取得できていれば**コメント検索へ直接進める**ようにする。
- **SRTは確定済み録画セグメントとの対応が基本**であり、録画セグメントのないコメント専用配信に架空のSRT生成・ダウンロードを表示しない。
- 配信記録は録画ファイル一覧と同義ではない。セッションを上位、動画・SRT・欠損を下位として整理する。

## 5. 共通の状態表現・情報鮮度

### 5.1 状態の原則

**配信状態、録画状態、コメント収集状態、SRT状態、画面の取得状態、操作結果は独立して表現**してください。色だけでなく状態名と必要に応じた記号・説明を併記し、状態の意味を作り替えないでください。

| 分類       | UIで区別するもの                                                                     |
| ---------- | ------------------------------------------------------------------------------------ |
| 配信       | 配信中／オフライン／不明／確認エラー／監視停止、必要に応じて確認中                   |
| 録画       | 待機／録画中／再接続中／確定処理中／完了／一部取得／失敗／停止等、実際に取得した状態 |
| コメント   | 待機／接続中／収集中／再接続中／完了／不完全／失敗／無効等、実際に取得した状態       |
| SRT        | 未生成／生成中／生成済み／生成失敗／保留等、実際に取得した状態                       |
| 画面データ | 初回取得中／取得済み／正常に0件／検索結果0件／取得失敗／古い情報／取得不可           |
| 操作       | 入力中／送信中／受付済み／実行中／完了／失敗／結果未確認／競合（発生した場合）       |

`UNKNOWN`を「オフライン」に、録画失敗を「配信終了」に、件数未取得を「0件」に、受付済みを「完了」に、取得できない容量を「0GiB」に変換しないでください。映像の欠損とコメントの欠損を混同しないでください。

### 5.2 典型的な表示パターン

| 状況                               | 表示の原則                                                                                                          | 避ける表現                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 初回読込・部分更新中               | 対象領域のみ「取得中」・控えめな進捗・`aria-busy`                                                                   | 根拠のない無限スピナー              |
| データが存在せず正常               | 「まだ記録がありません」＋必要なら次の操作                                                                          | 無言の空白、通信失敗と同じ表示      |
| 絞り込みに一致しない               | 「条件に一致する記録はありません」＋絞り込み解除                                                                    | 初期状態の空表示と同一視            |
| `UNKNOWN`・監視エラー              | 「状態不明」「確認できません」＋最終正常確認日時                                                                    | 「オフライン」「終了」と断定        |
| 更新失敗・古い情報                 | 「更新失敗」「前回取得 HH:MM:SS」と表示し、必要ならブラウザ標準の再読み込みを案内。前回値はラベルや控えめな枠で識別 | 以前の値を最新の値として表示        |
| UI側で情報取得不能                 | 範囲を明示して「現在の状態を取得できません」と表示し、必要ならブラウザ標準の再読み込みを案内                        | すべて0件、全録画が停止したとの断定 |
| 操作受付・処理中                   | 「受付済み」「処理中」を区別し、完了は結果確認後に表示                                                              | クリック直後に成功確定              |
| 競合・内容が変化                   | 保存できなかった理由、再取得・確認の導線                                                                            | 黙って上書き、成功通知              |
| 不完全・欠損あり                   | 対象機能、区間、理由、詳細への導線                                                                                  | 全量取得と誤認させる表示            |
| 削除保留・ファイル使用中・容量不足 | 対象・理由・再試行の可否・次にできること                                                                            | 処理が終わったとの断定              |

- 古い行の区別は、可読性が下がる過剰な淡色化や斜体だけに頼らず、**「前回取得値」ラベル・時刻・控えめな区切り**を優先する。
- 配信一覧の各行と、画面全体の最終取得時刻が異なる場合は混同させない。時刻が分かる粒度で表示する。
- `未取得`／`0件`／`取得失敗`／`対象外`／`無効`／`未生成`の違いは、短い日本語で一貫して伝える。

### 5.3 状態の強調と文言

- 配信中は緑、録画中は赤、コメント収集中は青で表示する。**録画中の赤い点は穏やかなパルス＋「録画中／REC」**、**エラーは静止した警告・×アイコン＋「失敗／エラー」**とし、同じ赤でも誤認させない。アニメーションは`prefers-reduced-motion`で抑制する。
- アプリロゴはシステム全体の録画状態に連動させ、待機中はアクセントの青、録画中は赤（中央の点が穏やかに明滅）、状態不明は警告系の色・形状で区別する。ブラウザのファビコンも状態に合わせる。ただし「配信中」だけでは録画中ロゴに切り替えない。
- 稼働中／停止／警告／異常／不明を意味的に区別する。黄色は注意、赤いエラーアイコンは異常を示すなど、色だけでなく文字・記号・動きの有無で判別可能にする。
- 文字・アイコン・色・必要な説明を組み合わせ、状況に応じて情報／警告／異常／取得中／不明の記号を用いる。装飾用記号には`aria-hidden`を使い、意味はテキストで伝える。
- 状態の要約には「何に問題があり、どこへ影響するか」を入れ、長い技術的理由は詳細へ置く。
- エラーと警告の見た目を区別する。取得不能な情報を成功・正常に見せない。

### 5.4 自動更新と表示の鮮度

- 上部の共通位置には**「表示時点（最終取得）」のみ**を配置し、アプリ独自の画面再読込ボタンは置かない。必要に応じて各セクション・各行の最終確認時刻も示す。
- 定期更新は必要な領域だけを更新し、フォーム入力中、ダイアログ表示中、ドラッグ中、テキスト選択中、ブラウザタブが非表示のときには、**操作を妨げないよう更新を停止・延期**する。
- 更新再開後も、スクロール、フィルター、入力内容、選択範囲、フォーカスを可能な限り維持する。行の並びが変わる場合は不必要な画面ジャンプを避ける。
- 前回値の表示中に更新失敗した場合は、その値の取得日時を残す。次の取得成功を確認するまで新しい情報として表示しない。
- 画面全体の再読み込みはブラウザ標準機能に委ねる。自動更新失敗時は前回取得時刻と失敗を表示し、必要ならF5／Ctrl+Rを案内する。SRT再生成など機能固有の再試行操作は残す。ブラウザ再読み込みによって外部サービスの監視枠を消費する手動確認を実行しない。

## 6. 共通コンポーネントとインタラクション

### 6.1 共通コンポーネント

App Shell、Sidebar、Page Header、Breadcrumb、Section Header、Button、Icon Button、Dropdown、Toggle、Input、Select、Checkbox、Metric、Status Indicator、Capacity Bar、Data Table、Search／Filter Bar、Pagination、Modal／Drawer、Confirmation Dialog、Tooltip、Toast、Inline Alert、Empty／Loading／Stale State、Key–Value Details、Log Detailsを一貫した見た目と挙動で実装してください。

- 同じ操作には同じラベル・形・配置・フィードバックを使用する。アイコンのみの操作にはアクセス可能な名前とツールチップを付ける。
- 一覧の操作は必要最小限を直接見せ、編集・削除・詳細等は適切なアクションメニューへ整理する。
- 項目が多い詳細画面は、短い概要の下に表・属性一覧・展開可能な詳細を置く。巨大なカードや長文を並べない。
- 入力の検証エラーは該当フィールドの近くに表示し、エラー箇所へフォーカスできるようにする。

### 6.2 操作結果と二重送信の防止

- トグル、保存、ダウンロード、再生成、停止・再開、削除には、処理中・確定済み・失敗・結果不明を適切に表示する。
- **トグル操作は実際の反映を確認してから確定表示**する。失敗・結果未確認のときに、画面上だけ成功状態へ固定しない。
- 操作中は対象のボタン等を必要な範囲で一時無効化し、重複操作を防ぐ。別の配信・別のセグメントの操作まで不必要に止めない。
- バックエンドが受付と完了を区別する操作では、UIも「受付済み」「実行中」「完了」を区別する。完了確認方法を表示し、確認できない場合は「結果未確認」とする。
- 競合等で保存に失敗したら、変更が反映されていないこととブラウザ標準の再読み込み・再編集の手順を示す。既存データを無言で上書きしない。

### 6.3 通知と障害

- 成功は控えめなトースト、継続中の問題は該当領域のインラインアラートで示す。
- エラーの通知は読める時間を確保し、必要な場合は詳細を開けるようにする。無限に増えるトーストの山は作らない。
- エラー本文は操作を続けるための説明を先に書き、長い技術的メッセージは展開・コピー可能にする。
- 通知がキーボード操作とスクリーンリーダーで理解できるよう、`aria-live`や適切なフォーカス制御を使用する。

### 6.4 危険な操作と未保存変更

- 削除などの破壊的操作は、対象名・対象数・ファイルや記録への影響範囲・復元可否を確認ダイアログに示す。既定のフォーカスは原則として**キャンセル**にする。
- 録画・監視のON/OFF設定と、進行中ジョブの停止・再開は別の操作として見た目も文言も区別する。
- 設定・編集フォームで未保存の変更がある場合は明示し、移動時には意図せず破棄しないよう配慮する。
- ドロワー・ダイアログはEscや閉じる操作、フォーカスの閉じ込めと閉鎖後の復帰を一貫させる。

### 6.5 数値・日時・単位

- 日時は設定済みタイムゾーンで表示し、必要時に`JST`等の基準を併記する。相対表示には絶対日時を確認できる手段を用意する。
- 件、秒、分、GiB等の単位、数値の丸め、右揃え、日付表記を画面間で統一する。
- 取得できない容量や件数は`0`で埋めない。Windows側の保存先パスとその他のパス表記を誤認させない。

## 7. ダッシュボード（`/`）

### 7.1 主な役割

**「今どうなっているか」を短時間で把握する画面**とします。障害の技術的な原因調査はシステム状態へ、個別の動画・SRT・コメントの確認は該当する配信セッション詳細へ進ませてください。

### 7.2 情報の優先順位

1. **優先KPI**：監視対象配信者数、現在配信中、現在録画中、コメント収集中。
2. **稼働中セッション**：配信者、サービス、配信状態、録画状態、コメント収集状態、開始時刻・経過時間（取得できる場合）。行から**該当セッション詳細へ直接移動**できること。
3. **異常・容量**：容量警告や、稼働に影響する直近の問題を必要な場合だけ簡潔に示す。問題箇所へ移動できること。
4. **補足KPI**：本日の録画件数、本日のコメント件数、録画ファイル総容量、保存先の空き容量。
5. **最近の録画**：直近の録画をコンパクトに表示し、詳細へ直接進めること。

- 件数の大小だけで異常を推測せず、機能別の状態に基づいて表示する。
- 異常がないときに巨大な正常バナーや空の警告領域を占有しない。
- 進行中のセッションがない場合は「現在配信中の対象はありません」と表示し、通信障害による状態不明と区別する。
- 一部のセクションが取得失敗しても、正常に取得できたセクションは使えるようにする。
- 保存容量からはシステム状態の保存先情報または設定の保存条件へ、警告からは該当イベントやセッションへ直接遷移する。

## 8. 監視対象（`/streamers`）

### 8.1 一覧の構造

**「誰を監視し、何を有効にしているか」を管理する画面**です。配信者名を主情報、ユーザーIDを補助情報として、一覧性の高いテーブルを使用してください。

表示項目：プラットフォーム、配信者名、配信者ID、監視ON/OFF、配信状態、録画ON/OFF、録画状態、コメント収集ON/OFF、コメント収集状態、最終確認日時。最終配信日時・最終録画日時は補助表示や詳細で確認できるようにする。

- 監視・録画・コメント収集は**独立した3つのトグル**とし、現在のジョブ状態とは視覚的に区別する。
- 一覧から、該当配信者で絞り込んだ**配信記録**へ直接遷移できるようにする。
- 編集・履歴・削除は行アクションに整理し、巨大なボタン列を作らない。
- 必要な絞り込み（サービス・状態等）と、選択状態・最終確認の鮮度を見せる。
- 更新中や変更失敗時に誤ったトグル位置を確定表示しない。

### 8.2 追加・編集

「監視対象を追加」からモーダルまたはドロワーを開き、追加と編集でフォームを共通化してください。

項目：プラットフォーム（TikTok LIVE／ツイキャス）、ユーザーIDまたは対応URL、表示名、監視ON/OFF、録画ON/OFF、コメント収集ON/OFF。

- 入力形式の例、必須／任意、誤りをフィールドに近接して表示する。
- 編集は既存値を初期表示し、保存・キャンセル・未保存変更を明確にする。
- 重複登録や不正な入力の理由を短い日本語で伝える。
- 削除は保存から分離し、関連する履歴・ファイルへの影響を明示する。
- 録画設定のON/OFFと稼働中セッションの手動停止／再開は混同させない。

## 9. 配信記録（`/recordings`）・セッション詳細

### 9.1 一覧は配信セッション単位

**「何が記録されたか」を確認する画面**です。見た目の名称は「配信記録」とし、`requirements.md` の録画履歴の機能・URLを維持してください。動画ファイルを基本行にするのではなく、**配信セッションを1行の基本単位**とします。

表示項目：配信者、プラットフォーム、配信タイトル、開始・終了日時、録画時間、録画ファイル数、合計サイズ、コメント件数、録画状態、コメント収集状態、詳細への導線。取得できない項目は「未取得」等で示し、0と混同しないこと。

- 検索・フィルター：配信者、プラットフォーム、日付範囲、録画状態。可能な場合に進行中／終了済みを見分ける絞り込みを追加してもよいが、未提供の検索機能を動作すると見せない。
- 録画あり／録画失敗／録画無効／コメントのみ等を、実際に存在するセッション情報に応じて区別する。
- **録画ファイルがないことを理由に、コメントのある配信セッションが見つからなくならない**ようにする。
- 一覧 → 詳細 → 戻るで、検索条件、並び、ページ位置を維持する。結果件数と現在位置を明示する。
- 一覧で全情報を展開せず、複数セグメントや欠損・障害の詳細はセッション詳細へ委ねる。

### 9.2 配信セッション詳細の情報順

1. **配信概要**：配信者・サービス・タイトル・日時・セッションの状態。
2. **取得結果の概要**：**録画状態**と**コメント収集状態**を別々に提示。記録できた動画・コメント件数を明示。
3. **録画セグメントと対応SRT**：セグメント連番、開始・終了、長さ、形式、サイズ、検証状態、動画ダウンロード、SRT生成状態・ダウンロード。**動画とSRTの対応が一目で分かる同じ行／まとまり**に置く。
4. **コメントへの導線**：この配信セッションで絞り込んだコメント検索へ移動。
5. **欠損・失敗**：影響を受けた機能と期間、理由、必要な詳細・ログへの導線。
6. **危険な操作**：削除対象・影響範囲を示す別領域。

- 詳細画面の上部から、配信記録一覧へ戻れるようにする。稼働中配信の場合は、提供される手動停止／再開を誤操作しにくい場所に配置する。
- **コメントだけ取得できたセッション**では動画欄を「録画なし（理由）」とし、コメント閲覧を主導線にする。動画ダウンロード・SRT生成を可能に見せない。
- どちらか一方の失敗によって、もう一方の成果物が隠れないようにする。

### 9.3 セグメント・SRT・欠損の見せ方

- セグメントごとに動画とSRTを対応づける。SRTが未生成でも、対応すべきセグメントが分かるようにする。
- SRT生成済み／未生成／生成失敗／保留、生成日時、再生成可否を明示する。再生成可能な場合は**対象セグメントと処理結果**を分かるようにする。
- 時刻同期の方法（実測／近似／手動補正／同期不能）、近似の注意、同期失敗理由は必要に応じて展開できるようにする。
- 動画ファイル不在、SRT未生成、検証失敗などのときにダウンロード可能なボタンを出さない。
- ファイルのみ、履歴のみ、両方の削除を提供する場合は、操作ごとの対象と影響範囲を明示する。未提供の削除操作は追加しない。
- 動画プレイヤー・再生コントロール・動画と同期したコメント表示は設けない。

## 10. コメント検索・閲覧（`/comments`）

### 10.1 画面の役割

**「誰が、いつ、何を投稿したか」を配信横断で調べる画面**です。配信記録の詳細からは、そのセッションに絞り込まれた状態で開けるようにしてください。コメント本文を主情報として読みやすく表示します。

### 10.2 検索・結果

- 主検索欄：コメント本文。
- 詳細フィルター：投稿者ID、投稿者表示名、配信者、プラットフォーム、配信セッション、日付範囲。追加条件は展開式で整理する。
- 検索語・フィルターの適用状態、結果件数、現在ページ、条件のリセットを分かりやすく表示する。
- コメント行には投稿日時または受信日時、配信者、プラットフォーム、投稿者表示名、投稿者ID、本文、録画開始からの経過時間（取得できる場合）、関連セッションを表示する。
- 投稿者名・IDが長くても本文の幅を奪わない。改行・絵文字・長文も読めるようにする。
- ツイキャス匿名番号は取得できた場合だけ表示し、未取得の番号や推測による人物同定を行わない。
- 大量のコメントはページネーションで扱い、全画面を不必要に再描画しない。
- **関連する配信セッションへの直接リンク**を設け、戻った際には検索条件とページ位置を可能な限り保持する。

### 10.3 SRTへの導線

- コメントエクスポート形式は**SRTのみ**であり、CSV／JSONL／TXT／ASS等のコメント出力メニューは設けない。
- SRTが必要なときは、該当する録画セグメントのSRT取得へ案内する。コメント検索結果の範囲とSRTの対象セグメントを混同させない。
- セグメントが存在せずSRTを生成できない場合は、その旨を明示する。コメント閲覧そのものは維持する。

## 11. システム状態（`/system`）

### 11.1 ダッシュボードとの責務分離

ダッシュボードが**「今、何が起きているか」**を知らせるのに対し、システム状態は**「何が原因で、どこに影響し、何を確認できるか」**を扱います。両画面に同じ大型KPI群やイベント一覧を重複して配置しないでください。

- 冒頭：全体の状態、監視機能、録画・コメント取得、データ保存、録画保存先、最終監視実行日時を簡潔に表示。
- 次段：録画エンジン・関連ツールの利用可否、バージョン、直近の失敗（取得可能な情報に限る）。
- 次段：外部サービスとの接続、監視頻度制約・再試行待ち等、実際に取得できる診断状態。
- 末尾：時系列の警告・エラー、保存先のファイル照合結果等、提供される診断情報。

### 11.2 イベントと診断情報

- イベントの一覧は**時刻／重要度／対象／要約**を主にし、長い技術メッセージは展開・コピーできるようにする。
- エラーの対象配信・録画・セグメントが特定できる場合は、該当セッション詳細に直接リンクする。
- 警告と異常を区別し、影響範囲と次にできる確認・再試行方法を先に示す。
- 保存先照合などの結果は正常・不足・不一致・未確定などの違いを区別する。照合・確認と削除の操作を混ぜない。
- 診断中／取得失敗／古い情報の状態と、最後に確認できた時刻を示す。実在しない「別Coreの接続画面」等は追加しない。

## 12. 設定（`/settings`）

### 12.1 セクション構成

**設定は1つの主要画面の中で、目的に応じたセクションまたはタブに分類**してください。設定のカテゴリをサイドバーの主要ナビに昇格させないでください。

| セクション        | 表示・編集するUI項目                                                                         |
| ----------------- | -------------------------------------------------------------------------------------------- |
| **監視**          | サービス別監視頻度、変更できない上限、設定値と実効値の違い（取得可能な場合）                 |
| **録画・保存**    | 同時録画上限、録画品質、保存先、最低空き容量、保存期限、自動削除、TikTok録画エンジン優先順位 |
| **コメント・SRT** | コメント収集ON/OFF、SRT表示秒数など`requirements.md`に規定され提供される設定                 |
| **表示**          | 表示タイムゾーン、フォント（Windows標準／Noto Sans JP）                                      |
| **詳細設定**      | ログレベル、Webポートの自動／固定設定など提供される設定と状態表示                            |

- 長い単一フォームを避け、選択中カテゴリを明確に示す。関連項目を近接させ、長い説明はヘルプや補足に置く。
- **編集可能／読み取り専用／未保存／保存中／再起動後反映**を見分けられるようにする。
- 設定項目を視覚的に分割しても、保存の単位と実際の反映結果が一致するようにする。未保存の値が意図せず消えたように見せない。
- APIキーやシークレットが必要な項目は、設定済み／未設定等を表示し、平文を露出させない。

### 12.2 サービス別監視頻度の入力

| サービス    | 入力範囲                      | UIに必要な説明                       |
| ----------- | ----------------------------- | ------------------------------------ |
| TikTok LIVE | `0 < r ≤ 10` 回／分（小数可） | サービス全体で共有する上限：10回／分 |
| ツイキャス  | `0 < r ≤ 60` 回／分（小数可） | 初期値：10回／分、上限：60回／分     |

- サービスごとに入力欄を分け、単位「回／分」、上限、初期値、反映タイミングを近くに示す。
- `0`、負数、上限超過、数値以外の入力はフィールド近傍でエラー表示する。監視停止は配信者ごとのON/OFFで行い、`0回／分`という意味を作らない。
- **監視頻度は配信者個別ではなく、同じサービス内の監視対象全体で共有する**旨を説明する。
- 設定値と実際の確認頻度は異なる場合がある。外部サービスの制限やコメント取得の優先等で低下するなら、取得できる実測情報とともにその旨を示す。
- 変更できないサービス上限は読み取り専用にする。変更反映の成功・失敗を適切に知らせる。

### 12.3 フォント選択とプレビュー

ラベル「フォント」の**単一選択プルダウン**を「表示」に置き、選択肢を次の2件に限定してください。

1. **Windows標準（初期値）**：`"Segoe UI Variable", "Segoe UI", "Yu Gothic UI", sans-serif`
2. **Noto Sans JP**：`"Noto Sans JP", sans-serif`＋`font-feature-settings: "palt" 1;`

- 選択した書体で日本語・英数字・日時を短くプレビューする。
- 保存前にプレビューを反映させる場合は、保存済みとの違いを表示し、キャンセルで元の状態に戻す。
- 選択は再読込・ページ移動後も保持され、見出し・本文・表・ダイアログに反映される。
- **テーマの設定、切り替えボタン、OSテーマ連動のUIを設けない。**

### 12.4 保存と反映

- 変更が即時反映される項目と、再起動後に反映される項目を明確に表示する。
- 編集中、保存中、成功、失敗、競合の違いを表示し、保存が確定する前に反映済みと表示しない。
- 保存先のアクセス可否等が確認できない場合は理由・確認先を示す。利用可否不明を正常として扱わない。

## 13. PC対応・アクセシビリティ

### 13.1 対応幅

Windows PCブラウザを対象とし、**1440px、1280px、1024px**を主な確認幅とする。125％・150％の拡大、可能なら200％表示も検証してください。

- PCのウィンドウを狭めた場合も、文字・ボタン・ダイアログが重なったり操作不能になったりしないようにする。
- 必要なら列の優先順位、詳細展開、部分的な横スクロールを設計するが、データテーブルの読みやすさを維持する。
- スマートフォン・タブレット専用メニュー、モバイルカード変換、下から出るモバイルシート等は実装しない。

### 13.2 WCAG 2.2 AAを目標としたUI

- 十分な文字コントラスト、常に分かるフォーカス表示、色以外による状態識別。
- キーボードによるサイドバー・検索・行アクション・トグル・ダイアログの操作。
- ドロワー／ダイアログの開閉時のフォーカス制御と、Tab移動の分かりやすさ。
- 入力ラベル、必須条件、単位、エラーメッセージの関連付け。
- `aria-busy`、`aria-live`、アクセシブルネーム、装飾アイコンへの`aria-hidden`の適切な使用。
- 長いメッセージ、フォント2種類、拡大表示、狭いPCウィンドウでも読み取り可能な構成。
- アニメーションを必要最小限にし、`prefers-reduced-motion`に従う。

## 14. UI設計・実装・レビューの進め方

1. **現状の確認**：実在する画面、表示データ、操作、下位ビューと`requirements.md`の差分を把握する。
2. **情報設計の確定**：6つの主要ナビと下位ビューの責務、配信セッションを中心とする階層、画面間のリンクと戻り方を整理する。
3. **操作フローの検証**：以下の代表タスクを使い、メニュー名だけから正しい画面へ行けるか、無駄な再検索がないかを確認する。
   - 今録画している配信の状態を確認する。
   - ある配信者の過去の記録を探す。
   - **コメントだけ取得できた昨日の配信**を見つける。
   - 特定セグメントの動画とSRTをダウンロードする。
   - 録画失敗の理由と影響範囲を確認する。
   - サービス別の監視頻度と表示フォントを変更する。
4. **デザインシステムの整備**：ライト系単一配色、2種類のフォント、4pxグリッド、数値・単位、共通の状態表現を統一する。
5. **共通部品の実装**：ナビゲーション、テーブル、検索、ドロワー、通知、空・失敗・古い情報・処理中の各状態を揃える。
6. **主要画面と下位ビューの実装**：ダッシュボード → 監視対象 → 配信記録／セッション詳細 → コメント → システム状態 → 設定を中心に、直接リンクを接続する。
7. **実ブラウザでのUI検証**：操作フロー、検索の保持、部分更新、状態の鮮度、フォント、PC幅、拡大、キーボード操作を検証する。
8. **説明依存・視覚階層の監査**：実画面の補助説明文を一時的に隠し、主要な操作・情報の関係・状態が把握できるか確認する。また、スクリーンショットを縮小・ぼかして、重要情報と関連グループの強弱を確認する。いずれも補助テストとし、必要なラベル・注意事項を削除する根拠にはしない。
9. **実利用シナリオと回帰の検証**：第4.2節・本節の代表タスクを実際に操作し、誤認・迷い・無駄な遷移を記録する。正常、空、検索結果0件、読込中、取得失敗、古い情報、操作中・失敗などの代表状態を確認し、共通コンポーネント変更が別画面を壊していないか点検する。

### 実表示の検証ルール

- 少なくとも主要6画面および重要な下位ビューを、実際のPCブラウザでレンダリングした状態で確認する。Playwright等が利用可能ならスクリーンショットを取得し、配置・文字切れ・コントラスト・余白・テーブル密度・状態表現を見直す。
- 1440px／1280px／1024px、拡大表示、両フォントの切替、日本語の長い配信タイトル・ID・ファイル名、コメント長文、日時・数値の混在を確認する。必要に応じて空・失敗・古い情報等の代表状態で撮影する。
- 自動検査（型チェック、ビルド、必要なUIテスト、アクセシビリティ検査など）と、スクリーンショットの目視・キーボードでの操作を区別して実施する。**自動検査の合格だけで、視覚品質や操作性を確認済みとしない。**
- 実ブラウザ・検証ツールにアクセスできない場合は、その範囲を**未検証**と明記する。スクリーンショットを取得・確認していないのに「視覚検証済み」「完成」と報告しない。
- UI上の分かりにくさを発見したときは、安易な説明文追加で終わらせず、**第2.5節の修正順序**で再設計し、再描画・再操作して確認する。

レビューでは、主観的な点数だけで合否を判断せず、**「どの画面で、誰のどのタスクに支障があり、どう再現し、どう修正するか」**を記録してください。色や見た目の整いだけでなく、情報の意味、操作結果、エラー時、ページ間の移動を含めて確認してください。

## 15. UI受け入れ基準

### 15.1 情報構造と導線

- [ ] サイドバーは**6つの主要ナビ**であり、詳細・編集・イベント等は下位ビューとして整理されている。
- [ ] サイドバーの表示名は「ダッシュボード／監視対象／配信記録／コメント／システム状態／設定」。主要URLは確定仕様から変更していない。
- [ ] ダッシュボードの稼働中配信・最近の録画・警告から、関連する記録や診断へ直接遷移できる。
- [ ] 配信記録は配信セッションを基本単位とし、録画の有無とコメント収集の有無を混同せず表示できる。
- [ ] 録画のないコメント取得セッションを見失わず、コメント閲覧へ進める。動画なしで架空のSRT操作は出さない。
- [ ] 一覧 → 詳細 → 戻るで、検索条件・絞り込み・ページ位置が維持される。
- [ ] ダッシュボードは状況把握、システム状態は原因調査という役割が明確で、同じ情報の無意味な重複がない。

### 15.2 状態・操作・データの正確さ

- [ ] 配信／録画／コメント収集／SRT／画面更新／操作結果を独立した状態として表示できる。
- [ ] **未取得と0件、監視停止と接続失敗、受付と完了、未生成と生成失敗、現在値と古い値**を明確に区別する。
- [ ] 上部に情報の表示時点を共通配置し、アプリ独自の画面再読込ボタンは設けない。前回値の表示や更新失敗を誤認させず、ページ再読み込みにはブラウザ標準機能を利用する。
- [ ] 定期更新が入力・編集中に作業を妨げず、スクロール・フォーカス・検索条件を不用意に失わせない。
- [ ] 二重送信を防止し、結果未確認や競合の際に成功と表示しない。
- [ ] 危険操作の対象と影響範囲、未保存変更、操作後の結果を分かりやすく示す。
- [ ] サービス別監視頻度の入力範囲、共通監視枠、実効値との差、エラー表示が分かりやすい。
- [ ] 録画セグメントごとの動画・SRT対応、状態、欠損区間、再生成可否、ダウンロード可否を識別できる。
- [ ] コメントを配信横断で検索でき、関連セッションへ移動できる。コメントエクスポートはSRT以外を追加していない。

### 15.3 ビジュアル・表示環境・品質

- [ ] ライト系テーマを**1種類のみ**使用し、テーマ切り替えやOSテーマ連動は実装していない。
- [ ] 設定のフォントプルダウンは**Windows標準／Noto Sans JP**の2択。初期値、`palt`、選択保持、プレビュー、全画面反映を検証している。
- [ ] 情報の階層、4pxグリッド、テーブルの数値・単位・行高・状態表現が統一されている。
- [ ] 主要な画面の目的、情報の関係、状態、操作の優先順位が、長い説明文に頼らず**配置・グルーピング・視覚階層**から把握できる。
- [ ] 追加した補助説明・サブタイトル・バッジ・カード・アイコン・グラフには、重複しない明確な役割がある。汎用SaaS風の定型表現やカードの入れ子で情報密度を損ねていない。
- [ ] 必須ラベル・数値単位・状態・安全上の説明を残したうえで、冗長なUI文言を削り、自然で簡潔な日本語にしている。
- [ ] 配信中＝緑、録画中＝赤、コメント収集中＝青。録画中とエラーを形状・文字で区別し、録画連動ロゴ・ファビコンと動きの抑制を確認している。
- [ ] 1440px／1280px／1024px、PCブラウザ拡大表示、キーボード操作、フォーカス、ラベル、コントラストを確認している。
