# 構成

LiveRecorder は WSL2 内で Web、REST API、監視、ジョブ管理を動かします。CLIの `start` がループバックソケットを確保し、Uvicorn 1 workerへ渡します。`status`、`url`、`backup`、`stop` は同じ実行時状態を参照します。録画には監督下の子プロセスを使います。

| 領域 | 責務 |
| --- | --- |
| `platforms/`・`monitoring/` | TikTok・ツイキャスの応答とコメントを正規化し、サービスごとに監視枠を制御 |
| `services/` | 配信の状態遷移、個別ジョブの開始・停止、削除台帳 |
| `db/`・`alembic/` | SQLite WAL、外部キー、マイグレーション、検索 |
| `storage.py`・`recording/` | 保存先の照合、Windows上のファイル名とセッション採番、録画・メディア検証・確定。ツイキャスは初期HLSのプリロールと404後の再解決を扱い、公式監視が配信中なら同じジョブで再接続する |
| `comments/` | SQLiteへの原文保存、セグメントごとのSRT生成と版数の照合 |
| `web/` | 日本語の7画面とローカルJSON API。HTML断片は `templates/partials/`。変更時のHost・Origin・CSRFを検証 |
| `ops/` | 起動時の復旧、ログの記録と段階的読取、手動バックアップ |

SQLiteとログ・実行状態はLinux側、録画と対応SRTはWindows側の専用ドライブに置きます。DBの保存済み設定を反映した実効録画ルートを、運用者が確認した他インスタンスのルートと照合します。フォルダ割当とセッション内の採番は永続化されます。確定ファイルの上書きを防ぎ、未確定ファイルと予約行を起動時に照合します。

録画とコメントは別ジョブです。録画履歴では最新ジョブ、セッション全体の欠損、各セグメントの検証結果を表示します。SRTは確定した動画ごとに生成し、入力版数の差やコメント書込の終了待ちを追跡します。削除では対象と方式を台帳へ記録し、実ファイルを照合した後にSQLiteを確定します。コメント期限削除はSRTの処理を先に行います。

システム状態は健康状態とイベント要約を表示します。ログ画面は内部JSON Linesと利用可能なイベント要約を対象に、サーバー側で絞り込みます。ログの記録時と閲覧前に秘密情報を除去し、実際に記録された識別子で関連画面をつなぎます。

## ツイキャス録画のプリロール除外

1. `recording/hls_playlist.py` は、公式APIの `current_live.hls_url` を起点に、許可されたマスター、メディア、初期化ファイルを解決します。明示キューの対、または先頭のプリロール用メディア・初期化URIと本編への切り替わりを検出できれば、FFmpegに渡すプレイリストから先頭を除外します。本編が共有する初期化情報や、前のセグメントから引き継ぐバイト範囲は維持します。
2. 録画中に `#EXT-X-MAP` の初期化情報が変わる場合は、境界までを前のFFmpeg入力で処理し、後続を新しい入力として同じジョブで続けます。この切り替えではネットワーク障害用の再接続回数を消費しません。HLSの取得に失敗した場合には、再接続と起点URLの再解決を行います。
3. HLS上で除外できなかった場合は、正式保存前の先頭候補を `recording/segments.py` で検査します。既知のプリロール1周期分のH.264スライスとAACパケットについて、順序と繰り返し数が両方のストリームで一致した場合に限り、`recording/manager.py` が仮録画と未確定行を取り除きます。採番とSRT生成は保存対象の録画だけに進みます。起動時の未確定録画の回収も同じ確定処理を使います。

詳細は [Featureの実装計画](../specs/001-initial-live-recorder/plan.md) と [検証状況](LIMITATIONS.md) を参照してください。
