# 構成

LiveRecorder は WSL2 上の 1 プロセスです。ブラウザ、CLI、REST は同じサービス層を呼びます。

- `web/` は HTML と `/api/v1` です。データベースへ業務ルールを直接書きません。
- `services/` が配信記録とジョブの開始・停止を決めます。
- `platforms/` が TikTokLive とツイキャス公式 API を隠します。
- `recording/` が Streamlink、yt-dlp、FFmpeg を子プロセスとして実行します。
- `comments/` がコメントの保存と SRT を担当します。録画の失敗では止めません。
- SQLite は Linux 側、動画と SRT は設定した Windows ドライブです。複数の試作インスタンスを同時に動かす場合、DB・ログ・runtimeだけでなく、動画・SRTの保存ルートも分離します。

画面の設計では、`/system` が健康状態とイベント要約を表示し、`/logs` が `ops/` の構造化ログ（ローテーション済みを含む）と利用可能なイベント要約を読み取り専用で参照します。ログの絞り込みとページングはサーバー側で行い、関連画面へのリンクは記録された識別子に基づきます。録画履歴は配信セッション単位で、最新ジョブの完了だけでなく全ジョブ・セグメント・欠損を集計します。SRTは有効な動画セグメントごとに生成し、コメント確定待ちと後着コメントの再同期を区別します。 論理削除済み配信者は同一アカウントの再登録時に履歴を維持して再有効化します。コメント保存期限（初期`0`＝無期限）が有効な場合は、収束済みセッションの対応SRTとSQLiteコメントを安全に期限削除し、動画・履歴は維持します。ファイル名の衝突はセッション固定識別子と上書き禁止の確定で防ぎ、**配信者フォルダの異ID安全名衝突はサービス横断・永続マッピングで分離する。既存アプリとの実効録画ルート重複は録画開始前に拒否する。**SRT再生成時は入力版数を公開前後に照合します。実装状況は [制限と未検証](LIMITATIONS.md#仕様変更への対応状況) を参照してください。

待ち受けは `127.0.0.1` だけです。ポート 0 のソケットは閉じずに Uvicorn へ渡します。変更操作は POST と CSRF、Host / Origin の確認が必要です。

詳細なフィールドと外部APIの検証結果は、初期の1 Feature（`specs/NNN-initial-live-recorder/`）の `data-model.md`・`research.md` 等で必要に応じて具体化します。成果物が未作成の場合は既存ファイルと仮定せず、作成・確認してください。
