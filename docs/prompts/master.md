## 2. Spec Kitによる一気通貫実装

既存のSpec Kitを使用してください。
再初期化は不要です。

今回はアプリケーション全体を1つのFeatureとして扱います。機能別のvertical sliceは別Featureにせず、同じ `tasks.md` 内の独立して検証できるタスク群に分割します。

Feature名：
initial-live-recorder

**実行前のFeature固定ゲート：** 現在の作業ブランチ、`.specify/feature.json`（存在する場合）と `SPECIFY_FEATURE_DIRECTORY`（設定されている場合）の指す実際のFeatureディレクトリ、および既存の `specs/*-initial-live-recorder/` を照合してください。**Gitブランチの切り替えだけではSpec KitのアクティブFeatureが切り替わったと判断しない**こと。既存Featureがあれば番号・既存成果物を保ったまま再利用し、重複Featureを自動作成しないでください。指す先の不一致があればSkillの手順に従って同一Featureを明示的に選択・設定し、再確認してから着手してください。不一致を解消できないときは別Featureへ書き込まないでください。

以下の工程を順番に実行してください。

1. speckit-specify
2. 必要に応じてspeckit-clarify
3. speckit-plan
4. speckit-tasks
5. speckit-analyze（可能な場合はチェックリストも作成・照合）
6. speckit-implement
7. speckit-converge

各Skillの実行手順は、
.cursor/skills/speckit-\*/SKILL.md
を参照してください。

CursorがSkillを直接呼び出せる場合は使用してください。
直接呼び出せない場合はSKILL.mdの手順を実行してください。

specs/NNN-initial-live-recorder/（`NNN` は事前確認した既存Feature番号を使用）
以下に必要な仕様成果物を作成してください。

spec.md、plan.md、tasks.mdは必須です。
research.mdは外部API実証結果、**data-model.mdはセッション横断採番・衝突時の固定識別子・複合外部キー・論理削除再有効化・コメント期限削除／削除復旧、contracts/は設定ON/OFF・状態遷移・期限削除・SRT版数競合・削除操作の入出力契約**の確定に必要なので初期Featureで作成してください。その他の成果物は必要に応じて作成してください。

正本の要件とSpec Kit成果物の対応関係を明確にしてください。
要件・受け入れ条件の追跡可能性を維持し、`RISK-01`〜`RISK-15` を該当する `tasks.md` の検証タスクと結び付けてください。**`requirements.md` §17の固定テストID `TC-xxx` と§23の受け入れID `AC-xxx` を変更・再採番しない**こと。初期Feature内に**要件追跡表 `traceability.md`** を作り、少なくとも「原本の節番号／`AC`／関連する `TC`／Spec見出しまたは要件ID／`tasks.md` タスクID／テストコード・実機検証証跡／結果（実機検証済み・ローカル検証済み・未検証・実装不可）」を記録してください。各 `AC` に最低1件の対応を求め、未対応・未検証を空欄にせず、その理由を記します。既存 `TC` で覆えない `AC` は原本§17に新規 `TC` を追記してから成果物を更新し、**既存IDを振り直しません**。P0/P1横断条件（状態遷移、採番、保存先分離、配信者フォルダ名衝突、ファイル名衝突、配信者再有効化、コメント期限削除と旧バックアップ、SRT版数、ログ読取・閲覧時秘匿）には単体・統合・障害テストを必ず設定してください。

重要：
`speckit-analyze` では **Spec間の照合に加え、`requirements.md` の各節と§23の全 `AC` が `traceability.md` でSpec／タスク／テストへ展開されているか**を原本から照合してください。重大な仕様矛盾、要件漏れ、依存関係の問題が見つかった場合は、該当する `spec.md`／`plan.md`／`tasks.md`／`traceability.md` を修正して再分析し、解消してから `speckit-implement` に進んでください。**実装前ゲート：** 設定変更時のジョブ停止・復帰と手動停止優先、`ENDING`／終了未確認の収束、同一セッションの番号予約とクラッシュ復旧、削除2方式と障害復旧、コメント期限削除（SRT先行・SQLite消去、生成／書込排他）と再登録、ファイル名衝突、SRT版数／公開競合・再同期、ログの安全な段階的読取について、遷移表・DDL／制約・API契約・テストが互いに整合することを確認します。RISK-01〜04の外部依存は未実証のAPIを保証せず、実施できなければ未検証・制限付きと明示します。
それ以外は各Skillの完了後、利用者の追加入力を待たず、次の工程へ進んでください。

ただし、Skillの必須ゲート、安全確認、

## 3. 実装戦略

全体を1つのFeatureとしますが、
tasks.mdは独立して実装・検証できる作業単位に分割してください。

次の順序で実装してください。

Phase 1：実現性調査

- TikTokLive / Euler Stream
- Streamlink / yt-dlp / FFmpeg
- ツイキャス公式API
- 匿名コメント番号の取得可否
- Python 3.12 / WSL2との互換性、および現行作業ツリーの `.python-version`・`pyproject.toml`・`uv.lock`・開発憲法等と解消記録の再照合
- API制限、ライセンス、利用条件

Phase 2：共通基盤

- 設定管理
- SQLite / SQLAlchemy / Alembic
- データモデル（`recording_segments.stream_session_id`、複合外部キー、セッション単位一意制約・予約／クラッシュ復旧、**配信者IDとWindows安全フォルダ名のサービス非依存・永続対応**、衝突時の固定名、配信者再有効化、コメント期限削除、削除時の参照整合性を実装前に確定）
- ログと例外処理（現行／ローテーション済みログのサーバー側読取・検索／ページング、**記録時＋旧ログを含む応答生成前のマスキング**も初期実装対象）
- 保存先管理（既存LiveRecorderの実効ルートとDB永続設定の照合、同一／親子パスの録画起動拒否）
- ジョブ管理と状態遷移

Phase 3：TikTok LIVE

- 配信者登録
- 監視と配信開始・終了検知
- 自動録画
- コメント収集
- SQLite永続化
- 録画セグメント確定
- SRT自動生成（後着コメントと公開前後の版数競合、0件時の旧SRT除去を含む）
- 再接続と障害記録

この段階でCLIによるEnd-to-End検証を実施してください。

Phase 4：ツイキャス

- Basic認証
- 配信監視
- 自動録画
- コメント収集
- 匿名番号取得の検証
- TikTokと共通の保存・管理機構との統合

Phase 5：Web UI / REST API

- 運用・データはダッシュボード（`/`）、配信者一覧（`/streamers`）、録画履歴（`/recordings`）、コメント（`/comments`）の順にする。
- 管理はシステム状態（`/system`）、ログ（`/logs`）、設定（`/settings`）の順にする。
- 録画履歴は配信セッション単位とし、コメントだけの記録も表示する。SRTの再生成は対象セグメントの詳細で扱う。
- システム状態は健康状態と診断を要約する。ログは構造化ログと利用可能なイベント要約を読み取り専用で参照し、**バックエンドの読取器が存在しない場合も実装して**サーバー側の検索・ページング・詳細表示と、記録された相関情報に基づく画面間の導線を提供する。
- 設定のコメント保存期限（初期`0`）と、期限削除済みコメント・SRTの非復元表示、および配信者再登録時の既存行復帰を確認する。
- 主要7画面と必要な下位ビューを実ブラウザで確認し、ログの秘匿・読取境界・取得失敗も検証する。

Phase 6：WSL2運用

- CLI
- プロセス管理
- 自動ポート割り当て
- endpoint.json
- Windowsサインイン後の自動起動
- 安全な停止
- 障害復旧
- SQLiteバックアップ（期限削除前のコメントが残る手動バックアップの運用警告・破棄／差し替え手順、手動復元時の期限再照合）

Phase 7：品質確認

- 単体テスト
- 統合テスト
- 障害テスト
- UI動作・表示検証
- 要件の受け入れ判定
- 導入・運用ドキュメント

ただし、詳細はrequirements.mdの§19および§23を正とします。

## 5. 品質と安全性

以下を必ず守ってください。

- 動く最小のE2E経路を先に完成させる
- 動画録画とコメント収集を独立させる
- 取得済みデータを保全する
- UNKNOWNをOFFLINEに変換しない
- 未収集と0件を区別する
- 未確定動画を完成扱いしない
- SQLiteをWSL2のLinux側へ置く
- 録画動画・SRTは指定Windowsドライブへ保存し、管理画面やAPIでダウンロードを提供しない
- 秘密情報をログやGitへ残さない
- 要件で除外された機能を実装しない
- 動作しないダミーUIを完成扱いしない
- 破壊的操作の安全性を確保する
- 公開配信または権限がある配信だけを対象とする
- DRM、CAPTCHA、アクセス制御等を回避しない

既存の別アプリケーションLiveRecorderを変更、
停止、削除しないでください。

試作環境と既存環境のDB、ログ、録画動画・SRTの保存先、
実行時状態ファイルが衝突しないようにしてください。録画先の**初期例は `/mnt/d/live-rec-lab/recordings`** です。環境変数を設定するだけで済ませず、DBの設定を反映した実効録画ルートを既存アプリ・別試作の実際の設定と照合してください。比較対象を自動取得できなければ運用者に設定確認を求め、衝突したルートで録画を起動しないでください。

## 7. 自律実装ループ

tasks.md生成後、実装を開始してください。

各タスクについて以下を繰り返してください。

1. タスクの目的と依存関係を確認
2. 必要なコード・テストを作成
3. 静的解析・テストを実行
4. 失敗した場合は原因を調査
5. 根拠に基づいて修正
6. 関連する回帰テストを実行
7. 完了条件を満たしたらtasks.mdを更新
8. 次の未完了タスクへ進む

途中でテストが失敗したまま放置しないでください。
単なる推測に基づく修正を繰り返さないでください。

外部サービスの実機検証が不可能な場合は、
モックによる検証と実機検証を区別してください。

実機検証ができないことだけを理由に、
他の独立した実装タスクを中断しないでください。

ただし、未確認の外部API契約を捏造してはいけません。

必要に応じて調査、局所的な試作、テストを実施し、
検証結果をFeatureのresearch.md等へ残してください。

## 8. 実装完了後のConverge

最初の全タスク実装が終了したら、
speckit-convergeを実行してください。

**元の `requirements.md` 全節・§17の `TC`・§23の `AC` を起点に** `traceability.md`、spec.md、plan.md、tasks.md、テストコードと実際の実装／実行結果を照合し、
次の問題を検出してください。**Feature成果物の内部整合だけで合格とせず、原本からの転記漏れを独立に確認**してください。

- 未実装
- 部分実装
- 仕様違反
- 必要なテストの欠落
- 原本 `AC`／`TC` の未対応、追跡表上の証跡欠落・未実施の完了誤認
- 動作しない機能
- 要求されていない余分な実装

Convergeによってタスクが追加された場合は、
speckit-implementで追加タスクを実装してください。

その後、再度Convergeを実行してください。

最大3サイクル繰り返してください。3サイクル後も要件未達や重大な不整合が残る場合は、完了扱いせず未解決として報告してください。

未解決の外部依存や実機検証事項は明示的に残してください。
無限ループや根拠のない修正は行わないでください。
