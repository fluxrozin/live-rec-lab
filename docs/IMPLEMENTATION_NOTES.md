## 1. この文書の読み方

本書は、2026-11-23に提供された `live-rec-lab.zip` の `.specify/bugs/` 下にある**12件の不具合記録（assessment / fix / test の36文書）**、および `specs/001-initial-live-recorder/` と `.specify/memory/constitution.md` を基にした再利用用メモである。ZIPにはアプリケーションの**ソースコード本体、稼働中のSQLite DB、動画実体、原本のHTTP/HLS応答**は含まれていない。したがって、以下の「実配信で確認」は、**添付された検証記録がそう報告している**という意味であり、今回ソースや録画を再実行・独立検証したことを意味しない。

文書間で競合する場合は `docs/prompts/master.md` に定める優先順位（`requirements.md` → `docs/UI_UX.md` → `.specify/memory/constitution.md` → `docs/design/` → Feature仕様 → 5つの運用補助資料（`docs/ARCHITECTURE.md`、`CONFIGURATION.md`、`INSTALL_WSL2.md`、`TROUBLESHOOTING.md`、`LIMITATIONS.md`）→ **本書** → `README.md`）に従う。本書の対策案には**その環境で成功した技法**と**まだ一般化できない仮説**が混在する。バイナリの絶対パス、閾値、バージョン、ライブラリの戻り値の形は、次回の実装環境で再検証する。

### 根拠の強さ

| 区分 | 意味 | 次回試作での扱い |
| --- | --- | --- |
| **実配信・実ファイルでの限定確認** | 修正後プロセスとDB/ffprobe/コメント行等を照合したという記録がある | 同一条件の再現性・記録範囲・残存不具合を別途確認 |
| **ローカル検証** | モック、ローカル映像、単体・回帰テスト等では通過した | 実サービスの互換性や欠落のない収録の保証にはしない |
| **部分確認／保留** | 一部の失敗経路は解消したが、目的の本番条件では未確認 | 完了と呼ばず、受け入れ条件と不足証跡を記録 |
| **失敗／旧知見** | 修正後にも症状が再現し、その後の別修正で改善した可能性がある | 時系列として保管し、古い修正を採用しない |

個別の `test.md` にある `verified` / `partial` / `failed` は**その不具合報告の判定**であり、アプリ全体の完成判定とは異なる。

## 3. TikTok LIVE：監視・セッションライフサイクル

### 3.1 通信失敗をOFFLINEに変換しない

- **観測**：TikTokへのHTTP応答前の接続失敗が、他のエラーと同じ「配信状態を確認できません」へ潰されていた。さらにHTTP 403/429/5xxの本文が空またはHTMLの場合、JSON解析が先に失敗し、レート制限・拒否の意味を保持できなかった。
- **有効だった対策**：HTTP status判定を本文解析より先に行い、`connect_error`、`timeout`、`invalid_json` 等の安定した診断コードを記録。サービス／配信者単位でバックオフし、同一エラーのイベント連打を抑止する。記録には対象、最終成功確認時刻、最後の失敗時刻、監視復帰を残す。
- **実績と限界**：モックによる回帰と常駐DB上の `OFFLINE` / `LIVE` 復帰を確認したと記録されている。ただし接続失敗の根本原因、DB上の判定と実際の配信状態の一致は未確認。試作では403等に300秒の待機を採用したが、**300秒を普遍的な仕様としない**。
- **転用するルール**：`LIVE` とRoom IDが揃ったときのみセッション開始。`liveRoom.status` の `2` はLIVE、`4` は終了候補、`1/3`・不正値・通信失敗は終了確定に使わない。APIとSDKの実際の版・契約を再確認する。

### 3.2 `UNKNOWN` / `ERROR` を配信終了の根拠にしない

- **観測**：監視エラーのたびにセッションが終了猶予へ入り、配信中にも `ENDED` → 同じ配信で新ジョブ起動を繰り返した。複数の無効FLVと空試行が重なり、実際に残った再生可能動画が短かった。
- **試行の修正**：配信の終了確認は**明確なオフライン信号＋猶予**で行い、`UNKNOWN`／通信エラーでは録画中ジョブとコメント収集を止めない。`last_seen_live_at` を更新するのは配信中を確認したときだけ。`ENDING` は猶予中の状態であり、`ENDED` と同じ停止命令ではない。
- **検証状況**：修正後の短い実配信で有効MP4・単一ジョブを観測。ただし本来問題になった「配信中に監視失敗が続くケース」は実配信で再現していない。
- **未解決**：監視が `OFFLINE` を返さず、録画プロセスだけ終了した際、セッションが長時間 `LIVE` に残る経路。期限切れの一律強制終了も、無期限LIVE放置も避け、矛盾状態の診断・追加照合・終了根拠を設計する。

### 3.3 同一監視エラーとエンジン切替警告を連打しない

- **観測**：毎回のセグメント作成でStreamlinkへ戻り、直後にyt-dlpへフォールバックするため、エンジン切替のイベントが対で増えた。同一の監視失敗もポーリングのたびに積み上がった。
- **対策**：同一ジョブ内では**実際にデータを書けたエンジン**を次の試行の第一候補とし、表示だけの「切替」を作らない。真の切替・新しい失敗内容・回復後の再発は残す。継続中の同一エラーは重複抑止し、持続時間・直近発生・件数は診断で追えるようにする。
- **検証**：実配信セッションで切替警告がジョブあたり1件になったと記録。ただしエンジン自身のエラー原因や、録画が再生可能かは別検証。

## 4. TikTok LIVE：コメント受信

### 4.1 SDKの開始完了と「受信終了」は別物

- **観測**：試作時点のTikTokLive 7.0.1では `client.start()` が**受信タスクを生成して返す**。開始コルーチンの戻りを接続終了と解釈した結果、遅れて入るコメントを収集前に切断していた。
- **修正**：当該版の戻り値契約に合わせて受信タスクの終了まで待機。受信終了後はコメントキューをドレインして永続化し、例外を上位の再接続処理へ伝播。キャンセル時はSDK受信タスク、WebSocket、HTTPクライアントを回収。
- **証跡**：遅延受信・例外・キャンセルのモックテスト、実配信で受信2件＝保存2件＝DB行2件の一致が記録されている。**配信に存在した全コメント2件の保証ではない**。収集ジョブは失敗件数0のまま `PARTIAL` で終わり、その理由の記録が不足。
- **次の実装**：使用版のSDKソース・戻り値契約を確認し、`start`/`connect`/`disconnect` とバックグラウンドタスクの生存管理をテスト。保存成功・失敗・切断理由・時間帯・最終受信時刻を別に記録し、「0件受信」と「収集未実施」を区別する。

## 5. 録画エンジン・ファイル確定・FFmpeg

### 5.1 長さ・音声・バイト数だけで `valid` にしない

- **観測**：FFmpeg 6.1.1がTikTok FLV内の映像コーデックを認識できなくても、ffprobeが音声と長さを返した。68MB級のFLVが `valid` に記録され、同名MP4が0バイトのまま残っていた。
- **修正**：録画対象の動画は、存在・非0バイトに加え、**映像ストリームの `codec_name` と出力ファイル自体のprobe結果**を確認する。映像不明、リマックス失敗、0バイトMP4は成功扱いにしない。破損物だけを安全に除き、元の有意な一時ファイルは回復可能な形で保存する。**元ファイルを再生可能と実証できない限り「代替形式で成功」としない**。
- **検証**：同じファイルのコピーでFFmpeg 6.1.1は拒否、Linux版9.1はHEVCとして読み取り `hvc1` のMP4へリマックス可能と記録。元のDBに残っていた誤判定行は自動修正していない。
- **注意**：HEVC MP4の `hvc1` タグは**実際にHEVCと判定できた場合だけ**付ける。`hvc1`を付ければ未知コーデックが直るわけではない。ストリームの存在確認と、映像内容の完全性は別の検査である。

### 5.2 ffmpegとffprobeは「同じ運用バージョンの組」を解決する

- **観測**：ホームに新しいLinux版9.1があっても、非対話シェルや常駐プロセスのPATHは `/usr/bin` の6.1.1を見ていた。`~/.bashrc`内の`export PATH=...`は非対話起動に反映されない場合がある。
- **対処**：ffmpegとffprobeをセットで実行可能・バージョン・対応コーデックを確認。試行時は `~/.local/opt/ffmpeg-9.1/bin` が揃う場合優先し、無ければPATHに戻す仕組みを採用した。**その絶対ディレクトリは試作マシン固有の経験であり要件に固定しない**。次回は設定可能な候補と機能チェックで解決し、実際に起動した子プロセスのバイナリを記録する。
- **証跡**：修正後プロセスで `hevc/hvc1` のMP4を生成し、ffprobeで映像と音声を確認したと記録。ファイルの完全再生と全配信の収録率は未確認。
- **落とし穴**：**コード差分を作っただけでは起動中のPythonプロセスの動作は変わらない**。ソース更新時刻とプロセス起動時刻、使用バイナリを突き合わせたうえで再検証する。Windows版 `ffmpeg.exe` をWSLのPOSIXパスへそのまま適用しない。

### 5.3 MP4の長さは「確定後のMP4」で測る

- **観測**：あるセグメントはDBで77.933秒、確定済みMP4のffprobeでは35.966秒だった。リマックス前のFLV/一時ファイルの長さを保存していたことが一因とされた。
- **修正**：正式に残す出力ファイルへリマックス／リネームした**あと**にプローブし直し、サイズ・長さ・コンテナ・コーデックとDBを照合する。残存する乖離はログ・診断で区別。SRTの時間範囲は確定した媒体の再生時間を基準にする。
- **限界**：ffprobeが成功しても、冒頭から終わりまで音声・映像が欠けていない保証はない。再生確認や、配信の実時間との差の確認が必要。

### 5.4 `ENDING`、子プロセス終了、手動停止、取消を分ける

- **観測**：短い終了猶予中の `ENDING` を録画終了扱いして、停止タイムアウト時にタスク取消が走った。ファイルが `pending` のままで、手動停止でないのに `CANCELLED` と表示された。
- **改善**：猶予中は録画を続け、明確な終了確定・手動停止を停止条件にする。停止・取消時にも子プロセスを回収して、残った有意な一時データを可能な限り確定し、状態を正しく区別する。起動時の回復処理は過去の異常 `CANCELLED` / `pending` も検査対象にする。
- **実績**：修正後の配信で `invalid`/`pending` がゼロのセッションが観測されたが、同一配信のジョブ分割や部分完了は残った。子プロセスの再試行が短時間で失敗する原因は未取得のstderrがあり未解決。

### 5.5 空試行、セグメント連番、ジョブ状態は別管理

- **観測**：0バイトで破棄した試行まで連番を消費し、同じ配信に複数ジョブが作られるとファイル名が `_s001` に戻ることがあった。また空再接続だけでも `PARTIAL` と判定されていた。
- **改善**：**同一配信セッションに残すセグメント**を基準に番号を連続させる。空で保管価値のない試行はセグメント行・番号を使わない。ただし接続断による**取得欠損と再試行の事実**は `collection_gaps` とジョブログに保持。ファイルを残した `invalid` と、何も残らない空試行は区別し、過去のファイル名・番号をUI表示の都合で振り直さない。
- **実績**：修正後のセッションでは番号1～4が残り、ジョブ27単体は `COMPLETED` と記録された。一方、番号1～3のファイルは `invalid`、前のジョブは失敗、欠損区間61～68もあった。**単一ジョブの完了をセッション全体の成功と誤読するUIが残った**。
- **結論**：ジョブ単体の `COMPLETED` は「そのジョブ内の確定結果」の意味に限定する。**セッション集計の要約は、全ジョブ・全セグメント・欠損・コメント収集を見て**、有効ファイルと未回復の失敗を並列に知らせる。過去の `invalid` を新しいジョブの成功で隠さない。

## 6. ツイキャス：公式HLSとプリロール

### 6.1 録画元URLを守り、入力失敗を切り分ける

- **観測**：ffmpegのHLS入力で400/404に遭遇し、公式 `current_live.hls_url`、tc-hls、入力ヘッダ、アクセス制限が混在して原因が追いにくくなった。
- **試行時の方針**：公式APIが返す公開配信用 `hls_url` を優先し、FFmpegではURIを独立した引数にする。`-icy 0`、適切なUser-Agent / Refererを入力より前に渡す構成をローカルで検証。実際のURLや署名・認証情報をログへ出さない。合言葉・会員限定配信は回避して録らない。
- **限界**：この局所修正の `test.md` は `partial`。ffmpegオプションの正しさと**実配信で途切れず録れるか**は別。試作では一度tc-hlsを試し、後に公式URL優先へ戻している。実装案を混在させない。

### 6.2 プリロール除去はファイル名だけで判定しない

- **観測**：ツイキャスの試行で、約6.037秒・41KBの動画だけが残った。最初はHLSのセグメント名に `preroll-` がある場合の除去を実装したが、名前に一致しない公式プレイリストでは効かなかった。
- **試行の修正**：**初期の短いプレイリストを本編と断定してffmpegに渡さない**。プレイリスト更新と `#EXT-X-DISCONTINUITY` を見て、試作時は最初の不連続の手前を除き、加工後はローカルのループバックプレイリストからコピーした。別ホストの参照を無条件に追わず、外部接続先を制限した。
- **証跡**：検証記録では、同じ約6秒から**119.765秒のMP4**へ改善した実配信が1件あり、利用者はプリロールが除去されたと確認した。試作の待機上限20秒、暫定判定7秒は**条件依存のヒューリスティック**であり、将来の固定要件ではない。
- **残リスク**：最初の不連続より前が本編の冒頭である場合に、**本編まで削る可能性**。タグが来ない配信、複数の不連続、プログラム・プレイリスト更新の遅延での動作は未確認。毎回無条件に冒頭を切る処理を正規仕様にしない。元プレイリストと生成物を保護した検証用の診断要約で条件を確認する（署名URL・本文を平文ログに残さない）。

### 6.3 6秒の動画、空SRT、終了後再接続は別の不具合

- 本編を録れず短いセグメントしか無いと、その長さを基準とするSRTが0cueになることがある。この場合は`generated`の空ファイルではなく、**対応する時間帯に字幕対象コメントなし＝`skipped`**と表す。ただし**そもそもコメントを収集できていない**場合は別の取得失敗・未収集として表示する。
- 録画ジョブがまだ動いていることを、配信がLIVEである証拠にしない。オフラインが確定し猶予が過ぎれば再接続を止める。
- 有効動画があっても、その後に再接続失敗・欠損がある場合はジョブやセッションの**不完全性を残す**。成功ファイルの存在は全区間の成功を意味しない。

## 7. UIで露呈した「観測結果の誤読」

### 7.1 層別の状態を混ぜない

画面上の「配信中」「録画中」「最新録画ジョブ完了」「セッションの録画取得結果」「コメント収集中」「SRT生成済み」は異なる事実である。録画履歴の**一覧1行＝セッション**、セグメント詳細は**全ジョブにまたがる確定済み・無効・未確定の履歴**を保持し、最新ジョブの単独状態をセッション全体の状態にコピーしない。

推奨表示例（あくまで実際に情報が取得できる場合）：

```text
録画結果：有効 1本／要確認 3本　　欠損あり
最新ジョブ：完了　　過去ジョブ：失敗あり
コメント収集：不完全（理由：取得不能）
```

**「完了」と「欠損あり」は矛盾しないことがある**。前者がジョブの局所状態、後者がセッション全体の取得品質だからである。情報源が不十分なら「状態を集計できません」とし、完全取得と偽装しない。

### 7.2 エラー文と最終状態を混同しない

`last_error` に過去の「録画ファイルが空です」が残る一方、新しい有効セグメントが作られた事例があった。エラーの有無だけで現在の成功・失敗を決めず、**発生時刻・対象ジョブ・再発／回復状態**を示す。同一エラーの連打抑止は、根本原因の解消とは別。`UNKNOWN` のときは確認できた最終時刻を添える。

### 7.3 欠損・不一致とSRTの状態を見せる

- `collection_gaps` があるのに詳細画面で見えなかった事例がある。少なくとも**欠損の存在と影響領域**をセッション詳細で示し、該当時刻・理由を展開可能にする。
- DBが示す `.mp4` が存在せず `.part.ts` しか残らないケース、残ったMP4の長さとDBの記録が違うケースを、正常な動画として扱わない。
- SRTは**生成済み／未生成／生成失敗／同期不能／対象区間に字幕なし（スキップ）**を区別。0cueの空ファイルを「生成成功」にしない。
- ログへの導線では原因を断定できない情報を推測で紐付けず、サービス・ジョブ・セッション・時刻の既知情報を渡す。

## 8. 試作の進め方と検証の作法

### 8.1 修正を有効にする手順

1. 不具合を**症状・再現条件・時系列・事実／仮説**に分解し、`.specify/bugs/<slug>/assessment.md` に記録する。
2. 仕様が変わる場合は `requirements.md` と（表示に影響すれば）`docs/UI_UX.md` を先に更新する。具体的な試行値はここではなく本書やfeatureの `research.md` に置く。
3. 変更ファイルとテストを狭くし、`.specify/bugs/<slug>/fix.md` に差分・設計理由・不採用案を残す。
4. `ruff`、対象pytest、回帰pytestでローカル検証する。**パスしたテスト数を異なる時点で合算して最終値にしない**。
5. 実装が常駐プロセスに反映されたことを、**起動時刻、ファイル更新時刻、使用ffmpeg/ffprobe、インスタンスID**で確認する。既存アプリとはDB/ログ/録画先/ランタイム状態が衝突しないよう分離する。
6. 実サービス検証は**公開配信または許可済み配信**で行い、監視応答・録画・コメント・DB・最終ファイル・SRTを**同じセッションID**で相互照合する。
7. `.specify/bugs/<slug>/test.md` に、実配信で確認／ローカルで確認／未確認／失敗を別々に書く。再発は `assess` へ戻し、根本原因を再評価する。

### 8.2 次回試作で回すべき再現テスト

| 優先度 | 再現テスト | 合格とみなすために必要な証拠 |
| --- | --- | --- |
| **P0** | TikTokのLIVE中にHTTP403/タイムアウト/不明statusを模擬 | 元のセッション・録画・コメントを不用意に終了せず、復帰時に重複ジョブが起きない |
| **P0** | Streamlink失敗→yt-dlp切替→途中書込→再試行→手動停止・強制停止 | 無意味な切替連打がなく、ファイルを確定・保護し、欠損と各停止理由が残る |
| **P0** | コーデック不明のFLV、HEVC/H.264、0バイトMP4 | 不明な映像をvalidにしない。ffmpeg/ffprobe選択が再現でき、最終MP4のprobeとDBが一致する |
| **P0** | 同一配信で複数録画ジョブと空の試行 | 番号は**残したセグメントだけ**に付け、ジョブまたぎで重複せず、過去失敗と欠損を一覧／詳細から見失わない |
| **P0** | TikTokLive `start()` が受信タスクを返すモック | 遅延コメントを保存、受信例外を通知、停止でタスク解放。実配信では保存件数を別途確認 |
| **P0** | ツイキャスの短い先頭プレイリスト→不連続→本編 | 先頭だけで確定せず、本編と時間長を照合。**本編の先頭を削らない**検証も行う |
| **P1** | SRTの対象区間にコメント0件／収集未実施／時刻不明 | `skipped`・未収集・失敗を区別し、SQLite原文を維持する |
| **P1** | 旧DBにinvalid・pending・過去のファイル名の飛び | 旧データを無断で書き換えず、照合で不一致を可視化する |
| **P1** | Webの最新ジョブ完了＋前ジョブ失敗 | 「セッション全体の完全成功」に見えず、録画ファイル・欠損・コメント・関連ログに到達できる |

**実配信の受け入れで別途見ること**：録画ファイルが再生できる、音声が存在する、録画区間が配信実時間に見合う、冒頭／末尾の欠落がない、コメント収集が本当に継続する、SRTの時刻が再生位置と合う。ffprobe・DBで `valid` と出ただけでは最後の3項目を検証したことにならない。

## 9. 未解決・設計上の判断を残す事項

1. **セッション集計の定義**：複数ジョブ・複数セグメントに `FAILED`/`invalid`/gapがあるとき、どの条件で「一部取得」と要約するか。最新ジョブだけに依存しない判断を実装する。
2. **TikTokの監視が永続的に不明な場合の収束**：継続中録画を誤停止させず、孤立セッションを残し続けない状態照合・タイムアウト・アラートの方針。
3. **録画エンジンの短命終了**：Streamlink/yt-dlpのstderr、exit code、実際の出力バイトを採取し、合法的な別経路以外の回避はしない。
4. **FFmpegの導入方法と互換性**：試作時の9.1固定パスは移植性が低い。更新時点のLinuxバイナリとprobe互換性を検証する。
5. **ツイキャス本編冒頭の保全**：最初の不連続がプリロール境界とは限らない。実配信の複数パターンで精度を検証する。
6. **実ファイル・DBの不一致の診断**：過去のinvalid、0バイトMP4、残存 `.part.ts`、誤ったdurationを一括自動修正せず、検証・手動回収できる方法を設計する。
7. **コメント収集の理由不明PARTIAL**：受信0件と取得失敗、終了前に終了した理由、SDKの例外を追跡する。
8. **旧データと修正後データの差**：修正で既存行が遡及的に正しくなるとは限らず、UIは旧データの問題を隠さない。
9. **ツイキャス匿名コメント番号・Euler無料枠**：今回の12件には実用性の決定的な検証が無い。元の仕様にある「実測・一意照合が必要」の保留を維持。
