# LiveRecorder — UI/UX要求・設計仕様書

> UI固有の恒久仕様の正本。製品機能、URL、制約、データの意味は `docs/requirements.md` に従う。実装技術と契約は `docs/system-design.md` とFeature契約を参照する。節番号は追跡表との対応のため安定して管理する。選択・実行手順の正本は `prompts/redesign-ui.md`。

## 1. 適用範囲と確定前提

### UIに直接関係する確定前提

- 初期対象：TikTok LIVE、ツイキャス。日本語・Windows PCブラウザ専用。モバイル専用UIは不要。
- ログイン・ログアウト画面、ユーザープロフィールのUIは不要。
- Web上での動画再生・ライブプレビュー・録画動画と字幕のダウンロードは対象外。通常運用の録画動画と字幕はWindows側の保存先から開く。隔離開発時は専用Linux領域を使用する（要求§15.2.1）。
- コメント字幕は、対応する録画セグメント単位でSRTを自動生成し、必要に応じて再生成する。画面では生成状態を確認できる。
- フロントエンドは`docs/requirements.md`にあるJinja2＋HTMX＋軽量JavaScriptを前提とし、UIのためだけに大規模SPAを導入しない。
- **単一のライト系テーマ**を採用し、表示フォントのみ設定画面で2種類から選択可能とする。

## 2. ゼロベースのデザイン課題

### 2.1 デザイン課題の検討手順

`prompts/redesign-ui.md` の現状調査・設計コンセプト検討を参照する。

### 2.2 ビジュアルの裁量と確定制約

**デザインの見た目はゼロから考えてください。** 背景・表面・境界・アクセント、幅、角丸、余白、影、行高、アイコン等の具体値は採用デザインで決める。探索・比較・選択は `prompts/redesign-ui.md` §15 に従い、初期実装・単独再設計ともに3案を提示し、利用者が採用案を明示選択する。選択待ちがターン終了を伴う場合も同一Featureの選択記録から再開し、AIは代行選択しない。

次の事項は**自由裁量ではなく確定条件**です。

- 画面全体は**ライト系の単一テーマ**とする。ダークテーマ、テーマ切替、OSテーマ自動追従は設けない。
- 状態の意味を変えない。**配信中は緑系、録画中は赤系、コメント収集中は青系**を使用し、停止・警告・エラーと区別する。ただし正確な色コードは新デザインのコントラストを考えて決めてよい。
- 状態は色だけで示さず、文字や記号等を組み合わせる。録画中のロゴ・ファビコンの状態変化など、原本で定めた表示要件を維持する。
- 設定で選べる表示フォントは**「Windows標準」と「Noto Sans JP」の2種類のみ**。初期値と指定は以下を守る。

| 表示名                | フォント指定                                                  | その他                             |
| --------------------- | ------------------------------------------------------------- | ---------------------------------- |
| Windows標準（初期値） | `"Segoe UI Variable", "Segoe UI", "Yu Gothic UI", sans-serif` | `palt` 指定なし                    |
| Noto Sans JP          | `"Noto Sans JP", sans-serif`                                  | `font-feature-settings: "palt" 1;` |

- フォント選択は全画面へ反映し、画面遷移・再読込後も保持する。日本語・英数字・数値が混在するプレビューを用意し、選択中と保存済みの違いを明確にする。
- 数量・時刻・容量・経過時間の比較では、数値の整列、単位、桁数、日付形式を一貫させる。長い識別子・ファイル名・パス・技術ログは全文確認やコピーを可能にする。
- 色・文字・余白・角丸・アイコン・動きなどの設計判断を**再利用可能なデザイントークン／共通部品**として統一する。特定の4pxグリッドや固定色表は必須にしないが、体系のない場当たり的な数値は避ける。
- Windows PCブラウザでの可読性・キーボード操作・アクセシビリティを優先し、`prefers-reduced-motion` を尊重する。

### 2.3 新デザインの品質基準

落ち着いた業務用の運用コンソールとして、**正確、機能的、見通しがよく、高密度でも疲れにくい**体験を目指してください。過度なヒーロー、無意味な統計カード、装飾的なグラフ、ネストしたカード、派手なアニメーションは、利用者タスクに寄与する理由がなければ採用しないでください。必要なラベル・危険操作の説明・失敗理由は、ミニマルさを理由に削除しないでください。

### 2.4 設計自由度の扱い

画面別記述の情報・操作・状態と確定順序・表示契約は維持する。列・領域・ドロワー等の具体配置は設計仮説であり、同等以上の識別性・比較性・操作効率を根拠にAIが選択・検証できる。

拘束力は要求§1.3を正とする。8画面・URL・意味色・単一ライト・フォント2択・利用者の3案選択・業務状態の正確さ・危険操作防止はMUST。視覚階層と主要導線・操作可能性は維持する。内部インタラクションの詳細はSHOULD、追加品質試験はMAY。§5.4.1〜2、§6.3.1、§6.4.1、§6.7、§8.1.2、§13.7、§14.3〜5、§16の詳細方式・検証は以下の等価な簡易方式を認める。

| 対象             | 初期に許容する簡易実装                                                                       | 追加品質                                                             |
| ---------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 定期更新・安定ID | 操作中は対象DOMを更新しない。古い応答を破棄し入力・対象を保護。IDで誤対象を防ぐ              | 可視行の相対位置・全展開の厳密復元                                   |
| フォーカス       | 標準HTMLと安全な起点復帰。検索・ページ送りはブラウザ標準遷移でも可                           | 詳細な位置復元・通知制御                                             |
| 通知             | 成功は短時間、重要エラーは手動閉鎖または永続インライン表示                                   | ポインター／フォーカス中のタイマー停止（自動消去しない通知には不要） |
| カスタム順       | 標準的なドラッグライブラリまたは同等の簡易ドラッグと上下移動。明示確定・全順序・版照合を維持 | 端スクロール等の細かな操作最適化                                     |
| URL・履歴        | 標準GETフォーム・リンクで条件とページを復元。定期更新は履歴を増やさない                      | 詳細な閲覧基準の復元                                                 |
| キーボード       | ネイティブHTML・標準dialog等を優先。独自ARIA部品を作らない                                   | 高度な複合部品の専用操作（採用する場合はその意味に適合させる）       |
| 状態表示         | 主要状態・未知状態と意味色を共通化し、誤成功を防ぐ                                           | 全状態の組合せ自動検査                                               |

実現方法を単純化しても、未保存入力の消失・旧応答による確定値の巻戻し・危険操作の誤再送・誤対象への操作・操作不能・秘密露出は許容しない。合理的な差分と延期項目は記録し、個別承認は不要。

### 2.5 説明文に依存しないUI（構造的自己説明性）

**「文字を追加して説明する前に、レイアウトそのものを改善する」ことを全画面の設計原則としてください。** 目標は文字数の最小化ではなく、利用者が必要な情報と操作を、最小限の解読負荷で正しく把握できることです。

- 画面の目的、情報同士の関係、状態、操作の優先順位は、まず**情報の分類・近接配置・整列・余白・サイズ・文字の強弱・コントラスト・適切なコンポーネントの選択**で表す。見た目だけ整えた後に説明文を貼り付けて補わない。
- UIが分かりにくい場合、次の順序で修正する：**①情報の分類と粒度 → ②グルーピングと配置 → ③視覚階層・整列・余白 → ④操作部品と状態表現 → ⑤必要な短いラベル → ⑥それでも不可欠な補助説明**。説明文の追加を最初の解決策にしない。
- 関連する情報は近くに置き、異なる責務の情報は適切な距離または控えめな区切りで分ける。区別のためにカード・枠線・色面を無条件に増やさない。
- 画面見出しの直下に「この画面では〜できます」のような自己説明的な副題を機械的に追加しない。見出し・ラベル・バッジ・ツールチップ・説明文で同じ内容を繰り返さない。
- 画面ごとに適した表示形式を選択する。比較・検索が中心ならテーブル、状態の即時把握ならコンパクトなインジケーター、属性の確認ならキー／値、補足診断なら詳細展開を優先し、すべてを均一なカードへ変換しない。
- 低頻度の技術情報は、必要時に詳細を開ける**段階的開示**を基本とする。ただし、異常の存在、影響、重要な状態、回復に必要な操作を隠してはならない。
- アイコンや色だけで意味を説明しようとしない。操作名・数値の単位・状態名・エラー理由・破壊的操作の影響など、判断に必要な文字情報は残す。短文化によってアクセシビリティや安全性を損なわない。
- グラフやアニメーションは、実データの比較・変化・状態遷移の理解に明確に寄与する場合に限る。文章を減らすためだけの意味のない図表・ピクトグラム・動きを追加しない。

**補助説明文の追加判断**：その文章を一時的に隠したとき、主要な情報の関係と操作が分からなくなるなら、まず配置とラベルを見直してください。なお、安全上の警告や専門的な制約まで削除するためのテストではありません。

### 2.6 AI生成UIの定型化・過剰装飾を防ぐ

Claude Opus 5.5等のUI生成モデルが採用しがちな**汎用SaaSテンプレート、説明過多、カードの多層化、装飾の定型化**を無批判に持ち込まないでください。

- 見栄えのためのヒーロー領域、大きなスローガン、毎回のアイキャッチ文、不要な集計カード、架空のKPI、装飾的なグラフ、意味のないピル型バッジを追加しない。
- カード内カード、深い枠の入れ子、過大なパディング、無意味な角丸・シャドウ、過密なアイコン・アクション列を避ける。余白は「大きいほど上質」ではなく、**関係性と一覧性を伝える適切な密度**で評価する。
- 一部の画面だけ別の色・角丸・フォント・影・アイコン体系に変えない。個別画面の改善では既存のデザイントークン・共通部品を優先し、局所的なCSS上書きで見かけだけ整えない。
- 参考画面・デザインSkillは**情報の整理、視線誘導、密度、操作配置、状態表現**を分析する材料とし、色や装飾だけを模倣しない。既存UI・参考事例の視覚様式を採用する義務はない。外部Skillの一般的な美意識より、本書と`docs/requirements.md`を優先する。
- 表示内容は実際の利用者タスクから決める。仕様書で長く説明されている機能を、それだけで大きなUI要素へ昇格させない。仕様外の「便利そうな」機能や指標は実装しない。
- 視覚的な一貫性とユーザビリティに関する判断を、実装モデル自身の「洗練された」「分かりやすい」という自己評価だけで確定しない。実表示と操作で検証する。
- **明示的に禁止する定型装飾**：Interフォント、紫のグラデーション、光る／発光するボタン、セリフ体見出しの一語だけを斜体にする演出、4枚の統計カードを横一列に等間隔で並べるだけのダッシュボード冒頭。既定のフォント2択を厳守し、フォントを勝手に増やさない。
- **「AIっぽい」を印象論で終わらせない**：無根拠なKPIカード、無意味なアイコン・ピル・大きな見出しと副題、均等カードの反復、カード内カード、不要なグラデーション・影・余白、画面目的に合わない装飾的グラフを具体的に指摘する。検出した場合、色だけ塗り替えず、情報の分類・粒度・配置から修正する。
- 明確な禁止事項以外は、デザイン上の定型を**必要性・用途・実データ・操作効率**で判断する。一般的なUI部品そのものを禁じたり、奇抜さのために学習済みの操作慣行を壊したりしない。

### 2.7 UI文言：必要なラベルは残し、冗長な説明だけを削る

- 見出しは情報の対象、ボタンは実行する操作、状態ラベルは現在の事実を**短く具体的な日本語**で示す。技術的な内部処理名・英語表現の直訳・宣伝調のコピーをそのままUIへ持ち込まない。
- 「録画中」などの状態を、見出し・バッジ・本文で三重に説明しない。単一の視覚的まとまりで識別できるようにする。ただし、別々の文脈で必要な状態表示の反復は許容する。
- ラベルのないアイコンだけの操作へ置き換えて、説明文を減らしたことにしない。誤認しやすい操作は可視ラベルを優先し、ツールチップは代替の唯一の説明手段にしない。
- エラー、未保存変更、制約、権限・対象、不可逆な操作、反映時期など、事前判断に必要な内容には短い補足を残す。補足が長くなる場合は詳細展開へ分離する。
- 文字数・語数に一律の上限を設けない。文章を削った結果、意味・状態・操作対象が曖昧になったなら設計上の失敗として扱う。

### 2.8 情報デザインの共通契約

情報の意味・粒度・優先順位・比較単位・操作対象の関係を先に決め、その後で見た目を設計する。以下は全画面共通の表示契約であり、特定の画面構成や参考サイトの外観を採用する指示ではない。

- 主情報（対象を識別する名前、判断すべき状態、本文等）と補足情報（ID、サービス、時刻、単位等）は文字ウェイト、サイズ、色、近接配置によって区別する。補足情報も読めるコントラストを確保する。
- 関連属性は複合セル（主情報＋補足情報の二段または近接配置）にまとめ、不要な列を増やさない。独立した状態や数値の比較が必要な属性は、それぞれのラベルと比較軸を維持する。列を減らすために意味の異なる値を無名で連結しない。
- 一覧は見渡しやすさと選択の速さ、詳細は根拠と網羅性、本文閲覧は読書の連続性を優先する。同じ粒度の行は同じ順序・揃え・単位を用いる。長い文字列は必要に応じて折り返し・省略・全文展開を選び、情報自体を失わない。
- 強調は一次判断、影響のある異常、主要操作に絞る。二次指標は密度の高い補足表示を基本とし、全指標を均等な大型カードへ昇格させない。表示件数・検索結果・取得範囲・実際の全件数を混同しない。
- 画面別パターンを満たしつつ、外観・具体値はゼロベース探索と採用案の決定で定める。

## 3. 情報アーキテクチャ：8つの主要ナビ＋下位ビュー

### 3.1 「主要ナビゲーション数」と「画面数」を分ける

**サイドバーは「運用・データ」5項目、「管理」3項目の計8つの主要ナビゲーション項目**で構成します。主要画面は8画面であり、その下に配信セッション詳細、ログ詳細、追加・編集ドロワー、設定内セクションなどの下位ビューを設けます。これらの下位ビューは主要8画面に数えません。

| グループ     | サイドバー表示名   | 主要URL       | 役割・利用者の問い                       |
| ------------ | ------------------ | ------------- | ---------------------------------------- |
| 運用・データ | **ダッシュボード** | `/`           | 今、何が起きているか？                   |
| 運用・データ | **配信者一覧**     | `/streamers`  | 誰を監視し、何を収集するか？             |
| 運用・データ | **録画履歴**       | `/recordings` | どの配信で、何が記録・取得されたか？     |
| 運用・データ | **コメント**       | `/comments`   | 誰が、いつ、何を投稿したか？             |
| 運用・データ | **音声字幕**       | `/speech`     | 文字起こしと統合字幕はどこまで進んだか？ |
| 管理         | **システム状態**   | `/system`     | 何が正常で、どこに問題があるか？         |
| 管理         | **ログ**           | `/logs`       | いつ、どの処理で、何が記録されたか？     |
| 管理         | **設定**           | `/settings`   | 監視・保存・表示の条件をどう変更するか？ |

- 「配信者一覧」は`docs/requirements.md`の「配信者管理」、「録画履歴」は同名の既存機能に対応する**UI表示名**です。表示名を変更しても、既存の`/streamers`・`/recordings`、機能、保存対象、制約は変更しないでください。
- `/recordings`の一覧は引き続き**配信セッションを基本単位**とし、録画の有無とコメント収集の有無を独立して見せます。「録画履歴」という名称を理由に、動画ファイルがないセッションを除外しないでください。
- `/logs`は**Web UIの主要画面のURL**として扱います。ログの取得API・収集基盤・データモデルが既存実装にあると仮定してはなりません。既存の表示可能なログ情報に基づいて実装し、必要な取得手段が欠けている場合は不足を明示してください。
- **システム状態は健康状態・影響・診断の要約、ログは時系列の詳細調査**を担います。同一のログ全文一覧を両画面で重複させないでください。
- 新しい独立した「ライブ状況」「ストレージ」「イベント履歴」等の主要ナビ項目は設けません。ログ以外の情報は上記の8画面の関連領域・下位ビューへ整理してください。
- ログイン、ログアウト、ユーザー管理、モバイル専用画面、動画プレイヤー、未対応サービスのナビは追加しません。

```text
│  │   └─ 関連セッションへ移動
│  └─ 音声字幕
│      ├─ 待ち行列・状態・再生成・ASS状態
│      └─ 発話本文検索／録画詳細
└─ 管理
   ├─ システム状態
   │   ├─ 構成要素・録画方式・保存先の状態
   │   └─ 警告／エラー要約 → 対象の録画履歴／ログ
   ├─ ログ
   │   ├─ 時系列一覧・検索・絞り込み
   │   └─ ログ詳細・関連セッション／配信者への導線
   └─ 設定
       └─ 監視／録画・保存／コメント・SRT／音声字幕／表示／詳細設定
```

- 配信セッション詳細は**録画履歴の下位ビュー**とし、ダッシュボードや検索結果から直接開けるようにします。サイドバーに独立項目を増やしません。
- システム状態で分かった異常の詳細調査は、可能な範囲で**ログ画面の該当条件**へ導きます。ログを読んで判明した影響対象からは、録画履歴のセッション詳細等へ戻れるようにします。
- 配信者の追加・編集とログエントリの詳細は、必要に応じてドロワー／ダイアログ／行展開で扱い、主要ナビを増やしません。
- 主要URLは要求仕様§11.1に従い、音声字幕は `/speech`、発話本文は下位ビュー `/speech/cues` とします。ログの絞り込みや詳細のために新しい公開URL・APIを無条件に増やさず、提供されるデータ取得手段、クエリ、部分更新を活用します。

### 3.3 画面を分ける判断基準

1. **目的が異なるか**：全体監視／配信者設定／配信単位の確認／コメント閲覧・横断検索／音声字幕管理・発話本文／システム診断／ログ詳細調査／全体設定は分けます。
2. **情報の粒度が異なるか**：集約KPI、配信セッション、セグメント、コメント、診断要約、ログエントリを混在させず、概要から詳細へ進ませます。
3. **利用頻度が異なるか**：毎回見る健康状態はダッシュボード・システム状態へ、必要時に深掘りする詳細ログはログ画面へ置きます。
4. **操作の危険度が異なるか**：通常の閲覧と削除・停止操作を明確に分離します。
5. **画面間移動を減らせるか**：関連情報へ直接遷移できるなら新たな独立メニューや詳細画面を追加しません。

### 3.4 共通アプリケーションシェルを新規設計する

共通シェルの位置・寸法・見せ方は、固定サイドバーや既存レイアウトを前提とせずにゼロから設計してください。**「運用・データ」5項目／「管理」3項目というナビゲーションの分類・名前・順序、および各主要URLは確定**です。ユーザーが迷わず現在地を把握でき、下位ビューから親へ戻れることを優先してください。

- サイドバー等のナビゲーション表現を選ぶ場合、PCの作業幅と情報密度、現在地、グループの見分けやすさを根拠にサイズ・余白・アイコンを決定する。固定の220〜250px幅や旧画面の配置には拘束されない。要求§11.1・TC-034の「サイドバー表示名・表示順」はこの主要ナビの論理的な名称・順序を指し、固定サイドバーという物理配置を追加の合格条件にしない。
- ページ名、情報の取得時点、必要な主要操作を一貫した場所に示す。配置は自由だが、**取得時刻が不明な場合に現在時刻で代用しない**。
- アプリ独自の画面全体再読み込みボタンは設けず、ブラウザ標準の再読み込みを使用する。データの自動更新や表示鮮度は第5章に従う。
- 下位ビューでは親への戻り方と一覧の検索条件を保つ。破壊的操作は通常操作と誤認しない配置・表現にする。
- テーブルには必要な幅を与え、PCのウィンドウ幅や表示倍率が変わっても主要操作を利用できるようにする。

### 3.5 共通シェルの情報配置契約

- 主要ナビの選択中項目は視覚的な選択表示と `aria-current` 等で識別する。下位ビューでも親の主要ナビを維持し、パンくずまたは同等の明確な現在地・親への導線を置く。画面名と対象の名前・IDを混同しない。
- ページ見出し、ページ固有の主要操作、表示時点は全画面で予測しやすい配置とする。関連操作を近接配置し、行に属する操作をページ全体の操作と混同させない。説明だけの副題やロゴ下の宣伝文句は必須としない。
- ヘッダーの表示時点は取得成功の事実、各行・診断の時刻はその対象の観測時点とする。表示の更新と外部状態の確認は別である。共通ロゴ・ファビコンは§5.3〜5.5に従う。
- 固定・追従領域を採用する場合も、狭いPCウィンドウや拡大表示で本文、表、ダイアログ、フォーカス対象を覆わないことを確認する。アプリ全体の再読込操作、認証・テーマ切替・モバイル専用ナビは追加しない。

- 開発者モードでは共通シェルに「開発者モード」「隔離データ」を文字で常時表示する。通常運用では追加表示しない。サーバーの実効起動コンテキストに基づき、Webからのモード変更・専用画面・新テーマは設けない。

## 4. 情報の階層と画面間の動線

### 4.1 共通のデータ粒度

- **配信者**：監視の対象とその設定。録画ジョブそのものと同一視しない。
- **配信セッション**：一回のライブ配信を表す、記録の最上位の単位。
- **録画セグメント**：一つの配信セッションに属する個々の動画ファイル。セグメントごとにコメントSRT・音声SRT・ASSの対応と生成状態を示す。
- **コメント**：配信セッションに紐づく投稿。動画がなくても検索・閲覧対象となり得る。
- **障害イベント**：問題の発生箇所、影響対象、時刻、理由、確認できる範囲の回復情報を扱う。
- **録画ジョブ**：同一配信セッションに複数存在し得る実行単位。ジョブ単体の「完了」は、セッション全体の無欠損取得を意味しない。
- **ログエントリ**：実際に記録された時刻・重要度・出力元・本文・関連対象等を扱う。障害イベントと同一視せず、ログに存在しない構造化情報を推測で補わない。

**録画の成功とコメント収集の成功を「配信成功」の1状態にまとめないこと。** 配信セッションの概要の下に、録画・コメント・SRTの状態をそれぞれ表示してください。

**セッションの録画結果は最新ジョブ単独では代表させないこと。** 有効な録画・無効／未確定のセグメント・過去の失敗・欠損を一緒に把握できる情報階層とし、詳細で個々のジョブをたどれるようにしてください。

### 4.2 代表的なタスクフロー

| 利用者がしたいこと                     | 開始地点 → 到達先                                              | 維持する文脈                     |
| -------------------------------------- | -------------------------------------------------------------- | -------------------------------- |
| 現在の録画を確認                       | ダッシュボードの稼働中セッション → 該当セッション詳細          | 対象配信、表示時点               |
| 配信者を追加・編集                     | 配信者一覧 → 追加／編集ドロワー                                | 一覧の並び・絞り込み             |
| 配信者の過去の配信を確認               | 配信者一覧の行 → その配信者で絞り込んだ録画履歴                | 配信者フィルター                 |
| 昨日のコメントだけ取得できた配信を探す | 録画履歴 → 対象セッション → コメント                           | 日付・配信者・セッション         |
| 動画・SRTの状態を確認                  | 録画履歴 → セッション詳細 → 対象セグメント                     | セグメント連番、動画とSRTの対応  |
| コメント本文を検索                     | コメント → 検索結果 → 関連セッション                           | 検索条件・ページ位置             |
| 録画失敗の理由を調べる                 | ダッシュボードの警告 → システム状態／対象セッション → 関連ログ | エラー対象・時刻・関連セッション |
| 容量不足を確認する                     | ダッシュボードの容量表示 → システム状態／設定の該当セクション  | 保存先・利用可能容量             |
| 特定時刻のエラーを詳しく調べる         | システム状態の警告 → ログの絞り込み／詳細                      | 時刻・重要度・出力元・対象       |
| ログから影響を受けた配信を確認する     | ログの関連対象 → 録画履歴の該当セッション詳細                  | 配信者・サービス・セッション     |

- **主要な導線はコンテキストリンクを優先する。** 画面の一覧へ戻って再検索しなければ対象に辿り着けない設計を避ける。
- 一覧 → 詳細 → 一覧に戻る際、できる限り検索語、選択フィルター、並び順、ページ番号、スクロール位置を保持する。
- 「録画履歴へ」「コメントを見る」「関連ログを見る」などのリンクは、移動後の画面の文脈を具体的に示す。
- ブラウザによるページ再読み込みは画面データの再取得に限り、外部サービスへの監視要求を追加発生させない。外部サービスへの手動再確認機能を別途提供する場合に限り、その目的と影響が分かる名称で表示する。

### 4.3 配信セッションの扱い

| 録画         | コメント収集 | ユーザーへ見せるべき内容                             |
| ------------ | ------------ | ---------------------------------------------------- |
| 成功         | 成功         | 動画セグメント、コメント件数、対応するSRT            |
| 成功         | 失敗・不完全 | 動画と、コメント欠損・失敗理由                       |
| 失敗・未取得 | 成功         | コメントが残っていること、動画がない理由             |
| 無効         | 成功         | コメントだけを収集した配信であること                 |
| 失敗・無効   | 失敗・無効   | セッションが存在する場合は、記録された状態・障害内容 |

- 上表は**画面上の分類例**であり、内部のジョブ状態を新設する指示ではない。表示は`docs/requirements.md`に定義された状態と実際の取得データに従う。
- 動画のないセッションでも、コメントが取得できていれば**コメント検索へ直接進める**ようにする。
- **SRTは確定済み録画セグメントとの対応が基本**であり、録画セグメントのないコメント専用配信にSRTの生成・再生成操作を表示しない。
- 録画履歴は録画ファイル一覧と同義ではない。セッションを上位、動画・SRT・欠損を下位として整理する。

## 5. 共通の状態表現・情報鮮度

### 5.1 状態の原則

**配信状態、録画状態、コメント収集状態、コメントSRT・音声SRT・ASS状態、画面の取得状態、操作結果は独立して表現**してください。色だけでなく状態名と必要に応じた記号・説明を併記し、状態の意味を作り替えないでください。

| 分類        | UIで区別するもの                                                                                         |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| 配信        | 配信中／オフライン／不明／確認エラー／監視停止、必要に応じて確認中                                       |
| 録画        | 待機／録画中／再接続中／確定処理中／完了／一部取得／失敗／停止等、実際に取得した状態                     |
| コメント    | 待機／接続中／収集中／再接続中／完了／不完全／失敗／無効等、実際に取得した状態                           |
| 音声SRT     | 待機／処理中／保留／完了（発話あり・無発話）／失敗／対象外／削除済み                                     |
| 統合ASS     | 未生成／待機／生成中／暫定／生成済み／片側・欠損あり／失敗／スキップ／再同期待ち／期限削除済み／削除済み |
| コメントSRT | 未生成／生成中／生成済み／生成失敗／スキップ（字幕対象なし）／保留等、実際に取得した状態                 |
| 画面データ  | 初回取得中／取得済み／正常に0件／検索結果0件／取得失敗／古い情報／取得不可                               |
| 操作        | 入力中／送信中／受付済み／実行中／完了／失敗／結果未確認／競合（発生した場合）                           |

`UNKNOWN`を「オフライン」に、録画失敗を「配信終了」に、件数未取得を「0件」に、受付済みを「完了」に、取得できない容量を「0GiB」に変換しないでください。映像の欠損とコメントの欠損を混同しないでください。

「最新ジョブ：完了」と「セッション内に過去の失敗／欠損あり」は両立します。**ジョブ状態、セッションの取得結果、ファイル検証状態**を同じ「完了」ラベルに丸めないでください。録画ファイルの時間長が取得できても、映像・音声の検証や本編収録を確認できていなければ、完全取得と断定しません。

### 5.2 典型的な表示パターン

| 状況                               | 表示の原則                                                                                                          | 避ける表現                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 初回読込・部分更新中               | 対象領域のみ「取得中」・控えめな進捗・`aria-busy`                                                                   | 根拠のない無限スピナー              |
| データが存在せず正常               | 「まだ記録がありません」＋必要なら次の操作                                                                          | 無言の空白、通信失敗と同じ表示      |
| 絞り込みに一致しない               | 「条件に一致する記録はありません」＋絞り込み解除                                                                    | 初期状態の空表示と同一視            |
| `UNKNOWN`・監視エラー              | 「状態不明」「確認できません」＋最終正常確認日時                                                                    | 「オフライン」「終了」と断定        |
| 更新失敗・古い情報                 | 「更新失敗」「前回取得 HH:MM:SS」と表示し、必要ならブラウザ標準の再読み込みを案内。前回値はラベルや控えめな枠で識別 | 以前の値を最新の値として表示        |
| UI側で情報取得不能                 | 範囲を明示して「現在の状態を取得できません」と表示し、必要ならブラウザ標準の再読み込みを案内                        | すべて0件、全録画が停止したとの断定 |
| 操作受付・処理中                   | 「受付済み」「処理中」を区別し、完了は結果確認後に表示                                                              | クリック直後に成功確定              |
| 競合・内容が変化                   | 保存できなかった理由、再取得・確認の導線                                                                            | 黙って上書き、成功通知              |
| 不完全・欠損あり                   | 対象機能、区間、理由、詳細への導線                                                                                  | 全量取得と誤認させる表示            |
| 削除保留・ファイル使用中・容量不足 | 対象・理由・再試行の可否・次にできること                                                                            | 処理が終わったとの断定              |

- 古い行の区別は、可読性が下がる過剰な淡色化や斜体だけに頼らず、**「前回取得値」ラベル・時刻・控えめな区切り**を優先する。
- 配信一覧の各行と、画面全体の最終取得時刻が異なる場合は混同させない。時刻が分かる粒度で表示する。
- `未取得`／`0件`／`取得失敗`／`対象外`／`無効`／`未生成`の違いは、短い日本語で一貫して伝える。
- **字幕対象なし（スキップ）**／**収集未実施・収集失敗**／**字幕生成失敗**も区別する。SRTファイルがない理由を一律に「生成失敗」としない。
- 録画の「一部取得」「要確認」は、後続ジョブの正常終了だけで過去の欠損・無効セグメントが隠れない範囲で表現する。取得範囲の根拠が不十分なときは、取得品質を未判定として表示する。

### 5.3 状態の強調と文言

- 配信中は緑、録画中は赤、コメント収集中は青で表示する。**録画中の赤い点は穏やかなパルス＋「録画中／REC」**、**エラーは静止した警告・×アイコン＋「失敗／エラー」**とし、同じ赤でも誤認させない。アニメーションは`prefers-reduced-motion`で抑制する。
- アプリロゴはシステム全体の録画状態に連動させ、待機中はアクセントの青、録画中は赤（中央の点が穏やかに明滅）、状態不明は警告系の色・形状で区別する。ブラウザのファビコンも状態に合わせる。ただし「配信中」だけでは録画中ロゴに切り替えない。
- 稼働中／停止／警告／異常／不明を意味的に区別する。黄色は注意、赤いエラーアイコンは異常を示すなど、色だけでなく文字・記号・動きの有無で判別可能にする。
- 文字・アイコン・色・必要な説明を組み合わせ、状況に応じて情報／警告／異常／取得中／不明の記号を用いる。装飾用記号には`aria-hidden`を使い、意味はテキストで伝える。
- 状態の要約には「何に問題があり、どこへ影響するか」を入れ、長い技術的理由は詳細へ置く。
- エラーと警告の見た目を区別する。取得不能な情報を成功・正常に見せない。

### 5.4 自動更新と表示の鮮度

- 上部の共通位置には**「表示時点（最終取得）」のみ**を配置し、アプリ独自の画面再読込ボタンは置かない。必要に応じて各セクション・各行の最終確認時刻も示す。
- 定期更新は `docs/requirements.md` §11.1 の設定間隔（既定5秒）に従い、必要な領域だけを更新し、フォーム入力中、ダイアログ表示中、ドラッグ中、テキスト選択中、ブラウザタブが非表示のときには、**操作を妨げないよう更新を停止・延期**する。
- 更新再開後も、スクロール、フィルター、入力内容、選択範囲、フォーカス、ログ詳細の展開状態を可能な限り維持する。行の並びが変わる場合は不必要な画面ジャンプを避ける。
- 前回値の表示中に更新失敗した場合は、その値の取得日時を残す。次の取得成功を確認するまで新しい情報として表示しない。
- 画面全体の再読み込みはブラウザ標準機能に委ねる。自動更新失敗時は前回取得時刻と失敗を表示し、必要ならF5／Ctrl+Rを案内する。SRT再生成など機能固有の再試行操作は残す。ブラウザ再読み込みによって外部サービスの監視枠を消費する手動確認を実行しない。

操作開始後に届いた定期応答は、送信時に安全であっても適用直前に再判定する。検索条件・ページ・対象ID・設定保存版が変わった場合は旧応答を適用しない。設定入力中の値と選択カテゴリ、未保存状態を保全し、エラー時は入力を戻さず訂正を可能にする。非表示／操作による延期中は取得時刻を進めず、復帰時は現在条件の取得を一度だけ行って定期更新へ戻る。取得失敗や録画状態不明は、最後に確認した状態とその鮮度を示し、古い状態で録画マークを巻き戻さない。

録画詳細では壁時計の録画範囲と確定メディアの再生時間を異なるラベルで表示し、試行のエンジン・中断理由・欠損時刻の根拠を識別できるようにする。時刻不明は不明として表示する。コメントの欠損・保留超過・接続先確認失敗は正常0件と混同しない。削除の世代不一致・未接続・部分失敗は成功とは異なる結果を表示し、安全な再試行が可能な対象だけ案内する。システム状態の照合は確認総数と表示範囲・未確認を区別する（製品要件§6.5.1、§7.4、§10.4.1、§10.5、§14.2.1）。

#### 5.4.1 安定した識別子による表示状態の復元

- 部分更新の対象領域・データ行・操作部品・詳細展開に、既存の管理IDと部品種別からなる安定した識別子を割り当てる。配信者ID（DB ID）、セッションID、セグメントID、コメントID、発話の所属成果物版とcue識別子、照合実行IDと分類、ログの既存の安定位置（ファイル世代／位置等）、設定カテゴリと設定キーを利用する。表示名、行番号、並び位置、本文、同名ラベルだけでは同一対象と判定しない。DOM ID等の実装形式は任意だが、同一画面内で一意であり、同じ対象の再描画で安定すること。存在しない管理IDを新設したことにしない。
- 詳細復元を採用する場合（SHOULD）は更新前に対象領域のフォーカス、展開中の詳細、選択カテゴリ、適用済み条件、スクロール基準を記録する。スクロールは可能なら可視の安定行と表示領域内の相対位置を基準とし、ページ全体・内部スクロール領域を区別する。行の追加・削除・並び替えで単純な座標復元だけに頼らない。入力・選択・ドラッグ・ログ詳細読書等を破壊する更新は§5.4に従って延期し、再描画後の復元で代替しない。
- 更新適用直前に現在の画面、条件、対象ID、要求世代、操作状態・確定版を再照合する。適用が認められた応答だけで復元し、利用者が別の部品へ移動済みなら古いフォーカスを奪い返さない。消失した対象には同じ一覧の近傍に残る安全な操作部品、結果見出しまたは親への導線へ必要な場合だけ復帰し、同名の別対象・破壊的操作へ移さない。消失を知らせる必要がある場合は簡潔な通知を一度だけ行う。

#### 5.4.2 利用者操作と自動更新のフォーカス契約

| 契機                               | フォーカスと閲覧位置                                                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 定期更新・延期からの復帰           | 現在の操作対象、閲覧基準、展開状態を保全し、フォーカスを奪わない。自動スクロール・結果見出しの反復読み上げをしない     |
| 明示的な検索・条件変更・ページ送り | 最新要求の結果確定後に結果件数・見出しを通知し、必要な場合は結果先頭／見出しへ誘導。入力途中の検索補助は入力位置を維持 |
| トグル・行操作の保存               | 操作した対象と部品に維持または復帰。対象消失時は§5.4.1                                                                 |
| 入力エラー                         | 入力を保持し、必要なカテゴリを開き、最初の訂正可能な項目へ誘導                                                         |
| ダイアログの閉鎖                   | 起点へ復帰。対象が消失した場合は安全な代替位置                                                                         |

利用者操作より古い応答によってスクロール・フォーカス・通知・URL・確定値が巻き戻らないこと。非表示・延期中の情報時点を進めず、復帰時の取得は既存の§5.4の規則に従う。

### 5.5 状態インジケーターと時間表示の文法

一覧の既定表現はコンパクトなアイコン／記号＋短い状態名とし、背景色付きバッジは重要な例外や詳細上部の要約など、必要性がある箇所に限定する。下表は意味を割り当てるための表示パターンであり、内部状態や新しい状態遷移を追加するものではない。

| 意味                   | 推奨する記号・挙動                  | 色・表示上の契約                               |
| ---------------------- | ----------------------------------- | ---------------------------------------------- |
| 配信中                 | 点または配信を表す記号＋配信中      | 緑系、録画とは独立                             |
| 録画中                 | 赤い点＋録画中／REC、穏やかなパルス | 赤系、実際の録画状態だけ                       |
| コメント収集中         | コメント記号または点＋収集中        | 青系                                           |
| オフライン             | 中空円等＋状態名                    | 中立色、確認済みの場合だけ                     |
| 待機・処理中・再接続中 | 時計・進捗・循環矢印等＋各状態名    | 待機と実行・復旧を区別。実行中に限り必要な動き |
| 完了・検証済み         | チェック等＋何が完了したか          | 成功色。全区間完全取得とは別                   |
| 一部取得・要確認・保留 | 三角等＋理由の要約                  | 注意色。重要な理由は表示する                   |
| 不明・未確認           | 疑問符等＋状態名・確認時刻          | 注意または中立色、正常・0に置換しない          |
| 失敗・異常             | 静止した×等＋失敗／エラー           | 異常色。録画の赤い点と区別                     |
| 停止・無効・対象外     | 停止／横線等＋個別の状態名          | 中立色を基本に、理由を区別                     |

- 状態の意味は共通部品で一元管理し、状態の種別（配信／録画／コメント／字幕等）を必要な文脈で明示する。同じ記号だけで意味の異なる状態を判別させない。全行を色付きピルで埋めたり、同じ異常を多数の装飾で反復したりしない。
- 録画連動ロゴは外形と占有寸法を維持し、待機・録画中・不明を§5.3の色と内部記号で識別する。ファビコンも同じ確認済み状態を参照し、画面遷移・部分更新で不必要に初期化しない。録画が確認できないときは不明とし、古い応答で状態を逆転させない。動き抑制時も静的記号・ラベルで判別できること。
- 経過時間は確認済みの基準時刻と現在の表示時点を区別する。状態が最新かつ稼働中と確認できる間は、ブラウザで開始時刻から壁時計の経過を描画してよい（APIへの追加要求なし）。検知から／録画経過／推論処理経過等の基準を明示する。状態が古い・不明・終了・更新延期中の場合は進行中と断定せず、確認済みの値・時点を示す。確定メディア長や実取得時間を時計で増加させない。
- 再接続・進捗・トグル確定・行移動・ダイアログ・通知の動きは状態理解や操作結果に寄与する範囲に限定する。定期更新そのものに点滅や行全体の再出現を付けない。速度・緩急は採用時に決定し、`prefers-reduced-motion` では動きに依存しない表現へ切り替える。

### 5.6 共通状態表示変換器

- 状態種別、既存の状態コード、観測時点・根拠、設定値、画面取得の鮮度を共通の表示変換器で解釈し、日本語ラベル・意味色・記号・動きの可否・必要な補足を共通部品へ供給する。一覧、詳細、概要、診断、ロゴ／ファビコンで同じ状態の意味を変えない。表示変換器は読取専用であり、業務状態・取得品質・録画有無・DB・設定を変更しない。
- 初回監視未実施は確認中／未確認、監視停止は停止、通信失敗は確認不能として区別し、確認根拠のない初期値をOFFLINE等の確定値へ変換しない。最新の確認済み状態と前回値・取得失敗・未知コードを区別する。未知コード、欠損フィールド、未対応の状態種別でも描画を壊さず、状態不明／未確認と表示し、安全に秘匿処理された診断情報がある場合だけ確認可能にする。推測で新しい内部状態を定義しない。
- 全既知状態・初回未確認・未知コード・古い状態・不整合入力を表示変換のテストに含め、色・文字・記号・アクセシブルネーム・動きが§5.1〜5.5に一致することを確認する。録画マークは既存のシステム全体の確認済み録画状態を参照し、画面のフィルター結果や一覧件数だけで推測しない。

## 6. 共通コンポーネントとインタラクション

### 6.1 共通コンポーネント

App Shell、Primary Navigation（サイドバー等）、Page Header、Breadcrumb、Section Header、Button、Icon Button、Dropdown、Toggle、Input、Select、Checkbox、Metric、Status Indicator、Capacity Bar、Data Table、Search／Filter Bar、Pagination、Modal／Drawer、Confirmation Dialog、Tooltip、Toast、Inline Alert、Empty／Loading／Stale State、Key–Value Details、Log Table、Log Filter、Log Detailsを一貫した見た目と挙動で実装してください。

- 同じ操作には同じラベル・形・配置・フィードバックを使用する。アイコンのみの操作にはアクセス可能な名前とツールチップを付ける。
- 一覧の操作は必要最小限を直接見せ、編集・削除・詳細等は適切なアクションメニューへ整理する。
- 項目が多い詳細画面は、短い概要の下に表・属性一覧・展開可能な詳細を置く。巨大なカードや長文を並べない。
- 入力の検証エラーは該当フィールドの近くに表示し、エラー箇所へフォーカスできるようにする。

### 6.2 操作結果と二重送信の防止

- トグル、保存、再生成、停止・再開、削除には、処理中・確定済み・失敗・結果不明を適切に表示する。
- **トグル操作は実際の反映を確認してから確定表示**する。失敗・結果未確認のときに、画面上だけ成功状態へ固定しない。
- 操作中は対象のボタン等を必要な範囲で一時無効化し、重複操作を防ぐ。別の配信・別のセグメントの操作まで不必要に止めない。
- バックエンドが受付と完了を区別する操作では、UIも「受付済み」「実行中」「完了」を区別する。完了確認方法を表示し、確認できない場合は「結果未確認」とする。
- 明示的な拒否・競合で当該操作の不成立が確認できた場合はその理由と再取得・再編集の導線を示す。応答消失や不明な失敗では変更なしと断定せず、§6.2.1に従う。既存データを無言で上書きしない。

#### 6.2.1 操作結果の確定と受付照合

変更操作には、送信前の最後の確定値、送信中、受付済み／実行中、確定成功、明示拒否／競合、部分失敗、結果未確認を区別して表現する。受付は完了ではない。保存中は対象の確定表示を維持し、保留中の値がある場合は意図した変更として区別する。成功応答または照合済み結果だけで値・順位・結果を確定し、必要なら短い遷移・行内表示・通知で対象と変更内容を示す。

- 明示拒否で当該操作の不成立が確認できた場合は最後の確定値を保ち、競合時は最新値と未保存入力を区別する。タイムアウト、切断、応答欠落、処理結果を保証しないHTTPエラーは「結果未確認」として扱い、失敗／未変更を断定しない。
- 結果未確認時は現在値・設定版・業務ジョブ／削除操作IDを再取得する。安全な同一操作のみ再送可能とし、危険な新規実行・逆操作を自動で行わない。現在値だけで当該操作の実行有無を断定せず、判断不能なら理由を表示する。
- 遅延応答は同じ対象・操作にのみ関連付け、画面切替後の別操作を上書きしない。最新の業務値を再取得する。
- 対象範囲の競合する操作は結果確認まで抑止する。他対象の独立操作は妨げない。トグル等の成功アニメーションは確認後のみとし、読み上げを含む意味的な確定表示を演出のために旧値へ逆戻りさせない。

### 6.3 通知と障害

- 成功は控えめなトースト、継続中の問題は該当領域のインラインアラートで示す。異常の概要を示す画面から必要に応じてログへ進めるようにし、通知本文へ大量の技術ログを埋め込まない。
- エラーの通知は読める時間を確保し、必要な場合は詳細を開けるようにする。無限に増えるトーストの山は作らない。
- エラー本文は操作を続けるための説明を先に書き、長い技術的メッセージは展開・コピー可能にする。
- 通知がキーボード操作とスクリーンリーダーで理解できるよう、`aria-live`や適切なフォーカス制御を使用する。

#### 6.3.1 通知のライフサイクル

成功・情報は短時間の控えめな通知、警告・エラーは十分な確認時間または利用者による明示閉鎖とする。表示時間・最大同時表示数は採用済みデザインのトークンとして決定する。必要な通知には閉じる操作とアクセス可能名を設ける。自動消去する操作可能な通知ではポインター／フォーカス中の消去停止を推奨する。重要通知を手動閉鎖または永続インライン表示にする簡易方式でもよい。通知を閉じても継続中の異常や結果未確認が解消したことにはしない。

同一対象・操作・理由に対する通知を重複して積み上げず、別操作の結果を混同しない。定期更新の連続失敗は当該領域の鮮度とインライン表示を更新し、周期ごとにトーストや読み上げを繰り返さない。重要なエラー・継続中の問題は該当領域に残し、関連ログ・診断への既存導線を提供する。自動通知でフォーカスを奪わず、成功等は控えめな通知領域、緊急性のあるエラーは適切な警告として必要時のみ通知する。

### 6.4 危険な操作と未保存変更

- 削除などの破壊的操作は、対象名・対象数・ファイルや記録への影響範囲・復元可否を確認ダイアログに示す。既定のフォーカスは原則として**キャンセル**にする。配信者削除は履歴ありなら監視対象からの除外（論理削除）であり、既存履歴・動画を暗黙に消さない。同じサービス・IDを再登録するときは既存行の再有効化として扱い、過去履歴は保持し、監視・録画・コメントの3設定は再登録時の明示値で適用する。
- 録画・監視のON/OFF設定と、進行中ジョブの停止・再開は別の操作として見た目も文言も区別する。
- 設定・編集フォームで未保存の変更がある場合は明示し、移動時には意図せず破棄しないよう配慮する。
- ドロワー・ダイアログはEscや閉じる操作、フォーカスの閉じ込めと閉鎖後の復帰を一貫させる。

#### 6.4.1 共通操作部品のキーボード文法

ネイティブHTML要素を優先し、採用するコンポーネントの意味に適合するキーボード操作・アクセシブルネーム・選択／展開状態を共通化する。見た目だけのARIAロールを付けない。

| 部品                                              | 操作契約                                                                                                                                                                                                                                               |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 行アクションメニュー（ARIA menu型を採用する場合） | Enter／Spaceで開く・選択、上下矢印・Home／Endで項目移動、Escapeで閉じて起点へ復帰、Tabで通常のフォーカス順へ離脱。無効項目は実行不可。領域外クリック・サイズ変更時は安全な閉鎖または位置調整。通常リンク群を採る場合はその意味に対応する標準操作に従う |
| タブ（設定カテゴリ・照合分類等）                  | タブとパネルを関連付け、選択状態とフォーカスを識別。方向に対応する矢印とHome／End、必要なEnter／Spaceで選択。非表示パネルはフォーカス対象外。自動更新で選択を変えず、検証エラー時は該当パネルへ移動                                                    |
| モーダル確認・編集                                | 開いた対象を明示し、初期フォーカス・Tab範囲・Esc／キャンセル・閉鎖後の復帰を統一。破壊的操作の既定フォーカスは原則キャンセル。入力中の取消は未保存確認に従い、送信後の閉鎖を業務操作の取消と誤認させない                                               |

削除確認は対象ID・対象数・削除対象・保持対象・復元可否・現在の拒否／保留条件を既存の業務契約から明示する。必要な確認チェックは対象やダイアログを開き直すたびに初期化し、他対象の確認を流用しない。表示された確認にかかわらずサーバー側の版・世代・操作ガード・受付契約を維持する。メニューやダイアログ等を画面外に配置したり、固定領域でフォーカスを覆ったりしない。

### 6.5 数値・日時・単位

- 日時は設定済みタイムゾーンで表示し、必要時に`JST`等の基準を併記する。相対表示には絶対日時を確認できる手段を用意する。
- 件、秒、分、GiB等の単位、数値の丸め、右揃え、日付表記を画面間で統一する。
- 取得できない容量や件数は`0`で埋めない。Windows側の保存先パスとその他のパス表記を誤認させない。

---

#### 6.5.1 日時・経過時間の表示契約

日時・期間・媒体内位置は共通整形器で処理する。表示タイムゾーンは共通設定に従い、日付フィルターの境界は統合設計§17.2の変換規則に従う。表示用の省略・丸めをDB時刻、検索条件、安定ソート、同期計算へ逆適用しない。

| 用途               | 表示上の契約（例は形式候補）                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 共通表示時点       | 当日で日付が明白なら `15:32:08`、日付をまたいだ前回取得は日付を併記                                              |
| 一覧・最終確認     | 同一年は `11/24 15:32` 等、監視・ログ等の必要な精度では秒を表示。年が異なる場合は年を省略しない                  |
| 詳細・コピー       | 確認可能な絶対日時、表示タイムゾーン／UTCオフセット、記録されている精度。DSTで同一時刻表記が重なる場合も識別可能 |
| 録画範囲           | 開始・終了を区別し、日付／年をまたぐ場合は双方の境界が明白な表記                                                 |
| 経過・媒体長       | `HH:MM:SS` 等、24時間を超えても時間を0に戻さない。壁時計経過・実取得時間・メディア長は別ラベル                   |
| コメント・発話位置 | 取得済みの媒体内オフセットと基準を表示し、必要時にミリ秒精度を確認。時刻根拠なしは未確認、0秒と区別              |

元データにない秒・ミリ秒・タイムゾーン根拠を補って精密な実測と見せない。相対時刻だけに依存せず、詳細・キーボードで利用可能な表示等で絶対時刻を確認できるようにする。自動更新時の壁時計経過は§5.5の鮮度・稼働条件に従う。日付／年境界、タイムゾーン切替、DST、24時間超、同一秒に複数件、未確認の値を検証する。

### 6.6 複合セル・検索・共通デザインシステム

- 複合セルは対象の同定、日時の範囲、容量とファイル数、状態と確認時刻等、意味が近い属性に使う。数値列は右揃え、時刻・経過・容量・件数等は可能な限り等幅数字（`font-variant-numeric: tabular-nums`）で揃える。Noto Sans JPの `palt` と数字の整列を両立し、必要なら数値領域の機能指定・桁位置を調整する。フォントの選択肢は増やさない。
- 一覧の検索領域は主条件と詳細条件を分ける。詳細条件が閉じていても適用中の条件と件数を確認し、個別解除・一括解除を既存の検索契約の範囲で行えるようにする。結果件数、現在ページ、表示範囲を統一した位置・形式で示す。条件なしの空、検索結果なし、未取得、取得失敗は別の空状態とする。検索・ページングの値は統合設計§17を参照する。
- 行の主リンク、件数に紐づく既存の詳細リンク、低頻度操作のメニューを区別する。件数リンクは対象・移動先が明確なアクセス可能名を持ち、取得不能・削除済みを数値リンクで偽装しない。行全体のクリックだけに依存せず、選択・コピー・キーボード操作と競合させない。
- 共通トークンは少なくとも背景・表面・選択／ホバー、境界・フォーカス、主／補足／無効テキスト、アクセント、状態の意味色、タイポグラフィ（サイズ・ウェイト・行高）、余白、角丸、影、操作部品・アイコンの寸法、動き、重なり順を管理する。実装で場当たり的な値を散在させない。具体値は採用済みデザインに属する。
- ナビ、状態、操作、サービス識別に一貫した線画等のアイコン体系を採用する。例えば一覧／録画／コメント／音声／診断／ログ／設定、検索／絞り込み／期間／その他／移動／編集／削除を役割別に割り当てる。特定ライブラリ・ピクトグラムの形状は固定せず、装飾記号と意味を持つ記号、サービス記号と状態記号を区別する。静的資産は既存のCSP・ライセンス契約に従う。

### 6.7 URL・ブラウザ履歴の状態契約

- 既存APIで許可された閲覧モード、対象ID、適用済み検索条件、時刻順／一覧ソート、ページ番号・ページサイズをURLで表現し、初期表示・再読込・共有した同一ローカルURLから同じ条件を再現する。設定カテゴリ等の画面内選択はURLフラグメント等でもよい。編集中の未保存値・秘密情報・一時的なメニュー状態はURLに含めない。配信者の永続表示順・設定値の正本はSQLiteであり、URLで上書きしない。
- 明示的な検索確定・ページ送り・詳細遷移は通常のブラウザ履歴に反映する。検索条件・ソート・閲覧モードを変えたときは該当結果の先頭ページへ戻し、条件解除もフォームとURL・結果を一致させる。部分更新でも利用者が戻る／進む操作を行えば、該当履歴の条件と結果を復元する。範囲外ページは統合設計§17.2に従い条件を保持して有効ページへの導線を示す。
- 定期更新・表示鮮度・通知・メニュー開閉は履歴項目を増やさない。明示操作のURL反映は現在の要求世代の結果と整合させ、古い応答やキャッシュで確定値を巻き戻さない。戻る／進む・親への遷移で閲覧基準とフォーカスを§5.4.1〜2に従って復元し、必要なら保存済みデータを再取得する。未保存フォームからの離脱は§13.7に従い、取消時にURLと表示を不整合にしない。
- URLパラメータは既存の許可キー・型・上限・エンコード・安定順に従い、任意の遷移先、外部URL、無効なIDを信頼しない。履歴・部分更新から副作用を再送しない。ブラウザ履歴に残る検索語の取扱いに配慮し、秘密情報を検索条件・ログ・証跡へ混入させない。

## 7. ダッシュボード（`/`）

### 7.1 主な役割

**「今どうなっているか」を短時間で把握する画面**とします。障害の影響と診断概要はシステム状態へ、時系列の技術ログはログへ、個別の動画・SRT・コメントの確認は該当する配信セッション詳細へ進ませてください。

### 7.2 情報の優先順位

1. **優先KPI**：監視対象配信者数、現在配信中、現在録画中、コメント収集中。
2. **稼働中セッション**：配信者、サービス、配信状態、録画状態、コメント収集状態、開始時刻・経過時間（取得できる場合）。行から**該当セッション詳細へ直接移動**できること。
3. **異常・容量**：容量警告や、稼働に影響する直近の問題を必要な場合だけ簡潔に示す。問題箇所へ移動できること。
4. **補足KPI**：本日の録画件数、本日のコメント件数、録画ファイル総容量、保存先の空き容量。
5. **最近の録画**：直近の録画をコンパクトに表示し、詳細へ直接進めること。

- 件数の大小だけで異常を推測せず、機能別の状態に基づいて表示する。
- 「現在録画中」の集計は実行中の録画ジョブに基づける。「最近の録画」は最新ジョブ成功だけでセッション全体を無欠損と表現しない。過去の失敗が影響する場合は、必要最小限の「欠損あり／要確認」等を示して詳細へ導く。
- 異常がないときに巨大な正常バナーや空の警告領域を占有しない。
- 進行中のセッションがない場合は「現在配信中の対象はありません」と表示し、通信障害による状態不明と区別する。
- 一部のセクションが取得失敗しても、正常に取得できたセクションは使えるようにする。
- 保存容量からはシステム状態の保存先情報または設定の保存条件へ、警告からはシステム状態・関連ログ・該当セッションのうち適切な箇所へ直接遷移する。

---

### 7.3 補足診断の配置

要求§11.2.1に従い、補足KPI／保存容量領域に配信者別容量の上位・その他・総計と確認時点を置き、警告・エラーの期間選択（24時間／7日／30日）と範囲不足、関連ログ導線を設ける。環境要約は短く、システム状態の詳細へのリンクを中心にする。優先KPI・稼働中セッションを押しのけず、空の警告一覧や装飾目的のチャートを作らない。期間内0件と未確認を区別する。

### 7.4 概況・稼働中セッション・容量の表示契約

- 健康状態は優先KPIとは別のコンパクトな概況領域（例：健康状態ストリップ）で示す。稼働に影響する異常・容量警告は発見しやすい位置に、影響する機能・時点・診断導線をまとめる。正常時は控えめとし、優先KPIと稼働中セッションを押しのけない。音声推論だけの障害でアプリ全体の停止を示さない。
- 一次指標は§7.2の4指標の意味を保ち、二次指標（本日集計、保存容量、字幕待機・処理中・失敗等）は小さくまとめる。監視対象の全登録数と監視有効数など、異なる分母を併記する場合は区別する。指標の色や数字の強調は状態・優先度に基づき、単なる件数の大小で異常にしない。字幕補足KPIから既存の音声字幕画面へ進める。
- 稼働中セッションは識別（配信者・サービス・タイトル）、独立した稼働状態（配信・録画・コメント、取得済み件数等）、時間（開始根拠・経過）の3領域に整理し、同じセッションのまとまりで横断比較できるようにする。十分な幅では横並びを優先候補とし、狭い幅で折り返しても対応を失わない。取得できない情報は明示し、古い状態の経過表示は§5.5に従う。
- 保存先ボリュームの使用・空き・総容量（取得可能な値）と、管理対象動画・字幕の保持容量、設定上の保存容量上限・最低空き容量を別の指標として表示する。使用率を表示する場合は分母と絶対容量を近接させる。管理容量の上位・その他・総計の比較棒を用いるなら管理容量総計を共通分母とし、同一ボリュームの使用率とは別に表示する。未確認分・取得時点・対象ルートを明記し、論理削除済みも含むサービス＋配信者ID単位の集計（要求§11.2.1）を維持する。分母不明や0のときは率を捏造しない。警告は既存の空き容量・容量上限等の判定に基づき、新しい使用率しきい値を設けない。
- 最近の録画は識別・時刻・取得結果を短い複合セルで示す。警告・エラー集計は期間と保持範囲を明確にし、現在の影響のある警告と過去の事象数を混同しない。環境詳細や長いエラーはシステム状態・ログへ委ねる。

## 8. 配信者一覧（`/streamers`）

### 8.1 一覧の構造

**「誰を監視し、何を有効にしているか」を管理する配信者一覧画面**です。配信者名を主情報、ユーザーIDを補助情報として、一覧性の高いテーブルを使用してください。

表示項目：プラットフォーム、配信者名、配信者ID、監視ON/OFF、配信状態、録画ON/OFF、録画状態、コメント収集ON/OFF、コメント収集状態、最終確認日時。最終配信日時・最終録画日時は補助表示や詳細で確認できるようにする。

- 監視・録画・コメント収集は**独立した3つのトグル**とし、現在のジョブ状態とは視覚的に区別する。
- 一覧から、該当配信者で絞り込んだ**録画履歴**へ直接遷移できるようにする。
- 編集・履歴・削除は行アクションに整理し、巨大なボタン列を作らない。
- 必要な絞り込み（サービス・状態等）と、選択状態・最終確認の鮮度を見せる。
- 更新中や変更失敗時に誤ったトグル位置を確定表示しない。
- 通信障害や不明なTikTok room statusを「オフライン」へ置換しない。状態が不明な行は最終成功確認時刻と、確認できる場合は診断への導線を示し、過去のLIVE判定を現在の確定結果として表示しない。

- 名前・IDの検索欄、サービス・状態の絞り込み、デフォルト／カスタム順を一覧上部に集約。切替・検索は監視の実行順を変えない。
- カスタム順の非絞り込み状態だけにドラッグハンドルとキーボード操作を表示する。上下操作、確定、Escape取消、操作結果の読み上げとフォーカス保持を提供し、ドラッグだけに依存しない。検索中は並べ替え不可の理由と解除導線を出す。
- 保存中の旧応答や二重操作を抑止し、明示拒否・競合時は最後の確定順または再取得した最新順を表示して理由を提示。結果未確認時は最後の確定順を暫定表示し§6.2.1に従って照合する。成功前に確定と表示しない。並び順モード・カスタム順は再読込後も保持（要求§11.3）。

#### 8.1.1 一覧の列グループと行操作

| 論理領域 | 主情報・補足情報と操作                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| 配信者   | 表示名を主、サービス識別と正規IDを補足として近接配置。長いIDは全文確認可能にする                                   |
| 状態     | 配信・録画・コメントの実状態を区別し、最終確認・必要な失敗理由を補足。状態不明時は鮮度を示す                       |
| 設定     | 監視・録画・コメントの独立した3トグル。共通アクセント色のONと中立色のOFFを基本に、ON/OFFと保存状態を識別可能にする |
| 操作     | 編集、対象で絞り込んだ録画履歴・コメント、監視対象からの削除等の提供済み操作を行末等の予測可能な位置にまとめる     |

- 状態と設定を視覚的に分離する。トグルのONを録画中の赤や配信中の緑で示さず、監視OFFでも保存された録画・コメント設定値がONの場合は実状態と別に表示する。即時保存と安全停止の影響を既存の操作契約に従って知らせる。
- 行アクションは通常の閲覧・編集と破壊的操作を区切り、対象名を含むアクセス可能名、キーボード開閉・選択・フォーカス復帰を確保する。未提供のプロフィール操作等を追加しない。
- 一覧上部の総登録件数／絞り込み件数／取得可能な状態集計の範囲を区別する。並べ替えハンドルは§8.1の条件を満たす場合だけ表示し、操作中の行と確定順を識別できること。

#### 8.1.2 カスタム順の操作品質

- 並べ替えは専用ハンドルまたは明示的な移動操作から開始し、通常のクリック・文字選択・行操作と区別する。移動対象、挿入位置、開始時の全順序を認識でき、長い一覧の端スクロールは追加品質とし、標準の上下移動操作で全順序を編集可能にする。移動表示の複製等を使う場合はアクセシビリティ上の重複やID重複、誤った操作対象を作らない。
- ドラッグ、キーボード（上下移動・確定・Escape取消）に加えて、クリックだけで同等の順序編集ができる上下移動等の代替を用意する。対象のフォーカスを保ち、移動対象と現在位置／総数、未保存・保存済みを通知する。Escape、pointercancel、意図しないポインター捕捉消失等では未確定の移動を取り消し、操作開始時の順序を復元し、表示・スクロール・イベント処理を後始末する。移動中の動きは抑制設定でも操作可能とする。
- 確定操作まで永続化しない。全対象のID順・順序版で既存契約に従い保存し、保存中は重複・競合操作と定期更新を抑止する。途中の並びを個別保存しない。明示拒否・版競合・結果未確認の扱いは§6.2.1に従い、結果未確認のまま後続の並べ替えを送らない。絞り込み中・一部ページ表示では不可とし、必要なら要求§11.3の全順序編集ビューへ誘導する。監視順には影響させない。

### 8.2 追加・編集

「配信者を追加」からモーダルまたはドロワーを開き、追加と編集でフォームを共通化してください。

項目：プラットフォーム（TikTok LIVE／ツイキャス）、ユーザーIDまたは対応URL、表示名、監視ON/OFF、録画ON/OFF、コメント収集ON/OFF。

- 入力形式の例、必須／任意、誤りをフィールドに近接して表示する。
- 編集は既存値を初期表示し、保存・キャンセル・未保存変更を明確にする。platformと正規IDは読取専用とし、別アカウントは新規登録へ誘導する。要求§5.1.1の採用済み入力例・最大長・フィールドエラーを共通検証器に従って表示し、失敗時の入力を保持する。
- 重複登録や不正な入力の理由を短い日本語で伝える。
- 削除は保存から分離し、関連する履歴・ファイルへの影響を明示する。
- 録画設定のON/OFFと稼働中セッションの手動停止／再開は混同させない。監視OFFは当該配信者の監視と稼働中の録画・コメントを停止、録画OFFは録画のみ、コメントOFFはコメントのみ停止することを変更前に示す。復帰時も録画の手動停止指示を尊重し、設定ONを実行中の保証として描かない。

## 9. 録画履歴（`/recordings`）・セッション詳細

### 9.1 一覧は配信セッション単位

**「何が記録されたか」を確認する画面**です。サイドバーとページ名は「録画履歴」とし、`docs/requirements.md` の機能・URLを維持してください。動画ファイルを基本行にするのではなく、**配信セッションを1行の基本単位**とします。

表示項目：配信者、プラットフォーム、配信タイトル、開始・終了日時、録画時間、録画ファイル数、合計サイズ、コメント件数、録画状態、コメント収集状態、詳細への導線。取得できない項目は「未取得」等で示し、0と混同しないこと。

- 検索・フィルター：配信者、プラットフォーム、日付範囲、録画状態。可能な場合に進行中／終了済みを見分ける絞り込みを追加してもよいが、未提供の検索機能を動作すると見せない。
- 録画あり／録画失敗／録画無効／コメントのみ等を、実際に存在するセッション情報に応じて区別する。
- **録画ファイルがないことを理由に、コメントのある配信セッションが見つからなくならない**ようにする。
- セッションの録画結果は、そのセッションに属する**全録画ジョブ・全セグメント・取得欠損**に基づいて要約する。最新ジョブのみ完了でも、過去の無効ファイルや未回復の欠損があれば「全区間完了」と誤認させない。集計不能な項目は未判定とする。
- 一覧 → 詳細 → 戻るで、検索条件、並び、ページ位置を維持する。結果件数と現在位置を明示する。
- 一覧で全情報を展開せず、複数セグメントや欠損・障害の詳細はセッション詳細へ委ねる。

#### 9.1.1 セッション一覧の比較軸

| 論理列グループ | 推奨する複合セル・比較内容                                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 配信           | 配信者名＋サービス、タイトルを補足。対象セッションへの主リンク                                                                                       |
| 日時           | 開始と終了／継続中／終了未確認を近接配置。時刻根拠が異なる場合は区別                                                                                 |
| 録画時間       | 確定メディアの取得済み長さを独立した比較値とする                                                                                                     |
| サイズ         | 容量＋ファイル数。未取得と0・削除済みを区別                                                                                                          |
| コメント       | 保存済み件数と収集状態を区別。閲覧可能なら件数等から当該配信のコメントへ直接移動                                                                     |
| 録画・字幕状態 | セッションの録画結果とコメント収集状態を独立表示。既存の取得データで字幕状態を要約できる場合は種別ごとに区別し、複数セグメント・欠損・旧版等は詳細へ |
| 詳細           | 対象を明示した詳細リンク。行内リンクを重複した大型ボタンにしない                                                                                     |

列の具体的な数・配置は採用時に決める。要求項目を省かず、数値比較・状態の独立性・文字の可読性を維持する。高頻度の配信者・サービス・録画状態を主条件、日付範囲等を詳細条件の候補とし、適用中の詳細条件は閉じた状態でも識別・解除可能にする。

### 9.2 配信セッション詳細の情報順

1. **配信概要**：配信者・サービス・タイトル・日時・セッションの状態。
2. **取得結果の概要**：**録画状態**と**コメント収集状態**を別々に提示。記録できた動画・コメント件数を明示。
3. **録画セグメントと対応SRT**：セグメント連番、開始・終了、長さ、形式、サイズ、検証状態、SRT生成状態・再生成可否。**動画とSRTの対応が一目で分かる同じ行／まとまり**に置く。
4. **コメントへの導線**：この配信セッションで絞り込んだコメント検索へ移動。
5. **欠損・失敗**：影響を受けた機能と期間、理由、システム状態の診断概要やログ画面の関連エントリへの導線（対応可能な場合）。
   - 最新ジョブの状態だけでなく、**同一配信の過去ジョブの失敗、無効／未確定ファイル、`collection_gaps` の存在**を対象別に示す。詳細を展開する前でも「欠損あり／要確認」が分かるようにする。
6. **危険な操作**：削除対象・影響範囲を示す別領域。

- 詳細画面の上部から、録画履歴一覧へ戻れるようにする。稼働中配信の場合は、提供される手動停止／再開を誤操作しにくい場所に配置する。
- **コメントだけ取得できたセッション**では動画欄を「録画なし（理由）」とし、コメント閲覧を主導線にする。SRTの生成・再生成操作は表示しない。
- どちらか一方の失敗によって、もう一方の成果物が隠れないようにする。

#### 9.2.1 概要の並列比較と次の操作

- 配信概要・録画情報・コメント収集を同一セッション内の独立したキー／値領域としてまとめる。広いPC画面では並列比較を優先候補にし、縦積みの場合も見出しと属性の対応を維持する。長い技術メッセージは要約から展開できるようにし、欠損・未確認・ファイル不在など判断に必要な事実は冒頭付近でも識別できるようにする。古い失敗を現在進行中の障害と断定しない。
- セッション識別（配信者、サービス、正規ID、セッションID、タイトル）を上部にまとめる。コメント閲覧・発話本文閲覧・字幕処理状況への既存の文脈リンクは取得済み件数等を活用し、未取得や期限削除を閲覧可能な件数と偽らない。主要な録画・コメントの結果を埋没させる大型カードや重複ボタンを増やさない。
- 収集統計は§11.3に従い、保存成功を主に、受信・重複・理由付き破棄・最終保存失敗・未処理・再接続等の内訳を確認できるようにする。異なる集計単位のエラー事象とコメント件数を加算しない。

### 9.3 セグメント・SRT・欠損の見せ方

録画・コメントの試行予算の消費／上限、次回待機、抑止理由を必要時に表示する。上限到達で停止したコメント収集の明示再開は確認付きとし、設定・同一LIVE・制限解除等を満たす場合だけ許可。録画の手動再開とは対象を区別する。

- セグメントごとに動画とSRTを対応づける。SRTが未生成でも、対応すべきセグメントが分かるようにする。
- セグメント連番は**保存された番号を数値順**で示し、過去データの飛び番号や複数ジョブまたぎの番号をUIだけで振り直さない。必要なら所属ジョブ・再試行履歴を詳細で確認可能にする。
- `valid`/`invalid`/`pending` と、**保存ファイル実在・サイズ・最終ファイルの検証結果**を可能な範囲で照合して示す。DB上のMP4が見つからない場合や時間長が不一致の場合に「録画は正常」と断定しない。
- SRT生成済み／未生成／生成失敗／スキップ（字幕対象なし）／保留、生成日時、再生成可否を明示する。コメント収集が未確定の間に生成・スキップした場合は「コメント確定待ち」を併記し、後着コメントの反映待ち・再同期失敗を確定済みと誤表示しない。再生成可能な場合は**対象セグメントと処理結果**を分かるようにする。
- **SRTのスキップ（対象セグメント時間内に字幕対象コメント0件）**を、生成済み空ファイル・未収集・生成失敗と明確に分ける。実際にスキップされた理由を短い補足として示し、録画なしでは再生成操作を出さない。
- 時刻同期の方法（実測／近似／手動補正／同期不能）、近似の注意、同期失敗理由は必要に応じて展開できるようにする。
- 録画動画・字幕のダウンロードボタンやリンクは、ファイルの有無にかかわらず表示しない。
- 初期版の削除は「ファイルのみ（動画と全対応字幕、履歴・コメントは保持）」と「ファイル＋履歴」に限定する。「履歴のみ」は提供しない。進行中・未確定は削除不可とし、未完了・一部失敗・意図的削除とファイル不在を区別して表示する。
- 動画プレイヤー・再生コントロール・動画と同期したコメント表示は設けない。

#### 9.3.1 セグメントを親とする成果物のまとまり

動画のセグメント連番・録画範囲・確定メディア長・形式・サイズ・検証状態を比較軸とし、そのセグメントに属する動画、`_comment.srt`、`_speech.srt`、`.ass` を従属する成果物として関連付ける。同一行の複合セル、展開行、階層表等を候補とし、別セグメントの字幕を取り違えないことを優先する。

- 字幕ごとに種別・生成状態・実ファイル有無・版／鮮度・対象外の理由・許可された操作を区別し、詳細で実際の管理パスと根拠を確認できること。旧正常版と最新失敗、暫定と確定、欠損と再同期待ち、無発話・期限削除を単一の成功ラベルにまとめない。
- 欠損区間は対象（録画／コメント等）、開始・終了とその根拠、理由を比較可能にする。不明な終端を推測で埋めない。セグメントから所属ジョブ・試行・欠損・関連ログへ文脈を保って進める。
- 削除は通常の閲覧・字幕生成と離れた専用領域（例：詳細末尾）に集約する。ファイルのみ／ファイル＋履歴の影響をそれぞれ近接表示し、§16.7の終了未確認、対象の状態、削除可能条件を適用する。再生・ダウンロード・履歴のみ削除は追加しない。

## 10. コメント検索・閲覧（`/comments`）

### 10.1 画面の役割

**「誰が、いつ、何を投稿したか」を配信別に読み、必要に応じて配信横断で調べる画面**です。録画履歴の詳細からは、そのセッションに絞り込まれた状態で開けるようにしてください。コメント本文を主情報として読みやすく表示します。

- 同一主要画面の2モード（配信別閲覧／横断検索）。初期は配信一覧、セッション選択後に本文を読む。コメントのみのセッション、収集失敗・期限削除を区別。横断検索は従来の詳細条件を維持する。
- 昇順／降順の切替、時刻根拠、モード・条件・ページをURLに保持し、詳細から戻った場合に復元する。録画詳細からは配信別本文へ直接リンクする。

### 10.2 検索・結果

- 主検索欄：コメント本文。
- 詳細フィルター：投稿者ID、投稿者表示名、配信者、プラットフォーム、配信セッション、日付範囲。追加条件は展開式で整理する。
- 検索語・フィルターの適用状態、結果件数、現在ページ、条件のリセットを分かりやすく表示する。
- コメント行には投稿日時または受信日時、配信者、プラットフォーム、投稿者表示名、投稿者ID、本文、録画開始からの経過時間（取得できる場合）、関連セッションを表示する。
- 投稿者名・IDが長くても本文の幅を奪わない。改行・絵文字・長文も読めるようにする。
- ツイキャス匿名番号は取得できた場合だけ表示し、未取得の番号や推測による人物同定を行わない。
- 大量のコメントはページネーションで扱い、全画面を不必要に再描画しない。
- **関連する配信セッションへの直接リンク**を設け、戻った際には検索条件とページ位置を可能な限り保持する。

#### 10.2.1 本文を中心とする閲覧構造

コメント本文に最も広い可読領域を配分する。横断検索の標準的な論理領域は「時刻（投稿／受信の根拠）」「投稿者（表示名＋IDまたは取得済み匿名番号）」「本文」「配信コンテキスト（サービス・配信者・関連セッション・録画位置等）」とする。配信別本文では共通の配信コンテキストを見出しへ集約してもよいが、時刻根拠・録画位置・関連対象は確認できること。長文・改行・絵文字は本文で保持し、HTMLとして解釈せず、安全なテキスト表示とする。投稿者名・識別子は全文確認可能にしながら本文幅を圧迫しない。

- 配信別の入口はセッション単位の一覧とし、配信者・サービス・タイトル、日時、コメント状態・保存済み件数をまとまりとして示す。録画のないセッションも含み、期限削除・失敗・未取得を単純な0件としない。本文への導線は実際の閲覧可能性に従う。
- 配信別／横断のモード、本文検索、詳細条件、時刻昇降順、結果件数・表示範囲を一貫した構造で示す。件数の多さで本文の読書性を損なわない。録画位置は同期根拠のある値だけを示し、動画再生へのリンクにはしない。

### 10.3 SRTへの導線

- コメント画面は検索・閲覧に使い、コメント出力メニューは設けない。SRTの生成状態と再生成は録画セグメントごとに扱う。
- SRTの生成状態を確認するときは、関連する録画セッションの詳細へ移動する。字幕ファイルはWindows側の保存先で開く。コメント検索結果の範囲とSRTの対象セグメントを混同させない。
- セグメントが存在せずSRTを生成できない場合は、その旨を明示する。コメント閲覧そのものは維持する。

## 10A. 音声字幕・ASS管理の横断UX（要求§11.9）

- `/speech` は全体キューの管理を主目的にする。状態別件数を小さく集約し、処理中・保留・失敗を優先する。配信者・サービス・セッション・状態の絞り込みとページング、セグメントごとの媒体長／生成時間、モデル・言語・デバイスを比較できるテーブルを設計する。字幕生成時間は動画長と分離する。
- 旧正常版が存在しても最新試行が失敗なら両方を表示する。無発話、音声なし、未処理、依存利用不可、設定OFF、削除済み、ASS片側／暫定／期限削除を別状態として表示し、録画中の赤マークを音声推論中に転用しない。
- 個別再生成・失敗のみ一括再試行・ASS再生成は対象・受付・結果を分ける。重複操作を抑止し、不可理由を表示。発話本文への導線は管理下の確認済み結果のみ有効。`/speech/cues` はコメントと一貫した時刻／本文のリスト、セッションとセグメント、本文検索・時刻順・ページングを提供。自動認識の不確実性を簡潔に明示し、動画プレイヤーやファイルダウンロードは追加しない。
- 録画詳細には動画・コメントSRT・音声SRT・ASSを同じセグメントに対応付け、状態、版、実ファイル、再生成、発話本文リンクを区別。ファイル名表示は要求§10.3の実際の管理パスに従い、配信タイトルを含む長い名前も全文確認・コピーできるようにし、字幕種別を取り違えない。現在の配信タイトルから既存ファイル名を再構成しない。音声字幕未生成を録画失敗としない。ダッシュボードから字幕キュー・失敗へ移動でき、システム状態はGPU・モデル・キュー・負荷の診断を要約、ログへ相関IDで遷移する。
- 自動部分更新では絞り込み、時刻順、ページ、発話本文の選択、確認ダイアログ、設定未保存状態を保護。古い応答で試行状態・最新版を戻さない。

### 10A.1 音声字幕キューと発話本文の表示契約

- キューの一覧は処理対象をセグメント単位で同定できるようにする。配信者・サービス・セッションとセグメント／ファイル名、媒体確定時刻、動画長、処理経過／生成所要時間、モデル・言語・デバイス、cue数、音声SRTとASSの状態・鮮度・操作を整理する。関連属性は複合セルにしてもよいが、動画長と生成時間、実行状態と旧正常成果物を別々に比較できること。状態別件数は補足としてまとめ、処理中・保留・失敗の確認と再試行を優先する。
- 発話本文はコメントと同系統の検索・結果件数・順序・ページング・行構造を用いる。開始／終了のメディア相対時刻、発話本文、対応するセッション・セグメントの文脈を論理領域とする。配信者・セグメント共通情報を見出しにまとめる場合も、開始と終了、異なるセグメントの時刻基準を混同しない。長文・選択・コピー・読み途中の更新保護を共通化する。自動認識の不確実性を示し、コメント投稿時刻と発話時刻を同一視しない。
- 処理状況と発話本文を既存のURL・絞り込みで相互に辿り、録画詳細へ戻れるようにする。対象の成果物が期限削除・未生成・無発話・失敗等の場合は閲覧可否と理由を区別する。未確認のcueやダウンロードを提供しない。

## 11. システム状態（`/system`）

### 11.1 ダッシュボード・ログとの責務分離

ダッシュボードが**「今、何が起きているか」**、システム状態が**「何が正常で、どこに影響があり、何を確認すべきか」**、ログが**「いつ、どの処理で、実際に何が記録されたか」**を扱います。システム状態は**現在の健康状態と診断要約**に集中し、ログ全文を時系列で探索する機能を重複実装しないでください。

- 冒頭：全体の状態、監視機能、録画・コメント取得、データ保存、録画保存先、最終監視実行日時を簡潔に表示。
- 次段：録画エンジン・関連ツールの利用可否、バージョン、直近の失敗（取得可能な情報に限る）。
- 次段：外部サービスとの接続、監視頻度制約・再試行待ち等、実際に取得できる診断状態。
- 末尾：影響のある直近の警告・エラーの**要約**、保存先のファイル照合結果等、提供される診断情報。問題の詳細は「関連ログを見る」からログ画面へ導く。

### 11.2 異常の要約と診断情報

- 異常の要約は**発生・確認時刻／重要度／対象／影響／状態**を中心とし、利用者が次に調べるべきものを優先します。ログを全文表示する無制限の時系列一覧は置きません。
- 録画ツール診断は、取得できる場合は**実際に使用するffmpeg/ffprobeのバージョン・解決元、最終メディア検証の成否**を区別する。旧プロセス／古い情報の表示では確認時刻を明記する。特定の検証環境で使われたバージョン・ディレクトリを正常値として固定表示しない。
- 対象の配信・録画・セグメントが分かる場合は該当する録画履歴のセッション詳細へ、対応するログ情報が提供される場合は**ログ画面の関連エントリ**へリンクします。
- 警告と異常を区別し、影響範囲と次にできる確認・再試行方法を先に示します。
- 保存先照合などの結果は正常・不足・不一致・未確定などの違いを区別します。照合・確認と削除の操作を混ぜません。
- 要求§15.2.1に従い、通常運用で媒体保存先だけの異常によって録画が保留されている場合は、該当ルート・理由・対処と監視／コメント等の独立機能の状態を区別する。起動拒否は稼働中の正常なUI状態として表示しない。
- 診断中／取得失敗／古い情報の状態と、最後に確認できた時刻を示します。実在しない「別Coreの接続画面」等は追加しません。
- ログが取得できない場合でもシステム状態そのものを架空の正常値に置き換えず、診断結果とログの取得可否を別々に示します。

### 11.3 機能別ヘルスと収集統計

要求§14.5の機能別・対象別状態と最終確認／成功／期待次回・鮮度・影響を表示する。idle、disabled、blocked、正常、unknown、停止中を混同しない。エンジンの版・解決元・利用可否・実取得成功・直近失敗・累積／連続失敗を独立表示。コメントジョブの統計は録画詳細の取得結果に受信・新規保存・重複・破棄理由・保存失敗・未確定・最終受信を示し、収集全件性の保証ではないことを明確にする。環境情報はシステム状態で詳細化し秘密値は返さない。

### 11.4 ストレージ照合の操作

要求§10.5.1・§11.6.1の手動開始・取消を提供し、受付中の二重開始を抑止する。実行ID・開始時刻・処理済み件数・範囲・状態を保存済み値から更新する。総対象が不明なときは割合表示しない。最新実行と前回完了の時点・結果、部分／失敗／中断／取消／未実施を明確に区別し、表示上限・未確認を明示する。診断の延期・古さ・次回予定は要求§14.5.1に従う。照合ボタンは画面更新や削除ではない。

### 11.5 診断の比較軸と照合分類

- 機能別ヘルスは対象名・実状態・影響・確認時刻（必要に応じて期待次回）を短いまとまりで比較できるようにする。正常を示す大きなカードを対象数だけ反復しない。環境・外部連携はキー／値中心とし、秘密値を表示しない。
- 録画エンジンはサービス＋エンジン単位の比較表を優先する。エンジン名を主、版・解決元を補足とし、利用可否／採用実証の状態、最終取得成功、最終失敗・理由、累積／連続失敗・再試行数等を実際に取得できる範囲で区別する。インストール済み・利用可能・本編取得成功は同じ意味ではない。長い理由は要約＋全文／関連ログとし、未検証を利用可能と表示しない。
- 照合結果は管理ファイルの確認対象数・正常数・各異常分類・未確認範囲の要約と、分類別の該当ファイル詳細を分離する。分類別件数を選べるタブまたは同等の導線を優先候補とし、ファイル不在・サイズ不一致・検証不良・未登録・一時ファイル・未確認等を既存の分類契約に合わせて表示する。管理外・一時ファイルを管理ファイルの正常／異常の分母に混ぜず、分類重複の有無は実際の集計定義に従う。総数、列挙／ページの表示件数、取得範囲、未確認を区別し、部分結果を全件確定と扱わない。パスの全文確認・コピーを可能とし、分類内絞り込みは既存の取得契約の範囲で行う。
- 照合の開始／実行中／取消・結果と前回完了結果を別の領域に置き、分類の選択・詳細閲覧中の自動更新で文脈を失わない。照合のために削除・修復・取込を新設せず、§11.4の非同期・鮮度・負荷契約を維持する。長いイベント列で照合を押し下げず、詳細は独立ログ画面へ誘導する。

## 12. ログ（`/logs`）

### 12.1 画面の役割と表示範囲

**「いつ、どの処理で、何が起きたか」を時系列で確認・調査する独立画面**とします。サイドバー「管理」の「システム状態」と「設定」の間に配置し、システム状態からの詳細調査先として機能させます。コメント本文の履歴や配信セッションの録画履歴とは混同しません。

- 表示対象は`docs/requirements.md`で定めたアプリケーションの構造化ログ・ローテーション済みログ・利用可能な`system_events`要約に限ります。**これらを検索・表示するサーバー側の読取処理は初期実装必須**であり、新しい外部収集基盤・ログ専用DB・推定相関付けを追加要求しません。
- **一覧は時刻降順を初期値**とし、発生時刻、重要度、出力元（サービス・コンポーネント等）、メッセージ要約を読み取れる構成にします。関連配信者・セッション・イベント識別子等は、実際に取得できる場合のみ表示します。
- 全ログを同じ強さで色付けせず、ERROR／WARNING等の重要な行を適度に識別できるようにします。表示ラベルはログの実際の重要度を保持し、内部レベルを勝手に読み替えません。
- 技術ログは改行、長いパス、識別子、日本語と英数字の混在を崩さず、本文を選択・コピーできるようにします。
- 過去の `last_error` が残っていても、直近のジョブやファイルが成功した可能性がある。**発生時刻・関連ジョブ・その後の回復状況**を確認できる場合だけ文脈に反映し、ログの古いエラーを「今も失敗中」と断定しない。同じ警告の抑止があっても障害の解消とは見なさない。

### 12.2 検索・絞り込み・閲覧

- 時刻範囲、重要度、出力元、本文のキーワードを、**取得・検索可能な項目に限り**提供します。配信者やセッションでの絞り込みは、関連付けデータが存在する場合のみ追加します。
- 主要検索条件を上部にまとめ、低頻度の条件は展開式に整理します。適用中のフィルター、結果件数、取得範囲、並び順、現在ページを明示します。
- 大量のログは初期実装するサーバー側の検索・件数制限付きページングにより段階的に表示し、ブラウザへ全件読み込んで検索する前提にしません。未提供の全文検索・複雑な相関検索を実装済みと見せません。
- 行を展開すると、実際に存在するログの**秘匿処理後の完全な本文・タイムスタンプ・出力元・関連メタデータ**を確認・コピーできるようにします。スタックトレース等は読みやすく整形しますが、**秘密情報の再マスキング以外は本文を省略・改変しません**。一覧・検索結果・詳細・コピー内容に同じ秘匿ルールを適用し、未処理の生ログはブラウザへ渡しません。
- データが0件、条件に一致しない、取得できない、更新が失敗した、表示対象期間が限定されている場合を区別します。0件を「問題なし」の保証として扱いません。

### 12.3 システム状態・録画履歴との双方向導線

- システム状態の警告・エラー要約から、**時刻・重要度・出力元・関連対象**を可能な範囲で引き継ぎ、ログ画面の該当箇所へ進めるようにします。対応するログを特定できない場合は、特定済みと誤認させません。
- ログに配信者・配信セッション等の信頼できる関連情報があるときは、配信者一覧や録画履歴の該当詳細へ直接移動できるようにします。本文の文字列から識別子を推測して関連付けしません。
- ログ → 関連セッション → 戻る際は、検索語、フィルター、ページ位置、可能ならスクロール位置を保持します。
- ダッシュボード・録画履歴の障害箇所からも、適切な対象ログへの導線を設けます。ただし、実際に関連付けできない場合は利用可能な条件で開くよう明示します。

### 12.4 情報鮮度・安全性と機能範囲

- 共通の「表示時点（最終取得）」を使い、ログの発生時刻と画面取得時刻を混同させません。自動更新時も、読書・テキスト選択・展開・検索中の表示が勝手に流れたりフォーカスが移動したりしないようにします。
- ログに認証情報、トークン、個人情報等が含まれる場合は、`docs/requirements.md`に定める表示・秘匿上の制約を厳守します。古いログ・外部ライブラリの例外文も提供前にマスキングし、UIの便宜で機密を新たに露出しません。
- ログのダウンロード、ライブ追尾、一括削除、クリア、保持期限の編集等は**存在が確認できる機能のみ**表示し、見た目だけの操作を設けません。ログレベルの設定はログ画面に重複させず、設定画面の「詳細設定」へ集約します。
- 初期全体実装では、ログの一覧取得手段がない場合、正本の必須要件に従って最小の読取・検索・詳細取得機能を非UIタスクで実装する。単独UI再設計では不足を報告し、非UI変更は行わない。初期画面を空の仮表示だけで完成扱いせず、外部ログ基盤や不要な収集方式を増設しません。

---

### 12.5 ログの情報階層

時刻・実際のレベル・出力元・メッセージ要約を比較可能な密度で並べ、関連対象・相関IDは取得できる場合のみ補足として扱う。WARNING／ERROR等の実レベルは記号とラベルで識別し、通常ログや行全体を意味なく着色しない。長い技術本文は要約と全文展開を分離し、異常の存在・発生時刻・出力元を折りたたまない。詳細では秘匿後の完全な本文・スタックトレース・メタデータを読み取り・選択・コピーできるようにする。共通検索・フィルターの規則（§6.6）を適用し、読書中の自動更新抑止・展開保持を確認する。ログ画面だけで新たな収集や削除を行わない。

## 13. 設定（`/settings`）

### 13.1 セクション構成

**設定は1つの主要画面の中で、目的に応じたセクションまたはタブに分類**してください。設定のカテゴリをサイドバーの主要ナビに昇格させないでください。

| セクション        | 表示・編集するUI項目                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **監視**          | サービス別監視頻度、変更できない上限、設定値と実効値の違い（取得可能な場合）                                                                            |
| **録画・保存**    | 同時録画上限、録画品質、保存先（要求仕様§10.2の既定値と実効値）、最低空き容量、保存容量上限、保存期限、自動削除、TikTok録画エンジン優先順位、再接続回数 |
| **コメント・SRT** | コメント収集ON/OFF、ツイキャスコメント取得間隔、SRT表示秒数、コメント保存期限（日数。初期`0`＝無期限）                                                  |
| **音声字幕**      | 自動生成、モデル、認識言語、実行デバイス。GPU／モデル診断、次回試行反映                                                                                 |
| **表示**          | 表示タイムゾーン、フォント（Windows標準／Noto Sans JP）、自動更新間隔（秒）                                                                             |
| **詳細設定**      | ログレベル、固定Webポート（現在の待ち受け値／保存値・再起動要否）                                                                                       |

- 自動更新間隔は秒単位、固定Webポートは整数入力とし、既定値・許容範囲・反映時期を要求仕様§2.2・§11.1に従って示す。無効値は入力欄の近くに表示し、ポート保存時には再起動後の接続URLを案内する。
- 長い単一フォームを避け、選択中カテゴリを明確に示す。関連項目を近接させ、長い説明はヘルプや補足に置く。
- **編集可能／読み取り専用／未保存／保存中／再起動後反映**を見分けられるようにする。
- 設定項目を視覚的に分割しても、保存の単位と実際の反映結果が一致するようにする。未保存の値が意図せず消えたように見せない。
- APIキーやシークレットが必要な項目は、設定済み／未設定等を表示し、平文を露出させない。

全項目の型・既定・範囲・反映条件は要求§11.8.1〜3の正本に従う。設定APIから共有メタデータを取得し、単位・範囲・0の意味・反映時期を必要な位置に表示。容量・期限変更の影響を明示し、削除範囲拡大は明示確認する。環境値・内部しきい値は編集欄にしない。保存版の競合時は未保存入力を保持し、現行値との差を示す。

### 13.2 サービス別監視頻度の入力

| サービス    | 入力範囲                      | UIに必要な説明                       |
| ----------- | ----------------------------- | ------------------------------------ |
| TikTok LIVE | `0 < r ≤ 10` 回／分（小数可） | サービス全体で共有する上限：10回／分 |
| ツイキャス  | `0 < r ≤ 60` 回／分（小数可） | 初期値：10回／分、上限：60回／分     |

- サービスごとに入力欄を分け、単位「回／分」、上限、初期値、反映タイミングを近くに示す。
- `0`、負数、上限超過、数値以外の入力はフィールド近傍でエラー表示する。監視停止は配信者ごとのON/OFFで行い、`0回／分`という意味を作らない。
- **監視回数の上限は配信者個別ではなく、同じサービス内の監視対象全体で共有する**旨を説明する。個別の確認失敗や一時停止は当該配信者に留まり、サービス全体の明示的な制限は共有枠に適用される旨も示す。
- 設定値と実際の確認頻度は異なる場合がある。外部サービスの制限やコメント取得の優先等で低下するなら、取得できる実測情報とともにその旨を示す。
- 変更できないサービス上限は読み取り専用にする。変更反映の成功・失敗を適切に知らせる。

コメント保存期限の変更時は、動画・セッション履歴を残し、期限到達した**稼働SQLite内のコメントとアプリ管理のコメントSRT・統合ASS**のみが削除されること、**通常のアプリ操作では復元できない**ことを明示します。一方、削除前の手動SQLiteバックアップにはコメントが残る可能性があり、自動削除対象外であること、不要な旧バックアップは利用者が安全に破棄・差し替えることを近くに説明します。コメント期限削除済みセッションは「0件」「未収集」と区別し、録画履歴のSRT状態も期限削除済みとしてコメントSRT・ASSの再生成を不可にします。音声SRTは期限削除の対象外で、音声本文閲覧と音声再生成は維持します。

### 13.3 フォント選択とプレビュー

ラベル「フォント」の**単一選択プルダウン**を「表示」に置き、選択肢を次の2件に限定してください。

1. **Windows標準（初期値）**：`"Segoe UI Variable", "Segoe UI", "Yu Gothic UI", sans-serif`
2. **Noto Sans JP**：`"Noto Sans JP", sans-serif`＋`font-feature-settings: "palt" 1;`

- 選択した書体で日本語・英数字・日時を短くプレビューする。
- 保存前にプレビューを反映させる場合は、保存済みとの違いを表示し、キャンセルで元の状態に戻す。
- 選択は再読込・ページ移動後も保持され、見出し・本文・表・ダイアログに反映される。
- **テーマの設定、切り替えボタン、OSテーマ連動のUIを設けない。**

### 13.4 保存と反映

- 変更が即時反映される項目と、再起動後に反映される項目を明確に表示する。
- 編集中、保存中、成功、失敗、競合の違いを表示し、保存が確定する前に反映済みと表示しない。
- 保存先のアクセス可否等が確認できない場合は理由・確認先を示す。利用可否不明を正常として扱わない。

### 13.5 音声字幕の設定

モデル・言語・デバイスは選択可能な値と可用性を分け、GPU未検出・モデル未取得・推論依存欠落の理由と診断導線を示す。自動生成OFFと既存成果物の消去を混同しない。処理中の設定スナップショットを示し、保存後の次回設定と区別する。

### 13.6 設定行・カテゴリ内ナビと保存状態

- 確定済みの6カテゴリを設定画面内のナビ／タブ等で選択し、選択中・未保存変更あり・入力エラーありを区別する。PCの十分な幅ではカテゴリ選択領域と設定行領域を分離する構成を優先候補とする。主要ナビ項目や設定カテゴリは追加しない。
- 設定行はラベルと必要な補足、入力／選択部品、単位・範囲・反映条件を近接配置する。十分な幅では説明側と入力側の整列を優先し、長いパスや拡大表示では折り返せるようにする。読取専用の実効値・設定済み／未設定・現在稼働値は編集欄と見分けられる表現とする。値・選択肢・単位・反映時期は共通設定レジストリに従い、本書で再定義しない。
- 保存操作は一貫した保存領域（例：保存バー）にまとめる。変更なし、未保存（特定できる変更件数）、保存中、保存成功、保存済みだが再起動等の適用待ち、入力エラー、失敗・競合を区別する。保存・破棄は対象範囲を明示し、実際の保存単位と一致させる。保存競合や失敗で入力を消さず、破棄は利用者の意思に従う。
- 非表示カテゴリに検証エラーがあればカテゴリ側にもエラーの存在を示し、該当項目への移動・フォーカスとフィールド別エラーを提供する。他カテゴリの入力を保持し、保存前の値と確定済み値、再起動後反映値を混同しない。保存領域を追従させる場合は操作対象を覆わない。

### 13.7 フォーム変更・検証・離脱の契約

設定全体・配信者追加／編集の各フォームは、初期取得または直近の保存確認済みの値と版を基準とし、現在の入力・検証状態・実際の適用状態を独立して保持する。変更判定は入力イベントの有無ではなく共通設定レジストリ／入力契約の型・正規化・意味上の値で比較する（例：同じ数値を表す許容された表記差は変更としない）。不正入力は確定値に置換せず、未保存・検証エラーとして保持する。追加フォームは初期入力状態を基準とする。

- 元の値に戻した項目は変更件数から除く。カテゴリごとの未保存・入力エラーを識別し、選択カテゴリを切り替えても他カテゴリの入力を失わない。全設定の保存単位・原子性は既存契約に従い、現在の表示カテゴリだけが保存されると誤認させない。
- 保存成功時のみサーバーの確定値・版を新しい比較基準にする。再起動等の適用待ちは保存済みと稼働中の実効値を区別。失敗・結果未確認は入力と基準を保持し§6.2.1で照合する。競合時は最新値と未保存の編集値を区別し、利用者の確認なしに破棄、再適用、版更新による強制上書きをしない。明示的な破棄は現在の確定基準へ戻す（競合時は最新値を確認する）。
- クライアント検証はサーバーの検証契約の補助に限る。サーバー側のフィールドエラーと同様に項目名・理由を関連付け（`aria-invalid`、`aria-describedby`等）、非表示カテゴリにエラーがあれば該当パネルを開いて訂正可能にする。修正時は該当エラーだけを適切に再評価する。
- 未保存変更または結果未確認の操作を失う画面離脱・閉鎖・再読込・ブラウザ戻る／進むでは、可能な範囲で標準の離脱確認を用いる。変更がないときは不要な確認を出さず、離脱取消で入力・カテゴリ・URLを維持する。ブラウザが確認を保証しない場面でも保存成功を捏造しない。編集値をURL・永続ブラウザストレージ・ログへ無断保存しない。

## 14. PC対応・アクセシビリティ

### 14.1 対応幅

Windows PCブラウザを対象とし、初期実ブラウザ確認は1440px・1024pxを優先する。1280px、125％・150％・可能なら200％は追加検証。表示幅を狭めても操作不能にならない設計を維持する。

- PCのウィンドウを狭めた場合も、文字・ボタン・ダイアログが重なったり操作不能になったりしないようにする。
- 必要なら列の優先順位、詳細展開、部分的な横スクロールを設計するが、データテーブルの読みやすさを維持する。
- スマートフォン・タブレット専用メニュー、モバイルカード変換、下から出るモバイルシート等は実装しない。

### 14.2 WCAG 2.2 AAを目標としたUI

- 十分な文字コントラスト、常に分かるフォーカス表示、色以外による状態識別。
- キーボードによる主要ナビ・検索・ログの絞り込みと詳細展開・行アクション・トグル・ダイアログの操作。
- ドロワー／ダイアログの開閉時のフォーカス制御と、Tab移動の分かりやすさ。
- 入力ラベル、必須条件、単位、エラーメッセージの関連付け。
- `aria-busy`、`aria-live`、アクセシブルネーム、装飾アイコンへの`aria-hidden`の適切な使用。
- 長いメッセージ、フォント2種類、拡大表示、狭いPCウィンドウでも読み取り可能な構成。
- アニメーションを必要最小限にし、`prefers-reduced-motion`に従う。

### 14.4 隔離された開発専用UIプレビュー

UI設計と反復検証を実配信の有無から分離するため、開発工程で再現可能なプレビュー／fixture基盤を用意する。これは製品のライブプレビュー、動画再生、通常起動時の開発用HTTPルートではない。スターターに実装済みツールを収録することも意味しない。

- 採用前の3比較案は隔離モックアップとして提示する。採用案の製品テンプレート・CSS・JS・表示変換器を使う隔離fixtureで代表正常／空／ストレス／異常・遅延／逆順を検証する。実配信・字幕の実証を待たず実装できる。
- 開発用の独立起動またはテストハーネスとし、実運用DB・保存先・ログ・外部API・稼働プロセスに接続しない。模擬操作は隔離専用とし、通常起動へ登録しない。
- 通常運用相当のCSP、ローカル静的資産、秘匿、エスケープ、操作境界を検証する。模擬成功と実API・実配信・字幕実証を区別する。

### 14.5 UI自動品質検査と証跡

| 検証層                 | 代表検査内容（詳細ケースは追加品質）                                                                                                                                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 表示部品・HTML         | 状態変換器、既知／未知状態、日時整形、入力保持、エスケープ、ラベル、状態・操作とアクセス可能名、CSP互換                                                                                                                                         |
| 実ブラウザ操作         | §5.4.1〜2、§6.2.1、§6.3.1、§6.4.1、§6.7、§8.1.2、§13.7の操作。遅延／逆順、操作開始後の応答、応答消失後の現在値・業務状態照合、競合、対象消失、非表示復帰、戻る／進む、ドラッグ中断と代替操作を再現                                              |
| 表示・アクセシビリティ | DOM計測（意図しないページ横はみ出し、固定領域による遮蔽、操作不能）、コンソールのJS例外・CSP違反・意図しない外部通信、基本キーボード・ラベル・コントラスト・フォーカス・動き抑制確認（WCAG 2.2 AAを目標）。自動検査・詳細読み上げ環境検証は推奨 |
| デザイン品質           | 代表ストレス、1440px・1024px、ライト・両フォント、視覚階層と操作性を実ブラウザで確認。追加幅・画像証跡・独立レビューは推奨。                                                                                                                    |

- Playwright等のブラウザ自動化、axe-core等のアクセシビリティ検査を採用候補とし、Windows PCブラウザ・WSL2開発環境・既存のuv／Jinja2／HTMX・CSPとの適合、ライセンス、再現可能な依存固定を確認して選ぶ。開発・検証用依存に隔離し、製品の実行時依存やNode.js／SPAの必須導入にしない。等価な検査を実現する別方式も可。
- ページ全体の意図しないはみ出し、操作・フォーカスの遮蔽、必要情報への到達不能は不合格。§14.1に従う意図したテーブル内スクロールは、識別・操作・キーボードでの到達と必要情報の確認ができる場合のみ許容する。関連するJS例外・CSP違反・未許可の外部通信は解消し、その他の警告も分類・理由を記録する。自動アクセシビリティ検査の無違反だけでWCAG適合を断定しない。
- 証跡の保存・共有は `AGENTS.md` の証跡境界に従う。実運用の生画像・生ログ・実コメント／発話を共有資産に保存せず、Featureには架空データまたは秘匿確認済みの共有用証跡と安全な識別子だけを残す。承認・回帰・独立レビューの前に画像内容／メタデータ／共有権限を確認し、未確認資料を外部送信しない。
- コマンドまたは操作、対象画面・採用版、確認幅／フォント、期待結果・合否／未検証を簡潔に記録。画像は重要な比較・不具合・回帰に限定可。実ブラウザとfixtureの結果を区別し、未実施を合格にしない。

## 15. デザイン探索・承認・実装手順

実行手順は `prompts/redesign-ui.md` §15 に従う。初期計画直後、録画基盤と独立して架空データの比較3案を提示する。INITIAL・REDESIGNでは3案提示と利用者の明示選択を必須とし、選択前は採用案に依存する製品UI実装を保留する。独立作業は継続し、RESUMEでは選択記録を再利用、REFINEでは採用済み範囲の局所改善に限り再選択不要とする。

## 16. UI受け入れ基準

要求§17のA/B/Cを適用する。以下のチェックは製品機能・安全性・情報デザインの目標と代表検証候補であり、詳細方式の専用実装や全組合せの試験を要求しない。§2.4の簡易方式で同じ利用目的を満たせばよい。初期は8画面・利用者選択・主要導線・正確な状態・安全操作・主要ブラウザの代表操作と基本アクセシビリティをAとして確認する。厳密な復元・通知制御・詳細ドラッグ等はB/C、実施していない詳細は未検証とする。

### 16.1 情報構造と導線

- [ ] 共通ナビゲーションは**8つの主要ナビ（運用・データ5／管理3）**であり、セッション詳細・編集・ログ詳細等は下位ビューとして整理されている。
- [ ] 主要ナビの表示名と順序は「運用・データ：ダッシュボード／配信者一覧／録画履歴／コメント／音声字幕」「管理：システム状態／ログ／設定」。要求仕様§11.1の主要URL（`/logs` を含む）を維持している。
- [ ] ダッシュボードの稼働中配信・最近の録画・警告から、関連する記録や診断へ直接遷移できる。
- [ ] 録画履歴は配信セッションを基本単位とし、録画の有無とコメント収集の有無を混同せず表示できる。
- [ ] 録画のないコメント取得セッションを見失わず、コメント閲覧へ進める。動画なしで架空のSRT操作は出さない。
- [ ] 一覧 → 詳細 → 戻るで、検索条件・絞り込み・ページ位置が維持される。
- [ ] ダッシュボードは状況把握、システム状態は健康状態・診断要約、ログは時系列の詳細調査という役割が明確で、同じ情報の無意味な重複がない。
- [ ] システム状態の警告から関連ログへ、ログから関連する録画履歴・配信者一覧へ、利用可能な識別情報の範囲で遷移できる。

### 16.2 状態・操作・データの正確さ

- [ ] 配信／録画／コメント収集／コメントSRT／音声SRT／ASS／画面更新／操作結果を独立した状態として表示できる。
- [ ] **未取得と0件、監視停止と接続失敗、受付と完了、未生成と生成失敗、現在値と古い値**を明確に区別する。
- [ ] 上部に情報の表示時点を共通配置し、アプリ独自の画面再読込ボタンは設けない。前回値の表示や更新失敗を誤認させず、ページ再読み込みにはブラウザ標準機能を利用する。
- [ ] 定期更新が既定間隔・設定変更・再起動なしの反映に従い、入力・編集中に作業を妨げず、スクロール・フォーカス・検索条件を不用意に失わせない。遅延／逆順応答、送信後の操作開始、非表示復帰、設定保存／入力エラーで操作状態と取得時点を保全する（TC-077、TC-078）。
- [ ] 二重送信を防止し、結果未確認や競合の際に成功と表示しない。
- [ ] 危険操作の対象と影響範囲、未保存変更、操作後の結果を分かりやすく示す。監視／録画／コメントの設定OFFと復帰の影響、および削除2方式・一部失敗を正しく表示する。
- [ ] サービス別監視頻度の入力範囲、共通監視枠、実効値との差、エラー表示が分かりやすい。
- [ ] 録画セグメントごとの動画・SRT対応、状態、欠損区間、再生成可否を識別できる。録画動画・字幕のダウンロード操作を表示しない。
- [ ] 同じ配信の複数録画ジョブのうち最新ジョブが「完了」でも、前ジョブの `FAILED`、`invalid` / `pending` セグメントや既存の欠損区間が隠れず、セッション全体を完全成功と誤表示しない。
- [ ] 過去の飛び番号は機械的に振り直さず、保存された番号・ファイル名・所属ジョブの整合性を崩さない。
- [ ] SRTのスキップ／生成済み／生成失敗／収集未実施を区別し、0cueの空SRTを成功済みとして誤表示しない。
- [ ] 最終メディア検証とDBの不一致、古いエラー、監視のUNKNOWNと明示的終了を識別できる情報・診断導線を備える。
- [ ] コメントを配信横断で検索でき、関連セッションへ移動できる。コメント出力メニューを表示しない。
- [ ] ログは時系列・レベル・出力元・本文を取得可能な範囲で閲覧・絞り込みでき、長文詳細・コピー・空／取得失敗／古い情報の状態を適切に扱う。
- [ ] ログ画面に未提供の収集・ダウンロード・削除・全文検索等の機能を捏造しておらず、ログレベルの編集は設定へ集約されている。

### 16.3 ビジュアル・表示環境・品質

- [ ] ゼロベースの参考調査と採用理由を `<UI>/design.md` に記録する。初期は3〜5件、本格再設計は5〜10件を目安とし、取得不能は記録する。
- [ ] 初期実装・単独再設計ともに、情報構造・密度・シェル・視覚表現が実質的に異なる3案のモックアップを同一画面・同一データで提示する。
- [ ] 利用者が3案から明示的に選択した採用案と選択記録を `<UI>/design.md` に保存し、8画面へ一貫適用する。選択前は採用案に依存する製品UI実装を保留し、独立作業は継続する。
- [ ] Inter、紫グラデーション、光るボタン、セリフ見出しの一語イタリック、4枚並列統計カードの定型を使わず、冗長なAI風装飾を全画面で監査している。
- [ ] 実ブラウザで自己レビューし改善する。独立レビュー・比較画像・上位改善案の記録は単独再設計で推奨、実施不能は未実施とする。
- [ ] UI単独リデザインでは、録画・コメント・DB・API・安全性・CLI・サービス等の**非UIの振る舞いを変更せず**、関連するフロントエンド回帰試験を実施している。

- [ ] ライト系テーマを**1種類のみ**使用し、テーマ切り替えやOSテーマ連動は実装していない。
- [ ] 設定のフォントプルダウンは**Windows標準／Noto Sans JP**の2択。初期値、`palt`、選択保持、プレビュー、全画面反映を検証している。
- [ ] 情報の階層、選定したデザイントークン、テーブルの数値・単位・行高・状態表現が統一され、選定根拠が説明できる。
- [ ] 主要な画面の目的、情報の関係、状態、操作の優先順位が、長い説明文に頼らず**配置・グルーピング・視覚階層**から把握できる。
- [ ] 追加した補助説明・サブタイトル・バッジ・カード・アイコン・グラフには、重複しない明確な役割がある。汎用SaaS風の定型表現やカードの入れ子で情報密度を損ねていない。
- [ ] 必須ラベル・数値単位・状態・安全上の説明を残したうえで、冗長なUI文言を削り、自然で簡潔な日本語にしている。
- [ ] 配信中＝緑、録画中＝赤、コメント収集中＝青。録画中とエラーを形状・文字で区別し、録画連動ロゴ・ファビコンと動きの抑制を確認している。
- [ ] 1440px／1024px、両フォント、キーボード操作、フォーカス、ラベル、コントラストを確認する。1280px・拡大表示の追加検証は推奨。
- [ ] 主要8画面と重要な下位ビューを実ブラウザで確認し、補助説明文を隠すテスト、視覚階層のテスト、代表タスクの操作検証、共通部品の回帰確認を実施している（未実施のものは未検証として記録）。
- [ ] ログイン画面、動画再生、モバイル専用UI、未提供操作を追加していない。
- [ ] 実装できていないUIや未検証の動作を、成功・完成済みとして見せていない。

### 16.4 音声字幕・統合ASSの受け入れ

- [ ] 録画詳細と音声字幕画面でコメントSRT・音声SRT・ASSの対応・暫定／片側／期限削除・生成可否を区別し、発話本文を検索できる。
- [ ] 設定・GPU診断・キューの状態と反映時期が正しく、字幕処理や更新失敗で操作を破壊せず、ファイル本体を配信しない。

### 16.5 設定・検索・診断の受け入れ

- [ ] 全設定の既定値・範囲・単位・反映時期、保存失敗・競合時の入力保持、容量上限・再接続・取得間隔を確認する（TC-089〜090）。
- [ ] 名前・ID検索、デフォルト／カスタム順、ドラッグとキーボード、絞り込み中の制限、版競合と再読込後の保持を確認する（TC-093）。
- [ ] コメント配信別／横断、録画なし・期限削除済み、昇降順、時刻根拠とページ・検索条件の復元を確認する（TC-094）。
- [ ] 収集統計の区別、匿名表示・本文正規化と診断、取得不能を0としないことを確認する（TC-095〜096）。
- [ ] HTTPセキュリティヘッダー・エスケープと実ブラウザ機能の互換性を確認する（TC-091）。
- [ ] 機能別健康状態・エンジン診断・停止中・古い情報、ログの取得可能範囲と診断への導線を確認する（TC-098〜099）。
- [ ] 配信者別容量・警告期間集計・環境要約の正確性、未確認の区別と既存8画面の優先情報・5秒更新を確認する（TC-100）。

### 16.6 入力・照合・操作契約の受け入れ

- [ ] 登録時の入力例・制限・表示名既定・編集時の不変ID・フィールド別エラー・再有効化と入力保持を確認する（TC-102）。
- [ ] 手動照合の受付・重複防止・取消・途中結果・前回結果・未確認・鮮度と診断延期を確認する（TC-103、105）。
- [ ] 共通ページング・日付境界・エラー、同期版競合、非同期受付／完了、重複防止と結果不明時の安全な照合、予算・抑止・終了未確認の履歴削除拒否を確認する（TC-104、107）。

### 16.7 終了未確認・結果未確認・抑止の表示補足

終了未確認のセッションではファイル＋履歴削除を無効化し理由を表示する。ファイルのみは安全条件が成立する場合に限る。設定OFF・手動停止・枯渇・制限・待機を区別する。結果未確認時は危険な再実行を促さず、状態を再取得する。署名枠の不明・待機は診断に反映し、残枠を推測表示しない。

### 16.8 情報デザインの表示契約とストレス検証

- [ ] 主情報／補足情報、独立した比較軸、数値・日時・単位の整列、長い識別子の全文確認を主要一覧で確認し、列の圧縮による情報欠落や過剰な装飾がない（§2.8、6.6）。
- [ ] 8画面と下位ビューの現在地・親への導線、共通表示時点と対象別鮮度、主要操作の配置、拡大時の遮蔽防止を確認する（§3.5）。
- [ ] 一覧の状態記号・ラベル・色、録画連動ロゴ・ファビコン、動き抑制、状態不明時の経過表示、壁時計とメディア長の区別を確認する（§5.5）。
- [ ] 健康状態・優先KPI・補足KPIの階層、稼働中セッション3領域、管理容量とボリューム容量の分母・鮮度、障害集計と診断導線を確認する（§7.4）。
- [ ] 配信者の複合セル、実状態と共通アクセントの設定トグル、行アクションの安全な分離、絞り込み・ドラッグ／キーボード操作と確定順の維持を確認する（§8.1.1）。
- [ ] セッション一覧の比較軸・件数リンク、配信／録画／コメントの概要比較、セグメントに従属する3字幕・版・欠損・安全な削除2方式の表示を確認する（§9.1.1、9.2.1、9.3.1）。
- [ ] 本文中心の領域・投稿者／時刻根拠・配信文脈、配信別／横断検索・条件・昇降順・ページ復元、音声キューと発話本文への文脈リンク、長文・HTML風文字列の安全な表示を確認する（§10.2.1、10A.1）。
- [ ] エンジンの可否／実績、照合の分類別総数と表示件数・前回結果、診断鮮度、ログ重要度・要約／全文・秘匿・関連導線を確認する（§11.5、12.5）。
- [ ] 6カテゴリ内の入力行・範囲・単位・反映条件、保存領域の未保存／失敗／競合／適用待ち、非表示カテゴリのエラーへの移動と入力保持を確認する（§13.6）。
- [ ] 採用済みトークンと共通部品の対応、状態・サービス・操作アイコンの意味統一、両フォントの数値整列、フィルター・ページング・空状態の共通化を全画面で監査する（§6.6）。
- [ ] §14.3の初期代表ケースを実ブラウザで確認し、幅・フォント・結果・未検証を記録する。追加ケースの画像は必要に応じ保存する。

### 16.9 インタラクションとUI品質エンジニアリング

- [ ] 配信者・セッション・コメント・発話・ログ等の安定IDと部品種別でフォーカス・展開・スクロール基準を復元し、行追加・同名・対象消失で誤対象への移動がない（§5.4.1）。
- [ ] 明示検索・ページ送り・保存・入力エラー・ダイアログ閉鎖と定期更新でフォーカス／閲覧位置が契約どおり異なり、遅延・逆順・利用者の移動後に巻き戻らない（§5.4.2）。
- [ ] 全順序編集のドラッグ挿入位置・端スクロール・Escape／ポインター中断・キーボード・クリック代替・動き抑制・確定保存を確認し、競合・結果未確認・絞り込み中の誤保存がない（§8.1.2）。
- [ ] 確定値・送信中・受付／実行中・明示拒否／競合・部分失敗・結果未確認を区別し、応答消失後に現在値／業務ジョブ状態を照合し、危険な再実行をしない（§6.2.1）。
- [ ] 重要度別通知、手動閉鎖、ポインター／フォーカス中の消去停止、同一通知の抑制、周期失敗のインライン表示、読み上げとフォーカス保全を確認する（§6.3.1）。
- [ ] メニュー・タブ・ダイアログの意味に合うキーボード操作とフォーカス復帰、非表示領域への誤移動防止、削除／保持・確認チェックの初期化・安全な取消を確認する（§6.4.1）。
- [ ] 適用済み条件・モード・順序・ページのURL再現、変更時の先頭ページ、範囲外ページ、戻る／進む・閲覧基準復元、自動更新の履歴非追加、秘密／未保存値の非混入を確認する（§6.7）。
- [ ] 型付き比較で元値への復帰、複数カテゴリの変更／入力エラー、成功時のみ基準更新、競合・結果未確認・離脱取消時の入力保持と保存／適用待ちの区別を確認する（§13.7）。
- [ ] 年・日付境界、表示タイムゾーン／DST、24時間超、元の精度・同一秒の安定順・未知時刻、壁時計経過と媒体長を共通整形で検証する（§6.5.1）。
- [ ] 全既知状態・初回未確認・未知コード・古い状態の共通変換と一覧／詳細／概要／ロゴの意味整合を検証し、表示変換が業務状態を変更しない（§5.6）。
- [ ] 隔離fixtureで代表シナリオを確認し、通常起動に開発ルート・模擬機能がなく、実運用資源へ接続しない。実証結果とは区別する（§14.4）。
- [ ] 代表ブラウザ操作・DOMはみ出し／遮蔽・JS／CSP・基本アクセシビリティを確認し、採用版と結果・未検証を記録する。詳細自動検査・撮影・独立レビューは推奨。証跡の秘匿・Git除外は維持する（§14.5、AGENTS.md、TC-111）。
