# LiveRecorder — AIエージェント共通実装プロンプト集

Cursor・Codex・Claude Codeを横断して、初期一気通貫実装、UI選択後の継続、中断・引き継ぎ、初期完成後のUI変更を行う利用者向けガイド。プロンプト本文と完了条件は共通化し、ツール固有のモード切替・Goal操作だけを分離する。

## 1. 実行環境・使い方

### 1.1 使用モデルと共通ルール

| エージェント | 使用モデル  | 推論強度 | 実装モード                           |
| ------------ | ----------- | -------- | ------------------------------------ |
| Cursor       | Grok 4.7    | High     | Agent                                |
| Codex        | GPT-6.2 Sol | Medium   | 通常の実装モード（Plan解除）         |
| Claude Code  | Sonnet 5.5  | Medium   | Plan以外の編集・実行可能な権限モード |

モデル名・強度は利用者指定の運用設定であり、ツールごとの実際の選択肢に合わせて設定する。異なる製品間のMedium/Highを同一の計算量・品質とみなさない。難解な局所問題に限り、必要に応じてモデル・推論強度を変更する。

- リポジトリルートで実行し、既存のブランチ・作業ツリーを使用する。別エージェントへ移る場合は第4.4節に従う。同じ作業ツリーに複数の書き込みエージェントを同時に走らせない。
- `/goal`、`/plan` 等はシェルコマンドではなく、対応ツールの入力欄で実行する。各Goalは1行のまま入力する。コマンドや権限モードの実際の対応状況はインストール版・UI・設定で確認する。特にCursorのGoalは段階的提供。Goalが利用できない場合は同じプロンプトから先頭の `/goal` を除いて通常の実装モードで実行する。
- `implement.md` と `redesign-ui.md` は実行指示、`AGENTS.md` は共通開発規則、`docs/requirements.md`・`docs/system-design.md`・`docs/ui-spec.md` は正本。本書は起動・継続操作のガイドであり、既存の仕様や完了条件を上書きしない。パスはリポジトリルート基準。Claude Codeは `CLAUDE.md` の `@AGENTS.md` を通じて、または直接 `AGENTS.md` を読む。
- Goalはツールの権限、外部試験の許可、Git操作の許可を拡張しない。通常の開発操作を妨げない範囲で個別の権限を設定し、全権限の無条件許可は前提にしない。
- 初期実装ではSpec Kitを使用しない。エージェント固有のPlanモードや内部計画はSpec KitのPlanとは別物であり、使用可能。
- `tasks.md` は同梱済みのタスク一覧ではない。初回実装時にエージェントが機能単位で生成し、以後は同じファイルを更新する。`ui/design.md` もUI探索・選択時に生成・更新する。再開時は既存記録を優先し、欠けている場合だけ実コード・Git履歴・実動作の根拠から必要最小限で復元する。

### 1.2 GoalとPlanの使い分け

**標準：初期実装は第2節のGoalを直接実行する。** `implement.md` §2に既にPhase 1〜8の依存関係と最小計画があり、詳細な正本もあるため、別途全体計画の承認を必須にしない。Goal直行でもエージェントは内部で必要な計画を立て、実測に応じて更新する。

| 作業                                         | 推奨方式                                       |
| -------------------------------------------- | ---------------------------------------------- |
| 初期一気通貫実装                             | Goal直接実行（任意で短いPlan）                 |
| 初期実装の環境・技術リスクに懸念がある       | 短いPlan → Goal                                |
| 大規模構造変更・複数方式が競合する難解な変更 | Plan → Goal                                    |
| 全面UI再設計                                 | Goal直接実行（必要時Plan）                     |
| 小規模修正・局所改善                         | 通常指示、反復が必要ならGoal                   |
| 中断・UI回答・担当交代                       | 既存状態を復元して継続。全体Planを作り直さない |

Planは「どのように進めるか」、Goalは「何が成立するまで進めるか」を扱う。PlanとGoalの併用は、Planを承認して編集可能なモードへ移り、Goalで実行する順序を基本とする。計画のために別の承認ゲートを増やさず、計画の内容は正本を変更しない。

### 1.3 任意：初期実装前の短いPlan

必要な場合だけ、各ツールでPlanモードを選択（`/plan`、モード選択等）して次の通常メッセージを入力する。Planモードに入ったことを確認してから送る。

```text
AGENTS.md、prompts/implement.md、docs/requirements.md、docs/system-design.md、docs/ui-spec.md を読み、現在のリポジトリ・実行環境に照らして初期一気通貫実装の短い実行計画を示してください。既存のPhase 1〜8と完了条件は維持し、最小起動・安全基盤・録画とコメントの縦の疎通への最短経路、UI 5案提示の時期と選択待ち中に進める独立機能、依存ライブラリ・外部API・WSL/Windows/GPUの主要な実現性リスク、必要な試験許可と代替経路だけを重点確認してください。事前にすべての調査・模擬試験を完了させる必要はありません。仕様の再定義、Spec Kit、詳細な再タスク化、派生設計文書、製品コードの変更は不要です。重大な矛盾や利用者の判断が不可欠な事項だけを示し、内部方式は実装担当へ委任できる形にしてください。計画提示後は実装モードで第2節のGoalを実行する予定です。
```

計画はチャットまたはツール標準の計画表示で十分。別の `PLAN.md` や追跡表を必須にしない。計画承認はUI案の選択・実配信等の許可を兼ねない。

| エージェント | Planから実装への移行                                                                                                                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cursor       | Planモードを抜けてAgentへ。Buildで実装が自動開始するUIでは同じ計画を実行し、Goalは入力可能な時点で設定する。二重実行・別チャットからの並行編集はしない。                                                         |
| Codex        | `/plan` またはモード選択でPlanを終了し、通常の編集可能なモードで第2節のGoalを設定する。実装が自動開始した場合は安全な区切りでGoalを設定する。                                                                    |
| Claude Code  | Plan承認後、編集可能な権限モードへ移る。Goalは権限モードを切り替えないためPlanのまま設定しない。承認操作が実装を開始する場合は安全な区切りでGoalを設定する。Auto等は利用可能性・許可範囲を確認し、必須としない。 |

Planを採用した場合は、実装開始時に承認済みの計画を参照し、実測による合理的な修正は `tasks.md` に簡潔に記録する。別ツールで実装する場合は、必要な計画判断のみ `tasks.md` 等に引き継ぐ（会話だけに依存しない）。

## 2. 初期一気通貫実装（3ツール共通・推奨）

通常の編集可能な実装モードで次の1行を入力する。事前にPlanモードを使う必要はない。既存のGoalがある場合は第4節に従う。

```text
/goal prompts/implement.md を実行指示として読み込み、AGENTS.md と docs/requirements.md、docs/system-design.md、docs/ui-spec.md に従ってLiveRecorderの初期実装を一気通貫で完成させる。実装速度や早期終了よりも仕様への忠実性、正確性、実用性、完遂度を優先し、必要な時間と労力をかけて慎重かつ着実に実装する。承認済みのPlanがある場合は正本に反しない範囲で利用し、なければ既存Phaseに沿って必要最小限の内部計画を立てる。各機能の着手時に関連する正本・既存コード・採用版ライブラリの実際の挙動を確認し、推測による仕様変更や仮実装を避ける。特にデータ整合性、状態遷移、非同期・排他処理、外部APIと利用枠、録画・コメントの独立性、媒体の非上書き・保全、字幕生成、機能間の連携には慎重を期す。ただし過剰な事前調査・抽象化・派生文書・大量の模擬試験は避け、最も単純な等価方式で動く製品を作る。調査・計画に留まらず、製品コードの実装、起動、許可された実配信・実ファイル・実ブラウザ等による代表実動作確認、原因分析、修正、再確認を自律的に反復する。初期Spec Kitは使用しない。Phaseや個別機能の終了、テスト成功、進捗報告を全体の終了理由としない。利用者によるUIの5案からの明示選択、必要な許可、重大な仕様変更以外では途中承認を求めず、外部制約や選択待ちがある場合も独立した実行可能な機能を継続する。安全条件・権限・既存データ・Git操作制約を守る。tasks.md に実装状態、検証結果、利用可否、保留根拠、再開点を随時簡潔に記録し、UI選択は ui/design.md に記録する。終了前にタスク一覧だけでなく全正本と実コード・実際の動作結果を照合し、実装漏れ、未接続、通常利用を阻害する不具合、安全性・データ保全・固定契約の欠陥をその場で修正して再確認する。達成条件は prompts/implement.md §4 と docs/requirements.md §1.3 に従い、実行可能な初期残作業が0件であること。追加品質は初期残件と区別する。合理的に解消不能な外部制約のみ根拠・試行・代替・再開条件を記録して保留し、安全未確認の操作は無効化する。未検証を成功とせず、実装完了と実機検証完了を区別する。利用者判断待ち・強制中断・予算上限をGoal達成とみなさず、全体を進められない場合は再開可能な状態で停止する。利用者のUI選択待ちは一時的な停止条件であり、達成・永久的な実装不能ではない。独立作業を尽くしたら選択・許可待ちと再開点を記録して利用者へ制御を返し、同じ質問や失敗を自動反復しない。終了判定の証拠として、実行可能な初期残件数、必須UI選択の記録、実際に実行した起動・代表確認と結果、外部保留の理由と再開条件を会話にも簡潔に提示する。完成時は実際の起動手順、機能別の動作結果、保留事項を事実に即して報告する。
```

このGoalの成果物は実際に使用できるアプリケーション、整合した導入手順と検証結果であり、計画書・進捗報告・テスト結果だけではない。慎重さは製品機能の正確な実装と検証に投入し、形式的な厳密性を追求するためのものではない。

### 2.1 試験許可（必要に応じて通常メッセージで追加）

`implement.md` の「試験許可と再開」に従う。初回またはUI比較時にまとめて回答できる。次の例のうち、実際に許可する項目だけを具体的に記入して送信する。未記入・未回答は許可ではない。資格情報の値は貼り付けない。

```text
次の範囲の試験を許可します。記載した範囲内の修正・再試験に限り追加承認は不要です。
- 実配信：サービス、対象アカウント、目的、期間／終了条件、専用資格情報の選択、無料枠・上限：［記入］
- Windows：専用検証フォルダ、許可する操作、既存環境の保護パス：［記入］
- GPU／実音声：対象の許可済み音声、使用デバイス、モデル配布元と取得許可：［記入］
記載していない試験は許可しません。未許可の試験のみ保留し、独立した実装を続けてください。
```

## 3. UIの比較・選択後の継続

初期実装・単独全面再設計では、利用者がA〜Eの5案から1案を必ず選択する。比較HTMLを実際に開き、採用案を決める。選択前に採用依存実装は行わないが、独立作業は継続可能。UI選択は実配信等の試験許可を兼ねない。

### 3.1 採用案を決定した場合（通常メッセージ）

以下はB案を採用する例。実際に選んだ案に置き換える。既存Goalに対する回答であり、新しい `/goal` ではない。

```text
B案を採用します。採用結果を ui/design.md に記録し、元のGoal・完了条件と既存の実装・作業記録を維持して作業を再開してください。採用案のトークン・共通シェル・必要な共通部品・代表3画面を実表示と実操作で調整し、残り5画面へ展開してください。採用済みのUI比較・完了済みの調査や検証を形式的に繰り返さず、現在のGoalの完了条件まで、残りの実行可能な作業を自律的に続けてください。
```

回答後のGoal操作は第4.1節に従う。Codexでは必要に応じて `/goal resume`、Claude Codeでは通常の回答で継続し、Cursorでは現セッションの状態を確認する。Goalが失われた場合だけ元のGoalを再設定する。自動継続が選択待ちで空転する場合は一時停止または実行を中断し、利用者が選択するまで待つ。UI採用と追加の試験許可を混同しない。

### 3.2 全案を不採用とする場合（通常メッセージ）

```text
現時点ではどの案も採用しません。［具体的な改善点］を反映して、現行の確定UI要件と prompts/redesign-ui.md に従い、比較用の5案を改訂してください。採用案に依存しない作業は継続し、私が明示選択するまでは製品UIへの採用を行わないでください。
```

## 4. 中断・再開

### 4.1 ツール別のGoal操作

| 用途           | Cursor                                                                                             | Codex                        | Claude Code                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 設定           | `/goal <objective>`                                                                                | `/goal <objective>`          | `/goal <condition>`                                                                                                                         |
| 状態確認       | 現セッションの表示・履歴。対応コマンドは実行版で確認                                               | `/goal`                      | `/goal`                                                                                                                                     |
| 一時停止・中断 | CLIでは `Ctrl+C` でGoalを一時停止。GUIでは実行停止UIを確認                                         | `/goal pause`                | 実行中断（CLIの停止操作等）。Goalが残ったか `/goal` で確認                                                                                  |
| 再開           | 既存チャットを開く。CLIは `/resume` でセッション選択。通常の再開指示を使い、Goalの存続・動作を確認 | `/goal resume`（一時停止中） | 既存セッションで通常の再開指示。CLIの `/resume` またはシェルの `claude --resume` / `claude --continue` でセッションを復元後、`/goal` を確認 |
| 解除           | 実行版の対応UI・コマンドを確認                                                                     | `/goal clear`                | `/goal clear`                                                                                                                               |

Cursorの公式資料ではGoalの提供が段階的で、Codexと同一の状態操作やセッションをまたぐGoal復元は確認できない。Claude Codeはセッション終了時に有効だったGoalを再開時に復元するが、達成・解除済みのGoalは復元しない。修復が必要なエラーで解除されることもある。別のGoalを設定すると現在のGoalが置き換わるため、不要な再設定を避ける。Claude Codeの判定モデルは会話に提示された証拠に依存し、独自のファイル読取・コマンド実行はしない。条件は4,000文字以内。3ツール共通で、実装完了の判定根拠を会話に提示し、Goalの達成表示だけを製品完成の根拠にしない。

### 4.2 使用量制限・強制中断・コンテキスト圧縮後

同じセッション・ブランチ・作業ツリーを優先する。第4.1節に従い現在のGoalと実行状態を確認し、利用可能な状態になってから再開する。Goalが有効で自動継続中なら重複指示は不要。UI回答・必要許可があれば先に伝える。Codex・Claude Codeでは `/compact`、Cursor CLIでは `/summarize`（`/compress`）等が利用できるが、圧縮前後でファイルの実装状態が変わるわけではない。

再開指示が必要な場合、または新しいセッションに移った場合は次の通常メッセージを使う。

```text
現在のGoalと作業状態を復元し、中断された作業を再開してください。AGENTS.md、対象の実行指示（初期実装なら prompts/implement.md）、関連正本、tasks.md、ui/design.md を確認し、現在のブランチ、HEAD、Git履歴、ステージ済み・未ステージ差分、未追跡ファイル、実装済みコード、稼働プロセスと実行版、直近の検証結果を照合してください。中断時にコミット済みなら作業ツリーの差分が空でも未実装と判断せず、作業開始時の基準コミットまたは既知の直前チェックポイントからのコミット履歴・累積差分と現行コードを確認してください。基準が不明なら履歴と実コードから必要な範囲を復元し、推測で基準を決めないでください。存在しない作業記録は必要最小限で復元し、既存変更・利用者の選択・許可範囲を保護してください。完了済みの作業・選択済みUI・調査・試験を形式的にやり直さず、記録と実際の状態の食い違いを解消して次の実行可能な残件から着手してください。仕様への忠実性と正確性を優先し、実装・代表実動作確認・修正を続け、元の完了条件まで進めてください。無断コミット、ブランチ変更、初期化、作業ツリーの削除は行わないでください。
```

Goalが解除された、誤って達成扱いされた、別ツールへ移ったなど復元不能の場合は、元のGoal（初期は第2節、UI単独変更は第5節）を新しいセッションで設定する。必要な引き継ぎ情報を先に提示し、既存作業を再利用するよう指示する。通常指示が先に実装を開始する場合は二重起動せず、Goal設定は安全な区切りで行う。

### 4.3 難解な問題・進捗が停滞した場合（通常メッセージ）

```text
現在の停滞箇所について、実際のエラー、ログ、採用版ソース、関連仕様から原因を絞り込んでください。必要な時間をかけて慎重に分析し、最小の再現・修正・再確認によって解決してください。同じ失敗や調査を根拠なく繰り返さず、必要に応じて正当な代替経路を評価してください。外部要因で解消不能な範囲だけを根拠と再開条件付きで保留し、独立した実行可能な作業を現在のGoalに従って続けてください。
```

必要なら難解な箇所だけ利用可能な上位推論強度や別モデルに切り替える。既存の実装を最初からやり直す必要はない。別エージェントへの移行は次節に従う。

### 4.4 コミットによるチェックポイント保存・別エージェントへの引き継ぎ（任意）

使用量制限に達する前やUI選択待ちなどの安全な区切りで、利用者が必要に応じてコミットを明示許可する。`AGENTS.md` は無断commit・push・ブランチ切替を禁止しているため、Goalの設定だけでコミットを許可したことにはならない。強制中断後にAIが自動で保存できる保証はない。`tasks.md` は平常時から随時更新する。

作業開始時のブランチと基準HEAD（例：`git rev-parse HEAD`）を利用者のメモまたは `tasks.md` に記録すると、コミット済みの進捗も追跡しやすい。コミット自身のSHAはそのコミット内に書けないため、作成後の報告・Git履歴で確認する。

保存したい時点で次の通常メッセージを入力する。これはその時点の対象変更に限るコミット許可であり、以降の自動コミットの許可ではない。

```text
現在の作業を安全な区切りで停止し、tasks.md と必要に応じて ui/design.md を更新してください。機能別実装・実動作確認・利用可否、次の残件、外部保留の根拠と再開条件、UI選択・試験許可の状態（秘密の値は不要）、必要な実行環境・稼働状態を簡潔に記録してください。今回の作業に属するコミット可能な変更だけを確認し、AGENTS.md の規則で対象パスを明示してステージ・コミットしてください。既存の他の変更、秘密、DB、録画、生コメント・ログ、実行状態を混入させず、既存ステージ済み変更も保護してください。混在して安全に分離できなければコミットせず理由を示してください。push、ブランチ切替、破壊的操作は不要です。コミット後のSHA、残存差分、次の再開点を報告してください。これは中断保存であり完成報告ではありません。
```

再開時の確認方法（読み取り専用の例。`<BASE>` は作業開始時または既知のチェックポイントのコミットIDに置換する）。

```bash
git branch --show-current
git rev-parse HEAD
git status --short
git log -n 10 --oneline
git diff --stat
git diff --cached --stat
git log --oneline <BASE>..HEAD
git diff --stat <BASE> HEAD
```

必要に応じて `git diff`、`git diff --cached`、`git diff <BASE> HEAD -- <paths>`、`git show <commit>` で対象の内容を確認する。未追跡ファイルは `git status` から個別に確認する。基準コミットが現在の履歴と異なる場合は関係を確認し、勝手にmerge・rebase・resetしない。`git diff HEAD` が空でも実装がないことを意味しない。チェックポイントコミットは完成や試験成功を保証しない。

別エージェントへ交代する際は、旧エージェントの書き込み・バックグラウンド作業が停止したことを確認する。既存のアプリ・DB・録画処理を無断停止しない。新エージェントでは同じローカルブランチ・作業ツリーを開き、`AGENTS.md` と記録、Git履歴、現行コードから第4.2節の状態復元を行う。旧セッションのGoalやPlan・権限が自動移植されるとは限らない。元のGoalを新エージェントに設定し、選択済みUIと実装済み機能を再生成せず継続する。許可された試験範囲は明示的な記録・利用者の指示で確認し、不明な許可は引き継いだとみなさない。

## 5. 初期完成後のUI単独変更（任意）

初期実装のGoalが終了してから、必要に応じて別のGoalとして開始する。初期実装中のUI作業は第2節のGoalに含まれるため、別Goalに分割しない。

### 5.1 全面再設計（REDESIGN）

```text
/goal prompts/redesign-ui.md をREDESIGNとして実行し、AGENTS.md と関連する正本に従ってLiveRecorderの製品UIを再設計・実装する。既存UIと実際のバックエンド契約を確認し、最優先リファレンスを基に5案の比較プレビューを提示して、利用者の明示選択後に採用案のみを製品化する。確定8画面・操作・単一ライトテーマ等のUI条件と非UI契約を維持する。速度より正確性・視覚的品質・実用性を優先し、代表3画面から実データ・操作へ接続し、実ブラウザで視認・修正・再確認して全画面へ展開する。既存の録画・コメント・DB・API・CLI・安全性を無断変更せず、不要な抽象化や過剰な試験を避ける。ui/design.md と tasks.md に必要な記録を残し、対象UIの実行可能な残件を解消して README・manual を実装と一致させる。追加承認は正本で必要な場合のみ。比較案の提示や未検証を完成とみなさず、解消不能な外部制約は正本に従って記録・保留する。UI選択待ちは一時停止であり達成ではない。実際に確認した表示・操作、残件、保留根拠を会話にも示す。
```

5案の選択後は第3.1節で継続する。

### 5.2 採用デザイン内の局所改善（REFINE）

`［対象・改善内容］` を具体的な指示に置き換える。局所改善の場合は5案の再比較は不要。

```text
/goal prompts/redesign-ui.md をREFINEとして実行し、採用済みデザインを維持したまま［対象・改善内容］を改善する。関連正本・ui/design.md・現行コードと実表示を確認し、非UI契約と既存の正常動作を維持しながら最小の実用的な修正を行う。速度より正確性と実用性を優先し、対象画面と影響する共通部品を実ブラウザで視認・操作して修正結果を再確認する。実行可能な対象残件を解消し、実施した確認と未検証範囲を記録する。5案の再比較、無関係な再設計、非UIの再実装は行わない。実際の表示・操作確認結果と対象残件の有無を会話にも示す。
```

## 6. 終了時の確認

Goalの状態と製品の完成状態を混同しない。初期実装の完了判定は `implement.md` §4 と `docs/requirements.md` §1.3 に従う。最終報告では少なくとも次を区別する。

- 実装済み機能と実行可能な初期残件の有無。
- 実機確認済み、ローカル確認のみ、失敗、未確認、利用不可の範囲。
- 外部制約による保留の理由と再開条件、安全未確認の操作の無効化。
- 実際の起動手順と導入資料の整合性。

外部制約を除いて初期実装が完了していても、実機検証が残るなら「実装完了・実機検証残あり」など事実に即した表現とする。利用者判断待ち、使用量制限、強制中断は完了ではない。Goalの自動継続は権限・実行環境・利用予算の制約を超えるものではなく、無期限の継続や完成を保証しない。
