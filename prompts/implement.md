# LiveRecorder — Spec Kit 一気通貫実装プロンプト

あなたはシニアPythonエンジニアです。趣味・単一利用者向けのLiveRecorderを、GitHub Spec Kitで仕様化・計画・実装・検証し、実際に使える状態まで自律的に進めてください。応答・報告は日本語。設計書やスケルトンだけで終了しないでください。

## 1. 正本と作業範囲

毎セッション `AGENTS.md`（および利用中のエージェント固有指示）、開始・再開時は本書を全文確認する。要求正本は全体方針・拘束力・現在の機能に関係する節、統合設計は関連境界・設計節、UI正本とredesign-ui.mdはUI作業時に必要な範囲を読む。pyproject.toml・README・manual・コード・テスト・Featureは現在のタスクに応じ参照する。初回は目次・横断制約・依存を把握し、変更時は関連節を追加確認する。毎工程の全正本全文再読込や派生文書への全文転記は不要。製品要件は要求正本、UI固有条件はUI正本、技術設計は統合設計に従う。要求§1.3のMUST／SHOULD／MAYを全正本に適用する。確定機能・安全条件は維持し、内部構造・処理手順・状態管理・検証は等価な単純方式を採用できる。SHOULDの延期・差分は短く記録し、個別承認不要。合理的な技術選択・可逆的な仮定・正本に合わせる派生文書修正は委任されている。進捗と判断はtasks.md等に簡潔に記録する。

**Hard Gate**：実運用の無断停止・変更・データ破壊、秘密漏えい、未許可の実配信／署名等の外部サービス接続、利用条件違反、保護パス衝突、重大な製品仕様変更、許可されていないGit操作を禁止する。安全確認不能なら該当操作を止め、独立作業を進める。通常の開発用依存取得・公開資料閲覧・正当な静的資産取得は委任済み。モデル取得は要求§7.9の条件、ローカル自動試験は外部通信禁止を維持する。通常運用の登録・有効化による許可と、開発者／実接続試験の対象・目的・期間または終了条件・予算範囲の明示許可を要求§15.2.1に従って区別し、許可内の通常再試行に追加承認を求めない。

**Soft Gate**：技術調査、設計レビュー、候補比較、追加品質試験は推奨（UIの3案提示と利用者選択は必須）。不足は記録し、独立機能の実装を止めない。

**UI選択条件**：初期UI・全面リデザインでは3案を提示し、利用者が明示選択するまで採用案依存の製品UI実装のみ保留する。可能な独立作業を継続し、選択後は追加承認なしで進める。質問でターンが終了する環境では、比較案の参照先・未選択状態・対象Feature・完了／未完了タスク・次の独立作業をtasks.mdとUI設計記録に保存し、回答後に同じFeatureで続行する。バックグラウンド作業は前提にしない。

**Release Criteria**：実装済み・ローカル検証済み・実機検証済み・未検証・未実装を区別し、実運用を安全に開始できる機能だけを有効化する。未実証を成功にしない。実配信やGPUが利用できないことはUI実装の停止理由にしない。

## 2. Spec Kitによる一気通貫実装

### 2.0 初期化・再開

Gitの現在ブランチと差分を確認する。利用者の実装開始指示は現在のブランチ（mainを含む）での通常編集を許可する。既存変更を保護し、無断ブランチ作成・切替・commit・push・merge・reset・cleanを禁止する。フックにも適用する。Git未初期化や既存ファイルの破壊的上書きは確認する。

スターターには `.specify/`、`specs/`、生成Skillsを収録しない。`specify --help`、`specify init --help`、採用版の公式手順を確認し、必要ならuv toolでSpec Kitを導入する。利用中のエージェントに対応する統合を選び、例として `specify init --here --integration <統合名> --script sh` を使用する（採用版のヘルプ優先）。既存正本を保護し、無断で再初期化しない。生成済みSkillsの手順を読み、直接呼出し不能なら該当SKILL.mdの手順を実行する。既存憲法を再利用または正本に整合させ、未生成なら `speckit-constitution` でAGENTS.mdから生成する。

初期実装は単一Feature `initial-live-recorder`、初回 `specs/001-initial-live-recorder/`。`SPECIFY_FEATURE_DIRECTORY`、`.specify/feature.json`、既存候補を照合して明示指定する。ブランチ名から推測しない。既存Featureの番号・成果物を保持し、既存spec.mdを再Specifyで上書きしない。競合する対象が解決できない場合は当該書込みを止める。中断再開はtasks.md・コード・検証結果を確認し、不足工程から続行する。

### 2.1 工程

1. Constitution（未生成時）→ Specify → Clarify（重大かつ合理的に判断不能な事項のみ）→ Plan → Tasks → Checklist（簡易確認、採用Skillの契約に従う）→ Analyze（原則1回）。
2. Analyzeは読取専用。指摘を確認し、正本への整合修正を別工程で行う。開始指示でプロジェクト側の修正は包括委任済み。採用Skillが個別承認を求める場合はその契約を守るが、プロジェクト独自の重複承認を追加しない。承認対象だけを保留し、独立作業を続ける。ターン終了が必要なら現在地を記録して再開する。重大な仕様変更は利用者判断を求める。関係ない実装を停止しない。
3. Implementで独立して動作する単位を実装し、その場でテスト・修正する。
4. Convergeは重要な未実装・不具合がある場合に限り、採用Skillの追記専用契約を守って追加タスク→実装→回帰を行う。全体監査の繰返しではなく差分を中心にする。

spec.md、plan.md、tasks.mdを中心に、採用Skillが要求する成果物を作る。research.mdは採用判断、data-model.md・contracts/は未確定事項や複雑な境界の具体化、quickstart.mdは実行手順、checklists/requirements.mdは簡潔な品質確認とする。正本の全文複製は不要。traceability.mdに機能、AC／TC、関連FR／DM／RISK、タスクまたはテスト、結果をまとめ、未検証は明記する。独立監査という別工程は設けず、全AC/TCの簡易照合は統合時に一度行い、以降は変更範囲と関連回帰を確認する。固定IDの存在・参照切れは簡易スクリプト等で自動化してよい。AC-054／055／082、TC-068／069／109は開発チェックで、製品pytestの必須条件ではない。

## 3. 実装順序（依存する作業だけを待つ）

以下は優先順の目安。単一Featureのtasks.mdに実際の技術依存を記載し、独立タスクは並行・前後して実施できる。

### Phase 1：環境・最小準備と早期UI比較

Windows 11／WSL2 Ubuntu 24.04／Python 3.12／uvを確認。`uv python pin 3.12`、初回 `uv lock`、必要に応じ `uv sync --locked --no-install-project`、最小パッケージ作成後 `uv sync --locked`。音声extraは後段で同期。pyproject.tomlの依存下限・ビルド依存は採用候補であり、互換性・取得不能・解決失敗時は必要機能と安全条件を保つ範囲で版制約を調整し、理由を記録して再lockする。uvが未使用extraも解決するためspeechの衝突がコアを妨げる場合は、一時的にextra定義を分離し、音声段階で正式定義とロックを復元する。既存ロックを理由なく更新しない。FFmpeg／ffprobeを確認。TikTokLive、Euler Stream、Streamlink、yt-dlp、ツイキャス公式API・匿名番号・HLS、録画権限・ライセンス・無料枠から有望経路を選ぶ。各機能の有望な第一候補を1つ選び正常経路から実装する。全候補の同時実装・実証は不要。確定機能として必要な代替経路は後段で拡充し、未実装は明記する。安全・利用条件に不明があれば実接続だけを保留。実装後に採用実証する。匿名番号の確実な取得経路がなければNULLとし、他のコメント機能を進める。

**初期計画直後（Phase 1から独立タスクとして着手）**：`prompts/redesign-ui.md` INITIALに従って架空データで3案を提示し、利用者の明示選択を求める。実配信、API実装、DB完成、字幕実証を待たない。選択待ちは採用案依存の製品UIのみ保留。比較提示後に実行可能なら独立実装を進める。質問でターン終了する場合は§1の再開手順を使い、回答後に同じFeatureで採用案を展開する。選択の代行禁止。

### Phase 2：最小隔離とTikTok垂直スライス

一時SQLite・最小設定・ログ・CLI・専用Linux保存先・外部通信拒否・worker別隔離を先行。空の隔離DBから登録・起動・停止・保存確認を可能にする。直ちにTikTokの検知→独立した録画とコメント→SQLite→確定動画→コメントSRTをローカルHLS／模擬イベントと実FFmpegで通す。命名・時刻・非上書き・管理対象保全・状態の正確さを守る。全設定レジストリ、詳細診断、削除台帳、完全復旧機構、全否定試験の完成を着手条件にしない。未整備の危険操作・実運用は無効。許可済み実配信があれば必要な実接続境界を先に確認して検証する。

### Phase 3：コア拡充・ツイキャス・共通基盤（独立作業可）

垂直スライスを基にSQLite／Alembic、設定レジストリ、状態・ログ、通常／隔離設定解決・保護パス・排他、共通サービスを必要分から整備する。ツイキャスも同じコアで実装し、公式HLS等の優先順、プリロール、コメントAPI・匿名番号経路を確認する。明示制限時は代替経路で回避しない。状態・配信ID・再接続・欠損・時刻・ファイル確定・世代・削除・期限の不変条件を実用化までに満たす。セグメント単位の共通ガード・SQLite共通台帳・同一ボリューム一時ファイルで録画確定／字幕公開／削除の機構を共有し、未完了対象の限定照合を優先。不明対象は安全な保留・手動確認とし、自動修復を強制しない。復元は要求§15.2.1の停止・退避・検査・マーカー・照合または安全な差戻しを中心に、専用復元UIや自動修復なしでよい。通常運用と開発者モードを分離し、開発支援は既存API、Swagger/OpenAPI、詳細ログ、diagnose、隔離fixtureとスナップショットを優先。専用トークン経路や障害注入APIは必要時のみ。

### Phase 4：Web／APIと音声後処理（独立実装可）

履歴・検索・設定・ログ・システム状態・手動照合、音声字幕を含む8画面と必要下位ビューを作る。早期に選択済みのUI案を展開し、未選択なら採用案依存部分のみ保留。実配信や字幕未実証でもfixtureで検証する。UI正本§2.4に従い標準HTML、操作中DOM非置換、標準GET／リンク、簡易ドラッグ・上下移動、重要通知の手動閉鎖を優先。同期操作は短いDB取引、非同期は業務ジョブ・台帳で重複防止。通常運用のHTTP防御と動画・全字幕本体のHTTP非公開を維持する。

音声段階で `uv sync --locked --extra speech`（必要な依存調整後にlock）を実施。faster-whisperは遅延importまたは子プロセス内で読み込み、未導入・モデル未取得・GPU不可は理由付きblockedとし、録画／コメント／Webを止めない。基本VAD・時間境界・音声SRT・基本レーンの統合ASS、GPU／明示CPU選択、独立実行、公開・再生成・削除・期限処理、旧正常版保護を実装。高度な品質フィルタ・語時刻・高密度最適化・詳細負荷試験は追加品質。採用環境で実音声・外部プレイヤーを確認できれば実施する。音声SRTとASSは初期製品の正式機能のまま維持する。

### Phase 5：運用・統合・収束

WSL起動・Windowsサインイン起動、停止・復旧、管理対象の保存先、ログ回転・バックアップ・停止中手動復元を整備。通常と隔離開発者の診断、隔離コピーからの調査、外部通信排他・永続予算を確認する。実運用データを開発者起動に直接使用しない。実機条件が未確認なら当該機能を保留して報告する。最終的に正本の全ACを簡易照合し、重要な欠落を修正する。

## 4. 技術制約と安全性

要求§2・§10・§13・§14、設計§3・§10.1.1・§16、AGENTS.mdに従う。単一管理プロセスと必要な子プロセス、SQLiteのLinux側保存、通常のWindows側録画、サービス横断の配信者フォルダ、独立録画・コメント、秘密非露出、ループバック限定を維持する。実効パスをDB設定まで含めて確認し、既存アプリの領域・稼働プロセスを変更しない。録画ルート未接続や不明時は媒体操作のみ安全に保留する。排他的な媒体確定方式は要求§10.3に従い隔離Linuxで先行し、実使用Windowsマウントの専用試験フォルダで非上書き等を実証するまで通常媒体操作を保留する。過剰な抽象・将来用ダミー・別SPA・不要な基盤は追加しない。

## 5. 検証と修正

要求§17のA/B/Cを正とする。初期はAの基本正常系・重要否定系を優先し、複合TCの詳細はB/Cへ延期可。B/Cでも要求§17の代表安全条件は利用開始前に確認し、未達の操作を無効化する。安全性に関わる条件は利用開始前に確認する。複数IDの統合検証を認め、専用pytestや全組合せは不要。コア段階は `uv run --locked ruff check .`、独立試験は `uv run --locked pytest -n auto -m "not serial and not live and not hardware"`、続いて `uv run --locked pytest -n 0 -m "serial and not live and not hardware"`。音声導入後は `--extra speech` を加えて関連試験を行う。負荷に合わせworker数を調整し、対象テストは直列デバッグ可。実配信／実機は明示許可と `--run-live`／`--run-hardware`、実通信排他を要する。ローカルでは外部接続・モデル取得を拒否し、所有子だけを回収する。未実行・skip・想定外0件を成功にしない。

コアの独立性、誤削除防止、時刻同期、状態区別、再起動、HTTP防御、並列隔離を重点的に試験する。UIの代表ブラウザ検証はUI正本に従う。実配信・GPU・Windows等の実機結果とローカル試験を分ける。修正後の稼働コード版を確認し、失敗は原因・修正・関連回帰まで進める。実装に必要な情報が不足する場合、可逆的仮定で進めるか該当箇所だけ保留する。安全な既存処理を壊してテストを通さない。

同一原因への調査・修正・再検証で有意な進展がなくなったら、回数固定ではなく進展と重要度で打ち切り、原因・試行・未解決・再評価条件をtasks.md等に短く残して独立作業へ移る。安全未達は無効化し、統合時に重要な残課題を再評価する。無期限の反復や全体監査の繰返しをしない。

## 6. 完了・報告

README・manualを実装されたCLI・画面・動作に合わせる。実装・検証していないものを既成事実にしない。完成度は要求§17.5のL0〜L4に従う。一気通貫の目標はL2（2サービス・3種字幕・8画面・基本管理／運用の実装と代表ローカル検証）。外部API・GPU等の実測未了は別に記録し、未実装のMUSTがあればL2未達／部分到達とする。L3は機能ごとに実使用環境での基本経路・安全条件を確認して判定する。追加品質はL4で改善し、全体停止ゲートにしない。機能ごとに実装／検証／利用可否を明示し、安全に使用できない操作は無効化する。

最終報告は実装済み機能、起動手順、実行コマンド・結果、未実装／未検証・既知問題・次の作業に絞る。途中中断時はtasks.mdに現在地を残す。UI選択待ちの場合は3案の参照先と未選択状態を残し、利用者の回答後は同じFeatureで再開する。利用者の指示なしにcommit・push・mergeしない。
