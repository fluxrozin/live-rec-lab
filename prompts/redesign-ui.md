# LiveRecorder — UI専用再設計・実装プロンプト

## 1. 対象

`AGENTS.md`、`docs/requirements.md`、`docs/ui-spec.md`、現行UI・実装契約を確認し、UIを優先リファレンスに基づいて継承・改善し、実データ・操作へ接続する。単独実行はUI変更に限定し、API・DB・録画・コメント・安全性・CLIを勝手に変更しない。不足するバックエンドは報告し、初期全体実装時は全体タスクで完成させる。INITIAL（初期）、REDESIGN（単独全面）、RESUME、REFINE（採用デザイン内の局所改善）を区別する。INITIALではSpec Kit不使用、記録先は `ui/design.md` とルート `tasks.md`。初期完成後の単独変更では利用者希望時のみSpec Kitを利用可。

## 2. デザイン課題

**LiveRecorder — Modern Operations Console**：高品質なエンジニア向けSaaS管理画面と常時稼働するシステムの運用監視コンソールを融合する。Modern（現代的）、Minimal（必要十分）、Refined（洗練）、Professional（業務品質）、Data-centric（データ中心）、Calm（落ち着き）、Precise（正確）、Functional（機能的）、Consistent（一貫性）を設計の基本概念とする。高級感は装飾ではなく、整ったレイアウト、余白、文字、配色、情報密度によって表現する。

品質は `docs/ui-spec.md` §2.3.1 の観点で改善優先順位を決める。未調整の標準フォーム、古い管理画面、Bootstrap既定風外観、太い境界線、原色・過剰なグラスモーフィズム、均一カードの反復を避ける。標準HTMLは共通スタイルで活用する。

確定8画面・URL、単一ライト、意味色、Windows標準／Noto Sans JP、配信中・録画中・コメント収集中のパルス付き共通状態バッジ（動き抑制等を含む）、操作・情報の正確さは維持。`docs/ui-spec.md` §2.9〜2.10、§3.4、§5.5、§6.1.1、§13.6.1を重点とし、文字階層、余白・角丸、ライト配色、シェル、共通部品、設定画面を優先して継承する。説明文ではなく構造・密度・視覚階層・グルーピングで意味を伝え、AI的定型装飾・架空KPIを避ける。実際の利用タスク、空・長文・異常時の情報と操作を優先。内部の詳細復元や検査基盤は必要最小限。自動更新は操作中延期・旧応答破棄、フォーカスは標準HTML、通知はインラインと簡易トースト、並べ替えは簡易ドラッグ＋上下移動、検索は標準フォーム／ページ遷移を優先。詳細復元・端スクロール・専用検査基盤は追加品質。字幕は終了後生成の状態、削除はアーカイブ全体、保存期限は一つとする。

## 3. 探索・選択・実装

### 3.1 現状把握

利用タスク・必要な情報・実装状況を確認。

- INITIAL：現行の製品要求・UI・公開契約、優先リファレンスの画面／コード、存在する範囲の実装済みAPI・ルート・テンプレート変数・フォーム・CSRF・HTMXを確認する。未実装部分は設計契約を使い、旧リポジトリの契約を現行のものと推測しない。まだ存在しない現行UIの監査は不要。コア実装と並行して比較を開始できる。
- REDESIGN：現行アプリの関連テンプレート・CSS・共通部品・JS・FastAPIルート、テンプレート変数、フォームの値／保存範囲、POST・CSRF、HTMXのリクエスト／ターゲット／スワップ、API・バックエンド依存をコードと実表示から確認し、情報階層・密度・重複・操作・可読性の主要な改善点を特定する。既存の非UI契約を推測で変更しない。
- RESUME／REFINE：記録済みの調査を活用し、変更対象と関連契約に絞る。全監査のやり直しは不要。

公開情報のWeb検索は `AGENTS.md` に従い自律的に利用する。同じ架空データを用い、実データ成功と混同しない。

### 3.2 リファレンスハンター

最優先は <https://github.com/fluxrozin/live-recorder>（`docs/ui-spec.md` §2.9）。参照コミットを確認し、ライトの1440px画像（実画面・状態別）とシェル／tokens.css／app.css／共通マクロ／設定等のコードから、重点6領域・画面別構成・操作を分析する。旧仕様をそのまま移植しない。現行設定5秒更新・既定50件ページングを維持する。追加の外部UI（Linear、Vercel Dashboard、Raycast、GitHub等）は第二リファレンスとして改善に必要な場合だけ調査し、件数目標や全画像の取得を完了条件にしない。URL・版・実画面／画像／文書のみの区別・採否を `ui/design.md` に簡潔に記録する。閲覧不能なら同梱の基準値を使い、取得不能を明示して継続する。権限不明画像は共有・Git追加せずURLと分析を記録。コード再利用は現行契約・ライセンス・依存・CSPを確認する。

### 3.3 5つの比較用モックアップ

同じ基準時刻・矛盾のない架空データ・代表表示幅（原則1440px）・共通利用タスクで、設計思想の異なるA〜Eの5案を、利用者が閲覧できる共通比較用プレビューページ（HTML等、案切替または個別プレビューへのリンク）として提示する。以下を標準候補とする。

| 案  | デザイン方向                            | 主な差別化                                                                                 |
| --- | --------------------------------------- | ------------------------------------------------------------------------------------------ |
| A   | Heritage Console — 既存UI継承型         | 最優先リファレンスのシェル・密度・トークン・共通部品・設定を強く継承し、現行確定条件へ適応 |
| B   | Precision Workspace — 高密度・精密型    | Linear等を参考に、テーブル中心、整列、検索・比較効率、装飾の抑制                           |
| C   | Operations Monitor — 運用監視特化型     | 稼働中セッションと異常・鮮度の視認を優先し、監視に適した情報階層・配置                     |
| D   | Calm Studio — 洗練・静穏型              | Vercel DashboardやRaycast等を参考に、タイポグラフィ・余白・控えめな境界・設定の洗練        |
| E   | Functional Desktop — デスクトップ実用型 | Windowsアプリに近い操作感、反復操作・設定変更の効率、簡潔な操作配置（Web技術のまま実現）   |

Aは必ず既存UI継承型とし、B〜Eは調査結果に基づくより良い設計方向へ変更してよい。ただし5案すべてに実質的な差（情報階層、レイアウト、密度、視線誘導、操作部品、設定など）を持たせ、色・フォント・角丸だけの違いは不可。確定8画面・ナビゲーション、単一ライト、フォント2択、意味色、稼働中のパルスバッジ、設定の縦型カテゴリナビと共通保存バー、安全性・操作契約は全案共通。具体的な寸法・色コード・文字サイズ等は各案の思想に応じ調整できる。

各案は共通シェル付きダッシュボードを中心に、配信者一覧の代表行・検索／操作配置、設定のカテゴリナビ・設定行・保存バー、主要な共通部品（状態バッジ・ボタン・入力等）を同じ架空データで視覚比較できるようにする。配信者一覧と設定は部分見本でも十分で、完全な画面を各案で作る必要はない。重点6領域の差を実際に見比べられるものとし、各案の設計意図・利点・欠点・相対的な実装負担・主要差分・推奨理由を簡潔に示す。

標準成果物は1つのスタンドアロンHTML比較ページ（A〜E切替またはリンク、共通架空データ、ダッシュボード中心、配信者一覧・設定・共通部品の部分見本、短い比較）とする。実際に開けるファイルまたはローカルURLを提示し、閲覧のためだけに製品バックエンドやNode.jsを必須としない。静的HTML・CSS・最小JSで十分。比較用は隔離された軽量なモックアップとし、5案×8画面の制作、実API／DB接続、詳細操作、専用比較フレームワーク、製品のテーマ切替機構は不要。閲覧できる成果物を提示し、利用可能ならブラウザで代表表示を確認する。比較データ・資産を共用し、採用された1案だけを製品実装・検証する。

### 3.4 採用案の決定

**INITIAL・REDESIGNは利用者が5案から必ず明示選択する。** AIの代行・既定案の自動採用・無回答承認は禁止。選択前は採用依存実装・8画面展開を保留。独立作業は継続可。ターンが終了する場合は `ui/design.md`（初期完成後にSpec Kitを採用した場合のみ既存Feature内でも可）に5案の参照先・未選択状態、作業メモに再開点を記録。回答後は同一作業を再開し、選択された1案を製品UIとして実装する。選択案の設計思想・確定条件を損なわない範囲で他案の有用な部品・工夫を取り入れてよい。追加のデザイン承認不要。INITIALの選択質問と合わせ、必要なら実配信・Windows専用試験領域・GPU／モデル取得の許可を目的・対象・期間・予算とともにまとめて求める（選択と個々の試験許可は別判定、未回答は許可ではない）。許可待ちは該当試験だけ保留し、独立実装を続ける。全案不採用なら利用者の指摘を反映した改訂5案を提示する。RESUMEは記録済み選択を再利用、REFINEは局所改善のみ再選択不要。

### 3.5 デザインシステム

選択・採用理由、背景・文字・余白・境界・意味色・部品・フォーカス等を `ui/design.md` に記録して共通化。具体値は `docs/ui-spec.md` §2.10を起点に採用案で調整する。シェル寸法、タイポグラフィ、余白・角丸、ライトテーマ、共通状態バッジ、設定配置の採用値と主要差分を簡潔に記録する。必要な資産はローカル。参考コードの全移植・追加設計文書は不要。

### 3.6 実装・確認

`docs/ui-spec.md` §15.1 の順序を基本とする。トークン → 共通シェル → 必要な共通部品 → ダッシュボード・配信者一覧・設定の代表3画面 → 実表示・操作と共通側の修正 → 残り5画面・下位ビュー → 統合確認。設定は実設定・全カテゴリの入力保持・共通保存バー・保存結果・フォントプレビューまで先行接続する。必要な共通部品をJinja2マクロ／includeと共通CSSで揃え、UI正本§6.1.1の候補構成を使う。`tokens.css`・`app.css`・共通Jinja2マクロ／includeと最小JSを基本に、実画面で使う部品だけを作る。全コンポーネントの事前完成、デザインシステム管理ツール・専用ギャラリーは不要。承認ゲートを増やさず、独立作業は並行する。

ソースコード・DOM計測・自動試験の静的な結果だけでデザイン品質を判断しない。利用可能な実ブラウザでレンダリングした画面そのものを視認し（必要ならスクリーンショット、Playwright等で取得した画像）、文字の切れ・日本語と英数字の揃い・余白・密度・境界／角丸・状態バッジとアイコンの位置・設定入力と単位・共通シェルの整列を確認する。発見した問題を報告だけで終わらせず、実用性を損なうものをその場で修正し、影響する画面を再表示して確認する。共通部品・トークンに原因があればそこで修正し、画面別のCSS上書きを積み重ねない。実表示を確認できない環境では確認済みとせず、代替のローカル確認と未検証範囲を記録して独立実装を続ける。固定回数、全組合せの撮影、画像比較基盤、採点による合格ゲートは不要。

ダッシュボードは概況、データ一覧は比較・検索、コメント／発話は本文、設定は入力と確認を優先して密度を使い分ける。実フォントと共通部品の横断調整を行い、明確なプロトタイプ感を解消する。

8画面（局所改善時は対象）を実データへ接続。1440px・1024px、両フォント、主要操作、空・長文・異常、更新競合、キーボード、CSP/JSエラー、Windows localhostを実ブラウザで代表確認。重点6領域を代表画面で確認する。状態バッジは実状態・古い状態・エラー・動き抑制を代表確認、設定はカテゴリ移動・未保存・保存結果・失敗時保持を確認。数値のピクセル完全一致や全組合せの試験は不要。必要な隔離fixtureを再利用し専用模擬基盤を作らない。選択案の情報・操作と製品を照合し不足を修正。追加幅・倍率・自動撮影・詳細検査は必要時。未検証を成功にしない。

### 3.7 独立レビュー

単独全面再設計では利用可能なら別レビュアーで視覚階層・密度・操作性の改善上位3点を検討。初期は任意。利用不能なら自己レビューで改善し未実施を明記。

### 3.8 完了・再開

`ui/design.md` に比較・明示選択・採用トークン・代表結果・未検証をまとめ、実行可能なUI残件を解消する。README・manualを実装と一致させる。非UIを再実装しない。

## 4. 最終指示

操作と情報の正確性、実用的なデザインを両立したUIを完成させてください。デザイン案・モックアップ・機能接続・静的検査・問題の列挙だけで終了せず、実ソースを更新して実表示と操作を確認し、要求§1.3の初期残件に該当する不具合・明確な視覚的不整合を解消する。低頻度で非重大な追加品質は必要時に改善する。品質のためだけに追加承認や形式的な証跡を増やさない。
