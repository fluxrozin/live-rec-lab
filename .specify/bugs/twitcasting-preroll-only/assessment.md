# Bug Assessment: ツイキャスでプリロール約6秒だけが保存される

- **Slug**: twitcasting-preroll-only
- **Created**: 2026-11-24
- **Source**: pasted text
- **Verdict**: valid
- **Severity**: high

## Report

> ツイキャスの録画がプリロールの6秒しか保存されない

## Symptom

ツイキャスの配信録画で約6秒のMP4だけが残り、本編が欠落した。要件 §4.2.3 は公式HLSから本編を取得し、ファイルの有効性と本編の収録を個別に確認するよう求めている。録画の主要機能で配信本編を失うため重大度は high とする。今回確認できた範囲はローカル環境の1セッション。

## Reproduction

1. 録画権限のあるツイキャス公開配信を監視・録画する。公式APIの `current_live.hls_url` から取得したHLSプレイリストの変化を確認する。[NEEDS CLARIFICATION: 発生時の先頭プレイリスト、マスター・転送・メディアの構成と更新時系列]
2. ローカルDBの配信セッションID 2、録画ジョブID 1では、2026-11-24 11:30:15 JSTに録画を開始し、11:31:41 JSTにも同じ配信をLIVEとして観測している。ジョブは再接続5回、手動停止なしで、11:33:02 JSTに `PARTIAL`（終了理由 `platform_end`）となった。最後のエラーは「プレイリストの HTTP 応答 404」。
3. DBには有効なMP4が1件（6,037ms、41,471バイト）記録されていた。実ファイルを `ffprobe` で読み取り、6.037375秒、H.264映像、AAC音声を確認した。プリロールという内容の判定は利用者報告に基づく。
4. オフラインの模擬HLSでは、マスターが識別情報のない6秒の `ENDLIST` 付きメディアを返し、次回からそのメディアが404になるようにした。マスターを再取得すれば本編用の別バリアントが返る条件で、現行コードが6秒の入力を採用し、更新時も古いバリアントだけを取りに行くことを確認した。別途、FFmpegの正常終了と書き込み済みバイトを模擬すると、監視状態が `LIVE` でも再接続判定は `stop` だった。本件の実配信でFFmpegが正常終了したかは未確認。

既存の録画テストからHLS・終了判定関連8件を実行し、全件通過した。既存テストは命名済みプリロールからの移行や本編冒頭の保全を確認している。今回の模擬ケースでは公式通信や実配信の録画を行っていない。

## Suspected Code Paths

- `src/live_rec_lab/platforms/twitcasting.py:140` と `src/live_rec_lab/services/jobs.py:392` で、公式APIのHLS URL取得と同一Movie IDの再確認を行う。再取得はAPI残枠と監視枠に従い、実行できない場合がある。
- `src/live_rec_lab/recording/hls_playlist.py:131` と `:409` で先頭の境界を判断する。開始条件はメディアURIがあり、その全てが `preroll-` で始まるわけではないこと。短い先頭しかなく `ENDLIST` がある場合や開始時点での更新の有無を区別しない。
- `src/live_rec_lab/recording/hls_playlist.py:366` と `:397` で、取得先を最終URLや選択したバリアントに上書きし、更新時もそのURLを使う。更新時の `HlsPlaylistError` はそこで処理され、上位に失敗理由が渡らない。
- `src/live_rec_lab/recording/manager.py:243` で、再試行時に公式URLの再確認を試みる。 `:320` 以降ではファイルを確定してから再接続を判断する。 `:79` の共通判定は、データがある正常終了を `LIVE` 中でも終了扱いにできる。
- `src/live_rec_lab/recording/segments.py:296` で確定ファイルを検証する。コーデック、長さ、コンテナが有効なら6秒のファイルも `valid` になるため、これだけでは本編を取得したか判定できない。

## Root Cause Hypothesis

確信度は中。実データは短いファイルの確定とHLS再接続時の最終エラー404を示している。最有力は、本編と確定できない初期メディアを録画入力として採用し、公式HLSが本編へ切り替わる際に利用可能なプレイリストへ追従できなかったこと。現行コードでこの経路を模擬でき、過去の試行でも名前に依存する判定で約6秒しか残らなかった記録がある（`docs/IMPLEMENTATION_NOTES.md` §6.2）。今回のプレイリスト履歴とFFmpeg終了コードがないため、404の発生先、バリアント切替の有無、更新障害と本編欠落の直接の因果は未確定。実ジョブは再接続して `PARTIAL` になっており、模擬した正常終了分岐だけでは経過を説明できない。

## Proposed Remediation

**Preferred**　公式HLSの起点URLと現在読み込んでいるメディアURLを保持し、配信継続中に選択先が404になった場合は、起点からの再解決と、既存の監視枠・残枠制御を通した同一Movie IDのURL再確認を使って、有界の再試行で本編を取得する。開始時に短い有限プレイリストしかなく判定が曖昧なら、プレイリストの更新、メディアシーケンス、キューや不連続前後の初期化情報を使って本編への切替を確認する。通常の短い本編を保持するため、長さや命名のみで先頭を削除する条件は設けない。

録画終了の判断にツイキャス側のプレイリスト状態を伝える。配信が継続し本編取得の根拠がない場合は、FFmpegの終了やファイルの有効性だけでジョブを成功確定せず、再取得を試みる。復旧できない場合は取得済みデータを保全し、プレイリスト取得失敗と本編の欠損をジョブに残す。診断には取得段階、HTTPステータス、更新有無、セグメント数、`ENDLIST` の有無、プロセス終了区分を使う。

- 通常の短い本編や、本編冒頭に続く不連続のある入力を保持する。許可外への転送や制限付き配信に対する既存の制御も検証する。
- TC-020を模擬入力で、TC-067を許可された公開配信で検証し、先頭・本編・末尾と録画ジョブの最終状態を照合する。

## Risks & Considerations

- 本編の判定を待つ間にライブウィンドウから冒頭が消える可能性がある。判定にかける時間と配信冒頭の保全を、複数の実配信パターンで確認する。
- 公式APIの再確認はコメント収集優先と既存の残枠制御に従う。404からの復旧は、同一Movie IDと許可された公開HLSの範囲で行う。診断には署名URLや認証値を含めない。
- 録画再開時は既存のセグメント確定処理を使い、取得済みメディアやコメント字幕との対応を保つ。現時点の修正案にDBマイグレーションやAPI契約の変更は想定していない。
